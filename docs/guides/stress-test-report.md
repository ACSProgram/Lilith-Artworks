- 报告日期：2026-10-04
- 被测版本：应用 `0.2.0-alpha.4`，repository schema v4
- 已落实批次：批次 1（取消边界）、批次 2（跨进程强杀）、批次 2 补充（事务中途崩溃）、
  批次 3（大文件端到端）、批次 4（规模、灾备与参数边界）、批次 5（崩溃孤儿回收闭环）、
  批次 6（画板 DDS 完整性）、批次 7（认证发布内存、取消与回读）
- 未落实批次：批次 8（文档收尾）——本文只在「尚未覆盖」一节列出它对应的人工验收项

本文面向**使用者**：它回答两个问题——「这套自动测试到底证明了什么」和「它能保证我遇到的哪些真实情况」。
所有数字都来自真实运行，可复现命令见文末。规划与实现细节见

## 1. 一句话结论

自动压力测试以**独立进程**调用真实可执行文件，在任何界面都不参与的前提下，验证了七件事：

1. **强制结束进程不会损坏数据**：在提交、恢复、整仓备份的任意阶段把进程杀掉，仓库都能重新打开，
   并通过完整性检查与逐块摘要校验；未完成的动作被丢弃，不会出现「写了一半的成品」——
   包括杀在**数据库事务内部**（已写入、未提交）时，未提交的写入被整体丢弃。
2. **取消是干净的**：每个长操作在任意阶段取消，都不留残留文件、不推进历史，并且可以立刻重试成功。
3. **大文件可用（已覆盖到 4 GiB）**：64 MiB、256 MiB、1 GiB、4 GiB 四档全部实测通过
   （提交 → 有界改动 → 恢复 → 逐位一致），其中 4 GiB 档含「大文件 + 大改动」的最坏存储放大
   场景（每轮改 1 GiB）；测试档位设计覆盖到 8 GiB。
4. **磁盘与内存占用有界**：磁盘增量跟随「改动了多少字节」，而不是「文件有多大」；
   峰值内存不随文件大小线性增长（处理 4 GiB 文件用约 360 MB 内存）。
5. **规模与异常输入下行为正确**：300 次提交的深链、约 20 条分支的历史图、400 个 Artwork 的库、
   整仓灾备与 8 类参数越界输入，计数、搜索、移动、删除、恢复与拒绝行为都正确；
   崩溃留下的孤儿可被扫描发现、经确认后清理。
6. **画板素材的完整性可查**：导入图片后，画板 DDS 与数据库记录的双向检查能区分「正常 /
   缺失 / 损坏 / 孤儿」四类并如实计数（缺失与损坏只报告、不失败）；孤儿 DDS 与崩溃孤儿走同一条
   「扫描发现 + 用户确认清理」的回收闭环，被引用的 DDS 不会被误删。
7. **认证发布可用、可取消、可回读**：在 16K 级源图（约 268 MP）上，解码、TrustMark 编码与
   C2PA 签名的峰值内存不超出声明的解码预算量级、各阶段耗时被如实记录；在渲染 / 编码 / 签名
   任一阶段取消都不会留下半成品，`cancel-publication` 后仓库内副本与记录被清除；
   `decode-authenticity` 能读回 C2PA 声明与 TrustMark 绑定，`scrub` 覆盖最终成品与认证副本的
   摘要比对。

**它不覆盖**：断电持久性、界面视觉与交互手感（见第 5 节）。

## 2. 这些测试是怎么做的

理解下面三点，就能正确理解后文的「保证」边界：

- **被测对象是真实可执行文件**，以 `--headless`（无界面）模式作为**独立进程**启动。
  测试进程跨越进程边界，只通过命令行参数、标准输入与文件与被测进程交互，**不读取任何内部状态**。
  因此它测的是真实的启动、恢复与落盘路径，而不是「内部函数被调用不报错」。
- **干预手段只有三种**，全部来自进程外部：
  ① 在每个取消检查点通过标准输入下发「取消/继续」判定（进程会阻塞等待，因此能精确命中某一处代码位置）；
  ② 直接强杀进程（等价于任务管理器结束进程，不运行任何清理代码）；
  ③ 阶段标记文件（消除「猜时机」带来的抖动）。
- **断言只用两类事实**：磁盘事实（文件是否存在、大小、两个文件是否逐位相同）与命令返回的 JSON。
  没有「重开不报错就算过」这类弱断言。

所有测试都在项目 `target/stress-workspaces/` 下的临时工作区里完成，**不读取、不修改你的真实
仓库**；工作区随场景结束（含断言失败展开）自动回收。

无头入口由编译特性门控，**不存在于发布产物中**：它不会把应用变成「可被自动化驱动」的形态，
发布版的界面与业务行为与本文描述的现状逐位一致。全套测试里**只有两处**为了测试而触及产品
代码，且都由该特性门控、发布产物中不存在：① `history::commit` 在提交事务之前的标记点
（批次 2 补充）；② `authenticity/pipeline.rs` 在渲染 / 编码 / 签名三处的 `auth_checkpoint`
（批次 7，release 下逐位等价于既有的取消检查）。批次 7 另有一处契约性改动——授权作用域
抽象成可注入的来源——但它的两条实现都仍要求路径被显式授权，GUI 行为逐位不变。

| 巨大的工作文件（PSD 等） | 64 MiB / 256 MiB / 1 GiB / 4 GiB 四档：提交 → 有界改动 → 恢复最早的节点（要穿过整条增量链）与最新节点，产物都与当时的内容**逐位一致**；精简之后仍然如此 | C1、C2 |

| 崩溃后残留的孤儿文件会不会一直占着磁盘 | 孤儿**不会自动回收**，但可被扫描发现、经用户确认后清理；被引用的文件不会被误删 | B5 |
| 画板图片文件损坏、缺失或残留孤儿 | 双向检查区分四类并如实计数：记录缺文件计「缺失」、文件头/尺寸/解码不符计「损坏」、无记录的文件计「孤儿」；缺失与损坏只报告、命令仍成功返回 | H1 |
| 画板残留的孤儿 DDS 会不会一直占着磁盘 | 与崩溃孤儿同一条闭环：可被扫描发现、经用户确认后清理；被 `pin_board_images` 引用的 DDS 不会被误删 | H2 |
| 16K 级大图发布时内存会不会爆 | 解码 + TrustMark 编码 + C2PA 签名的峰值内存不超出声明的 1.5 GiB 解码预算量级；渲染 / 编码 / 签名各阶段耗时被记录，无超时与挂起 | G1、G2 |
| 发布中途取消会不会留下半成品 | 渲染 / 编码 / 签名任一阶段取消后都没有发布输出、没有残留临时目录、认证记录数为 0；仓库重开可用 | G3 |
| 发布成品能不能回读与校验 | `decode-authenticity` 读回 C2PA 声明（record ID、标题、创作者、权利声明）与 TrustMark 绑定并匹配本地记录；`scrub` 覆盖最终成品与认证副本的摘要比对，被替换的副本会被拒绝 | G4、G5 |
| 作品库变大后会不会变慢或出错 | 300 次提交的深链、约 20 条分支的历史图、400 个 Artwork 的库：树计数、搜索、节点移动、删除与恢复都正确；深链最深节点的恢复耗时与内存有界 | D1–D3 |
| 整仓灾备能不能可靠复制一个真实的库 | 含多个 Artwork 与提交的仓库：清单计数正确、副本可独立打开并通过完整性与链路校验、树结构与源仓库一致 | E1 |
| 输入越界会不会崩 | 备注/标题/搜索超长、非法提交类型、不存在的历史节点、已存在的输出路径、非法移动目标都被明确拒绝而非崩溃 | F1 |

术语：**快照（snapshot）** 是某个历史节点的完整内容副本；**增量（delta）** 是从一个节点回退到其父节点所需的差异数据。

## 4. 实测数据

### 4.1 A 组：取消边界（批次 1，2026-10-04）

27 次受控取消，全部以取消结果退出，且每次取消后都断言「无残留 + 重开可用 + 重试成功」。

| 场景 | 受控取消次数 | 最深检查点 | 最大耗时 | 峰值内存 |
| --- | --- | --- | --- | --- |
| A1 提交取消（每个检查点各一次） | 4 | 4 | 71 ms | 19.8 MiB |
| A2 恢复取消（链解析 / 导出前 / 发布前） | 6 | 6 | 69 ms | 17.5 MiB |
| A3 精简取消（父链回溯 / 子链回溯 / delta 发布前） | 6 | 6 | 59 ms | 20.2 MiB |
| A4 检查点取消（链解析 / snapshot 发布前） | 4 | 4 | 66 ms | 17.0 MiB |
| A5 整仓灾备取消（扫描前 / 复制 / 校验 / 发布前） | 4 | 18 | 169 ms | 17.2 MiB |
| A6 全库扫描取消（入口 / 逐节点 / 靠后节点） | 3 | 8 | 80 ms | 17.1 MiB |

A 组使用 96 KiB 工作文件，因此耗时是「取消路径本身」的开销；峰值内存为 debug 档无头进程自报值，
只作「确有数值可采」的证据。

### 4.2 B 组：跨进程强杀（批次 2 与批次 2 补充，2026-10-04）

5 次强杀，强杀点由「逐检查点闸门」确定命中（进程在目标检查点阻塞，测试随即强杀）。

| 场景 | 强杀点 | 强杀阶段 | 耗时 |
| --- | --- | --- | --- |
| B1 提交中途强杀 | 检查点 4 | 快照/增量已发布、数据库未提交 | 57 ms |
| B2 恢复中途强杀（导出前） | 检查点 5 | 链解析完成后 | 56 ms |
| B2 恢复中途强杀（导出后） | 检查点 6 | 导出并同步后、发布前 | 67 ms |
| B3 整仓灾备中途强杀 | 检查点 2 | 复制仓库文件 | 34 ms |
| B4 提交事务中途强杀 | 检查点 5 | 事务已写入（`INSERT` 已执行）、尚未 `COMMIT` | 83 ms |

强杀后的实测结论：`verify`（迁移 + 完整性 + 外键 + 语义校验）与 `scrub`（逐块摘要链）全部通过；
B1 恰好多出一枚完整的孤儿快照与一枚孤儿增量（清理队列为空，如实记录为缺口）；
B2 目标输出不存在，只留下未发布的完整临时文件（仓库之外）；
B3 源仓库可独立校验，暂存目录可识别，重跑灾备成功。

**B4（批次 2 补充）** 把强杀点推进到事务**内部**，用来验证 WAL + `synchronous = FULL` 承诺里
可观测的那一面。强杀后：head 与节点数不前进（未提交事务被丢弃）；父节点的快照仍被引用
（事务内的释放语句与提交同事务，一并被丢弃）；清理队列没有多出条目（事务内的入队同样被丢弃）；
已发布的快照与增量仍是磁盘孤儿；随后同一命令重跑成功且只前进一格。为此在 `history::commit`
的 `transaction.commit()` 之前加了一个 headless-only 标记点（feature 门控，发布产物中不存在），
它同时把提交路径的取消检查点从 4 个扩展到 5 个——A1 已同步覆盖到第 5 个。

### 4.3 C 组：大文件端到端（批次 3，2026-10-04）

工作文件用**稀疏构造**：先建立逻辑长度，只向有界区域写入真实随机字节，其余部分不占磁盘簇。
因此 4 GiB 逻辑文件的真实写入量只有数百 MiB，而快照仍约 4 GiB——这正是「逻辑体积」与
「磁盘成本」分离的地方。

C 组覆盖**两条正交的轴**——「文件多大」与「每次改动多大」：

| | 小改动（每轮逻辑的 1/128） | 大改动（每轮逻辑的 1/4，3 轮） |
| --- | --- | --- |
| 一般文件（`default` 64 MiB） | 日常编辑 | 日常里的大改 |
| 大文件（`large`/`heavy`/`extreme`） | 大文件的日常编辑 | 最坏存储放大（4 GiB 改 1 GiB） |

小改动档的轮数随档位下降（`default`/`large` 20 轮、`heavy` 10 轮、`extreme` 5 轮）：每轮提交
都要**重写整份快照**，轮数不降时 4 GiB 档光 C1 就要写约 80 GiB 快照。链深行为与文件大小无关，
20 层链已在 `default`/`large` 覆盖。

C1–C5 走小改动档（C1 端到端、C2 精简、C3 峰值内存、C4 链体积与账本、C5 恢复产物即删），
C6 走大改动档且每轮改动同一批区域（父版本旧内容也是真实随机数据，delta 无法靠压缩变小）。

| 项 | `default` 64 MiB | `large` 256 MiB | `heavy` 1 GiB | `extreme` 4 GiB |
| --- | --- | --- | --- | --- |
| 提交次数（1 次基线 + 改动轮数） | 21 | 21 | 11 | 6 |
| 提交总耗时 | 11.8 s | 41.8 s | 185.0 s | 151.1 s |
| 恢复**最早**节点（穿整条增量链） | 1.28 s | 5.78 s | 18.06 s | 46.93 s |
| 恢复**最新**节点（直接读快照） | 0.29 s | 1.00 s | 5.56 s | 20.18 s |
| 快照大小 / 逻辑大小（开销） | 67.70 MB（+0.88%） | 270.73 MB（+0.85%） | 1089.32 MB（+1.45%） | 4367.74 MB（+1.69%） |
| 增量合计 | 7.54 MB | 26.98 MB | 9.84 MB | 4.29 MB |
| 增量 / 快照 | 11.1% | 10.0% | 0.9% | 0.1% |
| 增量 / 改动字节数 | 0.72 | 0.64 | 0.12 | 0.10 |
| 大改动 C6：每轮改动 / 增量÷改动 | 16 MiB / 0.44 | 64 MiB / 0.43 | 256 MiB / 0.42 | 1 GiB / 0.42 |
| 提交峰值内存增量（允许上限） | 10.2 MB（33.6 MB） | 28.3 MB（58.7 MB） | 116.6 MB（159.4 MB） | 348.6 MB（562.0 MB） |
| 恢复峰值内存增量 | 6.1 MB | 23.2 MB | 111.8 MB | 343.2 MB |
| 磁盘账本：实测增量 / 预期增量（C1） | 79.53 / 79.48 MB | 318.64 / 318.60 MB | 1175.93 / 1175.91 MB | 4411.89 / 4411.89 MB |

说明：

- **快照不压缩、不去重**，因此快照大小约等于逻辑大小加每块 36 字节开销（上表开销即此项）。
  这是格式的既有特征，本批次只测量并如实记录，不做优化。
- **增量跟随改动量、远小于快照**：小改动下每轮只改动很窄的区域，增量合计通常在快照的
  1%–11%；大改动（C6，每轮改 1/4）下增量升至改动量的约 42%，仍远小于快照。长期使用下仓库
  占用由「一个完整快照 + 历次改动的增量」构成，而不是「每次提交累积一份完整副本」。
- **内存**：处理 4 GiB 文件的提交峰值约 362 MB、恢复峰值约 343 MB，基线约 12 MB。若实现把
  整个文件读进内存，增量会是 4 GiB，会立刻违反 C3 的断言（允许上限为逻辑的 1/8 加 24 MB）。
- **磁盘账本**：场景结束后的实测工作区增量与按「快照 + 增量 + 新增改动字节」计算的预期值偏差
  在 0.03% 以内；偏差超阈值会直接报警，这条断言用来兜住「存储放大失控」类回归。

### 4.5 D / E / F 组：规模、灾备与参数边界（批次 4，2026-10-04）

规模量级按**个人长期使用的真实上限**选取，而不是为凑数量构造的极端值。

| 场景 | 规模 | 关键实测 |
| --- | --- | --- |
| D1 深链 | 300 次提交（单分支） | 提交合计 19.9 s；最深节点恢复 257 ms（穿整条增量链）；提交峰值内存 21.9 MB，与链深无关；精简中间节点后最深节点仍逐位一致 |
| D2 多分支历史图 | 21 条分支、64 节点 | 删除一条分支后磁盘实体 84 → 80，其余分支 head 仍可逐位恢复；清空回收站后实体归零、Artwork 目录被回收 |
| D3 库规模 | 400 个 Artwork + 24 个分组 | 创建耗时 17.5 s；树计数、按标题搜索、节点移动均正确 |
| E1 整仓灾备规模 | 8 个 Artwork、16 节点 | 清单 fileCount 17、totalBytes 2.9 MB；副本独立 `verify` + `scrub` 通过、树计数与源仓库一致 |
| F1 参数边界 | 8 类越界输入 | 备注 501、非法提交类型、标题 161、空标题、搜索 161、不存在历史节点、已存在输出、非法移动目标均被明确拒绝且不 panic |

说明：D2 中每个非根节点同时持有自己的快照与一条反向增量，因此**磁盘实体数多于节点数**；
断言因此关注「删除后实体减少、其余分支仍可恢复」，而不是「实体数等于节点数」。

### 4.6 B5：崩溃孤儿回收闭环（批次 5，2026-10-04）

批次 2 的 B1 只断言「孤儿存在 + 不被引用 + 重开可用」，并如实记录「当前不会自动回收」。
统一清理体系落地后，未引用文件可被扫描发现、经用户确认后清理。B5 把这条闭环补成自动化断言：

1. 复用 B1 的强杀点造出孤儿快照与孤儿增量；
2. 把仓库内全部快照/增量的修改时间回拨到 30 分钟宽限期之外（只改测试工作区里文件的 mtime）；
3. 扫描**只**报告这两枚孤儿——被引用的文件即便同样「过期」也不报告，证明引用复查生效；
4. 确认清理删除孤儿、被引用文件保留；再扫描无候选（幂等）；重开可用、后续提交正常。

实测：扫描精确报告 2 枚候选，确认清理后孤儿消失、被引用实体保留，重开后 `verify` + `scrub`
通过。**孤儿仍不会被自动回收**——它是两段式（扫描报告 + 用户确认），这是设计而非缺陷。

### 4.7 H 组：画板 DDS 完整性（批次 6，2026-10-04）

画板记录只能由导入流程写入，因此 H 组先给无头入口补上 `create-board` / `import-board-images` /
`scrub-board-dds` 三个子命令（1:1 薄映射、feature 门控、不进发布产物），再用它们构造
「记录 → 文件」方向的缺失/损坏，以及「文件 → 记录」方向的孤儿。

| 场景 | 规模 | 关键实测 |
| --- | --- | --- |
| H1 双向检查 | 3 张图片 + 1 枚孤儿 DDS | 精确报告 images 3 / missing 1 / corrupt 1 / orphans 1；缺失与损坏**不使命令失败**；37 ms、峰值约 14.8 MB |
| H2 孤儿 DDS 回收 | 2 张图片 + 1 枚孤儿 DDS | 扫描只报告 1 枚孤儿（被引用 DDS 即便同样回拨到 30 分钟宽限期之外也不报告）、确认清理后归零、被引用 DDS 保留；47 ms |
| H3 规模与取消 | 单画板 300 张图片 | 全部命中、无缺失/损坏/孤儿；在第 1 个检查点取消后重试成功；600 个检查点（300 记录 + 300 磁盘文件）；132 ms、峰值约 15 MB |

说明：

- **缺失与损坏报告不失败**：这是设计取舍——缺失 DDS 的修复属历史迁移议题，检查只如实计数，
  由调用方（设置页完整性检查）决定如何呈现，不自动修复。
- **孤儿 DDS 的发现与清理复用崩溃孤儿同一条闭环**：`scan-unreferenced` 把画板 DDS 纳入扫描范围，
  经反向引用检查（`pin_board_images`）后只报告无记录者；确认清理由 `cleanup-unreferenced` 完成。
  扫描的 30 分钟宽限期同样适用，测试把文件修改时间回拨到宽限期之外。
- **规模量级按「现实可遇」选取**：单画板 300 张图片（个人素材板真实上限），而不是为凑数量
  构造的数千张。

### 4.8 G 组：认证模块（批次 7，2026-10-04）

认证批次是唯一触及安全边界的批次：`ensure_dialog_authorized` 的路径授权来源被抽象成
**可注入的作用域**——GUI 侧仍走 `window.fs_scope()`（行为与文案逐位不变），无头侧是一个
只允许 `--workspace` 之下路径的显式作用域。无头入口因此补齐 `enter-publication` /
`publish` / `cancel-publication` / `decode-authenticity` 四个子命令与 `--models`，
`scrub` 也扩展为「历史链 + 认证受控文件」两段。

| 场景 | 规模 | 关键实测 |
| --- | --- | --- |
| G1 发布峰值内存 | 16K 源图（16384×16384，≈268 MP） | 无头进程自报峰值 **1.92 GiB**（2,065,182,720 B），未超出保守上界 3.0 GiB（解码图 + 展平图 + TrustMark 输出各一份）；同量级于声明的 1.5 GiB 解码预算 |
| G2 发布各阶段耗时 | 同 G1 | 提交整体 214.7 s；渲染 33.9 s、编码 99.6 s、签名 0.66 s；无超时与挂起 |
| G3 发布取消（渲染 / 编码 / 签名） | 128×128 源图 | 三个阶段各取消一次（第 1/2/3 个检查点）：均 exit 2、`cancelled` 为真；输出文件不存在、输出目录无残留临时产物、认证记录数为 0；`cancel-publication` 后仓库内成品与记录归零，仓库重开可用 |
| G4 回读 | 128×128 源图 | `decode-authenticity` 读回 C2PA（`validationState = Valid`）与 TrustMark 绑定，`recordId` / `watermarkId` / 标题 / 创作者 / 权利声明与本地记录一致，候选带 `c2pa` + `trustmark` 两条证据；228 ms、峰值约 220 MB（含解码器模型） |
| G5 受控文件校验 | 128×128 源图 | `scrub` 报告最终成品 1、认证记录 1；替换认证仓库副本的字节后校验失败（错误含「已损坏或被替换」），证明是摘要比对而非计数；40 ms、峰值约 38 MB |

说明：

- **16K 场景只在 `extreme` 及以上档位运行**（生成 16384×16384 需约 1 GiB 内存，发布链路
  解码同样如此）；低于该档位时 G1/G2 **明确跳过并报告**，不静默降级。上表数值为 `extreme` 档。
- **大图由测试进程用已有的 `image` 依赖按需生成，用完即删，不提交进仓库**；认证夹具
  （ES256 凭据与 128×128 源图）复制进工作区后使用——无头进程只授权工作区之内的路径。
- **G3 的确定性来自第二处 headless-only 标记点**：`publish` 流水线内部原本只有
  `AuthenticityOperation` 的标志位、没有可阻塞的检查点，因此在渲染 / 编码 / 签名三处调用
  `crate::headless::auth_checkpoint`（feature 门控；release 下逐位等价于
  `ensure_not_cancelled`，发布产物中不存在），与 `history::commit` 的事务标记点同一范式。
- 取消路径的错误文案为「认证任务已取消」，与提交路径的「提交已取消」「备份操作已取消」区分。

### 4.9 测试档位与运行成本

档位由 `LILITH_STRESS_TIERS` 选择，默认 `default`。C 组的墙钟时间（指向发布档、16 逻辑核、
并发执行）实测如下。

| 档位 | 逻辑大小 | 预计峰值磁盘 | 用途 | 实测状态（2026-10-04） | 墙钟 |
| --- | --- | --- | --- | --- | --- |
| `default` | 64 MiB | ≈ 0.2 GiB | 日常典型体积 | **6/6 通过** | 28 s |
| `large` | 256 MiB | ≈ 1 GiB | 跨过明显的块级规模 | **6/6 通过** | 136 s |
| `heavy` | 1 GiB | ≈ 3 GiB | PSD 常见超限体积 | **6/6 通过** | 320 s |
| `extreme` | 4 GiB | ≈ 13 GiB | PSD 常态上限 | **6/6 通过** | 1219 s |
| `manual` | 8 GiB | ≈ 24 GiB | 4 GiB 现实上限的两倍冗余，需 ≥ 32 GiB 空闲 | 设计覆盖，未实测 | — |

四档整轮约 28 分钟，全部在发布档二进制上运行。

**关于全库校验的代价**：`scrub`（全库逐块校验）是 O(节点数 × 文件大小)——它要为每个历史
节点从最近的快照重放整条链，再把整份内容流式复算一遍块摘要。这是 4 GiB 档耗时的主要来源
（6 节点 × 4 GiB 的全链校验），也是应用把「空闲期的 head 快照校验」与「全库扫描」分成两条
路径的原因：前者是单个快照的代价，后者是整仓的代价。

**关于并发**：无头子进程是单线程的（内容定义分块滚哈希、SHA-256 与 zstd 都是单核路径），
所以串行执行时 16 核机器只用 1 个核、磁盘只跑到约 150 MB/s（盘可达 2 GB/s）。测试因此按
**磁盘预算**准入并行：多个场景同时运行，但「各自预计峰值磁盘之和」不超过
`LILITH_STRESS_DISK_BUDGET`（默认 24 GiB），且并发数不超过 `LILITH_STRESS_JOBS`
（默认可用核数）。没有任何预算守卫的盲目并行会让磁盘写满、运行中途失败，比慢得多更糟。
并发的代价是各场景的耗时变成「带负载」值（上表即为带负载墙钟）；4 GiB 档单个场景预计峰值
约 12.3 GiB，默认预算下只放行 1 个，所以该档仍近似串行，可用 `LILITH_STRESS_DISK_BUDGET`
调高以并行（需相应空闲磁盘）。

## 5. 尚未覆盖

明确**不做**自动化、或当前还不具备条件的部分：

| 项目 | 原因 |
| --- | --- |
| 断电持久性（已提交的数据在断电后是否仍在） | 结束进程不触及操作系统与磁盘的缓存、也不保证目录项落盘，结构上无法覆盖。该项由操作系统、磁盘与数据库的 `synchronous = FULL` 声明保证 |
| 界面视觉、交互手感、桌面集成（拖放、托盘、快捷键等） | 自动化不驱动界面；由人工验收清单覆盖 |
| 崩溃残留文件的**自动**回收 | 孤儿不会被自动回收；可被扫描发现并经用户确认后清理，这条闭环已由 B5 覆盖。「自动」回收是产品设计取舍，不是测试断言 |
| 异常 RFC 3161 时间戳服务的失败与超时 | 保留人工验收 |

## 6. 如何自己运行

> **这套测试很耗时间与磁盘，只在发布前运行。** 它以真实可执行文件、真实落盘路径跑极端
> 情况，`heavy`/`extreme` 档单次以十分钟计、峰值磁盘可达十几 GiB。**日常开发与任何收尾
> 阶段都不要运行**——只要不是准备发布，用轻量检查（`npm test`、`cargo fmt --check`、
> `cargo check`、`cargo test --lib`、`git diff --check`）即可。同一条约定也写在
> `docs/guides/validation.md` 的「压力测试：只在发布前运行」。

```text
# 1. 构建带无头入口的二进制（该入口不进发布产物）
cd src-tauri
cargo build --release --features headless

# 2. 建议把测试指向发布档：峰值内存、存储放大与耗时才有参考价值
LILITH_STRESS_BIN=target/release/lilith-artworks.exe \
  cargo test --features headless --test stress_large

# 3. 选择档位（默认 default；大文件档需要相应磁盘与时间）
LILITH_STRESS_TIERS=extreme LILITH_STRESS_BIN=... \
  cargo test --features headless --test stress_large

# 4. 取消、崩溃、规模、孤儿回收、画板 DDS 与认证（用 MiB 级文件，秒级到分钟级）
cargo test --features headless --test stress_cancel
cargo test --features headless --test stress_crash
cargo test --features headless --test stress_cleanup
cargo test --features headless --test stress_scale
cargo test --features headless --test stress_pin_board
cargo test --features headless --test stress_authenticity

# 5. 认证大图（16K 源图）：只在 extreme 及以上档位运行，否则 G1/G2 明确跳过
LILITH_STRESS_TIERS=extreme cargo test --features headless --test stress_authenticity
```

可调环境变量：

- `LILITH_STRESS_TIERS`：档位（`default`/`large`/`heavy`/`extreme`/`manual`）。
- `LILITH_STRESS_BIN`：被测可执行文件，建议指向发布档。
- `LILITH_STRESS_DISK_BUDGET`：磁盘峰值上限（接受字节数或 `KiB/MiB/GiB/TiB` 后缀，默认 24 GiB）。
- `LILITH_STRESS_JOBS`：并发场景数上限（默认可用核数）。

- 结果写入 `target/stress-report.jsonl`（每场景一行 JSON）与 `target/stress-ledger.jsonl`（磁盘账本）；
  工作区位于 `target/stress-workspaces/`，正常结束后自动回收。
- 这套测试**不在 CI 中**：它是发布前手动执行的套件，与 `cargo test --lib`、`npm test`、
  `cargo fmt --check` 三条自动门槛相互独立。
