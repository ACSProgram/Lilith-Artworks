- 报告日期：2026-10-16

  `0.2.0-rc.3` 上的完整重跑——八组全跑，C 组覆盖 `default`/`large`/`heavy`/`extreme`/`manual`
  五个档位。同日补测的 I 组、以及后续新增的 **C7、R3–R6、J1–J6、K 组、P 组**为 debug 构建实测，

第 6 节，测试策略见 `docs/guides/validation.md`。

## 1. 结论

自动压力测试以**独立进程**运行真实程序（不开界面、不读内部状态），验证了十九件事：

1. **强制结束进程不会损坏数据。** 在提交、恢复、整仓备份的任意阶段把进程杀掉，仓库都能重新
   打开，并通过完整性与逐块摘要校验；没做完的动作被丢弃，不会出现「写了一半的成品」——包括
   杀在**数据库事务内部**（已写入、未提交）时，未提交的写入被整体丢弃。
2. **取消是干净的。** 每个长操作在任意阶段取消，都不留残留文件、不推进历史，并且可以立刻重试成功。
3. **大文件可用（已实测到 8 GiB）。** 64 MiB、256 MiB、1 GiB、4 GiB、8 GiB 五档全部通过
   （提交 → 有界改动 → 恢复 → 逐字节一致）；4 GiB 档包含「大文件 + 每轮改 1 GiB」、8 GiB 档
   包含「大文件 + 每轮改 2 GiB」的最坏情况。8 GiB 是 `manual` 档，为 4 GiB 现实上限的两倍冗余。
4. **磁盘与内存占用有界。** 每次提交新增的磁盘占用跟随「改了多少字节」，而不是「文件有多大」；
   处理 4 GiB 文件约用 349 MB 内存、8 GiB 文件约用 644 MB 内存，都不随文件大小线性增长。
5. **规模和异常输入下行为正确。** 300 次提交的长历史、约 20 条分支、400 个作品的库、整仓
   备份、8 类越界输入，计数、搜索、移动、删除、恢复都正确；崩溃留下的孤儿文件可被扫描发现、
   经确认后清理。
6. **画板图片的完整性可查。** 导入图片后，能区分「正常 / 缺失 / 损坏 / 孤儿」四类并如实计数
   （缺失与损坏只报告、不失败）；孤儿图片走同一条「扫描发现 + 用户确认清理」的闭环。
7. **认证发布可用、可取消、可回读。** 在 16384×16384 像素（约 2.68 亿像素）的大图上，解码、
   加水印、签名的内存不超出预算；三个阶段任意取消都不留半成品；发布成品能读回证书信息。
8. **损坏的文件会被发现，并且能修好。** 仓库里的快照/增量被改坏后，全库校验会报错、恢复会
   拒绝，而一次「内容没变」的提交就能把它修好。
9. **同一仓库不会被两个进程同时写入。** 会写仓库的无头命令独占一个跨进程哨兵锁，第二个写
   进程拿到的是明确拒绝，而不是与前者在业务层竞态；锁由操作系统在句柄关闭时释放，因此被
   强杀的写进程**不会**把仓库锁死，随后的写进程仍能取得锁并提交成功。
10. **磁盘写满时是干净失败。** 在真实的快照写入路径上注入「写到这里就没空间」，产品返回
    清晰的「空间不足」错误、不推进历史、不留半成品、可重试；写到一半的字节不会被误当成
    完整快照。
11. **大文件在提交中途被取消或被强杀也是干净的。** 在档位大小（默认 64 MiB）的工作文件上，
    每个取消检查点各取消一次、再强杀一次，都无残留、历史不推进、可重试；强杀后 head 仍能
    恢复出与工作文件逐字节一致的内容。
12. **主库文件本身被改坏时会干净失败。** 把 `lilith-artworks.sqlite3` 的头部改写成非数据库
    内容或清空，两层校验都给出可行动的错误（退出码 1、指向作品数据库、无 panic），并且失败的
    打开**不会**把空文件重建为一个全新的空仓库——那会静默丢弃用户历史。
13. **长写任务持锁期间只读命令仍能作答。** 写进程持锁时，`list-tree` / `verify` / `list-history`
    照常返回并看到写之前的**一致**状态（含「快照已发布、数据库事务尚未提交」这个最易撕裂的
    窗口）；多个只读命令并发互不阻塞。
14. **核心算法有可比的性能基线。** 节点链提交/恢复、认证发布与回读、画板 DDS 导入与扫描、库树与
    搜索、整仓灾备、清理扫描的单位耗时被记录，并可经 `LILITH_STRESS_PERF_STRICT=1` 与
    `tests/perf-baseline.json` 比对，补上此前「只有上界、没有基线」的空白。
15. **非 ASCII 与特殊字符标题逐字符往返。** 中文、emoji、ZWJ 家庭序列、非 BMP 数学/花体字母、
    RTL 阿拉伯文、组合附加符号、零宽字符、内部换行与制表符、以及标题里带 `/`、`\`、`:`、`*`、`?`
    都能写入并原样读回——这同时证明**标题不会被当成文件名**（否则这些字符在 Windows 上会直接失败）。
16. **标题长度按字符而不是按字节计数。** 160 个 emoji（640 字节）与 160 个 CJK（480 字节）都被
    接受并逐字符往返，161 个被拒绝；首尾空白先裁掉再计数。
17. **不受信任的字节换不来崩溃或资源耗尽。** 四个解析器（快照/增量容器、DDS 头、C2PA 清单、
    设置文件）各自喂进数百组确定性畸形输入：一律干净拒绝或正确接受，**没有 panic、越界或无界分配**；
    被接受的容器必须自洽（块数量不超过文件容量、可物化且长度等于声明值），被接受的 DDS 尺寸必须落在
    声明上限内，解析失败的设置文件必须被**原样保留**（不被覆盖成默认值）。随机化单点损坏（逐文件、
    多种子，R5）与画板 DDS 结构性损坏（R6）在真实磁盘路径上同样被检测到或如实报告。
18. **多操作交错不会损坏仓库。** 提交、整仓灾备、精简三类写任务持锁期间，只读命令都照常作答并看到
    一致状态；真正并发的「精简 + 全库校验」（不构造窗口、连跑 4 轮）下仓库仍完整、每个节点仍逐位
    恢复。写者持哨兵期间全库校验现在给出**明确拒绝**（「仓库正在被写入，请稍后重试」，J6 确定性覆盖），
    轻量只读命令保持原承诺不变。

**它不覆盖**：断电持久性、界面视觉与交互手感（见第 5 节）。

## 2. 这些测试是怎么做的

理解下面三点，就能正确理解后文的「保证」边界：

- **被测对象是真实程序**，以「无界面模式」作为**独立进程**启动。测试进程只通过命令行、标准
  输入与文件与它交互，**不读取任何内部状态**。因此它测的是真实的启动、恢复与落盘路径，
  而不是「内部函数被调用不报错」。
- **干预手段只有三种**，全部来自进程外部：① 在每个「可以取消的位置」通过标准输入下发取消/继续
  （进程会阻塞等待，因此能精确命中某一处代码位置）；② 直接强杀进程（等价于任务管理器结束
  进程，不运行任何清理）；③ 阶段标记文件。
- **断言只用两类事实**：磁盘事实（文件是否存在、大小、两个文件是否逐字节相同）与命令返回的
  JSON。没有「重开不报错就算过」这类弱断言。

所有测试都在项目 `target/stress-workspaces/` 下的临时工作区里完成，不读取也不修改真实仓库；
工作区随场景结束自动回收。

无界面入口只在开发测试构建里存在，**正式发布版没有它**：它不会把应用变成「可被自动化驱动」的
形态，发布版的界面与业务行为与本文描述的现状一致。全套测试里**只有两处**为了测试而触及产品
代码，且都由该开关门控、发布版中不存在：① 提交事务之前的标记点；② 认证发布流水线里渲染 /
编码 / 签名三处的标记点。另有一处契约性改动——认证的路径授权来源抽象成可注入的形式——但两条
实现都仍要求路径被显式授权，界面行为逐位不变。

2026-10-16 又追加两处，都不属于上面这个「为观察而设的标记点」范畴，而是实测结论带出的补强：

- **无头入口的跨进程哨兵锁**：会写仓库的命令取一个 SQLite 写锁，第二个写进程被明确拒绝。
  只作用于无头进程（`headless` feature 门控，不进发布产物），GUI 路径逐位不变。
- **提交路径的 `create_snapshot` 提取**：把「写快照」一段抽成函数，好让磁盘写满注入走**真实**
  代码路径。这是纯重构，产品行为逐位不变，且进发布产物。

本轮新增的 C7（大文件中断）、R3/R4（主库损坏）、J1/J2（写读交错）、P（性能基准）以及门控守护
测试 `tests/gate_guard.rs`，**均不修改任何产品代码**——只有新增测试与基线文件
`src-tauri/tests/perf-baseline.json`。门控守护测试扫描全部 `stress_*.rs` 并断言 `headless`
门控行存在，防止「漏写门控 → 裸 `cargo test` 拉起 GUI」这类事故。

再往后的这一轮（R5/R6、J3–J5、K 组、P4–P6、四个解析器的畸形输入模糊）**同样不修改任何产品代码**：

- 新增的畸形输入生成器 `src/fuzz_support.rs` 由 `#[cfg(test)]` 门控，**不进任何产物**；
  `backup/test_support.rs` 里的伪随机源改为从它转出，避免出现两份实现。
- 共享测试助手 `tests/stress_support/mod.rs` 只多了一个「收集树标题」与一个「按标题查找节点」
  的纯函数——它们是测试侧的复用，不触及产品。
- 因此这一轮唯一的非测试改动是文档；产品行为与上一批完全一致。

## 3. 各项保证与证明场景

| 情形 | 已有的保证 | 证明场景 |
| --- | --- | --- |
| 提交历史的过程中强制结束进程（任务管理器结束、崩溃） | 仓库自洽：重新打开通过完整性、外键与全表语义校验，历史不前进，随后提交正常。**已发布但未被引用的文件会成为孤儿留在磁盘上，当前不会自动回收**（见第 5 节） | B1 |
| 提交**写到一半**（数据库事务已开始、尚未提交）时进程被杀 | 未提交的写入被整体丢弃：历史与节点数不前进、上一版快照仍被引用、清理队列没有多出条目；重开校验全过、随后提交正常 | B4 |
| 恢复某个历史节点时进程被杀 | 目标输出文件**不存在**；不会出现「半写文件被当成产物」；重新恢复得到与原文件逐字节相同的字节 | B2 |
| 整仓备份复制途中进程被杀 | 源仓库不受任何影响、可独立校验；目标目录只留下**可识别**的未发布暂存目录（`.lilith-artworks-*.tmp`），不会被误认为备份；重跑成功 | B3 |
| 长操作中途取消（提交、恢复、精简、检查点、整仓备份、全库扫描） | 无残留实体与临时文件、历史图不变、待清理队列为空，并且可以立刻重试成功 | A1–A6（28 次受控取消） |
| 巨大的工作文件（PSD 等） | 64 MiB / 256 MiB / 1 GiB / 4 GiB / 8 GiB 五档：提交 → 有界改动 → 恢复最早与最新的节点，产物都与当时的内容**逐字节一致**；精简之后仍然如此 | C1、C2、C6 |
| 磁盘会不会被撑爆 | 每次提交新增的占用跟随**改动的字节数**，而不是文件大小；快照不压缩但每次提交会释放上一版快照，仓库常驻大小 ≈「一个完整快照 + 所有增量」 | C4 |
| 打开大文件时内存会不会爆 | 处理 4 GiB 文件的提交峰值约 361 MB、恢复峰值约 356 MB；8 GiB 档分别为约 657 MB / 652 MB（基线约 12.5 MB），即**流式实现**，不把整个文件读进内存 | C3 |
| 恢复输出会不会留下垃圾 | 恢复产物是全尺寸的临时产物，测试在每个场景结束时断言输出目录已清空、工作区占用回落 | C5 |
| 崩溃后残留的孤儿文件会不会一直占着磁盘 | 孤儿**不会自动回收**，但可被扫描发现、经用户确认后清理；被引用的文件不会被误删 | B5 |
| 画板图片损坏、缺失或残留孤儿 | 双向检查区分四类并如实计数：记录缺文件计「缺失」、文件头/尺寸/解码不符计「损坏」、无记录的文件计「孤儿」；缺失与损坏只报告、命令仍成功返回 | H1 |
| 画板残留的孤儿图片会不会一直占着磁盘 | 与崩溃孤儿同一条闭环：可被扫描发现、经用户确认后清理；被记录引用的图片不会被误删 | H2 |
| 16K 级大图发布时内存会不会爆 | 解码 + 水印编码 + 证书签名的峰值内存不超出声明的 1.5 GiB 解码预算量级；各阶段耗时被记录，无超时与挂起 | G1、G2 |
| 发布中途取消会不会留下半成品 | 渲染 / 编码 / 签名任一阶段取消后都没有发布输出、没有残留临时目录、认证记录数为 0；仓库重开可用 | G3 |
| 发布成品能不能回读与校验 | 能读回证书声明（记录 ID、标题、创作者、权利声明）与数字水印绑定并匹配本地记录；全库校验会比对成品与认证副本的摘要，被替换的副本会被拒绝 | G4、G5 |
| 作品库变大后会不会变慢或出错 | 300 次提交的深链、约 20 条分支的历史图、400 个作品的库：树计数、搜索、移动、删除与恢复都正确；最深节点的恢复耗时与内存有界 | D1–D3 |
| 整仓备份能不能可靠复制一个真实的库 | 含多个作品与提交的仓库：清单计数正确、副本可独立打开并通过完整性与链路校验、树结构与源仓库一致 | E1 |
| 输入越界会不会崩 | 备注/标题/搜索超长、非法提交类型、不存在的历史节点、已存在的输出路径、非法移动目标都被明确拒绝而非崩溃 | F1 |
| 仓库里的文件被磁盘损坏、外部工具误写 | 全库校验报错并指出损坏；恢复被拒绝且不留半成品；一次「内容没变」的提交即可修复被改坏的最新快照，修复后内容逐字节一致 | R1、R2 |
| 磁盘写满（仓库所在卷没有空间） | 快照写入返回干净的「空间不足」错误、不推进历史、不留半成品、可重试；写到一半的字节不会被误认为完整快照 | 单元/集成测试（`backup::worker`、`backup::chunk_file`） |
| 同一仓库被两个进程同时写入 | 会写仓库的无头命令独占一个跨进程哨兵锁，第二个写进程拿到明确错误而不是与前者竞态；锁由操作系统在句柄关闭时释放，强杀不会残留 | I1、I2 |
| 大文件提交**中途**取消或强杀 | 无残留实体与临时文件、历史不推进、可立刻重试；强杀后 head 仍能恢复出与工作文件逐字节一致的内容 | C7 |
| 数据库主库文件本身被改坏（误写 / 清空） | 两层校验都失败并给出可行动的错误（退出码 1、指向作品数据库、不 panic）；失败的打开不会把空库重建为一个全新的空仓库 | R3、R4 |
| 长写任务进行时读命令还能不能返回 | 只读命令不被写锁挡住、立即返回并看到写之前的一致状态（含「文件已发布、事务未提交」的窗口）；并发读之间互不阻塞；**整仓灾备与精简**这两类长写同样如此 | J1–J4 |
| 重构是否让核心算法悄悄变慢 | 节点链、认证、画板 DDS、库树与搜索、整仓灾备、清理扫描的单位耗时被记录，并可经严格模式与基线比对，超过阈值即失败 | P1–P6 |
| 非 ASCII / emoji / 路径分隔符出现在标题里 | 逐字符往返（写入什么、读回什么）；标题不会被当成文件名（`/`、`\`、`:`、`*`、`?` 都能用） | K1 |
| 标题长度按什么计数 | 按**字符**：160 个 emoji（640 字节）与 160 个 CJK 都接受、161 个拒绝；首尾空白先裁掉再计数 | K2 |
| 只由空白或不可见字符组成的标题 | 只含空白（含 NBSP、行/段分隔符、NEL）的被拒绝；不属于 `White_Space` 的零宽字符会被接受（见第 5 节的边界） | K3 |
| 工作文件位于非 ASCII / 含空格 / 较深路径 | 建库 → 提交 → 恢复端到端可用，恢复产物逐字节一致 | K4 |
| `--source` 指向相对路径 / 工作区之外 / 不存在的文件 | 三者都被明确拒绝并说明原因（必须绝对路径 / 必须位于 `--workspace` 之内 / 文件不存在），不留下副作用 | K5 |
| 不受信任的字节喂给各解析器 | 快照/增量容器、DDS 头、C2PA 清单、设置文件一律干净拒绝或正确接受，无 panic / 越界 / 无界分配；被接受的容器必须自洽、被接受的 DDS 尺寸必须在上限内、解析失败的设置文件必须原样保留 | 单元模糊（`fuzz_support` + 四个解析器的测试） |
| 损坏落在文件的任何位置 | 逐个受管理文件、多种子地做单点改写，每一次都被内容级校验发现、退出码 1、无 panic，数据库级校验不受影响 | R5 |
| 画板 DDS 的畸形输入 | 结构性损坏（魔数 / DX10 / 格式 / 尺寸 / 截断）报为 `corrupt`；任意随机改写后扫描仍返回报告、不崩溃 | R6 |
| 精简与全库校验真并发（不构造窗口） | 两者都不挂起；精简必须成功；仓库仍完整、每个仍存在的节点逐位可恢复。全库校验在 4 轮里有 1 轮以**干净失败**收场（错误与原因不匹配，见第 5 节） | J5 |

术语：**快照**是某个历史节点的完整内容副本；**增量**是从一个节点回退到其父节点所需的差异数据。

## 4. 实测数据

### 4.1 A 组：取消边界

28 次受控取消，全部以取消结果退出；每次取消后都断言「无残留 + 重开可用 + 重试成功」。

| 场景 | 受控取消次数 | 最深取消位置 | 最大耗时 | 峰值内存 |
| --- | --- | --- | --- | --- |
| A1 提交取消（每个可取消位置各一次） | 5 | 5 | 119 ms | 16.0 MiB |
| A2 恢复取消（链解析 / 导出前 / 发布前） | 6 | 6 | 123 ms | 13.2 MiB |
| A3 精简取消（父链回溯 / 子链回溯 / 增量发布前） | 6 | 6 | 126 ms | 16.0 MiB |
| A4 检查点取消（链解析 / 快照发布前） | 4 | 4 | 93 ms | 13.2 MiB |
| A5 整仓备份取消（扫描前 / 复制 / 校验 / 发布前） | 4 | 18 | 289 ms | 13.4 MiB |
| A6 全库扫描取消（入口 / 逐节点 / 靠后节点） | 3 | 8 | 257 ms | 13.2 MiB |

A 组使用 96 KiB 工作文件，因此耗时是「取消路径本身」的开销；峰值内存为无头进程自报值，
只作「确有数值可采」的证据。

### 4.2 B 组：跨进程强杀

5 次强杀，强杀点由「逐可取消位置闸门」确定命中（进程在目标位置阻塞，测试随即强杀）。

| 场景 | 强杀点 | 强杀阶段 | 耗时 |
| --- | --- | --- | --- |
| B1 提交中途强杀 | 4 | 快照/增量已发布、数据库未提交 | 44 ms |
| B2 恢复中途强杀（导出前） | 5 | 链解析完成后 | 56 ms |
| B2 恢复中途强杀（导出后） | 6 | 导出并同步后、发布前 | 62 ms |
| B3 整仓备份中途强杀 | 2 | 复制仓库文件 | 32 ms |
| B4 提交事务中途强杀 | 5 | 事务已写入（`INSERT` 已执行）、尚未 `COMMIT` | 53 ms |

强杀后的实测结论：`verify`（迁移 + 完整性 + 外键 + 全表语义校验）与 `scrub`（逐块摘要链）
全部通过；B1 恰好多出一枚完整的孤儿快照与一枚孤儿增量（清理队列为空，属已知缺口）；
B2 目标输出不存在，只留下未发布的完整临时文件（仓库之外）；B3 源仓库可独立校验，暂存目录
可识别，重跑备份成功。

**B4（事务中途崩溃）** 把强杀点推进到事务**内部**：强杀后历史与节点数不前进（未提交事务被
丢弃）；父节点的快照仍被引用（事务内的释放语句与提交同事务，一并被丢弃）；清理队列没有多出
条目（事务内的入队同样被丢弃）；已发布的快照与增量仍是磁盘孤儿；随后同一命令重跑成功且只
前进一格。

### 4.3 C 组：大文件端到端

工作文件用**稀疏构造**：先建立逻辑长度，只向有界区域写入真实随机字节，其余部分不占磁盘簇。
因此 8 GiB 逻辑文件的真实写入量只有数百 MiB，而快照仍约 8 GiB——这正是「逻辑体积」与
「磁盘成本」分离的地方。

C 组覆盖**两条正交的轴**——「文件多大」与「每次改动多大」：

| | 小改动（每轮逻辑的 1/128） | 大改动（每轮逻辑的 1/4，3 轮） |
| --- | --- | --- |
| 一般文件（`default` 64 MiB） | 日常编辑 | 日常里的大改 |
| 大文件（`large`/`heavy`/`extreme`/`manual`） | 大文件的日常编辑 | 最坏存储放大（4 GiB 改 1 GiB、8 GiB 改 2 GiB） |

小改动档的轮数随档位下降（`default`/`large` 20 轮、`heavy` 10 轮、`extreme`/`manual` 5 轮）：
每轮提交都要**重写整份快照**，轮数不降时 4 GiB 档光 C1 就要写约 80 GiB、8 GiB 档要写约 160 GiB
快照。链深行为与文件大小无关，20 层链已在 `default`/`large` 覆盖。

| 项 | `default` 64 MiB | `large` 256 MiB | `heavy` 1 GiB | `extreme` 4 GiB | `manual` 8 GiB |
| --- | --- | --- | --- | --- | --- |
| 提交次数（1 次基线 + 改动轮数） | 21 | 21 | 11 | 6 | 6 |
| 提交总耗时 | 15.5 s | 36.8 s | 115.1 s | 151.3 s | 574.6 s |
| 恢复**最早**节点（穿整条增量链） | 1.42 s | 5.24 s | 17.09 s | 49.71 s | 97.72 s |
| 恢复**最新**节点（直接读快照） | 0.30 s | 1.06 s | 4.67 s | 20.56 s | 101.55 s |
| 快照大小 / 逻辑大小（开销） | 67.70 MB（+0.88%） | 270.73 MB（+0.85%） | 1089.32 MB（+1.45%） | 4367.74 MB（+1.69%） | 8738.19 MB（+1.73%） |
| 增量合计 | 7.54 MB | 26.98 MB | 9.84 MB | 4.29 MB | 3.21 MB |
| 增量 / 快照 | 11.1% | 10.0% | 0.9% | 0.1% | 0.04% |
| 增量 / 改动字节数 | 0.72 | 0.64 | 0.12 | 0.10 | 0.08 |
| 大改动：每轮改动 / 增量÷改动 | 16 MiB / 0.44 | 64 MiB / 0.43 | 256 MiB / 0.42 | 1 GiB / 0.42 | 2 GiB / 0.42 |
| 提交峰值内存增量（允许上限） | 10.1 MB（33.6 MB） | 28.1 MB（58.7 MB） | 116.9 MB（159.4 MB） | 348.6 MB（562.0 MB） | 644.5 MB（1098.9 MB） |
| 恢复峰值内存增量 | 6.0 MB | 23.1 MB | 111.7 MB | 343.2 MB | 639.2 MB |
| 磁盘账本：实测增量 / 预期增量（C1） | 79.53 / 79.48 MB | 318.64 / 318.60 MB | 1175.93 / 1175.91 MB | 4411.89 / 4411.89 MB | 8782.30 / 8782.30 MB |

说明：

- **快照不压缩、不去重**，因此快照大小约等于逻辑大小加每块 36 字节开销（上表开销即此项）。
  这是格式的既有特征，此处只测量记录，不做优化。
- **增量跟随改动量、远小于快照**：小改动下每轮只改动很窄的区域，增量合计通常在快照的
  0.04%–11%；大改动（每轮改 1/4）下增量升至改动量的约 42%，仍远小于快照。长期使用下仓库
  占用由「一个完整快照 + 历次改动的增量」构成，而不是「每次提交累积一份完整副本」。
- **内存**：提交峰值（绝对值）依次为 23.1 MB / 41.1 MB / 129.9 MB / 361.1 MB / 657.0 MB，
  基线约 12.5 MB——上表列的是扣除基线后的增量。若实现把整个文件读进内存，8 GiB 档的增量会是
  8 GiB，会立刻违反 C3 的断言（允许上限为逻辑的 1/8 加 24 MiB，即 1098.9 MB）。
- **磁盘账本**：场景结束后的实测工作区增量与按「快照 + 增量 + 新增改动字节」计算的预期值偏差
  在 0.06% 以内；偏差超阈值会直接报警，这条断言用来兜住「存储放大失控」类回归。

### 4.4 D / E / F 组：规模、灾备与参数边界

规模量级按**个人长期使用的真实上限**选取，而不是为凑数量构造的极端值。

| 场景 | 规模 | 关键实测 |
| --- | --- | --- |
| D1 深链 | 300 次提交（单分支） | 提交合计 18.4 s；最深节点恢复 201 ms（穿整条增量链）；提交峰值内存 16.5 MB，与链深无关；精简中间节点后最深节点仍逐字节一致 |
| D2 多分支历史图 | 21 条分支、64 节点 | 删除一条分支后磁盘实体 84 → 80，其余分支仍可逐字节恢复；清空回收站后实体归零、作品目录被回收 |
| D3 库规模 | 400 个作品 + 24 个分组 | 创建耗时 16.7 s；树计数、按标题搜索、节点移动均正确 |
| E1 整仓备份规模 | 8 个作品、16 节点 | 清单 fileCount 17、totalBytes 2.92 MB；副本独立 `verify` + `scrub` 通过、树计数与源仓库一致 |
| F1 参数边界 | 8 类越界输入 | 备注 501、非法提交类型、标题 161、空标题、搜索 161、不存在历史节点、已存在输出、非法移动目标均被明确拒绝且不 panic |

说明：D2 中每个非根节点同时持有自己的快照与一条反向增量，因此**磁盘实体数多于节点数**；
断言因此关注「删除后实体减少、其余分支仍可恢复」，而不是「实体数等于节点数」。

### 4.5 B5：崩溃孤儿回收闭环

崩溃产生的未引用文件可被扫描发现、经用户确认后清理：

1. 复用 B1 的强杀点造出孤儿快照与孤儿增量；
2. 把仓库内全部快照/增量的修改时间回拨到 30 分钟宽限期之外（只改测试工作区里文件的 mtime）；
3. 扫描**只**报告这两枚孤儿——被引用的文件即便同样「过期」也不报告，证明引用复查生效；
4. 确认清理删除孤儿、被引用文件保留；再扫描无候选（幂等）；重开可用、后续提交正常。

实测：扫描精确报告 2 枚候选，确认清理后孤儿消失、被引用实体保留，重开后 `verify` + `scrub`
通过。**孤儿仍不会被自动回收**——它是两段式（扫描报告 + 用户确认），这是设计而非缺陷。

### 4.6 H 组：画板图片完整性

画板记录只能由导入流程写入，因此 H 组先给无界面入口补上画板写入与校验命令（1:1 薄映射、
不进发布产物），再用它们构造「记录 → 文件」方向的缺失/损坏，以及「文件 → 记录」方向的孤儿。

| 场景 | 规模 | 关键实测 |
| --- | --- | --- |
| H1 双向检查 | 3 张图片 + 1 枚孤儿 | 精确报告 images 3 / missing 1 / corrupt 1 / orphans 1；缺失与损坏**不使命令失败**；35 ms、峰值约 12.6 MB |
| H2 孤儿图片回收 | 2 张图片 + 1 枚孤儿 | 扫描只报告 1 枚孤儿（被引用图片即便同样回拨到宽限期之外也不报告）、确认清理后归零、被引用图片保留；84 ms |
| H3 规模与取消 | 单画板 300 张图片 | 全部命中、无缺失/损坏/孤儿；在第一个可取消位置取消后重试成功；68 ms、峰值约 12.8 MB |

说明：

- **缺失与损坏报告不失败**：这是设计取舍——缺失图片的修复属历史迁移议题，检查只如实计数，
  由调用方（设置页完整性检查）决定如何呈现，不自动修复。
- **孤儿图片的发现与清理复用崩溃孤儿同一条闭环**：扫描把画板图片纳入范围，经反向引用检查
  后只报告无记录者；确认清理完成回收。扫描的 30 分钟宽限期同样适用，测试把文件修改时间
  回拨到宽限期之外。

### 4.7 G 组：认证模块

认证批次是唯一触及安全边界的批次：路径授权来源被抽象成**可注入的作用域**——界面侧仍走文件
选择器的授权作用域（行为与文案逐字节不变），无界面侧是一个只允许 `--workspace` 之下路径的
显式作用域。无界面入口因此补齐了进入发布 / 发布 / 取消发布 / 回读四个子命令。

| 场景 | 规模 | 关键实测 |
| --- | --- | --- |
| G1 发布峰值内存 | 16K 源图（16384×16384，≈268 MP） | 无头进程自报峰值 **1.92 GiB**，未超出保守上界 3.0 GiB；同量级于声明的 1.5 GiB 解码预算 |
| G2 发布各阶段耗时 | 同 G1 | 提交整体 62.0 s；渲染 2.0 s、编码 58.6 s、签名 0.20 s；无超时与挂起 |
| G3 发布取消（渲染 / 编码 / 签名） | 128×128 源图 | 三个阶段各取消一次：均以取消退出；输出文件不存在、输出目录无残留临时产物、认证记录数为 0；`cancel-publication` 后仓库内成品与记录归零，仓库重开可用 |
| G4 回读 | 128×128 源图 | 读回证书声明（验证状态 `Valid`）与水印绑定，记录 ID / 水印 ID / 标题 / 创作者 / 权利声明与本地记录一致，候选带证书与水印两条证据；233 ms、峰值约 205 MB（含解码器模型） |
| G5 受控文件校验 | 128×128 源图 | 全库校验报告最终成品 1、认证记录 1；替换认证仓库副本的字节后校验失败（错误含「已损坏或被替换」），证明是摘要比对而非计数；31 ms、峰值约 23 MB |

说明：

- **16K 场景只在 `extreme` 及以上档位运行**（生成 16384×16384 需约 1 GiB 内存，发布链路
  解码同样如此）；低于该档位时 G1/G2 **明确跳过并报告**，不静默降级。
- **大图由测试进程按需生成，用完即删，不提交进仓库**；认证夹具（签名凭据与 128×128 源图）
  复制进工作区后使用——无界面进程只授权工作区之内的路径。
- 取消路径的错误文案为「认证任务已取消」，与提交路径的「提交已取消」「备份操作已取消」区分。

### 4.8 R 组：损坏文件的检测与恢复

磁盘位损坏、外部工具误写或中断的复制，都会让仓库内快照/增量的字节与数据库记录的摘要不再
一致。R 组通过真实可执行文件验证「用户实际会遇到的三件事」：内容级校验必须报错、数据库级
校验不受影响、head 快照损坏后一次「内容没变」的提交即可修复。

| 场景 | 操作 | 关键实测 |
| --- | --- | --- |
| R1 最新快照被改坏 | 翻转 head 快照最后一个字节 | 全库校验失败并报「块哈希不匹配」；数据库级校验（不读文件内容）仍通过；恢复该节点被拒绝且无输出；一次内容未变化的提交把快照修好，随后校验通过、恢复逐字节一致；26 ms、峰值约 12.7 MB |
| R2 增量被改坏 | 把边增量写成非法内容 | 全库校验失败并报「无法读取恢复链 delta」；数据库级校验仍通过；head 自身持有快照、不依赖该增量，恢复仍成功且逐字节一致；31 ms、峰值约 13.3 MB |

**注意**：「仓库能打开」只代表数据库层完好（UUID、相对路径、摘要格式），不代表
文件内容完好；内容是否损坏由全库校验负责，两者分工明确、互不替代。

### 4.9 测试档位与运行成本

C 组的墙钟时间（指向发布档、16 逻辑核）实测如下。

| 档位 | 逻辑大小 | 预计峰值磁盘 | 用途 | 实测状态（2026-10-16） | 墙钟 |
| --- | --- | --- | --- | --- | --- |
| `default` | 64 MiB | ≈ 0.2 GiB | 日常典型体积 | **6/6 通过** | 33 s |
| `large` | 256 MiB | ≈ 1 GiB | 跨过明显的块级规模 | **6/6 通过** | 103 s |
| `heavy` | 1 GiB | ≈ 3 GiB | PSD 常见超限体积 | **6/6 通过** | 255 s |
| `extreme` | 4 GiB | ≈ 13 GiB | PSD 常态上限 | **6/6 通过** | 1275 s |
| `manual` | 8 GiB | ≈ 25 GiB | 4 GiB 现实上限的两倍冗余，需 ≥ 32 GiB 空闲 | **6/6 通过** | 3727 s |

C 组五档合计约 90 分钟；不含 `manual` 的四档约 28 分钟。整轮压力测试（八个组 + C 组五个档位；I 组为同日补测，见 4.10）
实测 **94.8 分钟**，全部在发布档二进制上运行。

本轮新增的 **C7、R3/R4、J1/J2、P 组**是 debug 构建上的小场景（C7 约 55 s，其余均在十秒级），
用于补覆盖与建立基线，不并入上面那份发布档完整重跑；它们的实测见 4.11–4.18（4.15 起是后续一批）。

**`manual` 档必须显式提高磁盘预算**：场景准入按「预计峰值磁盘」判超，而 `manual` 的
`peak_disk_floor` 本身（3 × 8 GiB + 64 MiB ≈ 24.06 GiB）就已超过默认的
`LILITH_STRESS_DISK_BUDGET`（24 GiB），不改会**整组记为跳过**（`record_skip`）而不是报错。
跑该档必须设 `LILITH_STRESS_DISK_BUDGET=40GiB`——C6 大改动场景的预计峰值约 32.2 GiB，是五档
里的上界。

**关于全库校验的代价**：`scrub`（全库逐块校验）的代价与「历史节点数 × 文件大小」成正比——
它要为每个历史节点从最近的快照重放整条链，再把整份内容流式复算一遍块摘要。这是 4 GiB 与
8 GiB 档耗时的主要来源（6 节点 × 4 GiB / 8 GiB 的全链校验：`manual` 的 C1 单次 `scrub` 就要
362.7 s，占该场景的大头），也是应用把「空闲期的 head 快照校验」与「全库扫描」分成两条路径的
原因。

### 4.10 I 组：多进程并发与高频命令

本组是 2026-10-16 补测的缺口（对应 `docs/planning/todo.md` 的「同仓库多进程并发缺乏防呆」）：
数据规模此前已有覆盖（D 组），但「命令并发」与「同一仓库多进程写入」既未设计也未测试。
下列数字为 **debug 构建**实测（该组只有 3 个用例、约 8 秒，不并入发布前的 release 完整重跑）。

| 场景 | 规模 | 关键实测 |
| --- | --- | --- |
| I1 并发写被拒 | 一个写进程停在检查点持锁，期间启动第二个写进程 | 第二个进程以明确错误退出（「不支持同一仓库的多进程写入」）、退出码 1；第一个进程随后正常提交；仓库自洽、无残留 |
| I2 强杀不残留锁 | 强杀持有锁的写进程 | 锁由操作系统在句柄关闭时释放；随后的写进程仍能取得锁并提交成功 |
| I3 高频连续命令 | 20 次连续提交（每次一个独立进程） | 历史节点 20、全库校验通过、无残留；同时验证锁在每次结束后都被正确释放 |

说明：

- **锁是 SQLite 的 `BEGIN IMMEDIATE` 写锁，不是锁文件**：本项目的强杀场景会把锁文件方案
  变成「残留锁把仓库永久锁死」，因此这里刻意让内核负责释放——I2 就是这条理由的证明。
- 覆盖范围**只限无头入口**：只读命令与 `init-repository` 不取锁，GUI 路径依赖单实例插件不变。
  「GUI 与无头同时写同一仓库」仍不受保护，见第 5 节。

### 4.11 C7：大文件提交的中断

A 组与 B 组此前只用 96 KiB 工作文件，C 组的大文件档不做取消与强杀——「文件到数百 MiB 时提交
到一半被取消 / 被杀」恰好落在两组之间的缝里。C7 把 A/B 的断言搬到档位大小的工作文件上（默认
`default` 64 MiB，可 `LILITH_STRESS_TIERS=large` 抬到 256 MiB）。

| 场景 | 操作 | 关键实测 |
| --- | --- | --- |
| C7a 逐检查点取消 | 在提交的 5 个取消检查点各取消一次 | 每次都以取消退出、无残留、待清理队列为空、历史不推进、仓库可重开；随后同一命令重试成功且只前进一格 |
| C7b 中途强杀 | 提交停在第一个检查点后 `TerminateProcess` | 历史不推进、无残留；随后另一个写进程仍能成功提交，head 恢复与工作文件逐字节一致 |

实测（`default` 档 64 MiB，debug 构建）：整个 C7 场景 **55.3 s**，含 5 次逐检查点取消 + 1 次强杀
+ 3 次成功提交 + 3 次全库校验。

### 4.12 R3 / R4：主库文件本身的损坏

R1/R2 改的是快照/增量的**内容**；R3/R4 改的是**主库文件本身**（`lilith-artworks.sqlite3`）——
这是 R 组此前的直接空白：库级单测覆盖了函数层，但没有用例验证「主库被改坏」时使用者看到的是
可行动的错误，而不是崩溃、静默通过或残留半成品。

| 场景 | 操作 | 关键实测 |
| --- | --- | --- |
| R3 主库头部被误写 | 覆盖文件头 16 字节（SQLite 魔数区）为任意字节，长度不变 | `verify` 与 `scrub` 都失败：退出码 1、错误指向「作品数据库」、无 panic、无残留临时文件 |
| R4 主库被清空 | 把主库截为 0 字节 | `verify` 失败并提示「缺少数据库 / 请从备份恢复」；**关键边界**：失败的打开不会把空文件重建为全新空仓库（主库仍为 0 字节），因此不会静默丢弃历史 |

说明：主库不可用时「两层校验」不再分歧——`verify`（要打开库）与 `scrub`（同样要打开库）都会失败，
这与 R1/R2 的情形（文件内容坏、库仍可打开）正好互补。

### 4.13 J 组：写 + 读交错

A–I 九组本质都是「单操作 × 单故障」的稀疏采样，「操作 A 进行到一半时操作 B 到来」此前没有采样点。
J 组的第一批采样点：**写进程持哨兵锁时，只读命令能否作答、是否看到一致状态**（更长的写任务与真并发
见 4.18）。

| 场景 | 操作 | 关键实测 |
| --- | --- | --- |
| J1 写持锁期间读 | 提交停在检查点 1（尚未发布文件）与检查点 4（快照已发布、事务未提交）时运行 `list-tree` / `verify` / `list-history` | 三个读命令都成功、未超时、远低于 30 s 上限；`list-tree` 与写之前逐字段一致、历史节点数未推进——读到的是一致快照，而非写入中间态 |
| J2 并发读 | 4 个只读命令同时运行 | 全部成功、互不阻塞；读后树不变、仓库仍健康 |

说明：**跨进程**只读命令不取哨兵锁（锁只对会写仓库的命令生效），因此不会被写进程挡住；SQLite 的
WAL 保证读事务看到某个一致快照。**进程内**「长写任务持仓库操作锁时读命令仍能作答」这条并发承诺由
`app/settings.rs` 的单元测试覆盖（`repository_read_answers_while_a_long_write_holds_the_operation_lock`），
它若回归会以超时失败而不是无限挂起；该路径只影响 GUI（无头入口每个进程只跑一个命令）。

### 4.14 P 组：核心算法性能基准

此前性能断言只有「上界」（峰值内存 ≤ 逻辑大小的 1/8 等），没有基线，因此「重构让吞吐缓慢退化」不会
被任何断言发现。P 组记录六项核心算法的单位耗时，并提供可选的严格比对。

下列数字为 **debug 构建**、单线程运行（`--test-threads=1`）实测；绝对值依赖机器与构建档，回归看的是
同档位下的相对变化。基线见 `src-tauri/tests/perf-baseline.json` 的 `debug` 段。

| 场景 | 规模 | 关键实测 |
| --- | --- | --- |
| P1 节点链 | 96 KiB 文件、48 节点 | 单次提交摊薄 **58.5 ms**；恢复最早节点（穿 47 步反向增量）**74.3 ms**，即 **1.6 ms/步**；恢复 head **38.6 ms**；恢复内容逐字节一致 |
| P2 认证 | 512×512 源图 | 发布整体 **747 ms**（渲染 450 / 编码 120 / 签名 12）；`decode-authenticity` 回读 **324 ms** |
| P3 画板 DDS | 16 张 512×512 PNG | 导入 **373 ms**（**23.3 ms/张**，含 BC7 编码）；DDS 完整性扫描 **414 ms**（25.9 ms/张） |
| P4 库树与搜索 | 5 个分组 + 100 个作品（106 个节点） | 整树装配 **36.9 ms**；命中全部的查询 **33.1 ms**、只命中一个的查询 **32.2 ms**（三次取最小） |
| P5 整仓灾备 | 4 个作品 × 3 次提交、256 KiB 版本，仓库 3.25 MiB | 扫描 + 复制 + 校验 + 发布合计 **335 ms**，约 **9.6 MiB/s**；副本独立 `verify` 通过 |
| P6 清理扫描 | 6 个作品 × 4 次提交、96 KiB 版本，仓库 2.59 MiB | 未引用文件扫描 **32.8 ms**（候选 0）、待清理队列重放 **32.0 ms**（待清理 0）（三次取最小） |

说明：

- 走真实可执行文件，因此耗时含进程启动与打开仓库的固定开销（这就是产品被调用时的实际成本）。
  小文件让这项固定开销可见，所以同时记录总耗时与摊薄值。
- P4–P6 各测 3 轮取**最小值**，削弱调度抖动；这是「相对基线」能用的前提。P5/P6 建库规模刻意很小
  （3 MiB 上下），因为它们要测的是**单位吞吐**而不是大文件——大文件的 I/O 成本由 C 组覆盖。
- 每次重复都断言结果正确（节点数、候选数、待清理数），基准里混进错误结果就等于失去意义。
- **默认只记录、不设硬断言**（只有数量级护栏），避免把机器噪声变成 flaky；真正的回归门是
  `LILITH_STRESS_PERF_STRICT=1` + `tests/perf-baseline.json`，超过 `LILITH_STRESS_PERF_FACTOR`
  倍（默认 2.5×）即失败。基线由 `LILITH_STRESS_PERF_UPDATE=1` 生成，按构建档分开记录。
- GPU 侧的纹理上传/绘制不在无头入口的覆盖范围内，本组不涉及。

### 4.15 K 组：输入域极值

F1 覆盖的是「数值 / 长度边界」，K 组补的是**字符域**与**路径域**。这是 Windows 桌面应用最经典的
一类崩溃与数据错乱来源：长度按字节而不是按字符计数、把用户可见的标题当文件名用、非 ASCII 路径在
命令行参数与文件系统之间转换时被替换或截断。

| 场景 | 输入 | 关键实测 |
| --- | --- | --- |
| K1 字符域往返 | 15 个标题：中文、emoji、ZWJ 家庭序列、非 BMP 数学/花体字母、RTL 阿拉伯文、组合附加符号、零宽空格、内部换行 / 制表符、`slash/back\slash`、`colon:star*question?`、尾随空格 | 全部逐字符往返（`list-tree` 读回与写入一致）；带路径分隔符的标题成功创建，证明**标题不会被当成文件名**；非 ASCII 子串搜索命中；emoji 标题的作品两次提交后恢复旧版本逐字节一致 |
| K2 长度按字符计数 | 160 / 161 个 emoji（4 字节/字符）、160 / 161 个 CJK（3 字节/字符）、首尾带空格的 160 emoji | 160 个都接受并往返；161 个都拒绝且错误提到 160；首尾空白先裁掉再计数 |
| K3 空白与不可见字符 | `"   "`、`"\t\r\n"`、NBSP、U+2028/U+2029、NEL、零宽空格 / 零宽连接符 / BOM | 只含空白的全部拒绝并带说明；三个不属于 `White_Space` 的零宽字符被接受并逐字符往返（见第 5 节的边界） |
| K4 路径域 | 工作区内的 `含空格 与中文 的目录/nested/deeper/最深层 🎨/作品 草案 🎨 v2.bin` | 建库 → 两次提交 → 恢复，产物逐字节一致；仓库 `verify` + `scrub` 通过、无残留 |
| K5 路径边界 | 相对路径、工作区之外的绝对路径、工作区内但不存在的文件 | 三者都被明确拒绝：「必须使用绝对路径」「必须位于 `--workspace` 之内」「不存在」；被拒绝的创建不会凭空造出源文件 |

实测：K 组 5 个用例 **5.2 s**（含 20 余次子进程）；全部通过。

### 4.16 畸形输入模糊：四个解析器

仓库里的容器、画板 DDS、认证清单与设置文件都是「读取不受信任字节」的解析器。此前只有手写的固定
边界（F1 的 8 类、R1/R2 的两种损坏形态），没有**随机化**输入。这一批用自写的确定性伪随机源
（`src/fuzz_support.rs`，只在 `cfg(test)` 下编译）生成结构感知的畸形输入——位翻转、字节替换、插入、
删除、清零、段落互换、整块覆写、续写——并对每个解析器扫固定种子。

| 解析器 | 输入构造 | 断言 | 实测 |
| --- | --- | --- | --- |
| 快照容器 `ChunkFile` | 384 组：纯随机字节 / 结构未知扰动 / 只扰动头部（魔数、版本、计数、长度） | 绝不 panic；`Ok` 时块数量不超过文件容量（每条记录至少 36 字节）且必须能物化、产物长度等于声明值；截断与续写必须被拒绝 | 通过（包含「确有扰动仍保持结构合法」的非空断言，防止模糊退化成空转） |
| 增量容器 `ChunkFileDelta` | 384 组：随机字节 / 随机扰动 | 绝不 panic；截断与续写必须被拒绝 | 通过 |
| DDS 头 `pin_board::dds` | 384 组：随机字节 / 只扰动 148 字节 DX10 头 / 整文件扰动 | 绝不 panic；被接受的尺寸必须在声明上限内（长边 ≤ 16384、像素 ≤ 2.68 亿）；负载长度必须覆盖声明尺寸；导入产物必须自报与返回值一致的尺寸 | 通过；另有对照用例确认「只改负载字节」仍可解析（结构校验的语义边界） |
| C2PA 清单 `read_manifest` | 96 组：随机字节 / 带 JPEG 或 PNG 魔数前缀 + 随机尾巴 | 绝不 panic（第三方解析器的 panic 会被 `catch_unwind` 捕获并把种子写进失败消息）；随机字节不可能被判定为「带有效清单」 | 通过 |
| 设置文件 `load_settings` | 80 组：随机字节 + 结构性畸形 JSON（空、`[]`、`null`、数字、截断、字段类型错、1 万层嵌套、10 万位数字、10 万字符字符串） | 绝不 panic；版本为当前版本时返回的设置必须通过 `validate_settings`（修正在内存里、不整份清空）；**解析失败的文件必须被原样保留** | 通过 |

实测：5 个用例 **0.68 s**，随 `cargo test --lib` 进 Windows CI。零新依赖（生成器是自写的 xorshift，
没有引入 proptest / quickcheck）。

### 4.17 R5 / R6：随机化损坏

R1/R2 改的是固定位置（文件末尾、整文件），R3/R4 改的是主库。R5/R6 把「改坏」扩展成随机化、逐个
文件、多种子。

| 场景 | 操作 | 关键实测 |
| --- | --- | --- |
| R5 随机化单点损坏 | 3 个受管理文件（1 枚 snapshot + 2 条 delta）× 4 个变体 = 12 次单点改写（偏移与掩码由种子决定，覆盖首/中/尾，另有一半只改头部 64 字节） | 每一次都被全库校验发现、退出码 1、无 panic；每一轮都确认数据库级校验（`verify`）不受内容损坏影响；复原后校验通过、最早版本逐字节恢复。实测 1.5 s |
| R6 画板 DDS 损坏 | 3 张导入图片；6 类结构性损坏（魔数 / DX10 fourcc / BC7 格式 / 宽 0 / 高 70000 / 截断）+ 1 类只改负载 + 24 次随机改写 | 6 类结构性损坏都精确报为 `corrupt`（其余计数不变）；只改负载**不会**被报为损坏（见第 5 节的语义边界）；24 次随机改写后扫描全部成功返回报告、计数不超过图片总数；复原后归零。实测 1.5 s |

### 4.18 J3–J5：多操作交错

J1/J2 只取了「提交持锁 × 读」这一个采样点。J3–J5 把写任务换成更长的两类，并加入真并发。

| 场景 | 操作 | 关键实测 |
| --- | --- | --- |
| J3 整仓灾备持锁期间读 | 灾备停在「正在复制仓库文件」阶段（持锁且以分钟计的长任务），期间运行三个只读命令 | 三个都成功、未超时、远低于 30 s 上限；历史节点数未推进（灾备不改源仓库）；灾备产物可独立 `verify` + `scrub`，源仓库节点数不变 |
| J4 精简持锁期间读 | 逐个检查点（6 个）停住精简，每个检查点上运行三个只读命令 | 检查点都被命中、读命令全部成功；`list-tree` 与精简前**逐字段一致**；取消后旧链完好、最早节点仍逐字节可恢复；正面对照确认精简完成后节点数减一 |
| J5 精简 + 全库校验真并发 | 不设闸门，`compact` 与 `scrub` 同时启动、各自跑完，连跑 4 轮 | 两者都不挂起；精简 4/4 成功；结束后仓库完整（`verify` + `scrub` 通过）、每个仍存在的节点逐位可恢复。全库校验的失败按类别记录：写者持哨兵时以「仓库正在被写入，请稍后重试」**明确拒绝**（复跑 4 轮里 2 轮），不再出现与原因无关的错误 |
| J6 全库校验 vs 写哨兵 | 闸门把写进程停在检查点（确实持有哨兵），此时运行 `scrub` 与 `verify` | `scrub` 立刻以退出码 1 拒绝且理由为「仓库正在被写入，请稍后重试」；同一时刻 `verify` 照常作答；写者结束后同一条 `scrub` 覆盖全部节点并通过 |

说明：J1–J4 把写进程停在检查点上再让读命令跑，**确定性高但危险窗口是构造出来的**；J5 刻意不构造
窗口，代价是它只能断言「不挂起 + 不损坏 + 干净失败」这类不变量，而不能要求每一次读都成功。J6 用
闸门把「写者持锁」这一状态固定下来，因此「明确拒绝」是可以确定性断言的；J5 则退化为分类度量。

## 5. 尚未覆盖

明确**不做**自动化、或当前还不具备条件的部分；带 ★ 的两条是本轮测出来的**产品侧边界**（已登记在
`docs/planning/todo.md`），不是测试缺口：

| 项目 | 原因 |
| --- | --- |
| ★ 画板 DDS 扫描只检查结构、不检查像素内容 | 写进 DDS 的记录只有尺寸与路径，没有内容摘要；扫描校验的是魔数 / DX10 / BC7 格式 / 尺寸 / 负载长度 / BC7 可解码，因此**只改负载字节不会被发现**。没有原始素材时像素语义本来就不可判定，所以这是当前的取舍而不是缺陷；要真正覆盖内容，需要给 DDS 记一份摘要（R6 会把这一条先测出来） |
| ★ 只由零宽字符组成的标题会被接受 | 标题的非空判定走 Unicode `White_Space`，而零宽空格（U+200B）、零宽连接符（U+200D）、字节序标记（U+FEFF）都不属于 `White_Space`，因此「看得见是空、实际非空」的标题是合法的。不影响数据安全，但属于可改进点；改动会先让 K3 失败，提示同步更新报告 |
| 断电持久性（已提交的数据在断电后是否仍在） | 结束进程不触及操作系统与磁盘的缓存、也不保证目录项落盘，结构上无法覆盖。该项由操作系统、磁盘与数据库的 `synchronous = FULL` 声明保证 |
| 界面视觉、交互手感、桌面集成（拖放、托盘、快捷键等） | 自动化不驱动界面；由人工验收清单覆盖 |
| 崩溃残留文件的**自动**回收 | 孤儿不会被自动回收；可被扫描发现并经用户确认后清理，这条闭环已由 B5、H2 覆盖。「自动」回收是产品设计取舍，不是测试断言 |
| 「无头 + 无头」以外的多进程组合（如 GUI 与无头同时写同一仓库） | 哨兵锁只覆盖无头入口；GUI 侧仍依赖单实例插件。GUI 与无头并存的组合不受保护，是本轮已知边界 |
| 性能绝对值的**跨机器**自动比对 | 基准与构建档、机器绑定；默认只记录、不设硬断言，严格比对需按机器放宽因子。不做跨机器自动门 |
| 异常 RFC 3161 时间戳服务的失败与超时 | 保留人工验收 |

## 6. 如何自行运行

这套测试中**八组便宜的分组（cancel / crash / cleanup / damage / pin_board / authenticity /
concurrency / input，合计约 30 秒）已进 Windows CI**，日常改动因此有自动回归保护；**其余三组
（`stress_large` / `stress_scale` / `stress_bench`）仍在发布前手动运行**——它们耗时长、磁盘占用高
（`heavy`/`extreme` 档单次以十分钟计、`manual` 档以一小时计，峰值磁盘可达十几至二十几 GiB），或需要
人工解读数值。此外四个解析器的畸形输入模糊随 `cargo test --lib` 在 CI 内自动运行。构建无头入口、
选择档位、环境变量与输出文件的完整命令见
`docs/guides/validation.md` 的「压力测试：便宜的分组进 CI，昂贵的仍只在发布前运行」；跑 `manual`
前必须先按第 4.9 节调高 `LILITH_STRESS_DISK_BUDGET`，否则 C 组会被记为跳过而不是失败。各档位的实测
数据与运行成本见本文第 4 节。
