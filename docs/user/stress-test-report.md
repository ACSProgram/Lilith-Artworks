# 可靠性压力测试报告

- 被测版本：应用 `0.2.0`，repository schema v4
- 报告日期：2026-10-17
- 数据来源：本文数字均来自真实运行——主体为 2026-10-17 在 release 构建上的完整重跑（八组轻量
  分组、C 组五个档位、G 组 16K 大图、规模组与性能基准），取消/强杀等轻量场景的细分耗时为此前
  同档位构建的实测
- 测试策略与运行命令（面向开发者）见 `docs/guides/validation.md`

这套测试针对 **强制结束进程、软件崩溃、长操作取消、超大文件、磁盘与内存极限、并发与损坏输入**
等极端情况，以**独立进程**运行真实程序并断言结果。本文记录它验证了什么、实测数据如何，以及
它**不**覆盖什么。

## 测试方式

理解三点，就能正确理解后文的「保证」边界：

- **被测对象是真实程序**，以「无界面模式」作为独立进程启动。测试进程只通过命令行、标准输入与
  文件与它交互，不读取任何内部状态——测的是真实的启动、恢复与落盘路径。
- **干预手段只有三种**，全部来自进程外部：① 在每个「可以取消的位置」通过标准输入下发取消/继续；
  ② 直接强杀进程（等价于任务管理器结束进程，不运行任何清理）；③ 阶段标记文件。
- **断言只用两类事实**：磁盘事实（文件是否存在、大小、两个文件是否逐字节相同）与命令返回的
  JSON。没有「重开不报错就算过」这类弱断言。

所有测试都在临时工作区里完成，不读取也不修改真实仓库；工作区随场景结束自动回收。

无界面入口只存在于开发测试构建，**正式发布版没有它**。全套测试中为了测试而触及产品代码的只有
两类：提交与认证流水线上的若干**观察标记点**（feature 门控，发布产物中不存在），以及一次纯重构
（把「写快照」抽成函数，让磁盘写满注入走真实代码路径）。两者都不改变发布版的界面与业务行为。

## 结论：验证了什么

1. **强制结束进程不会损坏数据。** 在提交、恢复、整仓备份的任意阶段把进程杀掉，仓库都能重新
   打开，并通过完整性与逐块摘要校验；没做完的动作被丢弃，不会出现「写了一半的成品」——包括
   杀在数据库事务内部（已写入、未提交）时，未提交的写入被整体丢弃。
2. **取消是干净的。** 每个长操作在任意阶段取消，都不留残留文件、不推进历史，并且可以立刻重试成功。
3. **大文件可用（已实测到 8 GiB）。** 64 MiB、256 MiB、1 GiB、4 GiB、8 GiB 五档全部通过
   （提交 → 有界改动 → 恢复 → 逐字节一致）；4 GiB 档包含「大文件 + 每轮改 1 GiB」、8 GiB 档
   包含「大文件 + 每轮改 2 GiB」的最坏情况。8 GiB 是 `manual` 档，为 4 GiB 现实上限的两倍冗余。
4. **磁盘与内存占用有界。** 每次提交新增的磁盘占用跟随「改了多少字节」，而不是「文件有多大」；
   处理 4 GiB 文件约用 351 MB 内存、8 GiB 文件约用 647 MB 内存，都不随文件大小线性增长。
5. **规模和异常输入下行为正确。** 300 次提交的长历史、约 20 条分支、400 个作品的库、整仓
   备份、8 类越界输入，计数、搜索、移动、删除、恢复都正确；崩溃留下的孤儿文件可被扫描发现、
   经确认后清理。
6. **画板图片的完整性可查。** 导入图片后，能区分「正常 / 缺失 / 损坏 / 孤儿」四类并如实计数
   （缺失与损坏只报告、不失败）；孤儿图片走同一条「扫描发现 + 用户确认清理」的闭环。
7. **认证发布可用、可取消、可回读。** 在 16384×16384 像素（约 2.68 亿像素）的大图上，解码、
   加水印、签名的内存不超出预算；三个阶段任意取消都不留半成品；发布成品能读回证书信息。
8. **损坏的文件会被发现，并且能修好。** 仓库里的快照/增量被改坏后，全库校验会报错、恢复会
   拒绝，而一次「内容没变」的提交就能把它修好。
9. **同一仓库不会被两个进程同时写入。** 会写仓库的无头命令独占一个跨进程哨兵锁，第二个写
   进程拿到的是明确拒绝，而不是与前者在业务层竞态；锁由操作系统在句柄关闭时释放，因此被
   强杀的写进程不会把仓库锁死，随后的写进程仍能取得锁并提交成功。
10. **磁盘写满时是干净失败。** 在真实的快照写入路径上注入「写到这里就没空间」，产品返回
    清晰的「空间不足」错误、不推进历史、不留半成品、可重试；写到一半的字节不会被误当成
    完整快照。
11. **大文件在提交中途被取消或被强杀也是干净的。** 在五个档位（64 MiB–8 GiB）的工作文件上，
    每个取消检查点各取消一次、再强杀一次，都无残留、历史不推进、可重试；强杀后 head 仍能
    恢复出与工作文件逐字节一致的内容。
12. **主库文件本身被改坏时会干净失败。** 把 `lilith-artworks.sqlite3` 的头部改写成非数据库
    内容或清空，两层校验都给出可行动的错误（退出码 1、指向作品数据库、无 panic），并且失败的
    打开不会把空文件重建为一个全新的空仓库——那会静默丢弃用户历史。
13. **长写任务持锁期间只读命令仍能作答。** 写进程持锁时，`list-tree` / `verify` / `list-history`
    照常返回并看到写之前的**一致**状态（含「快照已发布、数据库事务尚未提交」这个最易撕裂的
    窗口）；多个只读命令并发互不阻塞。
14. **核心算法有可比的性能基线。** 节点链提交/恢复、认证发布与回读、画板 DDS 导入与扫描、库树与
    搜索、整仓灾备、清理扫描的单位耗时被记录，并可经严格模式与基线比对，超阈值的性能退化会被
    发现。
15. **非 ASCII 与特殊字符标题逐字符往返。** 中文、emoji、ZWJ 家庭序列、非 BMP 数学/花体字母、
    RTL 阿拉伯文、组合附加符号、零宽字符、内部换行与制表符、以及标题里带 `/`、`\`、`:`、`*`、`?`
    都能写入并原样读回——这同时证明**标题不会被当成文件名**（否则这些字符在 Windows 上会直接失败）。
16. **标题长度按字符而不是按字节计数。** 160 个 emoji（640 字节）与 160 个 CJK（480 字节）都被
    接受并逐字符往返，161 个被拒绝；首尾空白先裁掉再计数。
17. **不受信任的字节换不来崩溃或资源耗尽。** 四个解析器（快照/增量容器、DDS 头、C2PA 清单、
    设置文件）各自喂进数百组确定性畸形输入：一律干净拒绝或正确接受，没有 panic、越界或无界分配；
    被接受的容器必须自洽，被接受的 DDS 尺寸必须落在声明上限内，解析失败的设置文件必须被
    原样保留。随机化单点损坏与画板 DDS 结构性损坏在真实磁盘路径上同样被检测到或如实报告。
18. **多操作交错不会损坏仓库。** 提交、整仓灾备、精简三类写任务持锁期间，只读命令都照常作答并看到
    一致状态；真正并发的「精简 + 全库校验」连跑 4 轮，仓库仍完整、每个节点仍逐位恢复；写者持
    哨兵期间全库校验给出**明确拒绝**（「仓库正在被写入，请稍后重试」）。

术语：**快照**是某个历史节点的完整内容副本；**增量**是从一个节点回退到其父节点所需的差异数据。

## 实测数据

### 大文件（C 组）

工作文件用**稀疏构造**：先建立逻辑长度，只向有界区域写入真实随机字节，其余部分不占磁盘簇。
因此 8 GiB 逻辑文件的真实写入量只有数百 MiB，而快照仍约 8 GiB——这正是「逻辑体积」与
「磁盘成本」分离的地方。

C 组覆盖两条正交的轴——「文件多大」与「每次改动多大」：

| | 小改动（每轮逻辑的 1/128） | 大改动（每轮逻辑的 1/4，3 轮） |
| --- | --- | --- |
| 一般文件（`default` 64 MiB） | 日常编辑 | 日常里的大改 |
| 大文件（`large`/`heavy`/`extreme`/`manual`） | 大文件的日常编辑 | 最坏存储放大（4 GiB 改 1 GiB、8 GiB 改 2 GiB） |

小改动档的轮数随档位下降（`default`/`large` 20 轮、`heavy` 10 轮、`extreme`/`manual` 5 轮）：
每轮提交都要**重写整份快照**，轮数不降时 4 GiB 档光 C1 就要写约 80 GiB、8 GiB 档要写约 160 GiB
快照。链深行为与文件大小无关，20 层链已在 `default`/`large` 覆盖。下表各行对应场景：
提交与恢复（C1）、精简（C2）、峰值内存（C3）、链体积与磁盘账本（C4）、恢复产物即删（C5）、
大改动端到端（C6）。

| 项 | `default` 64 MiB | `large` 256 MiB | `heavy` 1 GiB | `extreme` 4 GiB | `manual` 8 GiB |
| --- | --- | --- | --- | --- | --- |
| 提交次数（1 次基线 + 改动轮数） | 21 | 21 | 11 | 6 | 6 |
| 提交总耗时 | 11.9 s | 45.0 s | 283.4 s | 1112.1 s | 795.9 s |
| 恢复**最早**节点（穿整条增量链） | 1.39 s | 6.84 s | 29.63 s | 60.80 s | 180.91 s |
| 恢复**最新**节点（直接读快照） | 0.30 s | 1.05 s | 5.44 s | 64.43 s | 143.83 s |
| 快照大小 / 逻辑大小（开销） | 67.70 MB（+0.88%） | 270.73 MB（+0.85%） | 1089.32 MB（+1.45%） | 4367.74 MB（+1.69%） | 8738.19 MB（+1.73%） |
| 增量合计 | 7.54 MB | 26.98 MB | 9.84 MB | 4.29 MB | 3.21 MB |
| 增量 / 快照 | 11.1% | 10.0% | 0.9% | 0.1% | 0.04% |
| 增量 / 改动字节数 | 0.72 | 0.64 | 0.12 | 0.10 | 0.08 |
| 大改动：每轮改动 / 增量÷改动 | 16 MiB / 0.47 | 64 MiB / 0.45 | 256 MiB / 0.44 | 1 GiB / 0.44 | 2 GiB / 0.44 |
| 提交峰值内存增量（允许上限） | 12.2 MB（33.6 MB） | 30.2 MB（58.7 MB） | 119.6 MB（159.4 MB） | 351.2 MB（562.0 MB） | 647.4 MB（1098.9 MB） |
| 恢复峰值内存增量 | 7.5 MB | 24.4 MB | 113.7 MB | 346.1 MB | 642.0 MB |
| 磁盘账本：实测增量 / 预期增量（C1） | 79.53 / 79.48 MB | 318.64 / 318.60 MB | 1175.93 / 1175.91 MB | 4411.89 / 4411.89 MB | 8782.30 / 8782.30 MB |

说明：

- **快照不压缩、不去重**，因此快照大小约等于逻辑大小加每块 36 字节开销（上表开销即此项）。
  这是格式的既有特征，此处只测量记录，不做优化。
- **增量跟随改动量、远小于快照**：小改动下每轮只改动很窄的区域，增量合计通常在快照的
  0.04%–11%；大改动（每轮改 1/4）下增量升至改动量的约 44%–47%，仍远小于快照。长期使用下仓库
  占用由「一个完整快照 + 历次改动的增量」构成，而不是「每次提交累积一份完整副本」。
- **内存是流式的**：提交峰值（绝对值）依次为 24.7 MB / 42.7 MB / 132.1 MB / 363.7 MB / 659.9 MB，
  基线约 12.5 MB——上表列的是扣除基线后的增量。若实现把整个文件读进内存，8 GiB 档的增量会是
  8 GiB，会立刻违反断言（允许上限为逻辑的 1/8 加 24 MiB，即 1098.9 MB）。
- **磁盘账本**：场景结束后的实测工作区增量与按「快照 + 增量 + 新增改动字节」计算的预期值偏差
  在 0.06% 以内；偏差超阈值会直接报警，这条断言用来兜住「存储放大失控」类回归。

**大文件提交的中断（C7）**：把取消与强杀的断言搬到档位大小的工作文件上，随五个档位各自运行。

| 场景 | 操作 | 结果 |
| --- | --- | --- |
| C7a 逐检查点取消 | 在提交的 5 个取消检查点各取消一次 | 每次都以取消退出、无残留、待清理队列为空、历史不推进、仓库可重开；随后同一命令重试成功且只前进一格 |
| C7b 中途强杀 | 提交停在第一个检查点后强杀进程 | 历史不推进、无残留；随后另一个写进程仍能成功提交，head 恢复与工作文件逐字节一致 |

`default` 档（64 MiB）下整个 C7 场景约 55 s，含 5 次逐检查点取消 + 1 次强杀 + 3 次成功提交 +
3 次全库校验；8 GiB 档同样完成全套中断与恢复校验。

### 取消与强杀（A、B 组）

A 组：28 次受控取消，全部以取消结果退出；每次取消后都断言「无残留 + 重开可用 + 重试成功」。
A 组使用 96 KiB 工作文件，因此耗时反映的是「取消路径本身」的开销。

| 场景 | 受控取消次数 | 最深取消位置 | 最大耗时 | 峰值内存 |
| --- | --- | --- | --- | --- |
| A1 提交取消（每个可取消位置各一次） | 5 | 5 | 119 ms | 16.0 MiB |
| A2 恢复取消（链解析 / 导出前 / 发布前） | 6 | 6 | 123 ms | 13.2 MiB |
| A3 精简取消（父链回溯 / 子链回溯 / 增量发布前） | 6 | 6 | 126 ms | 16.0 MiB |
| A4 检查点取消（链解析 / 快照发布前） | 4 | 4 | 93 ms | 13.2 MiB |
| A5 整仓备份取消（扫描前 / 复制 / 校验 / 发布前） | 4 | 18 | 289 ms | 13.4 MiB |
| A6 全库扫描取消（入口 / 逐节点 / 靠后节点） | 3 | 8 | 257 ms | 13.2 MiB |

B 组：5 次强杀，强杀点由「逐可取消位置闸门」确定命中（进程在目标位置阻塞，测试随即强杀）。

| 场景 | 强杀点 | 强杀阶段 | 耗时 |
| --- | --- | --- | --- |
| B1 提交中途强杀 | 4 | 快照/增量已发布、数据库未提交 | 44 ms |
| B2 恢复中途强杀（导出前） | 5 | 链解析完成后 | 56 ms |
| B2 恢复中途强杀（导出后） | 6 | 导出并同步后、发布前 | 62 ms |
| B3 整仓备份中途强杀 | 2 | 复制仓库文件 | 32 ms |
| B4 提交事务中途强杀 | 5 | 事务已写入、尚未提交 | 53 ms |

强杀后的实测结论：`verify`（迁移 + 完整性 + 外键 + 全表语义校验）与 `scrub`（逐块摘要链）
全部通过。B1 恰好多出一枚完整的孤儿快照与一枚孤儿增量（清理队列为空，属已知缺口，见 B5）；
B2 目标输出不存在，只留下未发布的完整临时文件（仓库之外）；B3 源仓库可独立校验，暂存目录
可识别，重跑备份成功。B4 把强杀点推进到事务**内部**：强杀后历史与节点数不前进（未提交事务被
丢弃）、父节点的快照仍被引用、清理队列没有多出条目，随后同一命令重跑成功。

**崩溃孤儿回收闭环（B5）**：复用 B1 的强杀点造出孤儿快照与孤儿增量，把仓库内全部快照/增量的
修改时间回拨到 30 分钟宽限期之外，扫描**只**报告这两枚孤儿（被引用的文件即便同样「过期」也不
报告，证明引用复查生效）；确认清理删除孤儿、被引用文件保留，重开后 `verify` + `scrub` 通过。
孤儿不会被自动回收——「扫描报告 + 用户确认」两段式是设计而非缺陷。

| --- | --- | --- |
| D1 深链 | 300 次提交（单分支） | 提交合计 24.3 s；最深节点恢复 214 ms（穿整条增量链）；提交峰值内存 18.0 MB，与链深无关；精简中间节点后最深节点仍逐字节一致 |

| D3 库规模 | 400 个作品 + 24 个分组 | 创建耗时 23.6 s；树计数、按标题搜索、节点移动均正确 |

### 并发与交错（I、J 组）

**多进程写入与高频命令（I 组）**：会写仓库的无头命令独占一个 SQLite 写锁（`BEGIN IMMEDIATE`），
第二个写进程被明确拒绝；锁由内核在句柄关闭时释放，因此强杀不残留锁。

| 场景 | 操作 | 结果 |
| --- | --- | --- |
| I1 并发写被拒 | 一个写进程停在检查点持锁，期间启动第二个写进程 | 第二个进程以明确错误退出（「不支持同一仓库的多进程写入」）、退出码 1；第一个进程随后正常提交；仓库自洽、无残留 |
| I2 强杀不残留锁 | 强杀持有锁的写进程 | 锁被操作系统释放；随后的写进程仍能取得锁并提交成功 |
| I3 高频连续命令 | 20 次连续提交（每次一个独立进程） | 历史节点 20、全库校验通过、无残留；同时验证锁在每次结束后都被正确释放 |

**多操作交错（J 组）**：「操作 A 进行到一半时操作 B 到来」的采样。

| 场景 | 操作 | 关键实测 |
| --- | --- | --- |
| J1 写持锁期间读 | 提交停在检查点 1（尚未发布文件）与检查点 4（快照已发布、事务未提交）时运行 `list-tree` / `verify` / `list-history` | 三个读命令都成功、未超时、远低于 30 s 上限；`list-tree` 与写之前逐字段一致、历史节点数未推进——读到的是一致快照，而非写入中间态 |
| J2 并发读 | 4 个只读命令同时运行 | 全部成功、互不阻塞；读后树不变、仓库仍健康 |
| J3 整仓灾备持锁期间读 | 灾备停在「正在复制仓库文件」阶段，期间运行三个只读命令 | 三个都成功、未超时；历史节点数未推进（灾备不改源仓库）；灾备产物可独立 `verify` + `scrub` |
| J4 精简持锁期间读 | 逐个检查点（6 个）停住精简，每个检查点上运行三个只读命令 | 检查点都被命中、读命令全部成功；`list-tree` 与精简前**逐字段一致**；取消后旧链完好、最早节点仍逐字节可恢复 |
| J5 精简 + 全库校验真并发 | 不设闸门，`compact` 与 `scrub` 同时启动、各自跑完，连跑 4 轮 | 两者都不挂起；精简 4/4 成功；结束后仓库完整、每个仍存在的节点逐位可恢复；写者持哨兵时全库校验以「仓库正在被写入，请稍后重试」**明确拒绝** |
| J6 全库校验 vs 写哨兵 | 闸门把写进程停在检查点（确实持有哨兵），此时运行 `scrub` 与 `verify` | `scrub` 立刻以退出码 1 拒绝且理由明确；同一时刻 `verify` 照常作答；写者结束后同一条 `scrub` 覆盖全部节点并通过 |

说明：**跨进程**只读命令不取哨兵锁（锁只对会写仓库的命令生效），因此不会被写进程挡住。
「GUI 与无头同时写同一仓库」目前不受保护，见「边界」。

### 输入域（K 组）

覆盖**字符域**与**路径域**——长度按字节计数、把用户可见的标题当文件名用、非 ASCII 路径在
命令行参数与文件系统之间转换时被替换或截断，都是 Windows 桌面应用最经典的崩溃与数据错乱来源。

| 场景 | 输入 | 关键实测 |
| --- | --- | --- |
| K1 字符域往返 | 15 个标题：中文、emoji、ZWJ 家庭序列、非 BMP 数学/花体字母、RTL 阿拉伯文、组合附加符号、零宽空格、内部换行 / 制表符、`slash/back\slash`、`colon:star*question?`、尾随空格 | 全部逐字符往返；带路径分隔符的标题成功创建，证明**标题不会被当成文件名**；非 ASCII 子串搜索命中；emoji 标题的作品两次提交后恢复旧版本逐字节一致 |
| K2 长度按字符计数 | 160 / 161 个 emoji（4 字节/字符）、160 / 161 个 CJK（3 字节/字符）、首尾带空格的 160 emoji | 160 个都接受并往返；161 个都拒绝且错误提到 160；首尾空白先裁掉再计数 |
| K3 空白与不可见字符 | 纯空白串、NBSP、U+2028/U+2029、NEL、零宽空格 / 零宽连接符 / BOM | 只含空白的全部拒绝并带说明；三个不属于 `White_Space` 的零宽字符被接受并逐字符往返（见「边界」） |
| K4 路径域 | 工作区内的 `含空格 与中文 的目录/nested/deeper/最深层 🎨/作品 草案 🎨 v2.bin` | 建库 → 两次提交 → 恢复，产物逐字节一致；仓库 `verify` + `scrub` 通过、无残留 |
| K5 路径边界 | 相对路径、工作区之外的绝对路径、工作区内但不存在的文件 | 三者都被明确拒绝：「必须使用绝对路径」「必须位于 `--workspace` 之内」「不存在」；被拒绝的创建不会凭空造出源文件 |

### 损坏检测与修复（R 组）

磁盘位损坏、外部工具误写或中断的复制，都会让仓库内文件与数据库记录的摘要不再一致。R 组验证
三件事：内容级校验必须报错、数据库级校验不受影响、损坏能被修复或干净拒绝。

| 场景 | 操作 | 关键实测 |
| --- | --- | --- |
| R1 最新快照被改坏 | 翻转 head 快照最后一个字节 | 全库校验失败并报「块哈希不匹配」；数据库级校验（不读文件内容）仍通过；恢复该节点被拒绝且无输出；一次内容未变化的提交把快照修好，随后恢复逐字节一致 |
| R2 增量被改坏 | 把边增量写成非法内容 | 全库校验失败并报「无法读取恢复链 delta」；数据库级校验仍通过；head 自身持有快照、不依赖该增量，恢复仍成功且逐字节一致 |
| R3 主库头部被误写 | 覆盖文件头 16 字节（SQLite 魔数区），长度不变 | `verify` 与 `scrub` 都失败：退出码 1、错误指向「作品数据库」、无 panic、无残留临时文件 |
| R4 主库被清空 | 把主库截为 0 字节 | `verify` 失败并提示「缺少数据库 / 请从备份恢复」；**关键边界**：失败的打开不会把空文件重建为全新空仓库，因此不会静默丢弃历史 |
| R5 随机化单点损坏 | 3 个受管理文件 × 4 个变体 = 12 次单点改写（偏移与掩码由种子决定，覆盖首/中/尾） | 每一次都被全库校验发现、退出码 1、无 panic；复原后校验通过、最早版本逐字节恢复 |
| R6 画板 DDS 损坏 | 3 张导入图片；6 类结构性损坏 + 1 类只改负载 + 24 次随机改写 | 6 类结构性损坏都精确报为 `corrupt`；只改负载**不会**被报为损坏（见「边界」）；24 次随机改写后扫描全部成功返回报告、计数不超过图片总数 |

注意：「仓库能打开」只代表数据库层完好，不代表文件内容完好；内容是否损坏由全库校验负责，
两者分工明确、互不替代。主库不可用时两层校验同时失败，与 R1/R2 的情形（文件内容坏、库仍可
打开）正好互补。

### 畸形输入模糊（解析器）

仓库里的容器、画板 DDS、认证清单与设置文件都是「读取不受信任字节」的解析器。模糊测试用
确定性伪随机源生成结构感知的畸形输入——位翻转、字节替换、插入、删除、清零、段落互换、
整块覆写、续写——并对每个解析器扫固定种子。

| 解析器 | 输入构造 | 断言 | 结果 |
| --- | --- | --- | --- |
| 快照容器 | 384 组：纯随机字节 / 结构未知扰动 / 只扰动头部 | 绝不 panic；`Ok` 时块数量不超过文件容量且必须能物化、产物长度等于声明值；截断与续写必须被拒绝 | 通过 |
| 增量容器 | 384 组：随机字节 / 随机扰动 | 绝不 panic；截断与续写必须被拒绝 | 通过 |
| DDS 头 | 384 组：随机字节 / 只扰动 148 字节 DX10 头 / 整文件扰动 | 绝不 panic；被接受的尺寸必须在声明上限内（长边 ≤ 16384、像素 ≤ 2.68 亿）；负载长度必须覆盖声明尺寸 | 通过 |
| C2PA 清单 | 96 组：随机字节 / 带 JPEG 或 PNG 魔数前缀 + 随机尾巴 | 绝不 panic（第三方解析器的 panic 会被捕获并把种子写进失败消息） | 通过 |
| 设置文件 | 80 组：随机字节 + 结构性畸形 JSON | 绝不 panic；版本为当前版本时返回的设置必须通过校验（修正在内存里、不整份清空）；**解析失败的文件必须被原样保留** | 通过 |

零新依赖（生成器是自写的确定性伪随机源），随单元测试进 Windows CI 自动运行。

### 性能基准（P 组）

性能断言此前只有「上界」（峰值内存 ≤ 逻辑大小的 1/8 等），没有基线。P 组记录六项核心算法的
单位耗时，并提供可选的严格比对（超过基线的设定倍数即失败）。下列数字为 debug 构建、单线程
运行实测；绝对值依赖机器与构建档，回归看的是同档位下的相对变化。

| 场景 | 规模 | 关键实测 |
| --- | --- | --- |
| P1 节点链 | 96 KiB 文件、48 节点 | 单次提交摊薄 **58.5 ms**；恢复最早节点（穿 47 步反向增量）**74.3 ms**，即 **1.6 ms/步**；恢复 head **38.6 ms**；恢复内容逐字节一致 |
| P2 认证 | 512×512 源图 | 发布整体 **747 ms**（渲染 450 / 编码 120 / 签名 12）；回读 **324 ms** |
| P3 画板 DDS | 16 张 512×512 PNG | 导入 **373 ms**（**23.3 ms/张**，含 BC7 编码）；DDS 完整性扫描 **414 ms**（25.9 ms/张） |
| P4 库树与搜索 | 5 个分组 + 100 个作品 | 整树装配 **36.9 ms**；命中全部的查询 **33.1 ms**、只命中一个的查询 **32.2 ms**（三次取最小） |
| P5 整仓灾备 | 仓库 3.25 MiB | 扫描 + 复制 + 校验 + 发布合计 **335 ms**，约 **9.6 MiB/s**；副本独立 `verify` 通过 |
| P6 清理扫描 | 仓库 2.59 MiB | 未引用文件扫描 **32.8 ms**、待清理队列重放 **32.0 ms**（三次取最小） |

说明：基准走真实可执行文件，耗时含进程启动与打开仓库的固定开销。P4–P6 各测 3 轮取最小值，
削弱调度抖动；每次重复都断言结果正确。**默认只记录、不设硬断言**（只有数量级护栏），真正的
回归门是严格模式 + 基线文件。GPU 侧的纹理上传/绘制不在无头入口的覆盖范围内，本组不涉及。

### 运行成本

C 组的墙钟时间（指向 release 构建、16 逻辑核）实测如下：

| 档位 | 逻辑大小 | 预计峰值磁盘 | 用途 | 实测结果 | 墙钟 |
| --- | --- | --- | --- | --- | --- |
| `default` | 64 MiB | ≈ 0.2 GiB | 日常典型体积 | 7/7 通过 | 29.5 s |
| `large` | 256 MiB | ≈ 1 GiB | 跨过明显的块级规模 | 7/7 通过 | 161.3 s |
| `heavy` | 1 GiB | ≈ 3 GiB | PSD 常见超限体积 | 7/7 通过 | 492.0 s |
| `extreme` | 4 GiB | ≈ 13 GiB | PSD 常态上限 | 7/7 通过 | 2288.3 s |
| `manual` | 8 GiB | ≈ 25 GiB | 4 GiB 现实上限的两倍冗余，需 ≥ 32 GiB 空闲 | 7/7 通过 | 7317.5 s |

C 组五档合计约 172 分钟；不含 `manual` 的四档约 50 分钟；整轮全套约 3 小时。高档位耗时的大头
是**全库校验**（`scrub`）：它要为每个历史节点从最近的快照重放整条链，再把整份内容流式复算一遍
块摘要，代价与「历史节点数 × 文件大小」成正比——`manual` 档 C1 的单次 `scrub` 就要 673.7 s。
这也是应用把「空闲期的 head 快照校验」与「全库扫描」分成两条路径的原因。

**磁盘预算**：场景按「预计峰值磁盘」准入，默认上限 24 GiB；跑 `manual` 档必须把
`LILITH_STRESS_DISK_BUDGET` 调到 40 GiB（C6 大改动场景的预计峰值约 32.2 GiB），否则整组会被
记为跳过而不是失败。

## 边界

明确**不做**自动化、或当前还不具备条件的部分：

| 项目 | 原因 |
| --- | --- |
| 画板 DDS 扫描只检查结构、不检查像素内容 | 写进 DDS 的记录只有尺寸与路径，没有内容摘要；扫描校验的是魔数 / DX10 / BC7 格式 / 尺寸 / 负载长度 / BC7 可解码，因此**只改负载字节不会被发现**。没有原始素材时像素语义本来就不可判定，这是当前的取舍而不是缺陷；要真正覆盖内容，需要给 DDS 记一份摘要 |
| 只由零宽字符组成的标题会被接受 | 标题的非空判定走 Unicode `White_Space`，而零宽空格、零宽连接符与字节序标记都不属于 `White_Space`，因此「看得见是空、实际非空」的标题是合法的。不影响数据安全，但属于可改进点 |
| 断电持久性（已提交的数据在断电后是否仍在） | 结束进程不触及操作系统与磁盘的缓存、也不保证目录项落盘，结构上无法覆盖。该项由操作系统、磁盘与数据库的 `synchronous = FULL` 声明保证 |
| 界面视觉、交互手感、桌面集成（拖放、托盘、快捷键等） | 自动化不驱动界面；由人工验收清单覆盖 |
| 崩溃残留文件的**自动**回收 | 孤儿不会被自动回收；可被扫描发现并经用户确认后清理（B5、H2 已覆盖闭环）。「自动」回收是产品设计取舍，不是测试断言 |
| 「无头 + 无头」以外的多进程组合（如 GUI 与无头同时写同一仓库） | 哨兵锁只覆盖无头入口；GUI 侧仍依赖单实例插件。GUI 与无头并存的组合不受保护，是已知边界 |
| 性能绝对值的**跨机器**自动比对 | 基准与构建档、机器绑定；默认只记录、不设硬断言，严格比对需按机器放宽因子 |
| 异常 RFC 3161 时间戳服务的失败与超时 | 保留人工验收 |

## 自行运行

八组轻量分组（cancel / crash / cleanup / damage / pin_board / authenticity / concurrency /
input，合计约 30 秒）已进 Windows CI，随每次提交自动运行；其余分组（`stress_large` /
`stress_scale` / `stress_bench`）只在发布前手动运行。`stress_baseline` 是 0.3 阶段 0 的
一次性基线采集，需要维护者临时准备的仓库副本，不属于发布流程，也不作为长期测试标准。

```text
# 构建无界面入口（不进发布产物）
cd src-tauri
cargo build --release --features headless

# 轻量分组（通常无需本地重复运行）
cargo test --features headless --test stress_cancel --test stress_crash

# 昂贵分组：指向 release 构建才有参考价值
LILITH_STRESS_BIN=target/release/lilith-artworks.exe \
  cargo test --features headless --test stress_large

# 档位与磁盘预算（跑 manual 档必须调高预算）
LILITH_STRESS_TIERS=extreme LILITH_STRESS_DISK_BUDGET=40GiB \
  LILITH_STRESS_BIN=target/release/lilith-artworks.exe \
  cargo test --features headless --test stress_large

# 16K 认证大图（extreme 档以上）
LILITH_STRESS_TIERS=extreme LILITH_STRESS_BIN=target/release/lilith-artworks.exe \
  cargo test --features headless --test stress_authenticity

# 规模组与性能基准
cargo test --features headless --test stress_scale
LILITH_STRESS_BIN=target/release/lilith-artworks.exe \
  cargo test --features headless --test stress_bench -- --nocapture --test-threads=1
```

可调环境变量：

| 变量 | 作用 |
| --- | --- |
| `LILITH_STRESS_TIERS` | 大文件档位：`default`（64 MiB）/ `large`（256 MiB）/ `heavy`（1 GiB）/ `extreme`（4 GiB）/ `manual`（8 GiB），默认 `default` |
| `LILITH_STRESS_BIN` | 被测可执行文件，建议指向 release 构建 |
| `LILITH_STRESS_DISK_BUDGET` | 磁盘峰值上限（默认 24 GiB）；跑 `manual` 档需设为 `40GiB` |
| `LILITH_STRESS_JOBS` | 并发场景数上限（默认可用核数） |
| `LILITH_STRESS_PERF_UPDATE=1` | 把性能基准测量写入基线文件 `src-tauri/tests/perf-baseline.json` |
| `LILITH_STRESS_PERF_STRICT=1` | 与基线比对，超过倍数阈值（默认 2.5×）即失败 |

结果写入 `target/stress-report.jsonl`（每场景一行 JSON）与 `target/stress-ledger.jsonl`
（磁盘账本）；临时工作区位于 `target/stress-workspaces/`，正常结束后自动回收。
