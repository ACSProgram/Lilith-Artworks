## 测试方式

理解三点，就能正确理解后文的「保证」边界：

- **被测对象是真实程序**，以「无界面模式」作为独立进程启动。测试进程只通过命令行、标准输入与
  文件与它交互，不读取任何内部状态——测的是真实的启动、恢复与落盘路径。
- **干预手段只有三种**，全部来自进程外部：① 在每个「可以取消的位置」通过标准输入下发取消/继续；
  ② 直接强杀进程（等价于任务管理器结束进程，不运行任何清理）；③ 阶段标记文件。
- **断言只用两类事实**：磁盘事实（文件是否存在、大小、两个文件是否逐字节相同）与命令返回的
  JSON。没有「重开不报错就算过」这类弱断言。

所有测试都在临时工作区里完成，不读取也不修改真实仓库；工作区随场景结束自动回收。

无界面入口只存在于开发测试构建，**正式发布版没有它**。全套测试中为了测试而触及产品代码的只有
三类：提交与认证流水线上的若干**观察标记点**（feature 门控，发布产物中不存在），一次纯重构
（把「写快照」抽成函数，让磁盘写满注入走真实代码路径），以及同样 feature 门控的无头选项
`--chunk-format v1|v2`（进程级覆盖「新节点写 v2」的设置项，用于在同一仓库里构造 v1/v2 混存
历史）。三者都不改变发布版的界面与业务行为。

## 结论：验证了什么

1. **强制结束进程不会损坏数据。** 在提交、恢复、整仓备份的任意阶段把进程杀掉，仓库都能重新
   打开，并通过完整性与逐块摘要校验；没做完的动作被丢弃，不会出现「写了一半的成品」——包括
   杀在数据库事务内部（已写入、未提交）时，未提交的写入被整体丢弃。
2. **取消是干净的。** 每个长操作在任意阶段取消，都不留残留文件、不推进历史，并且可以立刻重试成功。
3. **大文件可用（0.2.0 已实测到 8 GiB）。** 64 MiB、256 MiB、1 GiB、4 GiB、8 GiB 五档的
   提交 → 有界改动 → 恢复 → 逐字节一致在 0.2.0 全部通过；alpha1 的存储类断言曾按 v1 口径
   失败（快照体积与磁盘账本），已按 v2 的去重/压缩语义纠正断言，2026-10-19 用 release 构建
   重采四档（64 MiB–4 GiB）并通过，恢复正确性在每轮都成立（C7 全程通过）。8 GiB 的 `manual`
   档按维护者口径只在正式发布前跑。
4. **内存占用有界。** 处理 4 GiB 文件约用 351 MB 内存、8 GiB 文件约用 647 MB 内存（0.2.0
   实测），都不随文件大小线性增长（C3 在 alpha1 的四个档位都通过）；存储放大跟随**新增的不同
   内容**而不是文件大小（C1/C4 的账本断言已按 v2 口径纠正，四档全部通过）。
5. **规模和异常输入下行为正确。** 300 次提交的长历史、约 20 条分支、400 个作品的库、整仓
   备份、8 类越界输入，计数、搜索、移动、删除、恢复都正确；崩溃留下的孤儿文件可被扫描发现、
   经确认后清理。
6. **画板图片与笔迹的完整性可查。** 导入图片后，能区分「正常 / 缺失 / 损坏 / 孤儿」四类并如实计数
   （缺失与损坏只报告、不失败）；孤儿图片走同一条「扫描发现 + 用户确认清理」的闭环。笔迹几何的
   畸形 BLOB 在写入入口被逐类拒绝、批量写入要么整批成功要么整批回滚（H4/H5，2026-10-21 实测）。
7. **认证发布可用、可取消、可回读。** 在 16384×16384 像素（约 2.68 亿像素）的大图上，解码、
   加水印、签名的内存不超出预算；三个阶段任意取消都不留半成品；发布成品能读回证书信息。
8. **损坏的文件会被发现，并被干净拒绝。** 仓库里的快照/增量被改坏后，全库校验会报错、恢复会
   拒绝；提交路径不再顺带复检或修复旧快照（2026-10-20 移除），修复只能靠恢复较早的节点或整仓
   备份。
9. **同一仓库不会被两个进程同时写入。** 会写仓库的无头命令独占一个跨进程哨兵锁，第二个写
   进程拿到的是明确拒绝，而不是与前者在业务层竞态；锁由操作系统在句柄关闭时释放，因此被
   强杀的写进程不会把仓库锁死，随后的写进程仍能取得锁并提交成功。
10. **磁盘写满时是干净失败。** 在真实的快照写入路径上注入「写到这里就没空间」，产品返回
    清晰的「空间不足」错误、不推进历史、不留半成品、可重试；写到一半的字节不会被误当成
    完整快照。
11. **大文件在提交中途被取消或被强杀也是干净的。** 在五个档位（64 MiB–8 GiB）的工作文件上，
    每个取消检查点各取消一次、再强杀一次，都无残留、历史不推进、可重试；强杀后 head 仍能
    恢复出与工作文件逐字节一致的内容。
12. **主库文件本身被改坏时会干净失败。** 把 `lilith-artworks.sqlite3` 的头部改写成非数据库
    内容或清空，两层校验都给出可行动的错误（退出码 1、指向作品数据库、无 panic），并且失败的
    打开不会把空文件重建为一个全新的空仓库——那会静默丢弃用户历史。
13. **长写任务持锁期间只读命令仍能作答。** 写进程持锁时，`list-tree` / `verify` / `list-history`
    照常返回并看到写之前的**一致**状态（含「快照已发布、数据库事务尚未提交」这个最易撕裂的
    窗口）；多个只读命令并发互不阻塞。
14. **核心算法有可比的性能基线。** 节点链提交/恢复、认证发布与回读、画板 DDS 导入与扫描、库树与
    搜索、整仓灾备、清理扫描、调度候选扫描、孤儿清理与笔迹批量读写的单位耗时被记录，并可经严格
    模式与基线比对，超阈值的性能退化会被发现。
15. **非 ASCII 与特殊字符标题逐字符往返。** 中文、emoji、ZWJ 家庭序列、非 BMP 数学/花体字母、
    RTL 阿拉伯文、组合附加符号、零宽字符、内部换行与制表符、以及标题里带 `/`、`\`、`:`、`*`、`?`
    都能写入并原样读回——这同时证明**标题不会被当成文件名**（否则这些字符在 Windows 上会直接失败）。
16. **标题长度按字符而不是按字节计数。** 160 个 emoji（640 字节）与 160 个 CJK（480 字节）都被
    接受并逐字符往返，161 个被拒绝；首尾空白先裁掉再计数。
17. **不受信任的字节换不来崩溃或资源耗尽。** 四个解析器（快照/增量容器、DDS 头、C2PA 清单、
    设置文件）各自喂进数百组确定性畸形输入：一律干净拒绝或正确接受，没有 panic、越界或无界分配；
    被接受的容器必须自洽，被接受的 DDS 尺寸必须落在声明上限内，解析失败的设置文件必须被
    原样保留。随机化单点损坏与画板 DDS 结构性损坏在真实磁盘路径上同样被检测到或如实报告。
18. **多操作交错不会损坏仓库。** 提交、整仓灾备、精简三类写任务持锁期间，只读命令都照常作答并看到
    一致状态；真正并发的「精简 + 全库校验」连跑 4 轮，仓库仍完整、每个节点仍逐位恢复；写者持
    哨兵期间全库校验给出**明确拒绝**（「仓库正在被另一个进程写入；不支持同一仓库的多进程写入」
    ——全库校验自 2026-10-19 起按前台写命令取 owner lock，不再走只探测哨兵的只读路径）。
19. **`.clip` 的容器感知分块与 v1/v2 混存仓库在真实链路上成立。** 合成 CSFC 容器提交后，磁盘上的
    快照与增量公共头确实是 v2 / CLIP 分块 / CLIP 适配器；tile 结构、无 tile 记录与截断回退 CDC
    三种形态都逐字节恢复；v1 与 v2 节点可以在同一仓库里并存，跨格式链全部可恢复，检查点把含 v1
    增量的链物化为 v2 快照（M1–M4，全部通过）。

**产品侧修复：检查点分层。** 无头入口此前把取消来源直接接成闸门检查点，而分块主循环每块
查询一次取消，于是「每条边界一次检查点」变成「每块一次检查点」。现在取消观察分两层：
`CancelToken::is_cancelled` 是**交互检查点**，只在显式边界调用，仍写一行 marker、并在
`--cancel-on-stdin` 下阻塞等判定；`CancelToken::observed` 是**静默观察**，供热循环使用，只读
「取消是否已被判定」。边界判定的取消仍会被热循环在下一次静默查询时立刻看到，因此取消延迟不
回退；GUI 的取消来源本来就是廉价读取，两层共用同一个闭包、行为不变。发布产物不含无头入口，
GUI 路径行为逐位不变。

**复验结果。** `stress_cancel`（A1–A6，含逐个检查点的取消延迟与残留断言）、`stress_crash`
（B1–B4）、`stress_cleanup`（B5）、`stress_authenticity`（G4/G5）、`stress_large` 的
`default` 档（C1–C8）全部通过；A1/A3/A6/C7 这些此前「通过但覆盖位置已漂移」的用例，序号
也重新对应它们注释里声称的取消位置。修复批次与逐条证据见
`docs/planning/archive/alpha1-stress-failure-fix-plan-2026-10-18.md`。

## 保证一览

| 情形 | 已有的保证 | 覆盖来源 |
| --- | --- | --- |
| 提交历史的过程中强制结束进程（任务管理器结束、崩溃） | 仓库自洽：重新打开通过完整性、外键与全表语义校验，历史不前进，随后提交正常。**已发布但未被引用的文件会成为孤儿留在磁盘上，当前不会自动回收**（见「边界」） | B1 |
| 提交**写到一半**（数据库事务已开始、尚未提交）时进程被杀 | 未提交的写入被整体丢弃：历史与节点数不前进、上一版快照仍被引用、清理队列没有多出条目；重开校验全过、随后提交正常 | B4 |
| 恢复某个历史节点时进程被杀 | 目标输出文件**不存在**；不会出现「半写文件被当成产物」；重新恢复得到与原文件逐字节相同的字节 | B2 |
| 整仓备份复制途中进程被杀 | 源仓库不受任何影响、可独立校验；目标目录只留下**可识别**的未发布暂存目录，不会被误认为备份；重跑成功 | B3 |
| 长操作中途取消（提交、恢复、精简、检查点、整仓备份、全库扫描） | 无残留实体与临时文件、历史图不变、待清理队列为空，并且可以立刻重试成功 | A1–A6（28 次受控取消） |
| 巨大的工作文件（PSD 等） | 64 MiB / 256 MiB / 1 GiB / 4 GiB / 8 GiB 五档：提交 → 有界改动 → 恢复最早与最新的节点，产物都与当时的内容**逐字节一致**；精简之后仍然如此 | C1、C2、C6 |
| 磁盘会不会被撑爆 | 每次提交新增的占用跟随**新增的不同内容**，重复内容只写引用（v2 去重 + zstd）；因此仓库常驻大小不大于「一个快照 + 所有增量」，可压缩或稀疏的内容还会更小 | C1、C4 |
| 打开大文件时内存会不会爆 | 处理 4 GiB 文件的提交峰值约 364 MB、恢复峰值约 359 MB；8 GiB 档分别为约 660 MB / 655 MB（基线约 12.5 MB），即**流式实现**，不把整个文件读进内存 | C3 |
| 恢复输出会不会留下垃圾 | 恢复产物是全尺寸的临时产物，每个场景结束时断言输出目录已清空、工作区占用回落 | C5 |

## 实测数据

**口径**：本节各表都标明了采集批次；没有特别标注的细分表格是 2026-10-17 的 **0.2.0** 实测。

**墙钟不能当性能标准**：`stress_large` 的场景按预计峰值磁盘并发准入，`cargo test` 又默认并行
跑测试函数，所以一台机器上同时有多个被测进程在跑；而被测进程本身是单线程的（内容定义分块、
SHA-256 与 zstd 都是单核路径）。于是「整机 CPU 占用」随同时运行多少个场景而变，「单次操作墙钟」
被调度与争用拉长，两者都不能跨轮比较。2026-10-18 的复跑给了直接证据：同一组基准在 9 个测试
并行时 P1 单次提交摊薄 121.6 ms、P3 导入 1450.7 ms，改成 `--test-threads=1` 后分别是 53.7 ms
与 353.0 ms（2.3–4.1 倍差）。

因此本报告对性能的口径是：

- 只引用**单线程采集**的数字，即 `stress_bench` 带 `--test-threads=1`；且只在同一机器、同一
  构建档内比较。
- 跨版本谈「变快/变慢」时不引用群跑墙钟。同一轮另记的**进程 CPU 时间**（用户 + 内核）不含
  进程被剥夺的时间，用来回答「是不是更费算力」；它看不见磁盘等待，不能替代墙钟。
- 大文件档的墙钟只用于估算「这一轮要占多久机器」，不作为性能证据。

| --- | --- | --- |
| C7a 逐检查点取消 | 在提交的 5 个取消检查点各取消一次 | 每次都以取消退出、无残留、待清理队列为空、历史不推进、仓库可重开；随后同一命令重试成功且只前进一格 |

B 组：5 次强杀，强杀点由「逐可取消位置闸门」确定命中（进程在目标位置阻塞，测试随即强杀）。

| 场景 | 强杀点 | 强杀阶段 | 耗时 |
| --- | --- | --- | --- |
| B1 提交中途强杀 | 4 | 快照/增量已发布、数据库未提交 | 44 ms |
| B2 恢复中途强杀（导出前） | 5 | 链解析完成后 | 56 ms |
| B2 恢复中途强杀（导出后） | 6 | 导出并同步后、发布前 | 62 ms |
| B3 整仓备份中途强杀 | 2 | 复制仓库文件 | 32 ms |
| B4 提交事务中途强杀 | 5 | 事务已写入、尚未提交 | 53 ms |

强杀后的实测结论：`verify`（迁移 + 完整性 + 外键 + 全表语义校验）与 `scrub`（逐块摘要链）
全部通过。B1 恰好多出一枚完整的孤儿快照与一枚孤儿增量（清理队列为空，属已知缺口，见 B5）；
B2 目标输出不存在，只留下未发布的完整临时文件（仓库之外）；B3 源仓库可独立校验，暂存目录
可识别，重跑备份成功。B4 把强杀点推进到事务**内部**：强杀后历史与节点数不前进（未提交事务被
丢弃）、父节点的快照仍被引用、清理队列没有多出条目，随后同一命令重跑成功。

**崩溃孤儿回收闭环（B5）**：复用 B1 的强杀点造出孤儿快照与孤儿增量，把仓库内全部快照/增量的
修改时间回拨到 30 分钟宽限期之外，扫描**只**报告这两枚孤儿（被引用的文件即便同样「过期」也不
报告，证明引用复查生效）；确认清理删除孤儿、被引用文件保留，重开后 `verify` + `scrub` 通过。
孤儿不会被自动回收——「扫描报告 + 用户确认」两段式是设计而非缺陷。

### 并发与交错（I、J 组）

**多进程写入与高频命令（I 组）**：会写仓库的无头命令独占一个 SQLite 写锁（`BEGIN IMMEDIATE`），
第二个写进程被明确拒绝；锁由内核在句柄关闭时释放，因此强杀不残留锁。

| 场景 | 操作 | 结果 |
| --- | --- | --- |
| I1 并发写被拒 | 一个写进程停在检查点持锁，期间启动第二个写进程 | 第二个进程以明确错误退出（「不支持同一仓库的多进程写入」）、退出码 1；第一个进程随后正常提交；仓库自洽、无残留 |
| I2 强杀不残留锁 | 强杀持有锁的写进程 | 锁被操作系统释放；随后的写进程仍能取得锁并提交成功 |
| I3 高频连续命令 | 20 次连续提交（每次一个独立进程） | 历史节点 20、全库校验通过、无残留；同时验证锁在每次结束后都被正确释放 |

**多操作交错（J 组）**：「操作 A 进行到一半时操作 B 到来」的采样。

| 场景 | 操作 | 关键实测 |
| --- | --- | --- |
| J1 写持锁期间读 | 提交停在检查点 1（尚未发布文件）与检查点 4（快照已发布、事务未提交）时运行 `list-tree` / `verify` / `list-history` | 三个读命令都成功、未超时、远低于 30 s 上限；`list-tree` 与写之前逐字段一致、历史节点数未推进——读到的是一致快照，而非写入中间态 |
| J2 并发读 | 4 个只读命令同时运行 | 全部成功、互不阻塞；读后树不变、仓库仍健康 |
| J3 整仓灾备持锁期间读 | 灾备停在「正在复制仓库文件」阶段，期间运行三个只读命令 | 三个都成功、未超时；历史节点数未推进（灾备不改源仓库）；灾备产物可独立 `verify` + `scrub` |
| J4 精简持锁期间读 | 逐个检查点（6 个）停住精简，每个检查点上运行三个只读命令 | 检查点都被命中、读命令全部成功；`list-tree` 与精简前**逐字段一致**；取消后旧链完好、最早节点仍逐字节可恢复 |
| J5 精简 + 全库校验真并发 | 不设闸门，`compact` 与 `scrub` 同时启动、各自跑完，连跑 6 轮，逐轮记录两类拒绝 | 两者都不挂起；结束后仓库完整、每个仍存在的节点逐位可恢复；写者持哨兵时全库校验以「仓库正在被另一个进程写入；不支持同一仓库的多进程写入」**明确拒绝**。**精简也可能被拒绝**：全库校验现在同样按写命令取 owner lock，两个进程零等待互抢时后到者立即拿到明确拒绝（见「边界」），断言因此是「精简要么成功、要么拿到那条明确拒绝且随后重试成功」，重试在同一仓库上确定性通过。实测（全部 0 失败）：常规负载连跑 21 次 × 6 轮 = 126 轮，精简被拒绝 0 轮（重试分支未触发）、全库校验被拒绝 106 轮；放大并发（3 个同组实例并行）再跑 27 次 × 6 轮 = 162 轮，精简被拒绝 5 轮（重试后均成功）、全库校验被拒绝 98 轮，另有 3 轮全库校验以「找不到历史节点」**干净失败**（退出码 1、无 panic，见「边界」） |
| J6 全库校验 vs 写哨兵 | 闸门把写进程停在检查点（确实持有哨兵），此时运行 `scrub` 与 `verify` | `scrub` 立刻以退出码 1 拒绝且理由明确；同一时刻 `verify` 照常作答；写者结束后同一条 `scrub` 覆盖全部节点并通过 |

说明：**跨进程**只读命令不取哨兵锁（锁只对会写仓库的命令生效），因此不会被写进程挡住。
「GUI 与无头同时写同一仓库」目前不受保护，见「边界」。

### 损坏检测与修复（R 组）

磁盘位损坏、外部工具误写或中断的复制，都会让仓库内文件与数据库记录的摘要不再一致。R 组验证
三件事：内容级校验必须报错、数据库级校验不受影响、损坏被干净拒绝。R1 里「一次内容未变化的
提交把 head 快照修好」记录的是 2026-10-20 之前的行为——该自动修复（连同提交路径的整份复检）
已按 `../planning/archive/backup-scheduling-fix-plan-2026-10-20.md` §7 的 A7 移除，现行语义见
`../modules/history-and-backup.md`。

| 场景 | 操作 | 关键实测 |
| --- | --- | --- |
| R1 最新快照被改坏 | 翻转 head 快照最后一个字节 | 全库校验失败并报「块哈希不匹配」；数据库级校验（不读文件内容）仍通过；恢复该节点被拒绝且无输出。当时的实现还会由一次内容未变化的提交把快照修好、随后恢复逐字节一致；这条自动修复路径已于 2026-10-20 移除（见本节说明） |
| R2 增量被改坏 | 把边增量写成非法内容 | 全库校验失败并报「无法读取恢复链 delta」；数据库级校验仍通过；head 自身持有快照、不依赖该增量，恢复仍成功且逐字节一致 |
| R3 主库头部被误写 | 覆盖文件头 16 字节（SQLite 魔数区），长度不变 | `verify` 与 `scrub` 都失败：退出码 1、错误指向「作品数据库」、无 panic、无残留临时文件 |
| R4 主库被清空 | 把主库截为 0 字节 | `verify` 失败并提示「缺少数据库 / 请从备份恢复」；**关键边界**：失败的打开不会把空文件重建为全新空仓库，因此不会静默丢弃历史 |
| R5 随机化单点损坏 | 3 个受管理文件 × 4 个变体 = 12 次单点改写（偏移与掩码由种子决定，覆盖首/中/尾） | 每一次都被全库校验发现、退出码 1、无 panic；复原后校验通过、最早版本逐字节恢复 |
| R6 画板 DDS 损坏 | 3 张导入图片；6 类结构性损坏 + 1 类只改负载 + 24 次随机改写 | 6 类结构性损坏都精确报为 `corrupt`；只改负载**不会**被报为损坏（见「边界」）；24 次随机改写后扫描全部成功返回报告、计数不超过图片总数 |

注意：「仓库能打开」只代表数据库层完好，不代表文件内容完好；内容是否损坏由全库校验负责，
两者分工明确、互不替代。主库不可用时两层校验同时失败，与 R1/R2 的情形（文件内容坏、库仍可
打开）正好互补。

### 格式矩阵（M 组）

`cargo test --lib` 的单测覆盖格式层（头布局、摘要、容器解析、畸形拒绝、v1/v2 互读）；M 组补的是
**集成接缝**——在真实仓库里经无头二进制走「提交 → 增量 → 恢复 / 检查点 / 全库校验」，并用磁盘
事实（ChunkFile 公共头的版本 / chunker / adapter 字节，delta 先过 zstd 解压）逐提交核对，因此
「静默回退 CDC」或「格式标志被忽略」都会直接失败。夹具全部在运行时按确定性种子合成，**不提交
二进制样本**；真实 Clip Studio 输出的形态（块类型全集、异常组合）不由此组代表。

| 场景 | 装配 | 关键实测 |
| --- | --- | --- |
| M1 `.clip` tile 结构 | 6 个 8 KiB tile 的合成 CSFC；第二次提交只改第 3 个 tile | 快照与 delta 公共头都是 v2 / chunker = CLIP / adapter = CLIP；两个节点恢复逐字节一致；全链校验通过；29 ms、峰值 13.3 MiB |
| M2 无 tile 记录 | Exta 载荷头后直接是尾部（screencast 形态） | 整个 Exta 作单一结构单元，chunker = CLIP / adapter = CLIP；恢复逐字节一致；44 ms |
| M3 截断容器 | 删掉 `Foot` 块的合成 CSFC | 容器解析失败后回退 CDC（chunker = 0、adapter = 0、版本仍为 v2）；恢复逐字节一致；37 ms |
| M4 v1/v2 混存 | `--chunk-format v1` 两个节点 + 默认 v2 两个节点 | 仓库内并列存在 1 条 v1 delta 与 2 条 v2 delta；4 个节点全部逐字节恢复；对分支起点建检查点把跨格式链物化成 v2 快照；之后 4 个节点仍可恢复；29 ms |

四组合计约 1 秒（2026-10-18，release 构建）。断言只看公共头字节与恢复产物，不读日志，也不
假定内部实现；峰值内存约 13 MiB，与文件大小无关。

### 畸形输入模糊（解析器）

仓库里的容器、画板 DDS、认证清单与设置文件都是「读取不受信任字节」的解析器。模糊测试用
确定性伪随机源生成结构感知的畸形输入——位翻转、字节替换、插入、删除、清零、段落互换、
整块覆写、续写——并对每个解析器扫固定种子。

| 解析器 | 输入构造 | 断言 | 结果 |
| --- | --- | --- | --- |
| 快照容器 | 384 组：纯随机字节 / 结构未知扰动 / 只扰动头部 | 绝不 panic；`Ok` 时块数量不超过文件容量且必须能物化、产物长度等于声明值；截断与续写必须被拒绝 | 通过 |
| 增量容器 | 384 组：随机字节 / 随机扰动 | 绝不 panic；截断与续写必须被拒绝 | 通过 |
| DDS 头 | 384 组：随机字节 / 只扰动 148 字节 DX10 头 / 整文件扰动 | 绝不 panic；被接受的尺寸必须在声明上限内（长边 ≤ 16384、像素 ≤ 2.68 亿）；负载长度必须覆盖声明尺寸 | 通过 |
| C2PA 清单 | 96 组：随机字节 / 带 JPEG 或 PNG 魔数前缀 + 随机尾巴 | 绝不 panic（第三方解析器的 panic 会被捕获并把种子写进失败消息） | 通过 |
| 设置文件 | 80 组：随机字节 + 结构性畸形 JSON | 绝不 panic；版本为当前版本时返回的设置必须通过校验（修正在内存里、不整份清空）；**解析失败的文件必须被原样保留** | 通过 |

零新依赖（生成器是自写的确定性伪随机源），随单元测试进 Windows CI 自动运行。

## 边界

明确**不做**自动化、或当前还不具备条件的部分：

| 项目 | 原因 |
| --- | --- |
| 画板 DDS 扫描只检查结构、不检查像素内容 | 写进 DDS 的记录只有尺寸与路径，没有内容摘要；扫描校验的是魔数 / DX10 / BC7 格式 / 尺寸 / 负载长度 / BC7 可解码，因此**只改负载字节不会被发现**。没有原始素材时像素语义本来就不可判定，这是当前的取舍而不是缺陷；要真正覆盖内容，需要给 DDS 记一份摘要 |
| 只由零宽字符组成的标题会被接受 | 标题的非空判定走 Unicode `White_Space`，而零宽空格、零宽连接符与字节序标记都不属于 `White_Space`，因此「看得见是空、实际非空」的标题是合法的。不影响数据安全，但属于可改进点 |
| 断电持久性（已提交的数据在断电后是否仍在） | 结束进程不触及操作系统与磁盘的缓存、也不保证目录项落盘，结构上无法覆盖。该项由操作系统、磁盘与数据库的 `synchronous = FULL` 声明保证 |
| 界面视觉、交互手感、桌面集成（拖放、托盘、快捷键等） | 自动化不驱动界面；由人工验收清单覆盖 |
| 崩溃残留文件的**自动**回收 | 孤儿不会被自动回收；可被扫描发现并经用户确认后清理（B5、H2 已覆盖闭环）。「自动」回收是产品设计取舍，不是测试断言。强杀留下的未发布临时文件分两类：仓库根 `temp/` 下的 `.tmp*` 与预览会话目录由打开仓库时的清扫按 30 分钟宽限期直接回收（`cleanup.rs` 的 `sweep_repository_temp`）；作品 `temp/` 下的 `.tmp*`（快照 / 增量 / 检查点的 `NamedTempFile`，进程被杀时析构不运行）由未引用扫描报为候选、经用户确认后清理 |
| **小选区的像素域水印回读** | 选区任一边小于 256 px 时像素域回读不保证；更大的选区或更平滑的内容仍可能失败（回读率随边长与内容变化，实测表见「认证（G 组）」）。这是外部水印引擎的固有鲁棒性限制，不归本项目控制。**C2PA 声明与本地记录匹配始终不受影响**——它走 CBOR 文本串，不依赖像素域。发布时对任一边小于 256 px 的选区给出提示：框选处就地提示、发布结果区显示后端返回的警告，**提示不是错误，发布照常成功** |
| 全库校验的哨兵**探测**与并发写者互抢锁 | `repository_lock::probe` 用 `BEGIN IMMEDIATE` 判定「是否有写者」，零等待下它自身也会短暂持有写锁，因此与**同时启动**的写者取锁存在竞态：先到者成功，后到者拿到「仓库正在被另一个进程写入」。J5 的「精简必须成功」断言因此偶发失败（实测约 15%，与修复批次无关；同一份未改动的基线二进制同样 3/20）。处置已定：**改断言不改锁**（J5 已按「精简要么成功、要么拿到这条明确拒绝且随后重试成功」改写并复跑全绿），因此这条**产品侧的不对称仍存在**——同一仓库上「内容级只读扫描启动」与「写操作启动」撞在一起时，写操作可能拿到拒绝；要消除需让探测不动用写锁，属独立产品取舍，另行立项。探测是**一次性判定而不是锁**：若探测在写者取锁**之前**通过，写者随后照常写入，正在扫描的全库校验就可能以「找不到历史节点」这类普通错误**干净失败**（退出码 1、无 panic），而不是拿到那条明确拒绝——放大并发下实测 162 轮里出现 3 轮 |
| 「无头 + 无头」以外的多进程组合（如 GUI 与无头同时写同一仓库） | 哨兵锁只覆盖无头入口；GUI 侧仍依赖单实例插件。GUI 与无头并存的组合不受保护，是已知边界 |
| 性能绝对值的**跨机器**自动比对 | 基准与构建档、机器绑定；默认只记录、不设硬断言，严格比对需按机器放宽因子 |
| **分阶段** CPU 时间 | 性能基准只记录每次操作的整进程 CPU 时间；认证发布自报的渲染 / 编码 / 签名仍只有墙钟，要拆出各阶段的 CPU 成本需在产品侧加度量（本次未做） |
| 异常 RFC 3161 时间戳服务的失败与超时 | 保留人工验收 |

## 自行运行

九组轻量分组（cancel / crash / cleanup / damage / format / pin_board / authenticity /
concurrency / input，合计约 30 秒）已进 Windows CI，随每次提交自动运行；其余分组（`stress_large` /
`stress_scale` / `stress_bench`）只在发布前手动运行。`stress_baseline` 已于 2026-10-21 退役删除
（它是 0.3 阶段 0 的一次性采集，历史数值见 `docs/planning/0.3-baseline-2026-10-18.md`）。
本文 C 组的实测数字来自 2026-10-21 之前那几轮，之后新增的 C9（并行管道中间强杀）与 C10（4 MiB
管道边界）尚未实际运行，因此上表没有它们的行。

```text
# 构建无界面入口（不进发布产物）
cd src-tauri
cargo build --release --features headless

# 轻量分组（通常无需本地重复运行）
cargo test --features headless --test stress_cancel --test stress_crash

# 昂贵分组：指向 release 构建才有参考价值
LILITH_STRESS_BIN=target/release/lilith-artworks.exe \
  cargo test --features headless --test stress_large

# 档位与磁盘预算（跑 manual 档必须调高预算）
LILITH_STRESS_TIERS=extreme LILITH_STRESS_DISK_BUDGET=40GiB \
  LILITH_STRESS_BIN=target/release/lilith-artworks.exe \
  cargo test --features headless --test stress_large

# 16K 认证大图（extreme 档以上）
LILITH_STRESS_TIERS=extreme LILITH_STRESS_BIN=target/release/lilith-artworks.exe \
  cargo test --features headless --test stress_authenticity

# 规模组与性能基准
cargo test --features headless --test stress_scale
LILITH_STRESS_PROFILE=release LILITH_STRESS_BIN=target/release/lilith-artworks.exe \
  cargo test --features headless --test stress_bench -- --nocapture --test-threads=1
```

可调环境变量：

| 变量 | 作用 |
| --- | --- |
| `LILITH_STRESS_TIERS` | 大文件档位：`default`（64 MiB）/ `large`（256 MiB）/ `heavy`（1 GiB）/ `extreme`（4 GiB）/ `manual`（8 GiB），默认 `default` |
| `LILITH_STRESS_BIN` | 被测可执行文件，建议指向 release 构建 |
| `LILITH_STRESS_DISK_BUDGET` | 磁盘峰值上限（默认 24 GiB）；跑 `manual` 档需设为 `40GiB` |
| `LILITH_STRESS_JOBS` | 并发场景数上限（默认可用核数） |
| `LILITH_STRESS_PERF_UPDATE=1` | 把性能基准测量写入基线文件 `src-tauri/tests/perf-baseline.json` |
| `LILITH_STRESS_PROFILE` | 基线条目记到哪个构建档（`debug` / `release`）；用 debug 脚手架驱动 release 二进制时必须设 `release` |
| `LILITH_STRESS_PERF_STRICT=1` | 与基线比对，超过倍数阈值（默认 2.5×）即失败；墙钟与 CPU 时间都比，CPU 只在基线 ≥ 50 ms 时生效 |

结果写入 `<target>/stress/report.jsonl`（每场景一行 JSON）与 `<target>/stress/ledger.jsonl`
（磁盘账本）；临时工作区位于 `<target>/stress/workspaces/`，正常结束后自动回收。
