# 0.4 作品独立数据库、仓库升级、并发调度与识别页独立化（草案）

- 状态：**草案**。只记录目的、需求与大纲，细节后续完善，不作为实施依据
- 提出：2026-10-22，来自 `0.3-closeout-and-authenticity-refactor-plan-2026-10-22.md`
  §12 第 4 项（识别页的产品位置）与维护者同日追加的仓库升级要求
- 基线：`0.3.0-alpha.6`，repository schema v6，单一仓库数据库，打开旧仓库时静默迁移
- 归档口径：细化成正式计划前一直留在 `docs/planning/`，不进 `archive/`

## 1. 目的

1. **作品拆成独立数据库**。现在所有作品共用一个 SQLite 文件，写操作只能排队，多作品同时
   处理时彼此阻塞。改成每个作品一个库，不同作品的写入可以真正并行，单次操作的影响面也从
   「整个仓库」缩到「一个作品」。
2. **仓库升级规范化**。现在打开旧仓库会在后台静默迁移，用户既不知道发生了什么，也没有拒绝
   的机会；一旦升级，旧版软件就打不开这个仓库了。要把升级做成一件用户看得见、能选择、
   中途被打断也不会损坏原仓库的事。
3. **控制总线支持按作品并行**。现在所有命令过同一个写闸门，串行是唯一正确解；拆库之后这条
   前提消失，如果调度不跟着改，等于拆了库还在排队。要让不同作品的长任务真正并行，同时把
   并发数量管住——作品再多也只保持若干活跃长任务，而不是开一堆线程互相抢内存；用户正在看的
   那个作品始终优先。
4. **识别页独立出来**。识别是全局能力：验证一张别人发来的图片不属于任何作品。现在它挂在
   作品工作区里，必须先打开某个作品才能用。改造后它与作品库、历史、素材板并列，成为第四个
   独立入口，不再依赖「当前作品」这个上下文。

为什么放在一批：

- 拆库本身就是一次结构升级（单库 → 多库），必须走升级流程；先把升级框架做好，拆库就是它的
  第一个大用例，否则要先写一遍一次性迁移、等拆库时再推翻重写。
- 拆库把「串行」这个前提拿掉了，调度必须同批跟上，否则并行能力落不了地。
- 识别页现在挂在作品下，是因为它要读「当前分支的成品」；作品有独立库之后，「识别时用哪个库」
  必须先有答案。先迁页面再拆库会返工一次。

## 2. 现状与约束

- 打开旧仓库时 `library/schema.rs` 的迁移链在事务内静默执行（v1 → v2 → … → v6），没有界面、
  没有进度、没有用户确认；迁移不支持回退。
- 高于当前版本的仓库已有明确拒绝文案（「由更新版本创建，已拒绝打开以避免损坏仓库」）。
- 现有迁移用 `BEGIN IMMEDIATE` 事务保证单步原子，但**整个链不是原子的**：v1 → v6 分五步各自
  提交，中途被强杀会停在某个中间版本上。下次启动会从那个版本继续迁移，逻辑上能接上，但用户
  看到的是一个被改了一半的仓库。
- 仓库不只是一个数据库文件：同一目录下还有分块文件、成品与认证副本。升级只改数据库结构，
  但拆库会动整个数据布局。
- SQLite 单写者与跨进程 owner lock 是现有安全前提，升级期间必须继续持有独占锁。
- 所有命令经同一个协调器取锁：进程内写闸门按「退出 > 前台 > 交互 > 后台」排队，再加跨进程
  owner lock；只读命令只取共享 lease。所有作品共用一个库，所以「写操作串行」是唯一正确解。
- 真正执行跑在阻塞线程池上，**没有并发上限**。单个任务可能吃几百 MB 内存，作品多时同时开
  几个就是内存问题。
- 现有运行分类（只读 / 写 / 前台长命令 / 仓库写）是为**取锁**服务的，不是为**容量**服务的：
  它知道哪些是前台长命令，但没有「同时最多跑几个」这个概念。
- 自动备份与空闲校验已有让位机制（运行中检测 `should_yield` 主动退让）；调度改造必须接住
  它，不能另起一套。

## 3. 仓库升级功能

### 3.1 需求（用户可见行为）

- 打开仓库时先读版本，不匹配就进入升级流程：**主界面不挂载**，作品库、历史、素材板、发布
  与设置都不可用，窗口里只有升级页。
- 升级页说明：当前版本 → 目标版本、这次升级会做什么（哪几步、动哪些结构）、以及风险——
  **升级后旧版软件将无法再打开这个仓库**、大概要花多久、需要多少额外磁盘空间。
- 两个出口：
  - **升级**：进入进度界面；
  - **不升级**：不改动仓库一个字节，退出打开流程，并明确提示「请改用对应版本的软件打开」。
- 进度要真实：按迁移步骤上报（第几步 / 共几步 / 步骤名 / 已用时），不画假进度条。
- 升级失败或进程被杀：原仓库仍然能用旧版软件正常打开，残留的临时数据在下次启动时清理。
- 版本比当前软件**更高**时不走升级流程，直接给「请升级软件」的提示——那不是能靠升级仓库
  解决的事。

### 3.2 安全模型（中断不损坏原仓库）

- **绝不就地修改原库**。先复制一份原库作回滚副本（带时间戳命名），再复制一份到仓库内的临时
  目录（沿用拖放暂存的 UUID 命名习惯），迁移只在临时副本上跑。
- 副本迁移完成后先校验（完整校验、外键、版本号、关键表存在性），通过才替换。
- 替换必须是**一次原子覆盖**：临时副本 → 正式库文件，Windows 上要用 `ReplaceFile` /
  `MoveFileEx(REPLACE_EXISTING)` 语义，`std::fs::rename` 在目标已存在时会失败。这样任何时刻
  正式库都存在且完整（要么旧的、要么新的），不存在「改到一半没有库文件」的窗口。
- 不要把「原库改名 → 副本改名」当替换手段：两步之间被打断会让仓库暂时没有正式库，旧版软件
  打开时虽然不会新建空库，但会报「找不到数据库」，看起来像仓库坏了。
- 成功替换后才删除回滚副本。中途被打断时正式库仍是旧库，下次启动只需删掉临时残留并报告
  「上次升级未完成」，**不依赖状态标记来恢复数据**。
- 状态标记仍然要有，但它只承担两件事：清理残留、把「上次升级失败」告诉用户。即使标记本身
  丢失，仓库也不会因此损坏。
- 开始前做磁盘空间预检：需要约两倍数据库大小的额外空间（回滚副本 + 迁移副本），不足就拒绝
  开始并说明差多少，而不是中途失败。
- 升级全程持仓库独占锁，禁止第二个进程同时升级。

### 3.3 大纲（待细化）

1. **版本探测与启动路由**：新增应用级状态——正常 / 需要升级 / 升级中 / 升级失败 / 版本过新，
   前端启动流程据此决定挂主界面还是升级页。
2. **升级页界面契约**：信息项、两个按钮、进度来源、失败态与重试、关闭窗口的行为。
3. **迁移执行器改造**：把现在静默执行的迁移链改成可步进、可观测、可中断的执行器，每步上报
   开始与结束；现有「每步各自提交」的语义要么收敛成一次事务，要么显式接受「停在中间版本」
   并由状态标记覆盖它。
4. **副本与原子替换**：回滚副本与迁移副本的命名与位置、校验清单、原子覆盖的实现（Windows 上
   的 API 选择与失败重试）、回滚副本的保留与清理时机。
5. **中断恢复**：启动时检测临时残留与状态标记 → 清理、报告、把「上次升级未完成」呈现给用户；
   由于正式库始终完整，恢复路径里没有「修补数据」这一步。
6. **磁盘空间预检与错误文案**：预检口径（数据库大小 + 余量）、不足时的提示。
7. **旧版兼容口径**：升级后写新版本号，旧版软件按现有「拒绝打开更高版本」逻辑处理；升级页
   必须提前把这条讲清楚。
8. **与拆库的衔接**：拆库（单库 → 多库）作为升级框架的第一个大用例接入，进度按作品或按阶段
   上报；升级前的仓库结构探测要能同时识别「单库旧版本」与「单库当前版本」。
9. **验证**：枚举强杀点（复制中、迁移中、替换前、替换后），逐个给出期望结果；沿用现有压力
   测试范式，只在发布前跑。
10. **文档同步**：`docs/guides/release-policy.md` 现在写的是「打开旧版本仓库时按迁移链自动
    升级」，要改成显式升级流程；`docs/modules/library.md` 的打开流程与
    `docs/architecture/overview.md` 的启动生命周期同步补上「需要升级」这个应用级状态。

## 4. 控制总线与任务调度

### 4.1 需求

1. **以作品为单位并行**：不同作品的写互不阻塞；同一作品仍然单写者。
2. **长任务有活跃上限**：作品再多也只保持若干活跃长任务，其余排队，内存峰值不随作品数上涨。
3. **分配要公平**：不能一个作品的大任务长期占住配额，也不能让小任务饿死。公平只在后台作品
   之间成立——用户正在看的那个作品按 §5 优先。
4. **微任务直通**：毫秒级任务（快速检查、读单条记录、取缩略图元数据这类）不进调度器、不排队、
   不参与优先级比较、不产生调度事件。为它们做决策的成本远大于执行本身，一旦让它们排队，
   会出现「点一下要等备份跑完」这种最糟的体验。
5. **可观测**：队列长度、活跃数、各档耗时，能回答「为什么这次点了没反应」。

### 4.2 建议：按成本分三档，显式声明而不是猜

命令在注册处标注一档（一行注解），三档行为完全不同：

| 档位 | 典型命令 | 目标耗时 | 调度行为 |
| --- | --- | --- | --- |
| 微任务 | 快速检查、读单条记录、取缩略图元数据、设置读写 | < 10 ms | 直通执行：不入队、不占配额、不打点、不产生事件；只受作品级读/写语义约束 |
| 交互任务 | 用户点一下就等的写命令（改名、切分支、保存画板） | 几十 ms ～ 几秒 | 按作品排队，并发上限约等于 CPU 核数，**不占长任务配额** |
| 长任务 | 恢复、精简、检查点、整仓备份、发布签名、全库扫描、拆库迁移 | 秒级到分钟级 | 进长任务池，全局活跃上限（建议先定 2，按实测定），按作品轮转 + 优先级排序 |

两个判据写死在代码里，不做运行时自动升降档：按耗时把任务临时提升成「长任务」会让行为不可
预测，同一个按钮今天排队明天不排队，出了问题也难复现。改为记录超阈值日志（微任务实际超过
10 ms 就记一条），用真实数据回头修正标注。

为什么按作品轮转而不是纯优先级：纯优先级下，一个正在跑大备份的作品会不断有新任务插到队首，
其它作品永远轮不到。按作品轮转保证每个作品至少有一次机会，作品内部再按现有优先级排。

### 4.3 大纲（待细化）

1. **档位定义与标注方式**：谁标（命令注册处）、标在哪（现有一行分类注解旁再加一档）、默认值
   取什么（未标注时按交互任务处理，宁可多排一次队也不让长任务绕过配额）。
2. **长任务池**：自建有界池（不直接用默认阻塞线程池，后者上限高到等于没有上限）；容量、
   队列结构（按作品分组）、取任务的顺序、让位与抢占。
3. **作品级闸门**：把现在的全局写闸门拆成「每作品一把 + 全局一把」；跨作品操作（垃圾扫描、
   整仓备份、精简、空间统计）需要多把锁时，加锁顺序必须定死，避免死锁。
4. **微任务直通路径**：不经过池的具体实现，以及如何保证它不会破坏「同一作品单写者」
   （微任务里允许出现写操作吗？建议只允许读与极短的写，写仍走作品闸门）。
5. **公平性**：轮转实现、饥饿保护、前台任务优先、退出结算插队（现有 Shutdown 优先级要保留）。
6. **观测**：队列与活跃数上报给前端、超阈值日志、档位校准流程（用日志统计回头改标注）。
7. **与现有机制的关系**：自动备份的「只 try 不排队」、空闲校验的 `should_yield`、运行状态的
   busy 提示都要接到新调度上，不能出现两套并行状态。
8. **退出与关闭**：长任务在退出时的收尾顺序，与现有 5 秒兜底预算的关系。
9. **验证**：并发正确性（同一作品仍串行）、饥饿场景（多作品排队时每个都能推进）、微任务延迟
   不受长任务影响（跑备份时点开设置页仍即时响应）。

### 4.4 风险

- **档位标错**：把长任务标成微任务，它会绕过配额，几个同时跑就吃满内存。靠超阈值日志发现，
  这也是为什么微任务要有「超过 10 ms 记一条」。
- **多把锁引入死锁**：跨作品操作要拿多个作品的闸门，顺序不统一就会互等。加锁顺序必须写在
  文档里并加断言。
- **上限拍脑袋**：太小则长任务排队过久，太大则内存峰值不可控。先用实测数据定，不先写死。

## 5. 前台作品与单一渲染引擎

### 5.1 事实

- 主窗口同一时刻只查看一个作品：作品树里可以有很多作品，但「当前作品」永远只有一个。
- 素材板渲染（WebGPU 上下文、BC7 纹理、画布）服务的是「正在看的这块画板」；切作品时按现有
  策略全释放，切回来重新装载。
- 现有优先级只有任务类型这一个维度（退出 / 前台 / 交互 / 后台），没有「属于哪个作品」这个
  维度——拆库后需要它。

### 5.2 需求

1. **渲染引擎只有一份**。拆库不改变「一个窗口一个画板」这个事实，因此不按作品各建一个引擎、
   一个 WebGPU 上下文或一份纹理缓存；切作品换的是数据源，不是引擎实例。
2. **前台作品高优先级**。用户正在看的作品，它的任务优先于其它作品的后台长任务；切换作品后
   优先级立刻转移。
3. **后台作品的长任务不打断、但不挡路**。旧作品的备份、精简、校验可以继续跑，但不能让新
   作品的操作排队等它。

### 5.3 大纲（待细化）

1. **渲染层的单实例边界**：引擎、上下文与纹理缓存的生命周期挂在窗口上而不是作品上；切作品
   只换数据源与视口参数。
2. **「前台作品」的定义与转移**：当前作品 ID 作为调度器的一个输入，切换时原子更新；没有打开
   任何作品时不存在前台作品。
3. **优先级合成**：最终优先级 = 任务类型 × 是否前台作品；非前台作品的长任务降到最低档，
   前台作品的交互任务可以插队。
4. **切换时序**：新作品的首个任务必须能越过旧作品正在跑的长任务；旧作品的长任务在让位点
   暂停还是继续跑，需要明确。
5. **与现有让位机制的关系**：自动备份的让位与空闲校验的 `should_yield` 要认识「前台作品」，
   不能只看「有没有用户操作」。
6. **验证**：后台跑着备份时切作品，画布立即响应；两个作品同时有长任务时，前台那个先完成。

## 6. 其余部分大纲（待细化）

1. **目标与非目标**：明确不做多用户、不做多进程共享同一作品库、不改变单写者语义。
2. **数据模型拆分口径**：哪些表进作品库，哪些留在全局库（作品索引、应用设置、素材板归属、
   待清理队列各自归哪边）。
3. **迁移路径**：单库 → 多库的一次性迁移，接在 §3 的升级框架里；回滚方式与旧版本拒绝策略
   沿用同一套。
4. **写入并发模型**：见 §4；此处只补「拆库后每作品一把写锁如何落到具体仓储调用」。
5. **跨作品任务的重做**：垃圾扫描、整仓备份/精简/恢复、空间统计、空闲完整性检查在新结构下
   怎么扫、怎么汇总、怎么保证不出现「扫到一半作品被删」。
6. **识别页独立化**：入口位置、无作品时的空状态、与发布页共享的组件怎么复用、外部图片的
   路径授权边界（现在的仓库边界校验要重新定义）。
7. **风险与验证**：崩溃一致性、迁移中断、性能实测口径（并行写到底快多少，要用可复现的基准
   而不是感觉）。
8. **分批建议与依赖**：升级框架先行，拆库其次，调度与识别页随后。

## 7. 已明确的前提

- 拆库后是「每个作品单写者」，不是「同一作品允许并发写」——后者不在讨论范围。
- 升级必须由用户显式确认，不再有「打开即静默迁移」的默认路径；但**只向前、不降级**这条承诺
  不变，只是从静默执行改成显式流程。
- 不升级时仓库保持原样，软件退出打开流程，不写任何标记文件。
- 识别页迁出后不改变现有行为（拖放导入、记录搜索、框选放大镜、错误提示口径）。
- 拆库不改变「主窗口只查看一个作品」这个前提，因此渲染引擎、WebGPU 上下文与纹理缓存都只有
  一份，不按作品复制。
- 0.3 的发布前压力测试与 release 复测不受本计划影响，仍按 `docs/guides/release-policy.md`
  执行。

## 8. 待决策

- **无界面场景是否保留自动迁移**：命令行/headless 与自动化测试没有升级页，是允许它们按旧
  方式静默迁移，还是必须显式传「允许升级」参数。
- **升级能否取消**：取消即丢弃副本、原库不动，代价是白跑一遍。要做的话取消点定在步骤之间。
- **升级前是否额外做整仓备份**：副本策略已经保护原库，但整仓备份能覆盖「升级后数据逻辑出错」
  这种副本策略管不到的情况；代价是时间与磁盘翻倍。
- **拆库迁移的进度粒度**：按作品上报还是按阶段上报，直接决定进度条是否可信。
- **长任务活跃上限取多少**：建议先定 2（一个跑大备份时仍留一个给交互式长命令），按实测内存
  峰值再调；是否暴露给用户设置，建议不暴露，先用常量。
- **微任务耗时阈值取多少**：建议 10 ms，超过就记一条日志用于校准标注；阈值本身不参与调度，
  只用于发现问题。
- **微任务里允许写吗**：建议只允许读与极短的写，写仍走作品闸门；完全放开会让「同一作品
  单写者」这个前提失去可检查性。
- **切走后旧作品的长任务怎么办**：继续跑（后台慢慢做完）还是暂停到用户切回来？继续跑更符合
  「备份不打断」，但会长期占一个长任务配额。
- **非前台作品能否占满长任务池**：建议至少留一个配额给前台作品，否则用户切过去要等后台
  长任务结束。
- **前台优先会不会饿死后台**：用户反复切换作品时，后台作品的任务可能永远轮不到；需要保底
  时间片或最低配额。
