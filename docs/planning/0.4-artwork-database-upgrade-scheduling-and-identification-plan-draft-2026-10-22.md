# 0.4 作品独立数据库、显式升级与回退、并发调度与识别独立化

## 0. 已定决策（2026-10-22）

1. **无条件拆库**。0.4 落地“每个作品一个数据库”，不设实测门槛。部分拆分不可行：认证表
   与 `branches` / `history_nodes` 存在外键，发布事务还在同一事务里写认证配置、发布记录
   与清理登记；要拆就是全领域一起拆。
2. **一个仓库只有一个版本**。不引入版本目录、容器桩或多版本并存；仓库根目录仍然就是
   仓库本身。升级不复制 `artworks/` 载荷，只重建数据库。
3. **升级在暂存区完成，提交前旧仓库始终可用**。先把新数据库构建好并校验，最后才替换
   根库；任何一步失败或中断，旧根库不动，旧版软件仍能打开仓库。
4. **成功自动替换并删除旧数据**。全部作品迁移成功时，自动替换根库、清理暂存与旧库
   备份，不额外询问。
5. **出错时由用户选择**。有作品迁移失败时，**不预设默认动作**：用户选择回退（丢弃新库、
   保留旧仓库）或继续（提交带失败标记的新版本并删除旧版数据）。继续并删除旧版属于
   最高危险选项，必须用滑动确认（复用现有破坏性操作的滑块控件）。连新版本都无法构建
   的致命错误只提供重试/回退，不提供删除。
6. **残余文件自动清理或识别为垃圾**。暂存目录、未启用的作品库、旧库备份在成功/回退后
   删除；遗留物在启动时自动清理，或进入设置页的垃圾文件扫描，不静默留在仓库里。
7. **识别搜索用全局索引**。发布记录的权威数据在作品库，根库维护一份可重建的搜索索引；
   识别页不逐个打开作品库做全量搜索。识别页保留现有 UI，只去掉对当前作品的逻辑依赖。
8. **成本按任务种类分档，不按耗时数值卡**；长任务有全局上限。自动化通过显式命令绕过
   开始界面，但不保留静默自动迁移。

## 1. 目的与成功标准

### 1.1 目的

1. **每个作品一个数据库**：不同作品的写可以真正并行；单个作品库损坏或迁移失败不拖垮
   整个作品库；单次修复的影响面缩小到一个作品。
2. **把仓库打开变成显式流程**：不再“打开即静默迁移”。开始界面负责首次配置、仓库选择、
   版本探测、升级确认与失败决策。
3. **升级失败不丢旧数据**：提交前旧仓库保持完整；失败时由用户明确选择回退或继续；
   只有用户用滑动确认明确选择“继续并删除旧版”时才丢弃旧数据。
4. **控制总线按作品并行**：长任务有全局活跃上限、按作品公平分配、当前查看的作品优先；
   毫秒级任务直通，不参与排队。
5. **识别逻辑去作品化**：记录搜索改用全局索引，控制器与后端命令不再依赖当前作品。

### 1.2 成功标准

- `v1`–`v6` 仓库都能升级到 v7；升级的任何中断/失败都不会让旧仓库不可用。
- 全部作品成功时自动完成替换并清理旧数据，不需要用户再做决定。
- 有作品失败时进入一次性汇总，不自动回退也不自动删除；用户必须在“回退”与“继续并
  删除旧版”之间选择，后者必须滑动确认，且明确列出将丢失的作品。
- 提交前旧版软件能正常打开仓库；提交成功后旧版软件按现有“版本过新”逻辑拒绝。
- 作品 A 在跑长任务时，作品 B 的交互写不需要等 A 结束；长任务并发数有硬上限，内存
  峰值不随作品数量上涨。
- 作品树刷新、识别搜索不随作品数量线性变慢（走全局索引）；空间统计与整仓备份可以慢，
  但必须有进度、可取消。
- 单个作品库缺失或损坏时，作品树与其它作品仍可用，出错作品有明确提示。
- 识别页的控制器与后端命令不再接收或依赖当前作品/分支。

### 1.3 非目标

- 不做多版本并存、版本目录、容器桩或“旧版本仓库”管理；一个仓库同一时刻只有一个版本。
- 不做多进程共享同一作品库；仍然是一个进程写入，跨进程 owner lock 继续存在。
- 不做多窗口；主窗口同一时刻仍只看一个作品，渲染引擎、WebGPU 上下文与纹理缓存仍只有
  一份。
- 不做降级迁移；升级成功后旧版软件不能打开新仓库。
- 不在 0.4 做“同时发布两个作品”：发布/识别仍保持单活动认证任务（TrustMark 引擎只有
  一份），拆库只保证它们不阻塞其它作品的普通写。
- 不自动修复损坏的作品库或缺失的数据；只检测、报告、可重建。

## 2. 现状与约束（调查结论）

### 2.1 存储与打开

- 当前所有领域共用一个 SQLite 文件（仓库根目录下），每次操作新开连接，没有共享连接或
  连接池；WAL、`synchronous=FULL`、`busy_timeout` 在连接建立时统一配置。
- 打开旧仓库会沿迁移链逐级迁移，每步各自提交；整个链不是原子的，中途强杀会停在某个
  中间版本，下次打开继续。没有“需要升级”的应用级状态，也没有用户确认。
- 高于当前版本的仓库已有统一拒绝文案；迁移与校验共用它。
- 作品文件已经按作品分目录存放（快照、增量、成品、认证副本、画板 DDS），目录按作品
  UUID 命名；作品树移动不移动文件。缺目录是合法状态，按需创建。
- 仓库根目录还有锁库与 owner 元数据；它们属于运行时文件，不进入灾备副本，也不参与
  未引用文件判定。

### 2.2 写入与调度

- 写操作串行由多层机制共同保证：进程内写闸门按“退出 > 前台 > 交互 > 后台”排队；
  跨进程 owner lock 是每次写临时取的 `BEGIN IMMEDIATE`；之后还有共享运行锁、仓库
  lease 与仓库操作锁。两个同进程任务并发写会因为 owner lock 互相拒绝。
- `BackupState` 的全局操作锁与 `AppState` 的全局仓库操作锁都假定“一次只有一个写者”。
- 所有命令在阻塞线程池上执行，没有并发上限。长任务可能吃几百 MB 内存。
- 现有命令分类（只读 / 写 / 前台长命令 / 仓库写）是为取锁服务的，不是为容量服务；
  例如“创建分支备份”是写分类，但耗时是长任务级。成本档位必须与锁分类分开。
- 自动备份候选查询覆盖所有作品的分支；后台备份任意作品 A 时，前台对作品 B 的写会被
  同一把运行锁挡住。这是拆库要解决的真实场景。
- 自动备份与空闲校验已有让位机制；让位目前是进程级“有没有前台等待”，不是作品级。

### 2.3 拆库的三处跨库耦合

这三处必须与拆库同批设计，不能留到后续“顺手补”：

1. **作品树需要分支摘要**。树刷新要显示主分支标题、工作文件路径、分支数、备份告警数。
   分支搬进作品库后，要么每次刷树打开 N 个作品库，要么在根库维护摘要。摘要必须明确
   哪些字段允许短暂过期，否则每次提交都写根库，会把全局串行重新请回来。
2. **识别搜索跨作品**。发布记录的查询现在直接 join `branches` 与作品树。记录搬进作品库
   后，识别要么逐个作品库查，要么走全局索引。已定：走全局索引。
3. **删除与清理不能跨库原子**。永久删除作品现在在一个事务里删树、删历史、删发布记录
   并入队清理。拆库后必须改成“根目录删除为准 + 作品目录整体进清理队列”，所有入口
   先看目录，不能靠作品库文件是否存在来判断作品是否还在。

另外，发布事务同时写认证配置、发布记录与清理登记；拆库后这三者必须留在同一个作品库
事务里，不能一部分在根库。

### 2.4 识别页的实际耦合程度

- 识别视图不接收作品或分支；它的控制器也没有使用当前作品。
- 它调用的后端命令只要求“仓库已打开”，因为解码时要按标识符查本地发布记录；命令本身
  不接收作品/分支。
- 外部图片的授权规则已经成立：必须来自文件对话框或拖放暂存，必须位于仓库之外；拖放
  暂存目录在进程临时目录。迁移页面不改变这套规则。
- 因此“识别独立化”的工作量主要在**记录搜索的数据来源**与**前端路由**，不在识别算法。

## 3. 总体结构

```
启动
 └─ 读取设置
     ├─ 有仓库地址且是当前版本、可直接读取 ──→ 主界面
     └─ 其它 ──→ 开始界面
                  ├─ 无地址 / 空文件夹 → 选择或新建仓库
                  ├─ 非空非仓库 / 读取失败 → 警告，换仓库或退出
                  ├─ 旧版本 → 升级确认 → 进度 → 结果
                  ├─ 版本过新 → 提示升级软件，换仓库或退出
                  └─ 被其它实例占用 → 提示，退出或换仓库
```

- **仓库**：根目录就是仓库本身；根库保存作品目录、跨作品索引与队列；每个作品的数据库
  与载荷放在该作品的目录里。
- **开始界面**：应用级状态，主界面不挂载；承担首次配置、仓库选择、版本探测、升级确认、
  失败决策。
- **暂存区**：`.upgrade/<uuid>/`，只在升级期间存在；构建新数据库、保存旧库备份与恢复
  标记。成功/回退后删除；异常残留由启动清理或垃圾扫描处理。
- **索引**：`branch_index`（作品树与调度候选）与 `certification_index`（识别搜索）都是
  可重建缓存，权威数据在作品库或根库目录。

## 4. 数据布局 v7

### 4.1 文件布局

```
<仓库>/
  lilith-artworks.sqlite3          # v7 根库：目录、索引、跨作品队列
  artworks/<artwork-id>/
    artwork.sqlite3                # 该作品的数据库
    snapshots/ deltas/ artifacts/ boards/ temp/
  temp/
  .upgrade/                        # 升级暂存与恢复标记；只在升级期间有意义
    <uuid>/
      lilith-artworks.sqlite3      # 新根库（提交前不生效）
      artworks/<id>.sqlite3        # 新作品库（提交前不生效）
      old-root.sqlite3             # 提交时的旧根库备份
      state.json                   # 阶段、失败列表、待决策状态
  .lilith-write-lock.sqlite3
  .lilith-write-owner.json
```

- **一个仓库只有一个版本**：没有 `vN/` 目录、容器桩或版本管理页。仓库根目录始终是
  “当前版本”。
- **作品库与载荷同目录**：`artworks/<id>/artwork.sqlite3` 与该作品的分块、成品、认证
  副本、画板 DDS 放在一起；清理、备份、统计天然覆盖。`artwork.sqlite3` 是受管文件，
  不参与“未引用文件”判定。
- **载荷不复制**：升级只重建数据库；`snapshots/`、`deltas/`、`artifacts/`、`boards/`
  在提交前完全不动。回退只需要保留旧根库，因为载荷没有被新版本改过。
- **暂存目录**：放在仓库内的 `.upgrade/`，与仓库同卷；提交前不生效。它不是垃圾文件，
  但属于可清理的升级残留：成功/回退后删除；启动时发现没有待决策状态的残留则自动清理。
- **旧版软件兼容**：提交前根目录仍是旧版能打开的形态；`.upgrade/` 只是未知目录。旧版
  的清理扫描可能把它列为“其它”，不会自动删除；新应用启动时负责清理。

### 4.2 表归属

| 数据 | 位置 | 说明 |
| --- | --- | --- |
| `repository_meta` | 根库 | `format`、`schema_version = 7`、索引版本 |
| `library_nodes`、`artworks` | 根库 | 作品树与作品身份，权威 |
| `branch_index` | 根库 | 缓存：分支 → 作品、标题、工作文件、调度状态、告警；供树与调度器 |
| `certification_index` | 根库 | 缓存：可搜索的发布记录字段；详情回作品库取 |
| `pending_file_cleanup` | 根库 + 作品库 | 作品目录整体删除、外部条目留在根库；作品内文件入口作品库 |
| `repository_backup_runs` | 根库 | 整仓备份结果 |
| `branches`、`history_nodes`、`history_edges` | 作品库 | 权威 |
| `final_artifacts`、`certification_configs`、`certification_records` | 作品库 | 权威 |
| 素材板全部表 | 作品库 | 权威 |
| `artwork_meta` | 作品库 | 该库对应的作品 ID、库格式；打开时校验 |

- 作品库保留 `artwork_id` 列（查询方便），但不再有指向根库 `artworks` 的外键；打开时用
  `artwork_meta` 校验“这一行属于这个库”。跨库完整性由仓库一致性检查负责，不靠 SQLite
  外键。
- 认证表与 `branches` / `history_nodes` 的外键留在同一作品库内；发布事务仍然单库原子。
- 素材板表只依赖作品，天然可以整块搬走。
- `repository_backup_runs` 不搬：它是整仓备份，不属于单个作品。

### 4.3 作品库的身份与生命周期

- 每个作品库有唯一的 `artwork_meta`，记录作品 ID 与库格式；打开时校验路径、目录名与
  ID 一致，不一致按损坏处理，不猜测。
- 新建作品：先在 `artworks/<id>/` 创建并初始化作品库，再提交根库的作品树事务；根库
  事务失败则删除刚建的作品库。作品库创建失败则不创建作品。
- 作品已存在但作品库缺失：不自动新建空库（那会把“丢失”伪装成“空作品”）。作品树照常
  显示，选中时报告“作品数据缺失”，提供从备份恢复的指引。升级时被跳过的作品也走这条：
  根库目录保留作品行并标记“迁移失败”，作品库不存在，选中时显示失败原因与旧版本处置。
- 作品库损坏：只影响该作品；树、其它作品与开始界面仍可用。
- 作品被彻底删除：先删根库目录行并入队 `artworks/<id>` 整个目录；作品库文件在原位
  保留到清理执行；在清理完成前，任何入口都以根库目录为准，不把残留库当成有效作品。

### 4.4 目录、清理与删除

- 永久删除作品时，根库事务删除 `library_nodes` / `artworks`，并向根队列登记
  `artworks/<id>` 整个目录（含 `artwork.sqlite3`）；作品库内的清理队列随目录一起消失。
  外部文件（用户导出的成品）保持现有口径：不因删除作品而删除。
- 作品内的文件清理（替换发布、删除记录、失效认证副本等）登记到该作品库的队列；发布
  事务因此仍是单库原子。
- 根队列只保留“必须比作品库活得更久”的条目与迁移时无法归属的遗留条目；设置页与启动
  重放聚合根队列与各作品库队列。
- 未引用扫描按作品进行：在跨作品屏障内，为每个作品收集引用清单并核对它的目录；根库
  负责作品目录本身与 `temp/`。`.upgrade/` 不算普通未引用文件，按升级残留处理。
- 升级残留的清理规则：
  - `.upgrade/<uuid>/` 在没有待决策状态时由启动流程自动删除；有待决策状态时保留到用户
    选择“回退”或“继续”之后。
  - 已经移动到 `artworks/<id>/artwork.sqlite3`、但根库仍是旧版本的文件，属于升级残留；
    启动时识别为垃圾并自动清理或列在空间页，不参与旧版仓库的引用。
  - 旧版软件可能把 `.upgrade/` 列为“其它文件”；新应用启动后负责清理，不去改旧版逻辑。

### 4.5 版本与兼容

- 根库 `repository_meta.schema_version = 7`；每个作品库同样记录 `schema_version = 7`。
  根库与任一作品库版本不一致视为仓库不一致，开始界面报告并要求修复/恢复，不自动混用。
- 打开根库时：
  - 版本 1–6：开始界面显示升级；不自动迁移。
  - 版本 7：当前版本，正常打开。
  - 版本 > 7：拒绝打开，提示升级软件。
- 升级成功后旧版软件按现有“版本过新”逻辑拒绝打开新仓库；升级失败或回退后旧版软件
  仍能打开旧仓库。
- 新仓库（空文件夹创建）直接建 v7 结构，不经过迁移链。

### 4.6 schema 冻结与迁移复用

- 旧版单库的 v1 → v6 迁移链保持冻结，只用于在暂存区把旧库工作副本迁到 v6；不要用 v7
  的作品库建表语句去跑旧版本步骤。这是 0.3 已经踩过的“旧步骤建出新表”问题。
- v7 分为两套建表定义：根库（目录、索引、队列）与作品库（历史、认证、素材板）。两套
  都从空白创建，迁移只做数据搬运，不重写旧表。
- 触发器按库拆分：作品库保留分支/历史/画板完整性触发器；根库只保留作品树触发器。

### 4.7 旧仓库兼容（没有作品库的仓库）

0.3 及更早的仓库形态是：根目录直接放 `lilith-artworks.sqlite3`、`artworks/`、`temp/`
与锁文件，`artworks/<id>/` 里没有 `artwork.sqlite3`。0.4 必须兼容这种形态：

- 识别：根目录有可读的 Lilith Artworks 数据库、版本 1–6，且没有 v7 作品库，即为旧仓库。
  没有 `artworks/`、没有 `temp/`、只有空库都合法。
- 升级：在 `.upgrade/` 暂存区构建 v7 数据库；旧根库与载荷保持原样，直到提交。
- v1–v5：先把旧根库复制为工作副本，跑冻结迁移链到 v6，再从工作副本拆库；原根库不动。
- v6：直接只读读取原根库拆库。
- 旧仓库没有 `artwork.sqlite3` 是正常状态；升级后才会出现。旧版软件在提交前打开仓库
  不会看到 v7 作品库（它们只在暂存区，或提交后才移动到作品目录）。
- 升级失败/回退：删除 `.upgrade/` 与已移动但未启用的作品库；旧根库与载荷不动，旧版
  软件仍能打开。
- 旧仓库版本高于当前软件：不升级，开始界面提示升级软件。
- headless/自动化：显式升级指令；缺省返回“需要升级”，不静默迁移。

## 5. 仓库开始界面与升级

### 5.1 启动路由与跳过条件

应用启动后先读设置并**只读探测**当前仓库，不迁移、不创建：

- **跳过开始界面**的条件只有一条：已有仓库地址、探测成功、根库版本就是当前版本、
  没有待处理的升级状态。满足则直接进主界面。
- 其余情况进入开始界面：没有地址、目录不存在、空文件夹、非空但不是仓库、读取失败、
  旧版本、版本过新、被另一个实例占用、有待处理的升级结果。
- 首次安装没有仓库地址，也进入开始界面；这是它的“欢迎/选择仓库”状态。

开始界面显示当前仓库位置与探测结果；用户可以更换位置。更换后重新探测，不写任何东西。
**用户确认“升级”或“新建仓库”之前，不对仓库做任何写入。**

### 5.2 开始界面状态机

| 状态 | 界面 | 出口 |
| --- | --- | --- |
| 无地址 | 欢迎、选择文件夹 | 选择；选到空文件夹后可新建；退出 |
| 空文件夹 / 不存在 | 说明将新建 v7 仓库 | 新建；换位置；退出 |
| 非空非仓库 | 警告“这不是 Lilith Artworks 仓库” | 换位置；退出（不提供写入） |
| 读取失败 / 损坏 | 警告与错误原因 | 重试；换位置；退出 |
| 旧版本 | 当前版本 → 目标版本、步骤、风险、预计空间/时间 | 升级；不升级（退出应用）；换位置 |
| 升级中 | 阶段、当前作品、已用时、可取消（提交前） | 取消；提交后不可取消 |
| 升级完成（全部成功） | 自动替换并清理旧数据；显示简短完成提示 | 进入主界面 |
| 升级有失败作品（待决策） | 成功/失败作品列表、失败原因；回退与继续并删除旧版并列，不预设默认 | 回退（确认）；继续并删除旧版（滑动确认）；退出（保留待决策状态） |
| 升级致命失败 | 新版本无法构建；原仓库完好 | 重试；回退；退出；不提供删除旧版 |
| 版本过新 | “请升级软件” | 换位置；退出 |
| 被其它实例占用 | 占用者信息（脱敏） | 退出；换位置 |
| 有待处理的升级结果 | 恢复上次的汇总与选择 | 回退；继续并删除旧版；退出 |

- “不升级”按已定决策**直接退出应用**，不留在主界面。
- 空文件夹才提供“新建仓库”；非空文件夹即使看起来像别的数据，也不提供“就地新建”，
  避免写进无关目录。
- **失败汇总不预设默认动作**：主界面不挂载，必须由用户显式选择回退或继续并删除旧版；
  直接退出应用会保留待决策状态，下次启动继续询问。回退丢弃 `.upgrade/`、保留旧根库；
  继续提交带失败标记的新版本并删除旧版数据，必须滑动确认。
- “继续并删除旧版”必须滑动确认，复用现有破坏性操作的滑块控件；确认文案逐个列出失败
  作品，并明确“这些作品在新版本中只会留下载荷，原记录/历史不可恢复”。
- 连新版本都无法构建（根库/索引/目录失败）时不提供删除旧版，因为没有可替换的新版本；
  只能重试或回退。
- 退出应用不会丢失待决策状态：`.upgrade/` 与状态文件保留，下次启动重新显示汇总。

### 5.3 升级执行器

升级采用“暂存构建 + 单点提交”，提交前不修改旧根库与载荷：

1. 取得跨进程 owner lock（独占），确认没有另一个实例在写；读只读探测结果并制定计划。
2. **磁盘预检**：新数据库 + v1–v5 的迁移工作副本 + 旧根库备份 + 余量；不含载荷复制。
   空间不足直接拒绝并说明差多少，不进入构建阶段。
3. 在仓库内 `.upgrade/<uuid>/` 建立暂存区与状态文件（阶段、源版本、作品总数、失败列表、
   待决策标记）。
4. 旧版本低于 v6 时，把根库复制到暂存区并跑冻结的旧迁移链到 v6，再从工作副本拆库；
   原根库保持不动。源版本是 v6 时直接只读读取原根库拆库。
5. 在暂存区建 v7 根库（目录、索引、队列），并逐作品建 `artworks/<id>.sqlite3`。
   **单个作品失败时记录原因并跳过该作品，继续下一个**；根库、索引或全局目录失败才终止
   整次升级。
6. 建立 `branch_index` 与 `certification_index`；处理清理队列归属。失败作品不建作品库，
   但在根库目录中保留作品行并标记“迁移失败”；其载荷保持原样。
7. 校验：每个已建库 `integrity_check`、外键检查、版本一致、`artwork_meta` 身份、关键表
   行数与源库一致、索引计数一致、引用文件是否存在（缺失只警告）。单个作品校验失败
   按“单作品失败”处理。
8. **结果判定**：
   - 没有失败作品：直接进入提交，成功后自动清理旧数据，不需要用户确认。
   - 有失败作品：停在待决策状态，显示汇总；旧根库仍是活动库，用户选择回退或继续。
   - 致命失败：清理暂存，旧库不动，只提供重试/回退。
9. **提交**（全部成功，或用户明确选择“继续并删除旧版”后）：
   - 提交前对旧根库做 checkpoint 并清理 WAL/SHM sidecar；对新根库与所有新作品库做
     checkpoint 并关闭，确保提交只涉及主文件。
   - 把暂存区的成功作品库移动到 `artworks/<id>/artwork.sqlite3`；失败作品不移动。
   - 用平台层的**带备份路径的原子替换**把根库换成新根库，旧根库落到
     `.upgrade/<uuid>/old-root.sqlite3`。这是唯一提交点。
   - 提交成功后：全部成功时自动删除 `.upgrade/<uuid>/`（含旧库备份）；用户选择继续时
     同样删除，但这是滑动确认后的行为。
   - 提交失败：根库仍是旧的；暂存与已移动的作品库成为残留；提供重试/回退，不提供删除
     旧版。
10. **回退**：删除 `.upgrade/<uuid>/` 与已移动但未启用的作品库；旧根库与载荷不动。
11. 清理残留；进入主界面或回到开始界面。

- **旧仓库在提交前始终可用**：载荷不被升级修改，根库不被替换；失败列表与暂存都在
  `.upgrade/` 下。旧版软件在没有提交时仍能打开仓库。
- **为什么不需要复制载荷**：升级只读载荷、只写数据库。回退只需要旧根库与未动的载荷。
  代价是提交后新版本开始写入载荷，旧版本就不再可用；提交是单向的，符合“一个仓库一个
  版本”。
- **失败作品的载荷**：继续并删除旧版后，失败作品的目录与载荷仍在，但根库中只有“迁移
  失败”标记；它们会成为未引用文件，进入垃圾扫描或由用户手动保留。滑块确认必须说明
  这一点。
- **提交后不能再回退**：旧根库备份在成功提交后删除；这是“成功自动删除旧版”的代价。

### 5.4 中断、回退与恢复

| 中断点 | 期望结果 |
| --- | --- |
| 探测/预检后，暂存前 | 旧仓库不变，无残留 |
| 暂存构建/迁移/校验中 | 旧仓库不变；下次启动清理 `.upgrade` 残留 |
| 待决策状态 | 旧根库仍是活动库；`.upgrade` 保留；下次启动恢复汇总 |
| 提交前把作品库移入 `artworks/` 后中断 | 旧根库仍是活动库；新作品库是残留；下次启动清理或重试 |
| 根库原子替换中 | 要么旧根库、要么新根库；不存在空根库 |
| 提交后、清理前 | 新根库可用；`.upgrade` 含旧库备份，下次启动清理 |
| 提交失败 | 旧根库完好；暂存残留；重试/回退 |
| 回退中 | 旧根库不动；删除暂存与已移动的作品库 |

- 提交点只有“根库原子替换”一处；提交前旧根库一直完整。
- 状态文件只承担“清理残留、恢复待决策汇总、知道哪些作品库已移动”三件事，不承担
  数据恢复；即使状态文件丢失，旧根库仍然可用。
- 启动时的三元判定：
  - 根库是旧版本 + `.upgrade` 有待决策状态 → 显示上次的失败汇总，等待用户选择。
  - 根库是旧版本 + `.upgrade` 没有待决策状态 → 上次在构建阶段中断，自动清理残留。
  - 根库已是 v7 + `.upgrade` 仍存在 → 提交已完成，自动清理残留与旧库备份；不再显示
    待决策，失败作品由根库中的“迁移失败”标记呈现。
- **提交中中断**：状态文件记录“提交是否已获授权”（全部成功的自动提交，或用户明确选择
  继续）。已授权则重试提交；未授权或无法判断时，视为提交从未开始，清理已移动的作品库
  并回到旧仓库——这不是失败后的默认回退，而是本来就没有发生提交。根库在替换成功前
  始终是旧的，所以不需要恢复数据。
- 扫描旧根库与根库版本不一致的情况：根库是旧的，作品目录里出现 `artwork.sqlite3`，
  一律按升级残留处理，不当成有效作品库。

### 5.5 进度、预检与 headless

- 进度分三段：迁移与建库（按作品）、校验（按作品）、提交；不画假百分比。构建阶段可
  取消；提交开始后不接受取消。
- 磁盘预检读取旧库大小、新库估算大小、工作副本与余量；不含载荷。提示需要多少、差多少。
- 平台要求：目标卷必须支持原子文件替换。网络位置或设备命名空间上的仓库拒绝升级并
  说明原因。
- headless / 自动化没有开始界面：通过显式参数或直接调用升级命令来绕过开始界面；
  缺省遇到旧仓库时返回明确的“需要升级”错误，不静默迁移。
- 自动化遇到失败作品时返回结构化结果（成功/失败列表），**不自动回退**；调用方必须显式
  选择回退或继续并删除旧版。未选择时保持待决策状态并返回“需要决策”的错误。若调用方
  要“继续并删除旧版”，必须显式传危险参数，并自行承担数据丢失。
- GUI 的唯一升级路径是开始界面；自动化绕过的是“界面交互”，不是“显式确认”。

### 5.6 与设置页、创建仓库的关系

- 所有“设置仓库路径”的入口统一走探测与路由：当前版本直接切换；旧版本交给开始界面
  升级；不可读则留在设置里报错或转到开始界面。**只有一条升级路径**。
- 设置页不再自行静默初始化/迁移旧库；它只负责展示当前路径并发起“更换仓库”。新建
  仓库也由开始界面完成，避免两套创建逻辑。
- 切换仓库时仍要取写租约并让后台让位；升级/新建也不例外。

### 5.7 旧版兼容与错误文案

- 升级页必须提前说明：升级成功后旧版软件不能打开新仓库；升级失败或回退时旧版仍可用。
- 版本过新：沿用“由更新版本创建，已拒绝打开”的口径，改为开始界面的提示，并提供
  换仓库/退出。
- 仓库损坏或需要 WAL 恢复：探测只读；如果必须写入才能恢复，先提示用户，不在用户
  确认前自动恢复。
- 旧版软件在提交前打开仓库时，`.upgrade/` 可能被列为“其它文件”；这是升级残留，新
  应用负责清理，不影响旧版数据。

## 6. 锁与调度

### 6.1 跨进程 owner lock

- 语义不变：同一仓库同一时刻只允许一个进程写入。改成**进程内引用计数**：第一个写者
  取得 owner lock，后续同进程写者共享；最后一个写者释放。读不取 owner lock。
- 这样两个不同作品的写可以在同一进程内并行，而不会互相以“另一个进程正在写入”拒绝；
  另一个进程仍然立即被拒绝。
- 只读长任务的“探测是否有写者”要认识本进程已持有的共享 owner lock，不能把自己判成
  竞争者。
- owner 元数据保留 pid/角色/操作/心跳；共享时记录“多操作共享”，诊断日志能看出是哪个
  进程持有。

### 6.2 每作品闸门与跨作品屏障

- 进程内写闸门从“按仓库根目录一把”改为按 `(仓库, 作品)` 一把；同一作品仍然单写者。
- 新增跨作品屏障：普通作品操作取屏障共享 + 作品闸门；跨作品操作（永久删除、垃圾扫描、
  整仓备份、全库完整性扫描、升级）取屏障独占。
- **不采用“跨作品操作依次拿所有作品锁”**：那需要固定加锁顺序且容易死锁。屏障独占的
  代价是跨作品操作期间所有作品写暂停，但这与今天的行为一致，且这些操作不频繁。
- 固定锁序：屏障 → 作品闸门 → 全局索引锁；任何路径不得反向获取。索引更新在持有作品
  闸门时进行，跨作品操作在屏障独占下进行。
- 退出结算保持 Shutdown 优先级；退出时先停止接纳新长任务，再取消活动任务，最后释放
  owner lock。

### 6.3 成本三档：按任务种类分，不按耗时数值卡

成本与锁分类是两个维度；不能复用现有“只读 / 写 / 前台 / 仓库写”分类（例如分支备份是
写分类但属于长任务）。**档位绑定到任务种类**：同一个种类的任务耗时量级接近，种类在
代码里声明一次，运行时不再按毫秒数判断、不自动升降档。

| 档位 | 典型任务种类 | 调度行为 |
| --- | --- | --- |
| 微任务 | 读单条记录、缩略图元数据、快速检查、设置读写 | 直通：不入长任务池、不占配额、不打调度事件；写仍取作品闸门 |
| 交互任务 | 改名、切分支、保存画板、普通提交的元数据写 | 按作品排队；不占长任务配额；等待有上限 |
| 长任务 | 恢复、精简、检查点、分支备份、整仓备份、全库扫描、发布签名、升级/拆库 | 进入长任务池；全局活跃上限；按作品公平调度 |

- 每个命令/use-case 映射到一个**任务种类**，种类再映射到固定档位；映射表是唯一的判定
  来源。未登记的种类默认按交互任务处理，长任务必须显式登记。
- 不做“运行超过 X 毫秒就升成长任务”：那会让同一个按钮今天排队、明天不排队，问题难以
  复现。发现某类任务实际耗时与档位不符时，改种类映射并补测试，而不是运行时猜。
- 可以保留一条“某类任务耗时异常”的诊断日志用于发现标注错误，但它**不参与调度**，
  也不设固定阈值。
- 微任务的写仍走作品闸门，保证“同一作品单写者”可检查；微任务的读不需要闸门。

### 6.4 长任务池与公平性

- 自建有界池，全局活跃上限建议先定 2（一个后台 + 一个留给前台/交互式长命令），不直接
  使用默认阻塞线程池。上限先用常量，不暴露给用户；按实测内存峰值再调。
- 每个作品同一时刻最多一个活动长任务；每个作品同一类长任务最多一个排队项，重复请求
  合并/拒绝，避免一个作品刷满队列。
- 调度顺序：前台作品优先；同档内按作品轮转/最旧排队优先；超过一定等待时间的老任务
  提权，防止反复切换作品导致后台饿死。
- 纯优先级队列不采用：它会让一个忙碌作品不断插队。作品轮转 + 每作品一个排队项 +
  aging 足够简单，也容易观测。
- 后台长任务不被前台抢占到“杀进程”的程度：在让位点（节点边界、分块边界、批次边界）
  检查是否应让位；让位不写半成品状态。

### 6.5 前台作品与优先级

- 当前查看的作品 ID 作为调度器输入，切换作品时原子更新；没有打开作品时不存在前台作品。
- 前台作品的交互任务与长任务优先；非前台作品的长任务降到最低档。
- 长任务池至少保留一个配额给前台/交互式长任务；后台作品不能占满全部配额。
- 切走后旧作品的长任务继续跑（不暂停），但降到后台；用户切回来时，新任务可以越过
  旧任务排队，旧任务在下一个让位点让出配额或继续跑完，按实测选择。
- 自动备份与空闲校验的让位改为作品级：作品 A 有前台等待时，A 的后台任务让位；B 的
  后台任务不受影响。全局“手动提交待处理”仍可触发全局让位。

### 6.6 状态、取消与退出

- 运行状态从单槽改为列表：每条包含作用域（作品/全局）、作品 ID、任务类型、操作名、
  进度、开始时间；另附队列长度与活跃数。前端当前作品的状态高亮，其它显示为后台数量。
- 取消按操作 ID 定向：发布页取消自己的签名，设置页取消自己的扫描；不再用“取消所有”
  作为默认。退出仍可取消全部。
- 设置页的长任务 busy 判断改为“是否存在同作用域的冲突任务”，不是“全局有任务就禁用
  所有按钮”。
- 前端不再需要每 200 ms 轮询一个全局 busy 槽；保留轮询/事件两种获取方式，DTO 扩展为
  列表。

## 7. 跨作品功能重做

### 7.1 作品树与 `branch_index`

- 树刷新只读根库：作品树 + `branch_index` 聚合出主分支、分支数、告警数，不打开作品库。
- `branch_index` 字段覆盖：分支 ID、作品 ID、标题、工作文件路径、备份开关/间隔、下次
  到期、上次检查/成功、错误、告警标记。它是缓存，权威在作品库。
- 更新时机：建分支、改名、删分支、工作文件变更、备份/检查结果、告警状态变化。备份
  完成后的索引写入是**长任务结束后的短事务**，不持有长任务的锁。
- 索引写失败只记日志并标记 dirty；启动或手动“重建索引”时从所有作品库重建。树显示
  允许短暂过期，选中作品后以作品库为准刷新。
- 作品搜索按标题/工作文件路径查根库与索引，不逐个打开作品库。

### 7.2 调度候选

- 自动备份调度器读 `branch_index` 找到期分支，不每次轮询打开 N 个作品库。
- 选中候选后按作品取闸门，再打开该作品库执行备份；同一作品串行，不同作品可并行到
  长任务上限。
- 备份结果写作品库后更新索引（到期、上次成功、告警）。索引滞后最多导致一次多余的
  候选检查，不会导致数据丢失。
- “快速检查/全量检查”的判定仍以作品库中的分支元数据为准；索引只用于选候选。

### 7.3 垃圾扫描与清理

- 未引用扫描取屏障独占；按作品逐个构建引用清单（历史、认证、素材板、音频/纹理等），
  核对作品目录；根库处理作品目录、`temp/` 与锁文件。
- 清理执行同样聚合根队列与作品队列；作品队列的条目在本作品库事务里完成，根队列的
  条目在根库事务里完成。批量提交、可取消、幂等。
- 外部文件条目仍：空 id 的自动重放跳过，必须在设置页逐条确认；这条安全口径不变。
- `artworks/<id>/artwork.sqlite3` 属于受管数据，不进入未引用判定；作品删除时随目录一起
  进清理队列。
- `.upgrade/` 不是普通未引用文件：启动清理放弃决策状态的残留；有待决策状态时保留；
  空间页可以把残留列为“升级残留”，不混进用户文件的垃圾列表。

### 7.4 空间统计

- 数据库口径：根库 + 各作品库分别聚合；作品归属按作品目录/`artwork_meta` 归属。总量、
  分类占比、压缩比的口径保持 0.3 定义；SQLite 主库大小改为“根库 + 全部作品库”。
- 磁盘口径：扫描仓库目录时把 `artworks/` 与 `artwork.sqlite3` 一起计入；`.upgrade/`
  单独列为“升级残留”，不计入正常分类。
- 作品多时聚合会打开 N 个作品库。空间页是显式打开的低频操作，允许变慢；需要时提供
  进度/取消，不持久化缓存。
- 单个作品库损坏时，统计跳过该作品并列入“无法统计”，不让整页失败。

### 7.5 整仓备份与恢复

- 整仓备份取屏障独占：逐个 checkpoint 根库与作品库，复制整个仓库（含 `artworks/`、
  `artwork.sqlite3` 与必要运行时文件），排除 `.upgrade/` 残留，逐库校验，生成清单；
  `repository_backup_runs` 写根库。
- 单个作品库损坏时，整仓备份**默认失败并指名作品**，不静默跳过；用户可以先修复/移除
  该作品再备份。是否提供“跳过损坏作品”的显式选项，实施时定。
- 恢复仍是“把备份里的仓库目录当作新仓库打开”。开始界面探测版本并校验所有作品库。
- 备份清单包含每个作品库的路径与校验值；恢复校验不能只看根库。

### 7.6 空闲校验与完整性

- 手动全库完整性扫描保持前台长任务、屏障独占，逐作品逐节点校验；进度按作品 + 节点。
- 空闲校验按作品轮转：一次空闲窗口内选若干作品，各查一批节点；同一作品仍单写者。
  窗口空闲、仓库静默、开关默认关闭等 0.3 口径不变。
- 校验状态写在各作品库的节点列；失败定位到作品 + 节点。索引不需要参与校验。
- 作品库读取失败时，把该作品列入“无法校验”，不中断其它作品。

### 7.7 发布、识别与记录索引

- 发布仍取当前作品闸门与认证运行锁；生成质量预览、签名、写认证副本在作品库事务内
  完成。发布期间不阻塞其它作品的普通写。
- 发布成功后更新 `certification_index`（短事务）；索引失败不回滚发布，只标记 dirty。
- 识别解码按索引查候选记录，再打开所属作品库取完整记录/manifest；作品库不可用时显示
  索引级信息并提示详情不可用。
- 删除发布记录：作品库事务删除记录与登记清理，然后删索引行；索引删除失败由修复路径
  兜底。

## 8. 识别页

### 8.1 界面位置（已定）

- 仍保留作品工作区的“识别与溯源”页签，不新增顶层入口，不做无仓库解码。
- 控制器与后端命令不再接收/读取当前作品或分支；页签本身仍只在选中作品后可见，这是
  已知取舍。
- 没有配置仓库时不可进入识别页；开始界面会先保证仓库可用或退出。

### 8.2 `certification_index`

- 字段：记录 ID、作品 ID、分支 ID、水印/标识符、标题、创建者、输出路径、创建时间、
  输出大小/校验状态等列表展示所需字段。完整记录（含 C2PA manifest、区域、认证副本路径）
  仍以作品库为准，命中后再取。
- 搜索匹配字段与今天一致：记录 ID、水印 ID、标题、创建者、输出路径；上限 100 条。
- 作品标题从根库取，分支标题从 `branch_index` 取，索引不重复存标题，减少改名同步。
- 解码匹配：按记录 ID/水印 ID 查索引；命中后回作品库取完整记录并做现有校验。索引
  未命中不自动全库扫描，提供“重建索引”手动入口。

### 8.3 一致性与修复

- 模型：**作品库权威，索引可重建**。发布/删除记录在作品库提交后更新索引；崩溃窗口
  允许索引短暂缺失或多余。
- 多处兜底：打开某作品的发布页时对该作品的记录做一次轻量核对；搜索命中但记录不存在
  时删除索引行；索引版本变化或用户手动“重建索引”时扫描所有作品库重建（前台长任务、
  可取消、有进度）。
- 重建只读记录表，不读历史大表，成本可控。
- 单个作品库损坏时，索引重建跳过该作品并报告；不影响其它记录。

### 8.4 外部图片

- 规则不变：来自文件对话框或拖放暂存；必须授权；必须位于仓库之外；空路径拒绝。
- 拖放暂存仍在进程临时目录，退出清理规则不变。
- 迁移页面不改变图片解码、区域框选、放大镜与错误提示。

### 8.5 导航

- 记录点击后仍跳到所属作品并打开发布页：索引提供作品/分支 ID；作品不存在时提示记录
  失效，不打开空作品。
- 识别页的“再次导出/删除记录”等操作回作品库执行；权限与路径校验沿用现有口径。

## 9. 前端

### 9.1 启动与开始界面

- 应用启动先读设置，再探测仓库；**只有**“有地址 + 可直接读取 + 当前版本 + 无待处理
  升级”才直接挂主界面。其余显示开始界面。
- 开始界面是独立视图：自带标题栏/窗口控制、选择文件夹、新建、升级详情、进度、结果
  汇总、失败决策。它不挂载作品库、设置弹窗等主界面组件。
- 首次安装没有仓库地址 → 开始界面的欢迎态；选择空文件夹 → 新建；选择非空文件夹 →
  探测并警告或显示升级。
- 选择“不升级” → 退出应用。
- 全部成功的升级自动完成，显示简短完成提示后进入主界面。
- 有失败作品的升级停在汇总页：回退与继续并删除旧版并列，不预设默认动作；“继续并
  删除旧版”使用滑动确认，列出失败作品与数据丢失范围。
- 致命失败只显示重试/回退；不显示删除旧版。
- 设置页更换仓库时，若目标需要升级，关闭设置并转到开始界面；升级完成后再回到主界面。
- 主界面的“未配置仓库”空态可以移除；如果运行中仓库突然不可用（盘被拔掉等），显示
  错误态并提供“回到开始界面”。

### 9.2 主界面

- 作品树、历史、发布、素材板布局不变；识别页位置不变。
- 当前作品与分支仍是前端本地状态；新增“当前作品 ID”上报给调度器，用于前台优先。
- 作品库损坏时，选中该作品显示错误卡片；切到其它作品仍正常。

### 9.3 busy、进度与取消

- 运行状态 DTO 从单槽扩展为列表；前端当前作品的任务显示在原有状态位置，其它任务显示
  为后台数量/可展开列表。
- 取消按操作 ID；发布页、设置页各自取消自己的任务。退出仍可取消全部。
- 设置页长任务按钮只在同作用域冲突时禁用，不因其它作品的后台任务全局禁用。
- 开始界面有自己的升级进度订阅，不依赖主界面的运行状态 Provider。

### 9.4 错误隔离

- 根级兜底与区块兜底沿用 0.3 的分层错误边界；作品库损坏属于业务错误，显示在作品区，
  不触发整窗兜底。
- 开始界面的错误（探测、磁盘不足、替换失败、回退失败）必须可读、可重试、可退出。
- 破坏性滑块复用现有控件模板；确认文案必须列出失败作品与不可恢复的范围。

## 11. 验证

### 11.1 自动验证

- 迁移夹具：v1–v6 各一份旧布局仓库（根目录直接有数据库与 `artworks/`，作品目录里没有
  `artwork.sqlite3`），升级后逐表行数、外键、版本、`artwork_meta`、索引计数与源一致；
  空作品、多作品、回收站、素材板笔迹、发布记录各覆盖。
- 旧仓库兼容：没有 `artworks/`、没有 `temp/`、版本高于当前软件、旧根库带 WAL；
  分别给出明确结果，不误判为新仓库。
- 单作品失败：夹具中让一个作品库校验失败，升级停在待决策状态；选择回退后旧仓库完全
  可用、新库残留被清理；选择继续并删除旧版（测试中模拟滑块确认）后新版本可用、失败
  作品被标记。
- 致命失败：根库/索引构建失败时只提供重试/回退，不提供删除旧版；旧仓库不变。
- 提交失败：模拟根库替换失败，旧根库仍可用；作品库残留可清理；可重试/回退。
- 成功：全部作品通过时自动提交并删除 `.upgrade/`；旧版软件打开根目录被拒绝。
- 新仓库创建：空文件夹直接建 v7；非空文件夹拒绝；只读目录拒绝；磁盘不足拒绝。
- 开始界面：所有状态的路由与出口；确认前仓库文件哈希不变（只读探测）。
- 残留清理：`.upgrade/` 无待决策状态时自动清理；有待决策状态时保留并可恢复汇总；
  旧根库下已移动的 `artwork.sqlite3` 按残留处理。
- 索引：发布/删除/改名/作品删除后搜索与解码结果正确；索引缺失/多余时的修复。
- 多库备份/恢复：checkpoint、sidecar 清理、逐库校验、单库损坏的失败路径。
- 删除：根目录删除 + 作品目录/作品库入队；清理后残留为空；未引用扫描不把
  `artwork.sqlite3` 当孤儿。

### 11.2 故障注入矩阵

按 5.4 的中断点逐项注入：探测后、预检后、暂存构建中、迁移/校验中、待决策状态、
作品库移动中、根库替换前后、提交失败、回退中、清理中。每项断言：旧仓库可打开或新
版本完整；没有空根库；残留可清理；状态文件不参与数据恢复。

### 11.3 并发

- 两个作品同时写：都成功，互不等待；同一作品两个写：仍串行。
- 作品 A 后台长任务 + 作品 B 交互写：B 的延迟不随 A 时长增长。
- 前台作品切换：新作品的交互/长任务优先；后台作品不被永久饿死。
- 长任务上限：同时最多 N 个；每个作品最多一个。
- 屏障：垃圾扫描/整仓备份期间没有作品写；屏障释放后全部恢复。
- 退出：活动长任务取消、闸门释放、owner lock 引用归零；不出现退出死锁。
- 跨进程：第二个实例写被拒绝；只读探测与只读长任务不被本进程共享锁误判。

### 11.4 基准

- 作品数 1 / 10 / 100，记录数 1k / 10k：树刷新、识别搜索、空间统计、调度候选扫描。
- 单作品大分支（1 GB 级）后台备份时，另一作品的保存延迟 p50/p95/max。
- 拆库前后写入吞吐、内存峰值、长任务排队时间。
- 升级：不同旧库大小下的构建/校验/提交耗时、峰值磁盘、可取消点响应。
- 基准结果写入实施记录，不用感觉代替数据。

### 11.5 GUI 验收（维护者）

- 首次安装：开始界面选择空文件夹 → 新建 → 主界面。
- 非空非仓库文件夹：警告，不写入。
- 旧仓库：升级详情、升级进度、取消、强杀后重启、失败恢复。
- 升级全部成功：自动替换并进入主界面；旧版软件打开根目录被拒绝。
- 升级有失败作品：汇总列出失败作品；两个出口都不预设默认；选择回退后旧仓库完全可用；
  选择“继续并删除旧版”必须滑动确认，确认后新版本可用、失败作品被标记。
- 致命失败：只能重试/回退，不能删除旧版。
- 不升级：退出应用，原仓库不变。
- 版本过新：提示升级软件。
- 设置页更换仓库：当前版本直接切换；旧版本转到开始界面。
- 自动化：直接发送升级指令可以在没有开始界面的情况下完成升级；失败时不自动回退，
  必须由调用方显式选择回退或继续并删除旧版。
- 两个作品：A 后台备份时 B 保存画板/提交；B 的前台任务优先。
- 一个作品库损坏/缺失：树与其它作品可用，错误提示清楚。
- 识别页：拖放、搜索、记录跳转、框选放大镜、错误提示不变。

## 12. 风险与未决事项

### 12.1 风险

- **提交后不可回退**：成功升级会删除旧根库；这是“一个仓库一个版本 + 自动删除旧版”的
  代价。缓解：提交前完整校验；失败时必须由用户选择回退或继续；提交是唯一不可取消
  的点。
- **继续并删除旧版的数据丢失**：失败作品的原记录/历史会被丢弃，只剩载荷。缓解：回退
  与继续并列、不预设默认；滑块确认逐个列出失败作品；致命失败不提供该选项。
- **跨库一致性**：索引、分支摘要、清理队列都是新的失败面。缓解：权威数据只在作品库/
  根库目录，索引可重建，所有不一致都有检测与修复入口。
- **残留清理误删**：`.upgrade/` 与旧根库下的 `artwork.sqlite3` 必须只在“确认是升级
  残留”时清理；旧根库仍活动时绝不删除旧数据。用状态文件 + 根库版本双重判定。
- **锁重构引入死锁或双写**：owner lock 引用计数、屏障与作品闸门、索引锁的顺序必须
  写进文档并用测试守护。任何路径不得反向取锁。
- **网络/非本地卷上的原子替换语义不成立**：直接拒绝升级，不在不满足语义的卷上冒险。
- **性能回退**：树/调度已用索引，空间统计与全库扫描仍可能随作品数变慢；用基准决定
  是否需要进一步缓存。
- **范围膨胀**：拆库会牵动几乎所有模块。用批次边界控制，每批独立可验证、可回退。

### 12.2 实施时再定的参数

- 长任务全局上限（建议 2，至少留一个给前台）。
- 失败作品在“继续并删除旧版”后，载荷是保留为孤儿、列入垃圾扫描，还是随旧版一起删除；
  当前建议保留载荷并列入垃圾扫描，滑块文案必须说清楚。
- 成功升级后是否保留一份旧根库备份（当前按决策删除；若保留，需要额外的空间与清理
  入口）。
- 整仓备份遇到单个损坏作品库时，是失败还是提供显式“跳过”选项。
- 开始界面是否保留“最近仓库”列表（0.4 暂不做，先用设置/开始界面选择）。

## 13. 非目标与边界补充

- 不改变分块文件格式、不重写历史图算法、不改变备份调度的时间口径（除作品级让位外）。
- 不改变素材板渲染、纹理缓存与画板交互；只改它的数据库归属。
- 不改变识别算法、C2PA/TrustMark 校验口径与外部图片授权规则。
- 不引入外部消息中间件；调度与索引都在进程内/本地 SQLite 完成。
- 不为多用户、多进程共享同一作品库设计；单写者仍是每个作品的约束。
- 不做多版本并存、版本目录、容器桩或“旧版本仓库”管理；一个仓库只有一个版本。
- 不做降级迁移；升级成功后旧版软件不能打开新仓库。
- 不做自动逻辑修复：损坏的作品库、缺失的索引行只做检测、报告与可重建，不猜测数据。
