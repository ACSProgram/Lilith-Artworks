**已落地、实施时必须复用而非另建的能力**：

- **分支级快速检查开关**（`branches.backup_quick_enabled`）：§3.D 的 cheap fingerprint 升级
  在其上演进，不冲突。

- **退出握手**（`lib.rs` 的 `begin_webview_shutdown` / `confirm_app_shutdown`，约 115 行起）：

### 0.4 批次划分与依赖顺序

划分原则有两条：**底座先于功能**（契约、算法、数据模型先落地，功能只在其上叠加）；**同一 schema
迁移只做一次**（schema 是全局基线，重复迁移会让每一批都要重跑一遍兼容验证）。

| 批次                | 范围                            | schema                | 交付判据                                                  |
| ----------------- | ----------------------------- | --------------------- | ----------------------------------------------------- |
| 0.3-alpha1 架构与算法底座 | §3.A–E（阶段 1–5）                | 不变，保持 v4；无新增持久 schema（清理用连接内临时表）；可读 v1–v4     | 所有仓库写入口经过 coordinator；取消 / 深链 / 清理 / 灾备算法有基准            |
| 0.3-alpha2 功能批次   | §3.G + §3.H + §3.F + §3.I（阶段 6、7、8、9） | 一次 v4 → v5            | 仓储空间只读仪表盘；画板条目为多态；历史页免 restore 预览；链路校验按空闲时机全链恢复校对                |

**alpha2 内部顺序为 6 → 7 → 8；阶段 9 依赖阶段 5、6 与 7**：

- **阶段 6 保留原安排，排在画板改造之前**。为使它在阶段 7 之后仍然正确，阶段 6 的 DDS 分类必须按
  「**该条目是否存在实体文件**」判定，而不是按 kind 枚举；文字等无实体文件的 kind 没有位图载荷行，
  自然不计入 DDS 分类，因此阶段 7 落地后阶段 6 无需改动语义（只需重新定位 SQL）。
- **阶段 7 拥有 0.3 唯一一次 v4 → v5 迁移**，一次补齐 pin-board 的多态列（§3.H）、`history_nodes`
  的缩略图列（§3.F，供阶段 8 消费）与 `branch_notices` 告警表（§3.I，供阶段 9 消费）。阶段 8
  只**消费**缩略图列，不另开迁移。
- **阶段 8 排在阶段 7 之后**：缩略图存储列由阶段 7 建好，阶段 8 只做抽取、回退与回收。
- **阶段 9（§3.I）依赖阶段 5、6 与 7**：调度门控与防饿死 aging 来自阶段 5，`branch_notices`
  表与旧告警读写泛化来自阶段 7，设置页的「备份」页与「N 条链路待校验」入口来自阶段 6；与
  阶段 8 无依赖，可排在 7 之后的任意位置（列入队尾仅为表述顺序）。
- **阶段 6 的依赖是阶段 2、3、5**：阶段 5 提供清理扫描模式与引用清单接口，阶段 6 的磁盘扫描与
  DDS 分类直接复用它，不再标为「可选」。阶段 7 若重建画板表，阶段 6 的聚合 SQL 需按新的
  `file_path` 位置重新定位一次。

**为什么不是「A–F 进 alpha1、画板进 alpha2」**：§3.F 与 §3.H 原设计共用一次 v4 → v5 迁移。若把
§3.F 留在 alpha1、§3.H 推到 alpha2，只剩两条路：其一，两次迁移（v4 → v5、v5 → v6），schema 基线被
反复改；其二，alpha1 提前把 pin-board 的多态列也建出来，而「宽表 vs 公共表 + kind 子表」在 §6 仍是
未决项，等于提前冻结未定型的结构。同时，§3.H 是架构底座而 §3.F / §3.G 是新增功能，把底座推到功能
之后，会让 alpha1 的清理 / 校验 / 导出 / 灾备先按「每行都有 DDS」的旧不变量实现，alpha2 再按 §3.H
「主要改动面」逐处返工。

**基线敏感度**：alpha2 各节的行号与验收口径以 **alpha1 落地后的代码**为基线。alpha1 会重排
`app/settings.rs`、`app/workflows.rs`、`lib.rs` 与 `cleanup.rs` 的入口，因此 alpha2 实施前必须按
符号名重新定位一次，并同步更新 §0.3 的定位表。

### 0.5 2026-10-18 落实前修订（本轮已并入正文）

本轮不改变产品范围，只把会在实施时产生歧义或返工的口径写死：

- **schema 边界**：alpha1 不新增持久索引；清理改为连接内临时引用表。路径索引与所有持久 schema
  变更统一留到阶段 7 的 v4 → v5。见 §3.E、§4.1。
- **v5 迁移顺序**：阶段 7 同时完成 `branch_notices` 建表、旧备份告警读写泛化与旧列迁移；
  阶段 9 只新增 `linkVerifyFailed`、空闲门控与 kind 驱动 UI。`branch_notices` 使用
  `(branch_id, kind)` 复合主键并级联删除。见 §3.I、§4.2。
- **画板表结构**：采用「公共条目表 + 按 kind 载荷子表」；`pin_board_history` 外键改为指向公共
  条目表。v5 是向前兼容的表重建 + 回填，不承诺 append-only；阶段 6 的空间聚合查询在阶段 7
  后需重新定位 `file_path`。见 §3.G、§3.H。
- **统计口径**：仓储占用按「snapshot 文件 + 全部 `history_edges` delta + 成品/认证/画板 DDS +
  其它」计算；`history_nodes.chunk_file_size` 只作为节点重建读取量，不并入存储总量。见 §3.G。
- **错误契约**：typed `CommandError` 在 Tauri 适配层归一为现有字符串错误，结构化字段进入
  事件/日志；前端 `invokeCommand` 负责把 typed error 转成 `Error(message)` 并挂载可选字段。
  见 §3.A。
- **空闲校验**：门控同时检查 `is_visible()` 与 `is_minimized()`；运行期由校验循环在 delta 步
  边界通过 `should_yield` 让位给出到期备份，而不是依赖单线程调度器外部取消。见 §3.I。
- **依赖与归属**：`CancelToken` 由阶段 1 定义；阶段 9 增加阶段 6 依赖（设置页入口）；跨模块
  引用/完整性 provider 放在中立契约模块，不把 `pin_board` 导入 cleanup。见 §3.A、§3.E、§4。
- **发布基础设施**：`tools/release/verify-metadata.mjs` 的版本→schema 映射（0.2.x→v4、
  0.3.x→v5）与 Windows CI 的 `dev` 推送已在开发线启动时落地；阶段 7 用该映射校验 v5。
  见 §4.2、§5。

## 1. 现状判断

当前系统已经有清晰的领域目录、SQLite 事务、临时文件原子发布、反向 delta、可取消的压力测试，以及
rc.2 新增的诊断/取证体系。主要问题不是缺少模块，而是同一类基础能力在多个入口各自实现，形成了隐式
契约（下列引用以**符号名**为主，行号只给 2026-10-11 的**大致位置**；符号名比行号稳定，定位时以符号名为准）：

## 2. 0.3 目标架构

目标不是再增加一层「万能总线」，而是让每个跨边界动作只有一个可测试的执行路径：

```text
Tauri adapter       headless adapter       (future maintenance adapter)
       \                   |                         /
        ---- CommandContext + typed use-case ----
                    |
          OperationCoordinator
   operation id / lock order / cancel / progress / events
                    |
       RepositorySession + domain services
   Library | History/Backup | Authenticity | Pin-board
                    |
       SQLite + chunk files + cleanup ledger
```

约束如下：

1. adapter 只解析 DTO、检查文件选择器授权、装配 context 和映射错误，不包含业务分支。
2. use-case 不依赖 Tauri 类型；所有长操作接收 `OperationContext`（取消、阶段进度、日志、operation
   id、授权能力）。
3. 固定锁序为：跨进程仓库门闩 → coordinator 运行分类 → repository lease → repository operation
   guard → SQLite transaction。只读操作不得取得写锁；锁等待和让位必须可观测。
4. 事件总线不取代事务结果。命令返回最终 DTO，事件只表达 started/progress/finished、仓库变更和
   清理队列变化；UI 丢事件后用 revision 做一次快照补偿。
5. schema 与 ChunkFile 均采用**向前兼容**：旧仓库必须能经迁移打开，0.3 不在原地破坏 0.2 数据。
   ChunkFile 先保留 v1 reader，再以 feature flag/新版本写入。**0.3 只做一次 schema 迁移**：
   alpha1 不产生持久 schema 变更（连接内临时表不算），alpha2 的阶段 7 一次完成 v4 → v5。
   v5 允许表重建与数据回填（画板多态、旧告警列迁移），因此**不承诺 append-only**；迁移必须
   在一个事务内完成并覆盖 v1–v4 仓库（见 §0.4、§3.H）。
6. **关闭握手保持专用**，不作为事件总线里的普通事件：它必须保留「请求 → 前端结算 → 确认 → 15 秒
   兜底强退」的确认语义与不可逆 `shutting_down` 状态（rc.2 已实现）。事件总线只承载进度、失效与
   仓库变更通知。
7. **复用既有诊断体系**：事件通道的传输、运行切片（run id）、target 与标签沿用 rc.2 的日志/诊断
   基础设施（`docs/guides/logging.md`），不新建第二套观测通道；诊断模式只影响探针与取证，不改变
   事件语义。
8. **画板条目为多态**：领域层以「`kind` + 按 kind 解释的载荷」表达条目，位图/DDS 只是其中一种；渲染
   按 kind 分发到对应 provider，跨模块旁路（清理、校验、灾备、导出）按 kind 分派，**不假设条目都有
   实体文件**。
9. **事件契约唯一**：`AppEvent` 的枚举、字段与版本在 alpha1 阶段 1 定义；阶段 3 的前端订阅
   provider 只消费该契约，不另立一套。「冻结」指 v1 的封套与语义稳定，字段以可选方式扩展、
   新事件以增量版本追加，不要求 alpha2 的需求在阶段 1 就全部预知。

## 3. 改进工作流

每节标注所属批次：`[alpha1]` / `[alpha2]`。

### A. 契约与执行底座（必须最先）`[alpha1]`

准确做法：

- 在 `src-tauri/src/app/` 新增 `command_runtime`/`usecases`，定义 `CommandContext`、
  `RepositorySession`、`OperationId`、`OperationClass`（read、foreground、background）和 typed
  `CommandError { code, kind, message, retryable, operation_id }`；`CancelToken` 也在本阶段定义，
  阶段 4 的所有 I/O 步骤直接消费同一类型，不另行定义。
- **错误跨 IPC 的契约**：Tauri 命令仍返回现有的字符串错误（保持 0.2 的 `invoke` 失败形态与用户
  文案），typed `CommandError` 由适配层归一为字符串；`code`/`kind`/`retryable`/`operation_id`
  写入事件与日志，供 UI 决定重试与呈现。前端 `invokeCommand`（`src/shared/tauri.ts`）把已知的
  结构化错误重建为 `Error(message)` 并挂载可选字段，`App.tsx` 现有的 `String(error)` 路径不回归。
- `OperationCoordinator` 提供 `run_read`、`run_write`、`run_foreground`、`run_background`；统一
  `spawn_blocking`、运行锁、取消 token、阶段进度、耗时日志和事件发布。
- **本阶段定义 `AppEvent` v1 信封与首批事件**（枚举、字段、版本，见 §3.C 的事件清单）：信封字段
  （repository key、operation id、domain、phase、current/total、cancellable、completion revision）
  冻结，后续只允许追加可选字段；新增事件类型以独立版本号引入。阶段 3 只在此契约上补前端订阅与
  轮询降级，不重新定义事件；避免同一通道做两遍。
- 先迁移 create-artwork、settings、history fork/publish、backup commands 四组高风险入口，再迁移
  cleanup、pin-board 和 authenticity；每次迁移保持 command 名、DTO、用户文案不变。
- 把 `headless.rs` 改成 context 装配器，GUI workflow 也调用同一 use-case；加入「同一输入在两入口
  返回相同结果/错误码/锁分类」的契约测试。
- 按领域提供 `register_commands()` 分组函数或单独 registry 文件，集中注册仍保留，但不再让
  `lib.rs` 维护所有实现细节。

验收：create-artwork 等入口不再出现未经过 coordinator 的写流程；锁序测试覆盖正常、取消、切仓库
和退出；`cargo test --lib`、`cargo check --lib`、`npx tsc --noEmit`、`npm test`、`git diff --check`
通过。

### B. 仓库状态、设置与生命周期 `[alpha1]`

准确做法（在 rc.2 已有的握手与诊断设施上补齐，不另起炉灶）：

- `SettingsService::update(patch, expected_revision)` 成为设置页和托盘唯一写入口，原子写 JSON、
  更新内存快照、唤醒调度器和刷新托盘菜单在同一流程完成；陈旧 revision 返回 `settings_conflict`，
  不静默覆盖。现状是托盘 `set_automatic_backups_paused`（`app/settings.rs`）直接
  `write_json_atomic`，绕过了统一保存路径。**revision 是设置文件自己的单调计数，与 schema、
  ChunkFile 格式和版本号无关**：每次成功写入 +1，启动时读入，不参与发布元数据。
- 在仓库根目录增加 OS 文件锁和 owner metadata（PID、启动时间、应用版本、心跳）。GUI、headless 和
  维护命令打开仓库前都 acquire；冲突返回 `repository_busy`，异常退出只在 owner 已失效且满足 stale
  条件时回收。**落实口径（2026-10-18）**：按写操作 acquire/release，只读命令不取；锁本身仍是
  现有 SQLite 哨兵（内核锁即存活证明），owner 元数据写在同目录的 JSON 侧车文件里，取得锁即
  覆盖旧记录，不按 PID/心跳强行回收；锁文件从作品数据库发现、灾备复制与未引用扫描中排除。
- **复用现有哨兵，不另建第二把锁**：`repository_lock.rs` 的 SQLite 哨兵已覆盖 headless 的写命令并
  保证强杀不残留（锁由内核在句柄关闭时释放）；本阶段把它提升为仓库级 owner lock（同一锁文件 +
  owner metadata），GUI、headless 与维护命令共用。headless 现有的「写入命令持哨兵」路径改为持统一
  owner lock；只读命令仍不取该锁。
- 关闭路径**沿用 rc.2 的握手**（`app_shutdown_requested` / `confirm_app_shutdown` / 15 秒兜底），
  只把「结算失败、participant 超时、等待命令未返回」接入结构化诊断（复用 `[watchdog]` 与
  `[forensic]` 通道），不再新建 LifecycleCoordinator 去替换它。若后续需要冻结新命令，作为握手内部
  的排队规则实现，而不是新的并发层。
- 新增 `AppRuntimeProvider`、`useSettingsController`、`useRepositoryMaintenance`、
  `RuntimeProgressProvider`、`SettingsDialog` 和 `NoticeCenter`，App 只负责路由与注入。

验收：托盘与设置并发保存有 CAS 测试；双进程打开同仓库的冲突、stale owner 和释放可测；仓库切换/
退出期间最后一次素材板结算不丢失；现有 repository-switch 测试保持通过。

### C. 事件总线与模块模板 `[alpha1]`

准确做法：

- **`AppEvent` v1 信封已在阶段 1 定义并冻结**，本阶段只做消费侧：前端建立一个订阅 provider，
  controller 通过 repository key 和 operation id 丢弃旧事件，命令响应仍负责最终状态。事件清单
  （定义在阶段 1）为
  `OperationStarted`、`OperationProgress`、`OperationFinished`、`RepositoryChanged`、
  `CleanupQueueChanged`；事件带 repository key、operation id、domain、phase、current/total、
  cancellable 和 completion revision。**关闭请求不进事件总线**（见 §2 约束 6）。
- 复用诊断体系的传输与切片：事件经统一 provider 分发，落到日志时沿用 `run id`/`target`/标签，避免
  与 `log_frontend_diagnostics` 并行两套通道。
- 轮询保留为丢事件/启动恢复的 3 秒兜底，稳定后去掉 350 ms 高频轮询（当前在 `App.tsx` 的备份态
  轮询与 `useHistoryController.ts` 的递归轮询）。
- 统一模块目录契约：`types.ts`（边界 DTO）、`api.ts`（typed command adapter）、
  `use*Controller.ts`（竞态/请求代次/错误/忙状态）、`Module.tsx`（视图）。抽出 `useRequestEpoch`、
  `useAsyncOperation` 和 `useRuntimeSubscription` 三个小工具，避免复制各 controller 的 request ref
  和 finally 模式。
- Pin-board 先把生命周期、保存/导入/导出状态迁入 controller；WebGPU renderer 仍是纯渲染器，Channel
  只承载大 payload，状态变化走统一事件。渲染器的设备复用与占位符已由 rc.2 落地，不在本轮改动。

验收：四个领域 controller 使用同一套竞态与错误策略；事件丢失后 revision 补偿；不改变现有 DTO 与
页面功能。

### D. 分块、恢复与完整性算法 `[alpha1]`

准确做法：

- 在 `chunk_file.rs` 把格式头、chunker、hash、compression 抽成策略接口和明确的 `FormatVersion`。
  保留 v1 reader；新增版本先只在实验开关下写入，并记录配置，禁止按机器默认推断格式。
- **v2 激活口径（落实时按此执行）**：实验开关是**应用设置**（默认关闭），沿用 §3.B 的
  `SettingsService` 保存；开关只决定**新写入**的 ChunkFile 版本，不重写既有文件、不做仓库级批量
  迁移。每个 ChunkFile 的头部自带版本与策略位，reader 按文件头分派，因此同一仓库可长期混存 v1/v2；
  纯 v1 仓库在开关关闭时行为与 0.2 完全一致。0.3 发布前用阶段 4 的 benchmark 决定是否在发布版
  默认开启（判据：往返逐字节一致、CPU 不回退、恢复时延不劣化）；无论默认值如何，手工开启都只影响
  此后新生成的 snapshot/delta，旧节点在自然替换（重新 snapshot、检查点、精简）时才会写成 v2。
  开关状态写入诊断日志，便于解释仓库内的版本分布。
- `ChunkStore` 维护按虚拟偏移排序的 segment 起点和 reader 游标：顺序读命中当前段，跳跃读用二分
  查找；跨段读取一次完成。用深链和大文件 benchmark 比较 p50/p95，超过阈值才启用更复杂的索引结构。
- 把 `CancelToken` 传入 `ChunkFile::create`、reverse delta、payload copy、`resolve_chain`、
  `copy_original`、scrub 和 checkpoint。**检查粒度对齐研究结论**：转码步的取消地板是**每 tile**
  （320 KiB 原始数据，写 ≤12 ms / 恢复 ≤5.4 ms），更细的「每 64–256 KiB」在转码步不可达；廉价的
  框架块（zstd/none）可按块或每若干块检查。统一返回 typed Cancelled；所有临时输出由 guard 清理，
  进度按已处理字节而非只按节点数报告。
- `materialization_chain` 改成一次递归 CTE 返回链节点、父子边和路径，避免深链逐节点 SQL；scrub 按
  链批量解析，必要时使用有界磁盘缓存，避免对同一 delta 反复解压。
- 快速检查基线增加算法版本和 cheap fingerprint（至少 size、mtime、首尾采样；可用时加入 OS
  file-id/change counter）。基线不匹配或时间精度不足必须回退全量；手动提交继续强制全量。
- 在损坏恢复上保持当前语义：先验证 chunk/整文件摘要，再原子发布；把错误分类为缺失、格式、chunk
  摘要、整文件摘要和输出冲突，便于 UI/重试决策。
- **抽出单一容器解析模块**（如 `src-tauri/src/format/`）：负责 `.clip`/`.psd` 的 `detect` 与容器块
  定位，本阶段用它做 tile 对齐分块，阶段 8 用它定位缩略图块。**不在两处各写一份**——研究仓的
  `tools/harness/src/o5.rs` 与 `clip.rs` 只是参考实现，主仓合成为一个模块。

**研究结论（实测回流，2026-10-11）**

`research/compression-optimization/` 已按本节要求完成 P0–P5 的调查与实测（真实仓库
`F:\LilithData\Artworks`，3 作品 / 36 版本 / 6.32 GB），给出可直接落地的 v2 规格：

- **采用集（v2 = v1 + 四项）**：`格式 v2`（版本号 + 策略位 + 每块 `codec/recipe/logical_len`）→
  `O2 容器感知分块`（`.clip` 按 tile 对齐，解析失败一律回退 CDC）→ `快照 tile 级去重` →
  `O5 鲁棒性加固`（两轴错误分类 / 块级隔离 / 每 tile 取消 / 写入开关）。采用顺序
  **格式 v2 → O2 → 去重 → O5**。
- **收益是分层的，不能只看整仓**：整仓 **6.32 → ≈6.17 GB（−2.44%）**，但该数字被两个**物理不可压
  对象**主导（3D 快照占快照 67%、录屏 delta 占 delta 字节 78%）；**图层为主作品**的收益才是量级性的
  ——delta 净降 **18.6%**（含记录）、带 tile 容器单对最高 −47%、快照 tile 流可 −34%~−44%。**主收益
  应表述为「鲁棒性/可回退/版本分派」**，空间收益按文件类型分列，不用整仓平均。
- **O2 是收益主力且免费**：纯图层编辑 delta 净降 **18.6%**（含记录）、分块 CPU **−8%**；无 tile
  容器仅 −5.4%；回退 36/36，CDC 重建与仓库 33/33 一致。
- **O5 已量化到可验收**：80 个注入故障证明内容损坏**块级隔离且可单块修复**（受影响面恒为 1）；帧级
  损坏（`stored_len`/截断）**只保前缀恢复**（16%–96%）、不可隔离；错误分类扩成 `class × dimension`
  两轴；未知能力归 `Incompatible`（能力缺口，非数据损坏）；取消地板 = 每 tile（320 KiB），
  写 ≤12 ms / 恢复 ≤5.4 ms。
- **格式与块记录**：头部带 `version/chunker/hash/codec/adapter`；块记录 36 → 44 B（+8 B/块，本仓
  +1.5 MB，占整仓 0.02%）；`tools/harness/src/o5.rs` 提供 v2 容器读写器与两轴分类的**最小可运行
  样例**，可作为 `chunk_file.rs` 策略接口与读取器分派的参考。
- **明确否决**：`O6 解码域转码`（提交 **+104×** / 恢复 **+42×**，违反研究方案 **§8** 的「CPU ≤2×」
  验收线，且本仓可压上限仅 9.7%）；`O1/O1-lite`、`O3`、`O4`、`O7`（SQLite 页级）；`F3`（改分块
  参数，图层净降仅 −0.99%，未过 5% 门槛）→ **保留默认 `2/16/64 KiB`，不引入配置分支**。
  「图层文件 −1/3」属于已否决的 O6 路，**不作为 0.3 目标**。
- **必做的写入端加固**（尚未落地）：超 `max` 的结构单元**必须 CDC 切分**，否则 3D 大块截断恢复极差；
  `.psd` 适配器当前只 **detect + 回退**（结构待逆向确认）。

> 详细规格见研究仓 `docs/plan.md §3 / §8`，逐项代价见其 `docs/architecture-decisions.md`，整体对比见
> 其 `docs/v1-vs-v2-comparison.md`。研究仓全程**只读**真实数据。

验收：取消延迟按字节规模有上限（每 tile 口径）；深链恢复不再随 segment 数线性退化；v1 仓库可读，
v1/v2 混存仓库可读且开关关闭时新写入仍为 v1；损坏 snapshot/delta 不生成半成品且可重试；新增
benchmark 只作为 0.3 决策证据，不替代日常轻量检查。

### E. 调度、清理与灾备算法 `[alpha1]`

准确做法：

- 用 deadline heap 或 SQL `ORDER BY due_at, last_attempt, branch_id` 生成候选，维护唤醒信号；优先级
  固定为前台等待 > 手动提交 > 到期自动备份 > 空闲校验（口径重构见 §3.I），并用 aging 防止低优先级长期饥饿。取得锁后
  继续做资格复查。
- 每个任务拥有独立 `OperationId` 与 cancellation token；取消/让位只作用于目标后台任务，不再依赖单一
  `cancel_requested` + 多个补丁集合。失败退避按分支记录，不能阻塞其它分支。
- 调度执行仍以 repository writer lease 保证 SQLite 写互斥；只有证据表明跨 Artwork 并行有收益时，
  才引入按 repository/artwork 分片的 worker，先不并行写事务。
- cleanup 使用批量临时引用表，使用 anti-join 一次判定未引用集合，按 256–1000 条分批、每批可取消且
  幂等提交。**alpha1 不新增持久索引**：引用表是连接内 `TEMP` 表（随连接结束消失），分批事务复用同一
  临时表；`stored_path`/`snapshot_path`/`delta_path`/`output_path` 的持久索引随阶段 7 的 v5 迁移
  建立，届时 cleanup 切换为索引查询，临时表路径保留为兜底。
- **本阶段交付「引用清单 / provider 接口」**：cleanup 只接收通用清理目标或公开清单接口，不再直接
  导入 `pin_board::repository` 的路径常量（当前 `cleanup.rs` 顶部就导入 `is_dds_name`、
  `parse_board_dds_path`、`BOARD_DIRECTORY`）。该接口是 **§3.H 的前置条件**——阶段 7 要按 kind 分派
  清理/校验，只能通过它实现，否则又要把 `pin_board` 导进 cleanup。
  - **归属**：接口定义放在中立的契约模块（如 `src-tauri/src/contracts/`，或等价的
    `repository_contract.rs`），不放在任何一个领域内；领域实现 trait，应用层注册实现列表。
  - **最小形状**：`ReferenceInventory` 提供 `collect_targets(&Connection) -> Vec<ManagedFile>`
    （规范化路径 + 所有者类别 + 是否可删）与 `validate_target(&Connection, &ManagedFile) ->
    ValidationOutcome`。cleanup 用前者做 anti-join 与孤儿判定，scrub 用后者按所有者校验。
  - **演进规则**：阶段 5 只实现历史 snapshot/delta、成品、认证输出与画板 DDS 四类；阶段 7 增加
    kind 维度的导出/引用方法时以**新方法**扩展 trait，不改已冻结的方法签名，避免 alpha1 提前
    假设「每个条目都有实体文件」。
- **灾备完整性 provider 同样注入**：`repository_backup.rs` 不再直接导入 `library`/`authenticity`，
  改为接收契约模块中的读取 provider（manifest 校验、成品/认证文件清单）；领域原语仍由应用层装配，
  灾备核心只负责复制与 manifest。
- 灾备复制阶段边复制边计算 digest；manifest 校验复用已取得摘要，最终发布前保留一次抽样或全量可配置
  复核。外部文件变化继续以复制前后 metadata 复核拒绝。

验收：多分支到期任务不因一支失败固定停 60 秒；前台等待可观测且不会被后台抢锁；清理查询次数和大规模
孤儿耗时有基准；灾备 I/O 次数下降且校验语义不弱于 0.2；cleanup 不再导入 `pin_board` 的路径布局常量。

### G. 仓储/备份设置分离与仓储空间状态 UI `[alpha2]`

准确做法：

- **动机**：设置弹窗现有「仓库与备份」页把「仓库与数据安全」（仓库位置、完整性扫描、创建备份）、
  「自动备份」（调度与检查方式）和「文件清理」混在一页，而「仓储」（本地数据资产本身）与「备份」
  （灾备与调度）是两类不同心智模型；同时仓库占用、压缩比、分类占比等信息目前只在历史页按节点零散
  可见（`history_nodes.chunk_file_size`），没有仓库级视图，用户无法回答「仓库有多大、哪些作品/哪类
  文件占了多少、压缩效果如何」。本项把设置页按「仓储 / 备份」拆分，并为仓储补一个**只读空间状态
  仪表盘**。
- **设置信息架构拆分**（只重组导航与视图，不改写入路径与语义）：仓储页保留仓库位置、仓库完整性
  扫描、文件清理（队列 / 未引用扫描）并新增仓储空间状态；备份页承载自动备份调度与默认检查方式、
  创建备份（整仓灾备）与最近一次结果。写入仍全部经 §3.B 的 `SettingsService::update`；命令名、DTO、
  用户文案不变（呼应 §3.A「适配器只做装配」）；托盘刷新、仓库切换与 `AppState` lease 语义不变。
- **空间状态 UI 形态（推荐：仓储域内单开一栏，不塞进设置页的一节）**：这是信息密度高、含图表与明细
  钻取的界面，放进设置弹窗的单列页会挤占配置项，且它本质是「仓库仪表盘」而非配置项。推荐在仓储域内
  提供**「设置 / 空间」两个视图**（页内 tab，或左侧导航新增「仓储空间」项），与仓库位置 / 完整性
  同属仓储；**不推荐**独立顶层窗口——0.3 不引入新的窗口生命周期与跨窗口状态。
- **只读聚合命令**（新增，如 `get_repository_storage_overview`）：从 SQLite 聚合，走共享读租约、不取
  运行锁、不写 `last_attempt_ms`，与 `list_pending_file_cleanup` 同类。口径：
  - **总量口径（避免重复计数）**：snapshot 文件字节 = `Σ history_nodes.chunk_file_size WHERE
    snapshot_path IS NOT NULL`；delta 文件字节 = `Σ history_edges.delta_size`（每条边对应一个 delta
    文件）。非 snapshot 节点的 `chunk_file_size` 被写成子边 delta 大小（`STORAGE_METADATA_SET`），
    含义是**该节点的重建读取量**，**不得再加进存储总量**。
  - **完整公式**：`总量 = snapshot 文件 + 全部 delta + 成品输出（final_artifacts，按规范化路径去重）
    + 认证输出（certification_records.output_bytes，按路径去重）+ 画板 DDS（文件系统扫描）
    + 其它（SQLite 主库与 WAL、repository/temp、未识别文件）`。缩略图是 `history_nodes` 的 BLOB，
    已含在 SQLite 主库内，不单列；分类占比之和以该公式为分母，「其它」兜底。
  - 按 artwork 占比：snapshot 与 delta 按 `history_nodes.artwork_id` 汇总；成品、认证与画板按所属
    artwork 归属；无法归属的记录进「其它」并单独列出。`library_nodes` 的分组树用于把作品归到分组。
  - 压缩比**分层报告，不混算整仓平均**：snapshot 用 `Σ logical_size / Σ snapshot 文件字节`；delta
    用 `Σ 父节点 logical_size / Σ history_edges.delta_size`（delta 表示子→父的变化，还原目标是父
    节点；v1 delta 头声明只作交叉核对，§3.D 的 `FormatVersion` 提供精确声明后才作为独立口径展示）。
    这与 §3.D「收益分层」一致。
  - 明细钻取：artwork → 分支 → 节点，逐行显示 `logical_size`、`chunk_file_size`（在 snapshot 行
    标注为快照文件大小，在 delta 行标注为重建读取量）、`chunk_count`、压缩比与是否 checkpoint /
    snapshot；画板 DDS 与认证输出按类别展开。
- **磁盘真实占用 vs DB 记录口径**：画板 DDS 与认证输出的大小不在 DB 大小列中，需一次受控的文件系统
  扫描（复用 §3.E 的 `scan_unreferenced` 遍历模式）才能得到磁盘实际值。SQLite 主库与 WAL 的大小也
  只能从文件系统取得（缩略图 BLOB 已含在主库内，不二次相加）。仪表盘同时呈现「DB 记录大小」与
  「磁盘实际大小」两套口径；扫描未触发或不可用时降级为 DB 口径并明确标注。
- **与既有能力的关系**：只读命令经 §3.A 的 `CommandContext` / `OperationCoordinator`（只读分类）；
  扫描耗时需进度时复用 §3.C 的事件通道。
- **分类口径必须与 kind 解耦**：DDS 分类按「**该条目是否存在实体文件**」判定（即 `file_path` 非空），
  **不按 kind 枚举**。阶段 6 查询 `pin_board_images.file_path`；阶段 7 重建后同一判定改为 join
  `pin_board_bitmaps`（见 §0.4），只是 SQL 重新定位，口径不变。这样 §3.H 引入文字等无实体文件的
  kind 后，本项无需改语义（它们没有位图载荷行，自然不计入 DDS 分类），也就保住了「阶段 6 排在
  阶段 7 之前」的安排。

**关键取舍**

- **聚合权威口径**：以 SQLite 记录为权威（快、稳定），磁盘扫描作为可选补充（准、需遍历）；两者差异
  本身就是有用信号（DB 记录 vs 实际磁盘），不做静默合并。
- **是否持久化缓存**：不持久化、按需重算（避免为缓存新增 schema 与失效逻辑）；大仓库若需更快，先做
  查询次数 / 耗时基准再决定是否加内存缓存，**不新增表**。
- **是否进入统一事件 / 轮询体系**：单次读取即可返回时同步返回；含磁盘扫描时作为可取消长任务，复用
  统一进度通道与取消 token。

**约束与验收**

- **只读、不改仓库、不新增窗口**；不新增 schema 迁移（与 §3.H / §3.F 的 v4 → v5 迁移无关）。
- 拆分后设置保存、仓库切换、托盘刷新与既有测试语义不变；仓储页原有的完整性扫描、文件清理、创建
  备份入口不丢失（创建备份归入备份页）。
- 数值正确性：空仓库 / 单作品 / 多作品下总量与占比正确；分类占比之和等于总量（含「其它」兜底）；
  压缩比与 `history_nodes` 记录一致；删除 / 精简后统计随之更新。
- 大仓库聚合有基准（查询次数与耗时），不阻塞 UI；扫描路径可取消。
- `v1`–`v4` 仓库可读；未配置仓库时仪表盘显示空态而非报错。

### H. 画板条目模型泛化（多态 item）与原生文字 `[alpha2]`

准确做法：

- **动机**：现状把画板条目**硬编码为「一张 DDS 位图」**——`pin_board_images.file_path` 是实体文件、
  `read_texture` 读 DDS、`PinBoardImage` DTO 只有像素宽高、清理/校验/导出/灾备全部围绕 DDS 文件。
  这使画板只能承载位图：文字被迫先栅格化成 PNG → BC7 DDS（`PinBoardModule.tsx` 的 `renderTextImage`），
  于是**放大即放大位图 → 发糊**，位置也由栅格化时的 `padding`/`measureText` 决定而随缩放漂移。
  目标是把条目模型泛化为**多态 item**：每个条目带 `kind` 与按 kind 解释的载荷，**位图退化为其中一种
  kind**；文字为首个非位图 kind，后续可扩展笔迹（stroke）等，使画板真正成为「画板」。
- **为什么列入 0.3（而非顺手加功能）**：这是一次横切**存储模型 + 渲染分发 + 全部旁路**的改造，牵动
  schema 迁移、命令面/DTO、渲染器分发与清理/校验/导出/灾备，属于架构底座。
- **分层设计**：
  - **存储层**：**公共条目表 + 按 kind 载荷子表**（已定，见「关键取舍」）。`pin_board_items` 只保留
    与 kind 无关的公共列（`id`、`board_id`、`kind`、`created_ms`）；位置/图层/排序/变换仍按现状存于
    `pin_board_history` 的 step 行，不复制到条目表。位图载荷表 `pin_board_bitmaps`（`item_id` 主键 +
    `file_path`/`width`/`height`）；文字载荷表 `pin_board_texts`（`item_id` 主键 + `text`/`font_family`/
    `font_size`/`color`/`align`/`measured_width`/`measured_height`）。新增 kind 只加子表。
  - **渲染层**：渲染器按 `kind` 分发到对应 provider——位图 = 读 DDS；文字 = 前端按需栅格化。
    四边形 `points/uv`、命中判定、图层、step 历史**保持不变**（它们只依赖变换与包围盒，与 kind 无关）。
  - **旁路层**：清理、DDS 校验、导出、灾备**按 kind 分派**；无实体文件的 kind 不进入路径清单。
    分派通过 §3.E 交付的引用清单 provider 接口完成，**不把 `pin_board` 导入 cleanup**。
- **渲染路径（推荐：前端按需栅格化，复用既有纹理通道）**：文字 provider 用 2D canvas 按**请求长边
  `maxDimension`**（`texturePolicy` 已按视口缩放算出）重绘 → `ImageBitmap` → `copyExternalImageToTexture`
  上传为 `rgba8unorm` 纹理。既有两级缓存与「按 `maxDimension` 请求」机制**天然复用**：放大触发更高
  `maxDimension` → 重新栅格化 → 清晰，无需为文字新建缓存；纹理负载仍走既有 RGBA 分支（`isRgbaPayload`）。
- **为什么不由 Rust 栅格化**：需要内置 CJK 字体、文本整形与度量一致性，成本远高于前端；而前端已有
  canvas 度量与系统字体，**WebView2 的字体即最终显示字体**，度量与显示天然一致。Rust 端只负责存储与
  （导出时的）编码。
- **定位准确性**：文字项不再依赖栅格化 `padding` 决定视觉位置，改用「度量 → 四边形」映射；缩放只改
  视口变换，文字随四边形精确缩放，消除旧方案「缩放后偏移」。

**关键取舍**

- **表结构选型（已定）**：采用**公共表 + 按 kind 子表**（`pin_board_items` + `pin_board_bitmaps` /
  `pin_board_texts`），不采用 `pin_board_images` 宽表增列。理由：新增 kind 只加子表，公共表不积累
  NULL 列；代价是读取多一次 join，位图列表按 kind 过滤后 join 载荷表即可。`pin_board_history` 的外键
  从 `image_id → pin_board_images` 改为 `item_id → pin_board_items(id) ON DELETE CASCADE`，历史仍只
  记录变换/位置，不承担载荷。
- **命令面/DTO**：`PinBoardImage` 变为带 `kind` 的联合类型（可顺势更名为 `PinBoardItem`；前后端在同
  一提交内切换，不保留长期并存的两套 DTO）；导入/粘贴仍产生位图 kind；新增按 kind 的创建命令（如
  `create_pin_board_text`），文字项不再走图片导入链路。
- **step 历史是否承载载荷（0.3 决定：不承载）**：0.3 只支持创建、删除、移动、图层与排序；**不支持
  创建后改字/改色/改字号**，因此 `pin_board_history.transform_json` 保持纯变换语义。这样文字载荷只有
  一个当前版本，无需为撤销/重做引入载荷快照。后续若要支持编辑，按「载荷版本表 + step 引用版本」扩展，
  不改本阶段已定的公共表/子表边界；该扩展不在 0.3 承诺。

**主要改动面（打破「每个条目都有 DDS」不变量）**

非位图条目没有实体文件，会触碰若干假设「每行 `pin_board_images` 都有 DDS 路径」的既有路径，需逐处
按 kind 分派：

| 位置                                                                                                       | 现状假设                                 | 多态条目下的处理                                  |
| -------------------------------------------------------------------------------------------------------- | ------------------------------------ | ----------------------------------------- |
| `cleanup::scan_unreferenced` / `referenced_path_kind`；`library/schema.rs` 的路径 UNION（含 `pin_board_images.file_path`） | 每行有 `file_path`，参与引用判定与孤儿扫描           | 非位图 kind 无 `file_path`，**不进入路径清单**，避免被判为「缺失文件」 |
| `cleanup::scrub_board_dds`                                                                               | 逐条 `pin_board_images` 记录校验 DDS 存在/归属/解码 | 只校验位图 kind，跳过其余                              |
| `read_texture`（`pin_board/repository.rs`）                                                                 | 读取 DDS，超请求长边时解码缩放为 RGBA 预览           | 按 kind 分派：位图读 DDS，文字返回「无 DDS」信号交前端栅格化       |
| `read_image_png` / `export_images`（`pin_board/repository.rs`）                                              | 解码 DDS → PNG / 写盘                    | 按 kind 分派：位图读 DDS；文字由前端按导出分辨率栅格化为 RGBA，经专用命令交 Rust 编码 PNG |
| 灾备 / 恢复                                                                                                   | 递归复制 DDS 文件 + manifest 逐文件清单          | 非位图 kind 随 SQLite 走，**无需路径覆盖**，灾备天然覆盖      |

**文字导出链路（落实口径）**

- 新增一次性写盘命令（如 `write_pin_board_item_rgba`）：入参为导出目录中已授权的目标路径、像素宽高与
  RGBA 缓冲；Rust 用现有 `image` crate 编码 PNG 并原子发布，不读 DDS。授权与路径校验复用 §0.0 已落地的
  导出目录授权，不新开通道。
- 前端按导出倍率（目标长边由导出设置决定）用与屏幕显示**同一套字体度量函数**在 `OffscreenCanvas`
  上绘制，保证屏幕与导出定位一致；单张 RGBA 载荷设上限（如 64 MiB，超限则该条目报错而非降采样），
  批量导出逐条处理，避免一次 IPC 传多张大图。
- `read_image_png`（预览）对文字 kind 直接返回「无位图」信号，由前端画布渲染；只有显式导出才走上述
  写盘命令。

**schema 与兼容**

- 这是 **pin-board 表自 v2 引入以来的首次 schema 变更**（当前 `SCHEMA_VERSION = 4`）。按 §2 约束 5 做
  **向前兼容的 v4 → v5 表重建 + 回填**（不是 append-only）：旧仓库可读，旧 `pin_board_images` 行迁移为
  `kind = 0`（位图）的条目，`pin_board_history.image_id` 迁移为 `item_id`。
- **本阶段（阶段 7）拥有 0.3 唯一一次 v4 → v5 迁移**，在一个事务内完成全部持久 schema 变更：
  1. 建 `pin_board_items`、`pin_board_bitmaps`、`pin_board_texts`，按上文字段定义；三表均以
     `board_id`/`item_id` 级联删除。
  2. 把 `pin_board_images` 复制为 `pin_board_items(kind = 0)` 与 `pin_board_bitmaps`；
     重建 `pin_board_history` 指向 `pin_board_items`，保留全部 step 行。
  3. 删除旧表并重建索引（`pin_board_items(board_id, id)`、位图/文字子表按 `item_id` 主键、
     `pin_board_history(board_id, item_id, step)`）。
  4. `history_nodes` 追加 `thumbnail`（BLOB）与 `thumbnail_version`（整数）列，供阶段 8 消费。
  5. 建 `branch_notices` 并把 `branches.backup_disable_notice_pending = 1` 的行迁移为
     `kind = 'backupDisabled'` 通知，随后删除旧列（单一机制，见 §3.I）。
  6. 建路径索引（`stored_path`/`snapshot_path`/`delta_path`/`output_path`），供 cleanup 使用。
  7. `repository_meta.schema_version = '5'`。
- **重建方式**：SQLite 的表重建需在 `PRAGMA foreign_keys = OFF` 下进行（事务外切换），提交后先
  `PRAGMA foreign_key_check` 再恢复 `ON`；任一步失败整笔回滚，不留下半迁移仓库。新仓库的
  `create()` 直接建 v5 结构；**v1 → v2 迁移用的建表 SQL 必须冻结为 v2 旧形状**，不能复用更新后的
  建表常量，否则 v1 仓库会在 v2 步骤建出 v5 表、随后 v5 步骤无法重建。
- 迁移测试覆盖：v1/v2/v3/v4 仓库各升级到 v5 后数据与 step 历史完整、外键与级联删除正确、旧备份
  告警迁移后行为不变、失败注入时整笔回滚；新仓库从 v5 直接创建。

**约束与验收**

- 非位图条目**不落 DDS**、不进入 `pending_file_cleanup` 与孤儿扫描；无实体文件变化。
- 栅格化**有界、可取消**：单张文字纹理受既有 `PIN_BOARD_NATIVE_TEXTURE_LIMIT` 与上传预算约束；缩放
  触发的重绘需**去抖**，避免连续缩放抖动反复栅格化。
- **字体一致性**：固定字体族（沿用 `Microsoft YaHei UI` / `Segoe UI` 并兜底），创建时把度量结果
  （宽高）持久化；跨机字体缺失只影响显示度量，不改四边形尺寸。
- 验收：位图行为**不回退**（现有画板功能、清理、灾备、导出语义不变）；文字放大到 400% 边缘清晰；
  文字与位图在同一缩放下定位偏差 ≤ 1px；导出 PNG 含正确文字且与屏幕度量一致；RGBA 写盘命令拒绝
  未授权路径与超限载荷；`v1`–`v4` 仓库可读；`scan_unreferenced` / `scrub_board_dds` 不把非位图
  条目当作缺失文件；`npm run test:pin-board` 与 `cargo test pin_board --lib` 覆盖 kind 分派、迁移与
  外键级联；**新增 kind 只需实现 provider，不改核心几何/缓存**。
- **不在本项承诺**：具体新增 kind 的交互（笔迹工具等）不在 0.3 落地，0.3 只落地多态模型 + 文字这一种
  kind；**创建后编辑文字（改字/改色/改字号）不在 0.3 范围**——`pin_board_history` 保持纯变换语义，
  只有创建、删除、移动、图层与排序可撤销。后续扩展需引入载荷版本表，届时另立计划。

### F. 节点缩略图（提交时生成，免 restore 预览）`[alpha2]`

准确做法：

- **动机**：查看某个历史节点（尤其 `.clip`/`.psd` 这类分层工作文件）的内容，目前只能 `restore`
  出完整文件再用外部应用打开，代价高且打断浏览。
- **做法**：在**创建节点时**顺带抽取一份缩略图随节点保存。提交/自动备份的 worker 本来就要打开并
  流式读取工作文件（`backup/worker.rs`、§3.D），此刻抽取缩略图的边际成本最低；历史页直接显示
  缩略图，无需 restore。
- **依赖**：本阶段消费阶段 7 建立的 `history_nodes.thumbnail` 列（**不另开迁移**）与阶段 4 落地的
  容器解析模块（**不重复实现**），并由阶段 1 的提交 use-case 调用。这三条是 §4 依赖表里阶段 8 的
  真实前置，而不是「依赖 ChunkFile 格式 v2」。
- **关键取舍**：缩略图按**节点**存储、与链位置无关，因此查看时**不需要**对 delta 链做惰性区间读，
  避免把 §3.D 的 `ChunkStore` 区间读取复杂度引入 UI 路径。代价是存量节点没有缩略图（见下）。
- **归属**：抽取属「工作文件格式」能力，放在独立模块（如 `src-tauri/src/preview/`），由提交
  use-case 调用并把结果交给 history/backup 存储；backup 领域不硬依赖具体格式（呼应 §1「领域互不
  导入」）。格式检测复用阶段 4 的容器解析模块，不重复实现。
- **界面**：缩略图只读、按需加载。**选中节点时在右侧详情区显示**（时间轴模式左侧已是既有的时间轴
  列，见「历史图前端布局」，右侧留作节点详情），未选中或格式无预览时显示占位；节点卡片不内嵌大图。

**各格式来源（先按资料，落实前实测）**

| 格式                                              | 缩略图来源                                                                                                       | 备注                                                                                                                                                                                                                              |
| ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `.clip`                                         | CSFC 容器内嵌 SQLite（`SQLi` 块）的 `CanvasPreview` 表，存画布 PNG                                                       | 复用阶段 4 容器解析模块定位 `SQLi` 块（研究仓 `tools/harness/src/clip.rs` 的 `parse_csfc`/`walk_tiles` 为参考）；该 PNG 使用非标准 filter 字节（`kunohami/clip-studio-thumbnailer` 记录 ImageMagick 拒收、需 ffmpeg），`image` crate 解码需容错或回退 |
| `.psd` / `.psb`                                 | 优先 Image Resources 段的缩略图资源（ID 1036 = PS 5.0+，28 B 头 + JFIF/JPEG；ID 1033 = PS 4.0）；取不到时退回 Image Data 段的合并合成图 | 合成图只需按段长跳过 Layer and Mask 段，**不必解码图层**；compression 0 raw / 1 RLE / 2 ZIP / 3 ZIP+prediction；PSB 多处长度字段为 8 B（PSD 为 4 B）。§3.D 已记录 `.psd` 适配器当前只 detect + 回退、结构待逆向确认                                                               |
| 位图（png/jpg/webp/tiff/bmp/gif）                   | 直接解码并缩放                                                                                                     | 复用现有 `image` crate（`src-tauri/Cargo.toml` 已启用这些 feature）                                                                                                                                                                        |
| 其它分层（`.kra`/`.ora` = ZIP 内 `mergedimage.png` 等） | 可选                                                                                                          | 后续再加，不在 0.3 承诺                                                                                                                                                                                                                  |
| 未识别 / 解析失败                                      | 无                                                                                                           | UI 显示占位；**绝不因此让提交失败**                                                                                                                                                                                                           |

**存储（随节点：`history_nodes` 追加 BLOB 列）**

- 硬约束：缩略图**不得写进 ChunkFile 内容**。`history_nodes.sha256` 是工作文件内容的摘要，scrub 与
  恢复都以它为准；把缩略图塞进 snapshot 会破坏摘要语义。因此缩略图是**派生旁路产物**，随节点行存在
  数据库中，不参与完整性校验与恢复。
- 已定：内容小，**不单开文件或表**。在 `history_nodes` 追加 `thumbnail`（BLOB）与 `thumbnail_version`
  （尺寸/编码版本）列，由**阶段 7 的 v4 → v5 迁移**一并建立（见 §0.4），旧仓库可读，旧节点该列为空
  → 显示占位。
- 随之简化：删除节点/分支、精简、检查点替换时缩略图**随行删除**，不进入 `pending_file_cleanup`，也
  不需要 `scan_unreferenced` 路径模式与灾备路径覆盖；整仓备份的 SQLite 副本天然包含缩略图。
- 读取按需：图/列表读取必须使用**显式列名**、不得带出 BLOB；新增只读命令（如
  `get_history_node_thumbnail`）在选中节点时单独拉取。缩略图损坏或解码失败只影响该节点预览，不影响
  图读取与其它节点。

**约束与验收**

- 抽取**有界、可取消、只读**工作文件头部区域；任何失败只跳过缩略图，不影响提交结果与摘要；缩略图带
  自身版本号，可安全重建。缩略图固定最大边长与编码（如 ≤512 px，WebP/PNG）。
- 内容未变化的快速检查路径不打开工作文件，沿用 head 已有缩略图；**存量节点不回填**（0.3 不做链上
  惰性抽取）。创建分支不新建节点（`app/workflows.rs` 的 `fork_artwork_branch` 只固化检查点），分支
  起点沿用原节点缩略图。
- **检查点与 snapshot 替换不重新抽取**：检查点不改变工作文件内容。若在同一节点上建立 snapshot，保留
  该节点缩略图；若检查点新建节点行，复制被检查点化节点的缩略图。只有真正读取了新工作文件内容的提交
  才生成/更新缩略图；复制失败只让新节点无缩略图，不影响检查点结果。
- 验收：`.clip`/`.psd`/位图提交后历史页可预览；损坏或未知格式回退为占位且提交成功；删除节点后缩略图
  按清理语义回收；灾备副本保留或可重建缩略图。

### I. 空闲链路校验重构（默认关闭、按空闲时机、全链恢复校对）`[alpha2]`

**动机**：0.2 已落地「空闲链路校验」（`backup/scheduler.rs` 的第二优先级 `IdleVerify`，加
`branches` 的 `verified_history_id` / `verified_ms` / `verify_error` 列），但口径与维护者
预期不符：常驻运行没有开关；校验范围收敛到 head 的单个 snapshot——`materialization_chain` 在
目标节点持有 snapshot 时只返回该节点，而 head 恒持有 snapshot，因此中间任何一条 delta 损坏都
发现不了，「链路健康」名不副实；没有窗口空闲判定（用户正在使用时也可能跑）；没有频率控制；
失败只停留在历史页分支状态行，没有走作品库告警。维护者 2026-10-17 给出新口径，本节按其重构。

**维护者口径（2026-10-17）**：功能默认关闭；近期有改动的链路才进入审查清单，没有修改且经过
检查的链路不再查；只在「主窗口打开不算空闲」的时机运行，且不打扰频繁的自动备份；优先级最低，
频率只作量级参考（如每分支每天一次）、**不写死为时间规则**；校验 = 对整条链做一次完整恢复并
做哈希校对，通过即说明链上任何节点都没问题；失败要找出有问题的节点并报错，复用多次自动备份
失败的报错做成 shared 模板。

准确做法：

- **开关与设置**：新增全局设置 `idleLinkVerifyEnabled`，**默认 false**（`#[serde(default)]`
  即可，旧设置文件缺省即关闭，不需要 settings 版本迁移）。入口落在阶段 6 拆页后的「备份」页：
  开关 + 行为说明 + 「N 条链路待校验」只读计数（复用 `automaticBackupFileCount` 的快照统计
  模式，走共享读租约、不取运行锁）。该计数是派生的只读查询，**不写入设置快照、不持久化**。关闭时
  调度器完全跳过自动校验；**手动「重新校验此分支」不受开关影响**。托盘「暂停所有自动备份」继续
  一并暂停本功能（「别动仓库」的用户意图不变）。
- **首次开启的存量 backlog**：不做一次性补跑。开启后按「每次空闲窗口至多一条」自然消化，设置页
  显示待校验数；急用可手动重查单条，或运行全库完整性扫描兜底。这样保持「不打扰自动备份」的取舍，
  也避免开启瞬间形成长时间的全库读写。
- **审查清单（派生队列，不新建表）**：未进回收站、`head_history_id` 非空、
  `verified_history_id` 与 head 不一致（含 NULL）且 `verify_error` 为空的分支（现有查询口径
  保留）。三条规则：
  - **入队**：新提交改变 head（现有语义）；**精简、检查点建立/取消、snapshot 修复**会改写链
    文件但不变 head，随各自事务按 artwork 粗粒度清 `verified_history_id`，保证「已验证」只
    对当前链文件成立（粗粒度 vs 精确到受影响分支为阶段 9 待决）。
  - **通过后**：写 `verified_history_id` / `verified_ms` 并清空 `verify_error`；无改动不再
    入队——这是唯一硬规则，且与时间无关。
  - **失败后**：写 `verify_error` 退出队列，不自动重试，直到 head 再变化或用户手动重查
    （现有语义保留）。
- **空闲时机门控（按序，任一不满足即退出本轮，等待下次唤醒）**：
  1. 主窗口**不可见或已最小化**才算空闲：调度循环轮询 `is_visible()` **与** `is_minimized()`，任一
     命中即视为空闲（Windows 上最小化窗口的 `is_visible()` 可能仍为 true，两个都要查）；隐藏到托盘
     或最小化均算空闲（校验只读仓库文件、不碰工作文件，最小化时用户在用别的软件也不受干扰——明确
     取舍）。窗口可见且未最小化 = 用户正在使用，本轮不跑。
  2. 无前台命令等待、无待处理手动提交、无到期自动备份（沿用 §3.E 的第二优先级与让位机制）。
  3. head 静默 ≥ `IDLE_VERIFY_DELAY_MS`（10 分钟，现有常量）：避免校验正在被连续改写的链；
    这是防抖，不是频率。
  4. 取得运行锁后锁内复查：head 未变、仍空闲、仍无竞争（现有 `run_idle_verify` 结构保留）。
- **频率：每次空闲窗口至多一次，不设时钟**。「空闲窗口」= 主窗口从可见转为隐藏/最小化的一次
  连续期间，进程内判定，**无持久化、无计时器**。一次尝试无论完成、失败还是被抢占，都消耗该
  窗口的名额，下一次自动校验要等新窗口。候选按 head 创建时间最旧优先、每轮至多一条（现有）。
  典型日用（每天显隐数次）≈ 每天数条以内，且每条都对应真实改动；窗口连续悬挂数天也只校验
  一条——自觉的低频取舍，急用可手动重查或跑全库扫描。维护者的「每分支每天一次」仅作量级参考，
  不实现为任何计时器。
- **不打扰自动备份（维护者点名的取舍）**：
  - **选择期避让**：有到期备份就不启动（门控 2）。
  - **运行期抢占**：全链校验可能持续数分钟，这期间备份到期不能干等。校验循环在**每个 delta 步边界**
    调用阶段 5 提供的 `should_yield()`；一旦有到期自动备份、前台等待或待处理手动提交，立即停止、
    不写任何结果，让调度器先运行高优先级任务。不新增按 kind 的外部取消入口，也不依赖单线程调度器
    从外打断；用户手动取消仍走既有取消路径。
  - **防饿死复用阶段 5 的 aging**（§3.E 已含「优先级 + aging 防饥饿」交付物，参数为阶段 5
    待决项）：本功能**不另设时间阈值**——早期提案里的「挂起超 7 天免抢占」经维护者确认不
    采纳（计时式阈值），饥饿问题统一交回阶段 5 的 aging。
  - 手动提交与前台命令的让位沿用现有 `foreground_waiting` / `manual_pending`，不新增机制。
- **全链恢复校对（本节核心）**：对整条链做一次**完整恢复并哈希校对**——从 head 的 snapshot
  出发，沿父链逐条应用反向 delta 直到 root，每步结果与数据库摘要比对，最终根文件内容流入
  sink 逐块验哈希并核对整文件摘要。一次物化即证明：每条 delta 都被实际应用、每个节点摘要都
  被校对，链上任何节点都没问题。
  - **实现**：history 新增 `full_materialization_chain(head_id)`——纯父链查询，**绕过
    `materialization_chain` 的「就近 snapshot」短路**，保证中间存在检查点/分支起点 snapshot
    时也从 head 走完整条链；restore 侧把 `resolve_chain` 重构为接受显式链（或新增
    `resolve_full_chain`），复用 ChunkStore 分段、逐条 resolve、每步摘要比对与
    `copy_original` 逐块验哈希；取消与进度按步报告（与 §3.D 的 CancelToken 口径对齐）。
  - **沿途 snapshot 文件级校验的边界**：全链恢复只读取 head 起始 snapshot 的内容；链上其它 snapshot
    节点（中间检查点、分支起点、root）不在恢复路径上，逐个 `validate_snapshot`（文件摘要 + 全部分块
    验哈希）。**只校验本链节点上的 snapshot**，不遍历其它分支；跨分支与全库范围仍由
    `scrub_repository_integrity` 负责。这样「本链任何节点都没问题」的口径完整且代价有界。
  - **失败定位到节点**：每步摘要不符 → 「历史节点 X 的摘要与历史数据库不匹配」；delta
    缺失/损坏 → 「历史节点 X 的反向 delta 损坏或缺失」；中间 snapshot 损坏 → 同样带节点 id。
    全部写入现有 `verify_error` 列；历史页分支状态行照旧展示（独立于备份失败的第三态），
    错误文案现在带节点 id。
  - **代价**：约等于链上全部 delta 载荷之和 + 根文件一次流式读出，比 0.2 的 head 快照检查
    重；由「默认关闭 + 窗口空闲 + 每窗一条 + 最低优先级」兜住。全库完整性扫描
    （`scrub_repository_integrity`）保持按需全量定位，两者互补（既有口径不变）。
- **失败报错：kind 驱动的 shared 模板**。复用「连续失败禁用自动备份」的报错链路（作品树角标
  + 作品库顶部告警条 + 「查看分支设置」导航 + 「知道了」确认），泛化为按 kind 呈现：
  - **schema（阶段 7 建立并泛化）**：新建 `branch_notices(branch_id TEXT NOT NULL REFERENCES
    branches(id) ON DELETE CASCADE, kind TEXT NOT NULL CHECK (kind IN ('backupDisabled',
    'linkVerifyFailed')), message TEXT NOT NULL, created_ms INTEGER NOT NULL,
    PRIMARY KEY (branch_id, kind))`；复合主键让同一分支可同时有 `backupDisabled` 与
    `linkVerifyFailed`，且同 kind 只保留一条（重复失败更新 `message`/`created_ms`）。旧
    `branches.backup_disable_notice_pending = 1` 在 v5 迁移中转为 `backupDisabled` 行，**随后删除
    旧列**（单一机制，不保留只读兼容列）。阶段 7 同时把
    `next_backup_disable_notice_target` / `acknowledge_backup_disable_notices` 泛化为
    `next_branch_notice_target` / `acknowledge_branch_notices`（按 artwork/kind 过滤），作品树计数
    改为「有待处理告警的分支数」。
  - **阶段 9 只新增行为**：链路校验失败写入 `kind = 'linkVerifyFailed'`；校验通过时删除该分支的
    `linkVerifyFailed` 通知（`backupDisabled` 仍保持确认制）；前端换用 kind 驱动的共享告警组件。
- **手动重查升级**：`reverify_branch_history` 从「清错误 + 唤醒调度等待」改为**前台立即执行
  全链校验**（进度 + 可取消 + 写同一套结果列）。低频率的自动节奏下，手动入口必须即时，否则
  按钮点了要等到下一个空闲窗口才跑。

**关键取舍**

- **频率不写死时间**：用「每次空闲窗口至多一次」的机会式节流代替每日计时器；换来频率随真实
  使用自然浮动（约每天数条以内）、零持久化状态、重启安全。代价是长假悬挂只校验一条——接受，
  急用有手动入口。
- **抢占 vs 备份延迟**：全链校验重且时长不可控，不抢占会让频繁备份场景的备份延迟累积；抢占
  的代价是忙仓库上校验可能反复中途退出（不写结果、下窗续查），防饿死交回阶段 5 的 aging。
  不做「挂起 N 天豁免」式计时阈值。
- **最小化算空闲**：校验只读仓库、不碰工作文件，最小化时跑不影响用户别的操作，换来更多校验
  机会；若维护者改为「只认隐藏到托盘」，门控 1 随之收紧。
- **通知存新表而非新列**：与备份禁用告警共用一张表才是真正的 shared；代价是一次 schema
  迁移（已并入阶段 7）与旧列迁移（迁移后删除旧列）。

**约束与验收**

- 默认关闭；关闭时除手动重查外零调度行为。
- 窗口可见且未最小化期间绝不自动运行；运行中在 delta 步边界检测到更高优先级任务时通过
  `should_yield()` 停止，不写结果、不推进 `verified_ms`、不清 `verify_error`。
- 一次空闲窗口内多条待校验分支只执行一条；窗口重新可见再转入空闲后执行下一条。
- 全链校验通过 = 根文件整文件摘要一致 + 每步节点摘要一致 + 逐块哈希正确 + 本链沿途 snapshot
  文件级通过；任一失败的错误信息带节点 id 并写入 `verify_error`，同时入队 `linkVerifyFailed` 通知。
- `branch_notices` 使用 `(branch_id, kind)` 复合主键；同一分支可同时存在两种通知，重复失败只更新
  既有行；删除分支级联删除通知；校验通过删除 `linkVerifyFailed` 但保留待确认的 `backupDisabled`。
- 回归覆盖：中间存在检查点时仍从 head 走完整链；精简/检查点后分支重新入队；`should_yield` 抢占不写
  结果；旧 `backup_disable_notice_pending` 迁移为 `backupDisabled` 后行为不变且旧列已删除；`v1`–`v4`
  仓库经 v5 迁移后可读。
- 手动重查在开关关闭时仍可用且立即执行；设置页待校验计数与派生队列口径一致。
- 日志按 `docs/guides/logging.md`：开始/结束/耗时走 `run_logged` 常规档，失败为 `warn`，
  不带隐私内容。

## 6. 非目标与待决策

- 不重写领域业务规则，不把所有函数强行放进通用插件系统，不为事件总线引入外部消息中间件。
- 0.3 不为画板一次性实现所有 kind 的交互（笔迹工具等）；本阶段只落地**多态条目模型 + 文字**这一种非
  位图 kind，以验证「新增 kind 只需实现 provider、不改核心几何/缓存/旁路」这一可扩展性目标。
- **压缩侧方向已定**（§3.D「研究结论」）：`O2 容器感知分块采用`、`O6 不采用`、`hash 不变`
  （O4 否决）、分块参数保持默认 `2/16/64 KiB`、快照 tile 级去重采用。阶段 4 在真实写入端复核并实现，
  实验开关默认关闭、只影响新写入，不自动迁移已有文件；发布版默认值按 §3.D 的判据决定。
- **仓储空间状态只读**（§3.G）：只做只读聚合与设置信息架构拆分，不引入独立顶层窗口、不持久化统计
  缓存、不新增 schema；DDS 分类按「是否有实体文件」判定，不按 kind 枚举。
- **缩略图存储位置已定**（§3.F）：随节点存于 `history_nodes.thumbnail`（BLOB）+ `thumbnail_version`，
  由阶段 7 的 v4 → v5 迁移建立；不单开文件或表，不参与完整性校验与恢复。
- **画板表结构与历史语义已定**（§3.H）：采用 `pin_board_items` + 按 kind 载荷子表，v5 表重建并回填；
