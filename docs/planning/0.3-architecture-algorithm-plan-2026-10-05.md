# 0.3 架构与核心算法改进计划

- 规划日期：2026-10-05
- 目标版本：0.3（具体 alpha/rc 编号由版本发布时决定）
- 状态：提案，尚未实施
- 基线：`0.2.0-alpha.4`、repository schema v4

本计划只处理跨模块架构、运行协调和历史/备份核心算法。Library、History、Authenticity
和 Pin-board 的具体功能、页面布局和业务规则不在本轮重新设计；只有当它们暴露了架构边界、
并发或存储算法问题时才列入改造。

## 1. 现状判断

当前系统已经有清晰的领域目录、SQLite 事务、临时文件原子发布、反向 delta 和可取消的
压力测试。主要问题不是缺少模块，而是同一类基础能力在多个入口各自实现，形成了隐式契约：

## 2. 0.3 目标架构

目标不是再增加一层“万能总线”，而是让每个跨边界动作只有一个可测试的执行路径：

```text
Tauri adapter       headless adapter       (future maintenance adapter)
       \                   |                         /
        ---- CommandContext + typed use-case ----
                    |
          OperationCoordinator
   operation id / lock order / cancel / progress / events
                    |
       RepositorySession + domain services
   Library | History/Backup | Authenticity | Pin-board
                    |
       SQLite + chunk files + cleanup ledger
```

约束如下：

1. adapter 只解析 DTO、检查文件选择器授权、装配 context 和映射错误，不包含业务分支。
2. use-case 不依赖 Tauri 类型；所有长操作接收 `OperationContext`（取消、阶段进度、日志、
   operation id、授权能力）。
3. 固定锁序为：跨进程仓库门闩 → coordinator 运行分类 → repository lease → repository
   operation guard → SQLite transaction。只读操作不得取得写锁；锁等待和让位必须可观测。
4. 事件总线不取代事务结果。命令返回最终 DTO，事件只表达 started/progress/finished、仓库
   变更、清理队列变化和 shutdown 请求；UI 丢事件后用 revision 做一次快照补偿。
5. schema 与 ChunkFile 均采用追加兼容：先保留 v1 reader，再以 feature flag/新版本写入，
   不在 0.3 直接破坏 0.2 仓库。

## 3. 改进工作流

### A. 契约与执行底座（必须最先）

准确做法：

- 在 `src-tauri/src/app/` 新增 `command_runtime`/`usecases`，定义 `CommandContext`、
  `RepositorySession`、`OperationId`、`OperationClass`（read、foreground、background）和
  typed `CommandError { code, kind, message, retryable, operation_id }`。
- `OperationCoordinator` 提供 `run_read`、`run_write`、`run_foreground`、`run_background`；
  统一 `spawn_blocking`、运行锁、取消 token、阶段进度、耗时日志和事件发布。
- 先迁移 create-artwork、settings、history fork/publish、backup commands 四组高风险入口，
  再迁移 cleanup、pin-board 和 authenticity；每次迁移保持 command 名、DTO、用户文案不变。
- 把 `headless.rs` 改成 context 装配器，GUI workflow 也调用同一 use-case；加入“同一输入在两
  入口返回相同结果/错误码/锁分类”的契约测试。
- 按领域提供 `register_commands()` 分组函数或单独 registry 文件，集中注册仍保留，但不再让
  `lib.rs` 维护所有实现细节。

验收：create-artwork 等入口不再出现未经过 coordinator 的写流程；锁序测试覆盖正常、取消、
切仓库和退出；`cargo test --lib`、`cargo check --lib`、`npx tsc --noEmit`、`npm test`、
`git diff --check` 通过。

### B. 仓库状态、设置与生命周期

准确做法：

- `SettingsService::update(patch, expected_revision)` 成为设置页和托盘唯一写入口，原子写
  JSON、更新内存快照、唤醒调度器和刷新托盘菜单在同一流程完成；陈旧 revision 返回
  `settings_conflict`，不静默覆盖。
- 在仓库根目录增加 OS 文件锁和 owner metadata（PID、启动时间、应用版本、心跳）。GUI、
  headless 和维护命令打开仓库前都 acquire；冲突返回 `repository_busy`，异常退出只在 owner
  已失效且满足 stale 条件时回收。
- 把前端单 participant 生命周期改成 `LifecycleCoordinator`：仓库切换/关闭先冻结新命令，
  按顺序等待所有 participant 结算，再等待 repository lease 和 coordinator 任务；保留 15 秒
  watchdog，但把失败 participant 和超时写入结构化诊断。
- 新增 `AppRuntimeProvider`、`useSettingsController`、`useRepositoryMaintenance`、
  `RuntimeProgressProvider`、`SettingsDialog` 和 `NoticeCenter`，App 只负责路由与注入。

验收：托盘与设置并发保存有 CAS 测试；双进程打开同仓库的冲突、stale owner 和释放可测；
仓库切换/退出期间最后一次素材板结算不丢失；现有 repository-switch 测试保持通过。

### C. 事件总线与模块模板

准确做法：

- 定义版本化 `AppEvent`：`OperationStarted`、`OperationProgress`、`OperationFinished`、
  `RepositoryChanged`、`CleanupQueueChanged`、`ShutdownRequested`。事件带 repository key、
  operation id、domain、phase、current/total、cancellable 和 completion revision。
- 前端只建立一个订阅 provider；controller 通过 repository key 和 operation id 丢弃旧事件，
  命令响应仍负责最终状态。轮询保留为丢事件/启动恢复的 3 秒兜底，稳定后去掉 350ms 高频轮询。
- 统一模块目录契约：`types.ts`（边界 DTO）、`api.ts`（typed command adapter）、
  `use*Controller.ts`（竞态/请求代次/错误/忙状态）、`Module.tsx`（视图）。抽出
  `useRequestEpoch`、`useAsyncOperation` 和 `useRuntimeSubscription` 三个小工具，避免复制
  各 controller 的 request ref 和 finally 模式。
- Pin-board 先把生命周期、保存/导入/导出状态迁入 controller；WebGPU renderer 仍是纯渲染器，
  Channel 只承载大 payload，状态变化走统一事件。

验收：四个领域 controller 使用同一套竞态与错误策略；事件丢失后 revision 补偿；不改变现有
DTO 与页面功能。

### D. 分块、恢复与完整性算法

准确做法：

- 在 `chunk_file.rs` 把格式头、chunker、hash、compression 抽成策略接口和明确的
  `FormatVersion`。保留 v1 reader；新增版本先只在实验开关下写入，并记录配置，禁止按机器默认
  推断格式。
- `ChunkStore` 维护按虚拟偏移排序的 segment 起点和 reader 游标：顺序读命中当前段，跳跃读用
  二分查找；跨段读取一次完成。用深链和大文件 benchmark 比较 p50/p95，超过阈值才启用更复杂
  的索引结构。
- 把 `CancelToken` 传入 `ChunkFile::create`、reverse delta、payload copy、`resolve_chain`、
  `copy_original`、scrub 和 checkpoint。每处理一个 chunk 或 64–256 KiB 检查一次，统一返回
  typed Cancelled；所有临时输出由 guard 清理，进度按已处理字节而非只按节点数报告。
- `materialization_chain` 改成一次递归 CTE 返回链节点、父子边和路径，避免深链逐节点 SQL；
  scrub 按链批量解析，必要时使用有界磁盘缓存，避免对同一 delta 反复解压。
- 快速检查基线增加算法版本和 cheap fingerprint（至少 size、mtime、首尾采样；可用时加入
  OS file-id/change counter）。基线不匹配或时间精度不足必须回退全量；手动提交继续强制全量。
- 在损坏恢复上保持当前语义：先验证 chunk/整文件摘要，再原子发布；把错误分类为缺失、格式、
  chunk 摘要、整文件摘要和输出冲突，便于 UI/重试决策。

验收：取消延迟按字节规模有上限；深链恢复不再随 segment 数线性退化；v1 仓库可读；损坏
snapshot/delta 不生成半成品且可重试；新增 benchmark 只作为 0.3 决策证据，不替代日常轻量检查。

### E. 调度、清理与灾备算法

准确做法：

- 用 deadline heap 或 SQL `ORDER BY due_at, last_attempt, branch_id` 生成候选，维护唤醒信号；
  优先级固定为前台等待 > 手动提交 > 到期自动备份 > 空闲校验，并用 aging 防止低优先级长期
  饥饿。取得锁后继续做资格复查。
- 每个任务拥有独立 `OperationId` 与 cancellation token；取消/让位只作用于目标后台任务，
  不再依赖单一 `cancel_requested` + 多个补丁集合。失败退避按分支记录，不能阻塞其它分支。
- 调度执行仍以 repository writer lease 保证 SQLite 写互斥；只有证据表明跨 Artwork 并行有收益
  时，才引入按 repository/artwork 分片的 worker，先不并行写事务。
- cleanup 建立 snapshot/delta/artifact/board DDS 路径索引或批量临时引用表，使用 anti-join
  一次判定未引用集合，按 256–1000 条分批、每批可取消且幂等提交。
- 灾备复制阶段边复制边计算 digest；manifest 校验复用已取得摘要，最终发布前保留一次抽样或
  全量可配置复核。外部文件变化继续以复制前后 metadata 复核拒绝。

验收：多分支到期任务不因一支失败固定停 60 秒；前台等待可观测且不会被后台抢锁；清理查询
次数和大规模孤儿耗时有基准；灾备 I/O 次数下降且校验语义不弱于 0.2。

## 5. 验证与完成条件

- 日常阶段只运行与改动匹配的 `cargo fmt --check`、`cargo check --lib`、`cargo test --lib`、
  `npx tsc --noEmit`、`npm test` 和 `git diff --check`；不在普通收尾阶段运行压力测试。
- 0.3 发布前由维护者显式安排压力测试：取消/崩溃、4 GiB 往返、损坏恢复、规模、DDS、认证和
  跨进程门闩，并把实测写入 `docs/guides/stress-test-report.md`。
- 架构完成条件：GUI/headless 共享 use-case；所有仓库写入口经过 coordinator；反向依赖清零；
  设置 CAS 和跨进程冲突有测试；事件丢失可由 revision 恢复。
- 算法完成条件：取消响应有明确上限；深链恢复和清理查询不出现已知的线性退化；快速检查
  不再只依赖 size+mtime；v1 数据可读且新格式可回退；灾备完整性断言不减弱。

## 6. 非目标与待决策

- 不重写领域业务规则，不把所有函数强行放进通用插件系统，不为事件总线引入外部消息中间件。
- 是否启用新 chunker/hash/compression、是否按 Artwork 并行，必须由阶段 0/4/5 基准和磁盘/内存
  预算决定；默认只新增 reader/策略接口，不自动迁移已有文件。
- 跨进程门闩的 Windows stale owner 回收规则、快速 fingerprint 的采样大小、事件丢失后的快照
  TTL、调度 aging 参数在实现阶段记录为明确决策，不在本提案中伪装成已定契约。
- 当前 0.2 待人工验收项仍以 `docs/planning/current-handoff.md` 和 `docs/planning/todo.md`
  为准；本计划不把它们标记为已完成。
