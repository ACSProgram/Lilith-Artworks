- **退出握手**（`lib.rs` 的 `begin_webview_shutdown` / `confirm_app_shutdown`，约 115 行起）：
  `app_shutdown_requested` → 前端结算素材板 → `confirm_app_shutdown`，

据此，§3.B / §3.C 的目标由「新建事件与生命周期设施」调整为「**在既有诊断/握手设施上补齐统一入口**」。

### 0.4 批次划分与依赖顺序

划分原则有两条：**底座先于功能**（契约、算法、数据模型先落地，功能只在其上叠加）；**同一 schema
迁移只做一次**（schema 是全局基线，重复迁移会让每一批都要重跑一遍兼容验证）。

| 批次                | 范围                            | schema                | 交付判据                                                  |
| ----------------- | ----------------------------- | --------------------- | ----------------------------------------------------- |
| 0.3-alpha1 架构与算法底座 | §3.A–E（阶段 1–5）                | 不变，保持 v4；可读 v1–v4     | 所有仓库写入口经过 coordinator；取消 / 深链 / 清理 / 灾备算法有基准            |
| 0.3-alpha2 功能批次   | §3.G + §3.H + §3.F（阶段 6、7、8） | 一次 v4 → v5            | 仓储空间只读仪表盘；画板条目为多态；历史页免 restore 预览                      |

**alpha2 内部顺序为 6 → 7 → 8**：

- **阶段 6 保留原安排，排在画板改造之前**。为使它在阶段 7 之后仍然正确，阶段 6 的 DDS 分类必须按
  「**该条目是否存在实体文件**」判定，而不是按 kind 枚举；文字等无实体文件的 kind 的 `file_path`
  为空，自然不计入 DDS 分类，因此阶段 7 落地后阶段 6 无需改动。
- **阶段 7 拥有 0.3 唯一一次 v4 → v5 迁移**，一次补齐 pin-board 的多态列（§3.H）与 `history_nodes`
  的缩略图列（§3.F）。阶段 8 只**消费**该列，不另开迁移。
- **阶段 8 排在阶段 7 之后**：缩略图存储列由阶段 7 建好，阶段 8 只做抽取、回退与回收。

**为什么不是「A–F 进 alpha1、画板进 alpha2」**：§3.F 与 §3.H 原设计共用一次 v4 → v5 迁移。若把
§3.F 留在 alpha1、§3.H 推到 alpha2，只剩两条路：其一，两次迁移（v4 → v5、v5 → v6），schema 基线被
反复改；其二，alpha1 提前把 pin-board 的多态列也建出来，而「宽表 vs 公共表 + kind 子表」在 §6 仍是
未决项，等于提前冻结未定型的结构。同时，§3.H 是架构底座而 §3.F / §3.G 是新增功能，把底座推到功能
之后，会让 alpha1 的清理 / 校验 / 导出 / 灾备先按「每行都有 DDS」的旧不变量实现，alpha2 再按 §3.H
「主要改动面」逐处返工。

**基线敏感度**：alpha2 各节的行号与验收口径以 **alpha1 落地后的代码**为基线。alpha1 会重排
`app/settings.rs`、`app/workflows.rs`、`lib.rs` 与 `cleanup.rs` 的入口，因此 alpha2 实施前必须按
符号名重新定位一次，并同步更新 §0.3 的定位表。

## 2. 0.3 目标架构

目标不是再增加一层「万能总线」，而是让每个跨边界动作只有一个可测试的执行路径：

```text
Tauri adapter       headless adapter       (future maintenance adapter)
       \                   |                         /
        ---- CommandContext + typed use-case ----
                    |
          OperationCoordinator
   operation id / lock order / cancel / progress / events
                    |
       RepositorySession + domain services
   Library | History/Backup | Authenticity | Pin-board
                    |
       SQLite + chunk files + cleanup ledger
```

约束如下：

1. adapter 只解析 DTO、检查文件选择器授权、装配 context 和映射错误，不包含业务分支。
2. use-case 不依赖 Tauri 类型；所有长操作接收 `OperationContext`（取消、阶段进度、日志、operation
   id、授权能力）。
3. 固定锁序为：跨进程仓库门闩 → coordinator 运行分类 → repository lease → repository operation
   guard → SQLite transaction。只读操作不得取得写锁；锁等待和让位必须可观测。
4. 事件总线不取代事务结果。命令返回最终 DTO，事件只表达 started/progress/finished、仓库变更和
   清理队列变化；UI 丢事件后用 revision 做一次快照补偿。
5. schema 与 ChunkFile 均采用追加兼容：先保留 v1 reader，再以 feature flag/新版本写入，不在 0.3
   直接破坏 0.2 仓库。**0.3 只做一次 schema 迁移**：alpha1 不改 schema，alpha2 的阶段 7 一次完成
   v4 → v5（见 §0.4）。
6. **关闭握手保持专用**，不作为事件总线里的普通事件：它必须保留「请求 → 前端结算 → 确认 → 15 秒
   兜底强退」的确认语义与不可逆 `shutting_down` 状态（rc.2 已实现）。事件总线只承载进度、失效与
   仓库变更通知。
7. **复用既有诊断体系**：事件通道的传输、运行切片（run id）、target 与标签沿用 rc.2 的日志/诊断
   基础设施（`docs/guides/logging.md`），不新建第二套观测通道；诊断模式只影响探针与取证，不改变
   事件语义。
8. **画板条目为多态**：领域层以「`kind` + 按 kind 解释的载荷」表达条目，位图/DDS 只是其中一种；渲染
   按 kind 分发到对应 provider，跨模块旁路（清理、校验、灾备、导出）按 kind 分派，**不假设条目都有
   实体文件**。
9. **事件契约唯一**：`AppEvent` 的枚举、字段与版本在 alpha1 阶段 1 定义并冻结；阶段 3 的前端订阅
   provider 只消费该契约，不另立一套（避免同一通道被定义两次）。

## 3. 改进工作流

每节标注所属批次：`[alpha1]` / `[alpha2]`。

### A. 契约与执行底座（必须最先）`[alpha1]`

准确做法：

- 在 `src-tauri/src/app/` 新增 `command_runtime`/`usecases`，定义 `CommandContext`、
  `RepositorySession`、`OperationId`、`OperationClass`（read、foreground、background）和 typed
  `CommandError { code, kind, message, retryable, operation_id }`。
- `OperationCoordinator` 提供 `run_read`、`run_write`、`run_foreground`、`run_background`；统一
  `spawn_blocking`、运行锁、取消 token、阶段进度、耗时日志和事件发布。
- **本阶段定义并冻结最小 `AppEvent` 契约**（枚举、字段、版本，见 §3.C 的事件清单）。阶段 3 只在
  此契约上补前端订阅与轮询降级，不重新定义事件；避免同一通道做两遍。
- 先迁移 create-artwork、settings、history fork/publish、backup commands 四组高风险入口，再迁移
  cleanup、pin-board 和 authenticity；每次迁移保持 command 名、DTO、用户文案不变。
- 把 `headless.rs` 改成 context 装配器，GUI workflow 也调用同一 use-case；加入「同一输入在两入口
  返回相同结果/错误码/锁分类」的契约测试。
- 按领域提供 `register_commands()` 分组函数或单独 registry 文件，集中注册仍保留，但不再让
  `lib.rs` 维护所有实现细节。

验收：create-artwork 等入口不再出现未经过 coordinator 的写流程；锁序测试覆盖正常、取消、切仓库
和退出；`cargo test --lib`、`cargo check --lib`、`npx tsc --noEmit`、`npm test`、`git diff --check`
通过。

### B. 仓库状态、设置与生命周期 `[alpha1]`

准确做法（在 rc.2 已有的握手与诊断设施上补齐，不另起炉灶）：

- `SettingsService::update(patch, expected_revision)` 成为设置页和托盘唯一写入口，原子写 JSON、
  更新内存快照、唤醒调度器和刷新托盘菜单在同一流程完成；陈旧 revision 返回 `settings_conflict`，
  不静默覆盖。现状是托盘 `set_automatic_backups_paused`（`app/settings.rs`）直接
  `write_json_atomic`，绕过了统一保存路径。
- 在仓库根目录增加 OS 文件锁和 owner metadata（PID、启动时间、应用版本、心跳）。GUI、headless 和
  维护命令打开仓库前都 acquire；冲突返回 `repository_busy`，异常退出只在 owner 已失效且满足 stale
  条件时回收。
- 关闭路径**沿用 rc.2 的握手**（`app_shutdown_requested` / `confirm_app_shutdown` / 15 秒兜底），
  只把「结算失败、participant 超时、等待命令未返回」接入结构化诊断（复用 `[watchdog]` 与
  `[forensic]` 通道），不再新建 LifecycleCoordinator 去替换它。若后续需要冻结新命令，作为握手内部
  的排队规则实现，而不是新的并发层。
- 新增 `AppRuntimeProvider`、`useSettingsController`、`useRepositoryMaintenance`、
  `RuntimeProgressProvider`、`SettingsDialog` 和 `NoticeCenter`，App 只负责路由与注入。

验收：托盘与设置并发保存有 CAS 测试；双进程打开同仓库的冲突、stale owner 和释放可测；仓库切换/
退出期间最后一次素材板结算不丢失；现有 repository-switch 测试保持通过。

### C. 事件总线与模块模板 `[alpha1]`

准确做法：

- **事件契约已在阶段 1 冻结**，本阶段只做消费侧：前端建立一个订阅 provider，controller 通过
  repository key 和 operation id 丢弃旧事件，命令响应仍负责最终状态。事件清单（定义在阶段 1）为
  `OperationStarted`、`OperationProgress`、`OperationFinished`、`RepositoryChanged`、
  `CleanupQueueChanged`；事件带 repository key、operation id、domain、phase、current/total、
  cancellable 和 completion revision。**关闭请求不进事件总线**（见 §2 约束 6）。
- 复用诊断体系的传输与切片：事件经统一 provider 分发，落到日志时沿用 `run id`/`target`/标签，避免
  与 `log_frontend_diagnostics` 并行两套通道。
- 轮询保留为丢事件/启动恢复的 3 秒兜底，稳定后去掉 350 ms 高频轮询（当前在 `App.tsx` 的备份态
  轮询与 `useHistoryController.ts` 的递归轮询）。
- 统一模块目录契约：`types.ts`（边界 DTO）、`api.ts`（typed command adapter）、
  `use*Controller.ts`（竞态/请求代次/错误/忙状态）、`Module.tsx`（视图）。抽出 `useRequestEpoch`、
  `useAsyncOperation` 和 `useRuntimeSubscription` 三个小工具，避免复制各 controller 的 request ref
  和 finally 模式。
- Pin-board 先把生命周期、保存/导入/导出状态迁入 controller；WebGPU renderer 仍是纯渲染器，Channel
  只承载大 payload，状态变化走统一事件。渲染器的设备复用与占位符已由 rc.2 落地，不在本轮改动。

验收：四个领域 controller 使用同一套竞态与错误策略；事件丢失后 revision 补偿；不改变现有 DTO 与
页面功能。

### D. 分块、恢复与完整性算法 `[alpha1]`

准确做法：

- 在 `chunk_file.rs` 把格式头、chunker、hash、compression 抽成策略接口和明确的 `FormatVersion`。
  保留 v1 reader；新增版本先只在实验开关下写入，并记录配置，禁止按机器默认推断格式。
- `ChunkStore` 维护按虚拟偏移排序的 segment 起点和 reader 游标：顺序读命中当前段，跳跃读用二分
  查找；跨段读取一次完成。用深链和大文件 benchmark 比较 p50/p95，超过阈值才启用更复杂的索引结构。
- 把 `CancelToken` 传入 `ChunkFile::create`、reverse delta、payload copy、`resolve_chain`、
  `copy_original`、scrub 和 checkpoint。**检查粒度对齐研究结论**：转码步的取消地板是**每 tile**
  （320 KiB 原始数据，写 ≤12 ms / 恢复 ≤5.4 ms），更细的「每 64–256 KiB」在转码步不可达；廉价的
  框架块（zstd/none）可按块或每若干块检查。统一返回 typed Cancelled；所有临时输出由 guard 清理，
  进度按已处理字节而非只按节点数报告。
- `materialization_chain` 改成一次递归 CTE 返回链节点、父子边和路径，避免深链逐节点 SQL；scrub 按
  链批量解析，必要时使用有界磁盘缓存，避免对同一 delta 反复解压。
- 快速检查基线增加算法版本和 cheap fingerprint（至少 size、mtime、首尾采样；可用时加入 OS
  file-id/change counter）。基线不匹配或时间精度不足必须回退全量；手动提交继续强制全量。
- 在损坏恢复上保持当前语义：先验证 chunk/整文件摘要，再原子发布；把错误分类为缺失、格式、chunk
  摘要、整文件摘要和输出冲突，便于 UI/重试决策。
- **抽出单一容器解析模块**（如 `src-tauri/src/format/`）：负责 `.clip`/`.psd` 的 `detect` 与容器块
  定位，本阶段用它做 tile 对齐分块，阶段 8 用它定位缩略图块。**不在两处各写一份**——研究仓的
  `tools/harness/src/o5.rs` 与 `clip.rs` 只是参考实现，主仓合成为一个模块。

**研究结论（实测回流，2026-10-11）**

`research/compression-optimization/` 已按本节要求完成 P0–P5 的调查与实测（真实仓库
`F:\LilithData\Artworks`，3 作品 / 36 版本 / 6.32 GB），给出可直接落地的 v2 规格：

- **采用集（v2 = v1 + 四项）**：`格式 v2`（版本号 + 策略位 + 每块 `codec/recipe/logical_len`）→
  `O2 容器感知分块`（`.clip` 按 tile 对齐，解析失败一律回退 CDC）→ `快照 tile 级去重` →
  `O5 鲁棒性加固`（两轴错误分类 / 块级隔离 / 每 tile 取消 / 写入开关）。采用顺序
  **格式 v2 → O2 → 去重 → O5**。
- **收益是分层的，不能只看整仓**：整仓 **6.32 → ≈6.17 GB（−2.44%）**，但该数字被两个**物理不可压
  对象**主导（3D 快照占快照 67%、录屏 delta 占 delta 字节 78%）；**图层为主作品**的收益才是量级性的
  ——delta 净降 **18.6%**（含记录）、带 tile 容器单对最高 −47%、快照 tile 流可 −34%~−44%。**主收益
  应表述为「鲁棒性/可回退/版本分派」**，空间收益按文件类型分列，不用整仓平均。
- **O2 是收益主力且免费**：纯图层编辑 delta 净降 **18.6%**（含记录）、分块 CPU **−8%**；无 tile
  容器仅 −5.4%；回退 36/36，CDC 重建与仓库 33/33 一致。
- **O5 已量化到可验收**：80 个注入故障证明内容损坏**块级隔离且可单块修复**（受影响面恒为 1）；帧级
  损坏（`stored_len`/截断）**只保前缀恢复**（16%–96%）、不可隔离；错误分类扩成 `class × dimension`
  两轴；未知能力归 `Incompatible`（能力缺口，非数据损坏）；取消地板 = 每 tile（320 KiB），
  写 ≤12 ms / 恢复 ≤5.4 ms。
- **格式与块记录**：头部带 `version/chunker/hash/codec/adapter`；块记录 36 → 44 B（+8 B/块，本仓
  +1.5 MB，占整仓 0.02%）；`tools/harness/src/o5.rs` 提供 v2 容器读写器与两轴分类的**最小可运行
  样例**，可作为 `chunk_file.rs` 策略接口与读取器分派的参考。
- **明确否决**：`O6 解码域转码`（提交 **+104×** / 恢复 **+42×**，违反研究方案 **§8** 的「CPU ≤2×」
  验收线，且本仓可压上限仅 9.7%）；`O1/O1-lite`、`O3`、`O4`、`O7`（SQLite 页级）；`F3`（改分块
  参数，图层净降仅 −0.99%，未过 5% 门槛）→ **保留默认 `2/16/64 KiB`，不引入配置分支**。
  「图层文件 −1/3」属于已否决的 O6 路，**不作为 0.3 目标**。
- **必做的写入端加固**（尚未落地）：超 `max` 的结构单元**必须 CDC 切分**，否则 3D 大块截断恢复极差；
  `.psd` 适配器当前只 **detect + 回退**（结构待逆向确认）。

> 详细规格见研究仓 `docs/plan.md §3 / §8`，逐项代价见其 `docs/architecture-decisions.md`，整体对比见
> 其 `docs/v1-vs-v2-comparison.md`。研究仓全程**只读**真实数据。

验收：取消延迟按字节规模有上限（每 tile 口径）；深链恢复不再随 segment 数线性退化；v1 仓库可读；
损坏 snapshot/delta 不生成半成品且可重试；新增 benchmark 只作为 0.3 决策证据，不替代日常轻量检查。

### E. 调度、清理与灾备算法 `[alpha1]`

准确做法：

- 用 deadline heap 或 SQL `ORDER BY due_at, last_attempt, branch_id` 生成候选，维护唤醒信号；优先级
  固定为前台等待 > 手动提交 > 到期自动备份 > 空闲校验，并用 aging 防止低优先级长期饥饿。取得锁后
  继续做资格复查。
- 每个任务拥有独立 `OperationId` 与 cancellation token；取消/让位只作用于目标后台任务，不再依赖单一
  `cancel_requested` + 多个补丁集合。失败退避按分支记录，不能阻塞其它分支。
- 调度执行仍以 repository writer lease 保证 SQLite 写互斥；只有证据表明跨 Artwork 并行有收益时，
  才引入按 repository/artwork 分片的 worker，先不并行写事务。
- cleanup 建立 snapshot/delta/artifact/board DDS 路径索引或批量临时引用表，使用 anti-join 一次判定
  未引用集合，按 256–1000 条分批、每批可取消且幂等提交。
- **本阶段交付「引用清单 / provider 接口」**：cleanup 只接收通用清理目标或公开清单接口，不再直接
  导入 `pin_board::repository` 的路径常量（当前 `cleanup.rs` 顶部就导入 `is_dds_name`、
  `parse_board_dds_path`、`BOARD_DIRECTORY`）。该接口是 **§3.H 的前置条件**——阶段 7 要按 kind 分派
  清理/校验，只能通过它实现，否则又要把 `pin_board` 导进 cleanup。
- 灾备复制阶段边复制边计算 digest；manifest 校验复用已取得摘要，最终发布前保留一次抽样或全量可配置
  复核。外部文件变化继续以复制前后 metadata 复核拒绝。

验收：多分支到期任务不因一支失败固定停 60 秒；前台等待可观测且不会被后台抢锁；清理查询次数和大规模
孤儿耗时有基准；灾备 I/O 次数下降且校验语义不弱于 0.2；cleanup 不再导入 `pin_board` 的路径布局常量。

### G. 仓储/备份设置分离与仓储空间状态 UI `[alpha2]`

准确做法：

- **动机**：设置弹窗现有「仓库与备份」页把「仓库与数据安全」（仓库位置、完整性扫描、创建备份）、
  「自动备份」（调度与检查方式）和「文件清理」混在一页，而「仓储」（本地数据资产本身）与「备份」
  （灾备与调度）是两类不同心智模型；同时仓库占用、压缩比、分类占比等信息目前只在历史页按节点零散
  可见（`history_nodes.chunk_file_size`），没有仓库级视图，用户无法回答「仓库有多大、哪些作品/哪类
  文件占了多少、压缩效果如何」。本项把设置页按「仓储 / 备份」拆分，并为仓储补一个**只读空间状态
  仪表盘**。
- **设置信息架构拆分**（只重组导航与视图，不改写入路径与语义）：仓储页保留仓库位置、仓库完整性
  扫描、文件清理（队列 / 未引用扫描）并新增仓储空间状态；备份页承载自动备份调度与默认检查方式、
  创建备份（整仓灾备）与最近一次结果。写入仍全部经 §3.B 的 `SettingsService::update`；命令名、DTO、
  用户文案不变（呼应 §3.A「适配器只做装配」）；托盘刷新、仓库切换与 `AppState` lease 语义不变。
- **空间状态 UI 形态（推荐：仓储域内单开一栏，不塞进设置页的一节）**：这是信息密度高、含图表与明细
  钻取的界面，放进设置弹窗的单列页会挤占配置项，且它本质是「仓库仪表盘」而非配置项。推荐在仓储域内
  提供**「设置 / 空间」两个视图**（页内 tab，或左侧导航新增「仓储空间」项），与仓库位置 / 完整性
  同属仓储；**不推荐**独立顶层窗口——0.3 不引入新的窗口生命周期与跨窗口状态。
- **只读聚合命令**（新增，如 `get_repository_storage_overview`）：从 SQLite 聚合，走共享读租约、不取
  运行锁、不写 `last_attempt_ms`，与 `list_pending_file_cleanup` 同类。口径：
  - 总量与分类占比：`history_nodes.chunk_file_size`（snapshot / delta 存储字节）、
    `history_edges.delta_size`、`final_artifacts.byte_size`、`certification_records.output_bytes`，
    按文件类别（snapshot / delta / final artifact / board DDS / certification output / 其它）分列。
  - 按 artwork 占比：以 `artwork_id` 汇总上述各项，得到每个作品的总占用与占比；`library_nodes` 的
    分组树用于把作品归到分组。
  - 压缩比：节点级 `Σ logical_size / Σ chunk_file_size`（原始 vs 存储）；delta 的目标逻辑大小取自
    delta 头声明（§3.D 引入 `FormatVersion` 后为精确值，v1 数据用头声明 / `history_edges` 口径）。
  - 明细钻取：artwork → 分支 → 节点，逐行显示 `logical_size`、`chunk_file_size`、`chunk_count`、
    压缩比与是否 checkpoint / snapshot；画板 DDS 与认证输出按类别展开。
- **磁盘真实占用 vs DB 记录口径**：画板 DDS 与认证输出的大小不在 DB 大小列中，需一次受控的文件系统
  扫描（复用 §3.E 的 `scan_unreferenced` 遍历模式）才能得到磁盘实际值。仪表盘同时呈现「DB 记录
  大小」与「磁盘实际大小」两套口径；扫描未触发或不可用时降级为 DB 口径并明确标注。
- **与既有能力的关系**：只读命令经 §3.A 的 `CommandContext` / `OperationCoordinator`（只读分类）；
  扫描耗时需进度时复用 §3.C 的事件通道。
- **分类口径必须与 kind 解耦**：DDS 分类按「**该条目是否存在实体文件**」判定（即 `file_path` 非空），
  **不按 kind 枚举**。这样 §3.H 引入文字等无实体文件的 kind 后，本项无需改动（它们的 `file_path`
  为空，自然不计入 DDS 分类），也就保住了「阶段 6 排在阶段 7 之前」的安排（见 §0.4）。

**关键取舍**

- **聚合权威口径**：以 SQLite 记录为权威（快、稳定），磁盘扫描作为可选补充（准、需遍历）；两者差异
  本身就是有用信号（DB 记录 vs 实际磁盘），不做静默合并。
- **是否持久化缓存**：不持久化、按需重算（避免为缓存新增 schema 与失效逻辑）；大仓库若需更快，先做
  查询次数 / 耗时基准再决定是否加内存缓存，**不新增表**。
- **是否进入统一事件 / 轮询体系**：单次读取即可返回时同步返回；含磁盘扫描时作为可取消长任务，复用
  统一进度通道与取消 token。

**约束与验收**

- **只读、不改仓库、不新增窗口**；不新增 schema 迁移（与 §3.H / §3.F 的 v4 → v5 迁移无关）。
- 拆分后设置保存、仓库切换、托盘刷新与既有测试语义不变；仓储页原有的完整性扫描、文件清理、创建
  备份入口不丢失（创建备份归入备份页）。
- 数值正确性：空仓库 / 单作品 / 多作品下总量与占比正确；分类占比之和等于总量（含「其它」兜底）；
  压缩比与 `history_nodes` 记录一致；删除 / 精简后统计随之更新。
- 大仓库聚合有基准（查询次数与耗时），不阻塞 UI；扫描路径可取消。
- `v1`–`v4` 仓库可读；未配置仓库时仪表盘显示空态而非报错。

### H. 画板条目模型泛化（多态 item）与原生文字 `[alpha2]`

准确做法：

- **动机**：现状把画板条目**硬编码为「一张 DDS 位图」**——`pin_board_images.file_path` 是实体文件、
  `read_texture` 读 DDS、`PinBoardImage` DTO 只有像素宽高、清理/校验/导出/灾备全部围绕 DDS 文件。
  这使画板只能承载位图：文字被迫先栅格化成 PNG → BC7 DDS（`PinBoardModule.tsx` 的 `renderTextImage`），
  于是**放大即放大位图 → 发糊**，位置也由栅格化时的 `padding`/`measureText` 决定而随缩放漂移。
  目标是把条目模型泛化为**多态 item**：每个条目带 `kind` 与按 kind 解释的载荷，**位图退化为其中一种
  kind**；文字为首个非位图 kind，后续可扩展笔迹（stroke）等，使画板真正成为「画板」。
- **为什么列入 0.3（而非顺手加功能）**：这是一次横切**存储模型 + 渲染分发 + 全部旁路**的改造，牵动
  schema 迁移、命令面/DTO、渲染器分发与清理/校验/导出/灾备，属于架构底座。
- **分层设计**：
  - **存储层**：条目表区分「公共定位/变换」与「按 kind 的载荷」。位图载荷 = DDS 路径 + 像素尺寸；
    文字载荷 = `text`/`font_size`/`color`/`font_family`/`align`。
  - **渲染层**：渲染器按 `kind` 分发到对应 provider——位图 = 读 DDS；文字 = 前端按需栅格化。
    四边形 `points/uv`、命中判定、图层、step 历史**保持不变**（它们只依赖变换与包围盒，与 kind 无关）。
  - **旁路层**：清理、DDS 校验、导出、灾备**按 kind 分派**；无实体文件的 kind 不进入路径清单。
    分派通过 §3.E 交付的引用清单 provider 接口完成，**不把 `pin_board` 导入 cleanup**。
- **渲染路径（推荐：前端按需栅格化，复用既有纹理通道）**：文字 provider 用 2D canvas 按**请求长边
  `maxDimension`**（`texturePolicy` 已按视口缩放算出）重绘 → `ImageBitmap` → `copyExternalImageToTexture`
  上传为 `rgba8unorm` 纹理。既有两级缓存与「按 `maxDimension` 请求」机制**天然复用**：放大触发更高
  `maxDimension` → 重新栅格化 → 清晰，无需为文字新建缓存；纹理负载仍走既有 RGBA 分支（`isRgbaPayload`）。
- **为什么不由 Rust 栅格化**：需要内置 CJK 字体、文本整形与度量一致性，成本远高于前端；而前端已有
  canvas 度量与系统字体，**WebView2 的字体即最终显示字体**，度量与显示天然一致。Rust 端只负责存储与
  （导出时的）编码。
- **定位准确性**：文字项不再依赖栅格化 `padding` 决定视觉位置，改用「度量 → 四边形」映射；缩放只改
  视口变换，文字随四边形精确缩放，消除旧方案「缩放后偏移」。

**关键取舍**

- **表结构选型**：`pin_board_images` 宽表增列（列随 kind 增长、含大量 NULL）vs **公共表 + 按 kind 子表**
  （如 `pin_board_texts`，继承式）。倾向后者：新增 kind 只加子表、不污染公共表；代价是查询多一次 join。
- **命令面/DTO**：`PinBoardImage` 变为带 `kind` 的联合类型；导入/粘贴仍产生位图 kind；新增按 kind 的
  创建命令（如 `create_pin_board_text`），文字项不再走图片导入链路。
- **step 历史是否承载载荷**：`pin_board_history.transform_json` 现只存变换。文字创建后改字会改**载荷**
  而非仅变换——若要支持「改字/改色/改字号」的撤销/重做，历史需能存 kind 载荷（或引用载荷版本）。
  该决定直接决定「是否支持创建后编辑」，是本节最重要的未决项。

**主要改动面（打破「每个条目都有 DDS」不变量）**

非位图条目没有实体文件，会触碰若干假设「每行 `pin_board_images` 都有 DDS 路径」的既有路径，需逐处
按 kind 分派：

| 位置                                                                                                       | 现状假设                                 | 多态条目下的处理                                  |
| -------------------------------------------------------------------------------------------------------- | ------------------------------------ | ----------------------------------------- |
| `cleanup::scan_unreferenced` / `referenced_path_kind`；`library/schema.rs` 的路径 UNION（含 `pin_board_images.file_path`） | 每行有 `file_path`，参与引用判定与孤儿扫描           | 非位图 kind 无 `file_path`，**不进入路径清单**，避免被判为「缺失文件」 |
| `cleanup::scrub_board_dds`                                                                               | 逐条 `pin_board_images` 记录校验 DDS 存在/归属/解码 | 只校验位图 kind，跳过其余                              |
| `read_texture`（`pin_board/repository.rs`）                                                                 | 读取 DDS，超请求长边时解码缩放为 RGBA 预览           | 按 kind 分派：位图读 DDS，文字返回「无 DDS」信号交前端栅格化       |
| `read_image_png` / `export_images`（`pin_board/repository.rs`）                                              | 解码 DDS → PNG / 写盘                    | 按 kind 分派：文字需**重新栅格化**为 RGBA 后再编码（前端渲染 → 交 Rust 编码） |
| 灾备 / 恢复                                                                                                   | 递归复制 DDS 文件 + manifest 逐文件清单          | 非位图 kind 随 SQLite 走，**无需路径覆盖**，灾备天然覆盖      |

**schema 与兼容**

- 这是 **pin-board 表自 v2 引入以来的首次 schema 变更**（当前 `SCHEMA_VERSION = 4`）。按 §2 约束 5 做
  **追加兼容迁移**（v4 → v5）；旧仓库可读，旧行 `kind` 默认 0（位图）。
- **本阶段（阶段 7）拥有 0.3 唯一一次 v4 → v5 迁移**：同一次迁移里补齐 pin-board 的多态列与
  `history_nodes` 的缩略图列（后者供阶段 8 消费），避免连续两次迁移（见 §0.4）。

**约束与验收**

- 非位图条目**不落 DDS**、不进入 `pending_file_cleanup` 与孤儿扫描；无实体文件变化。
- 栅格化**有界、可取消**：单张文字纹理受既有 `PIN_BOARD_NATIVE_TEXTURE_LIMIT` 与上传预算约束；缩放
  触发的重绘需**去抖**，避免连续缩放抖动反复栅格化。
- **字体一致性**：固定字体族（沿用 `Microsoft YaHei UI` / `Segoe UI` 并兜底），创建时把度量结果
  （宽高）持久化；跨机字体缺失只影响显示度量，不改四边形尺寸。
- 验收：位图行为**不回退**（现有画板功能、清理、灾备、导出语义不变）；文字放大到 400% 边缘清晰；
  文字与位图在同一缩放下定位偏差 ≤ 1px；导出 PNG 含正确文字；`v1`–`v4` 仓库可读；
  `scan_unreferenced` / `scrub_board_dds` 不把非位图条目当作缺失文件；`npm run test:pin-board` 与
  `cargo test pin_board --lib` 覆盖 kind 分派与迁移；**新增 kind 只需实现 provider，不改核心几何/缓存**。
- **不在本项承诺**：具体新增 kind 的交互（笔迹工具等）不在 0.3 落地，0.3 只落地多态模型 + 文字这一种
  kind；创建后编辑文字取决于上文「step 历史是否承载载荷」的决定，未决前不作承诺。

### F. 节点缩略图（提交时生成，免 restore 预览）`[alpha2]`

准确做法：

- **动机**：查看某个历史节点（尤其 `.clip`/`.psd` 这类分层工作文件）的内容，目前只能 `restore`
  出完整文件再用外部应用打开，代价高且打断浏览。
- **做法**：在**创建节点时**顺带抽取一份缩略图随节点保存。提交/自动备份的 worker 本来就要打开并
  流式读取工作文件（`backup/worker.rs`、§3.D），此刻抽取缩略图的边际成本最低；历史页直接显示
  缩略图，无需 restore。
- **依赖**：本阶段消费阶段 7 建立的 `history_nodes.thumbnail` 列（**不另开迁移**）与阶段 4 落地的
  容器解析模块（**不重复实现**），并由阶段 1 的提交 use-case 调用。这三条是 §4 依赖表里阶段 8 的
  真实前置，而不是「依赖 ChunkFile 格式 v2」。
- **关键取舍**：缩略图按**节点**存储、与链位置无关，因此查看时**不需要**对 delta 链做惰性区间读，
  避免把 §3.D 的 `ChunkStore` 区间读取复杂度引入 UI 路径。代价是存量节点没有缩略图（见下）。
- **归属**：抽取属「工作文件格式」能力，放在独立模块（如 `src-tauri/src/preview/`），由提交
  use-case 调用并把结果交给 history/backup 存储；backup 领域不硬依赖具体格式（呼应 §1「领域互不
  导入」）。格式检测复用阶段 4 的容器解析模块，不重复实现。
- **界面**：缩略图只读、按需加载。**选中节点时在右侧详情区显示**（时间轴模式左侧已是既有的时间轴
  列，见「历史图前端布局」，右侧留作节点详情），未选中或格式无预览时显示占位；节点卡片不内嵌大图。

**各格式来源（先按资料，落实前实测）**

| 格式                                              | 缩略图来源                                                                                                       | 备注                                                                                                                                                                                                                              |
| ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `.clip`                                         | CSFC 容器内嵌 SQLite（`SQLi` 块）的 `CanvasPreview` 表，存画布 PNG                                                       | 复用阶段 4 容器解析模块定位 `SQLi` 块（研究仓 `tools/harness/src/clip.rs` 的 `parse_csfc`/`walk_tiles` 为参考）；该 PNG 使用非标准 filter 字节（`kunohami/clip-studio-thumbnailer` 记录 ImageMagick 拒收、需 ffmpeg），`image` crate 解码需容错或回退 |
| `.psd` / `.psb`                                 | 优先 Image Resources 段的缩略图资源（ID 1036 = PS 5.0+，28 B 头 + JFIF/JPEG；ID 1033 = PS 4.0）；取不到时退回 Image Data 段的合并合成图 | 合成图只需按段长跳过 Layer and Mask 段，**不必解码图层**；compression 0 raw / 1 RLE / 2 ZIP / 3 ZIP+prediction；PSB 多处长度字段为 8 B（PSD 为 4 B）。§3.D 已记录 `.psd` 适配器当前只 detect + 回退、结构待逆向确认                                                               |
| 位图（png/jpg/webp/tiff/bmp/gif）                   | 直接解码并缩放                                                                                                     | 复用现有 `image` crate（`src-tauri/Cargo.toml` 已启用这些 feature）                                                                                                                                                                        |
| 其它分层（`.kra`/`.ora` = ZIP 内 `mergedimage.png` 等） | 可选                                                                                                          | 后续再加，不在 0.3 承诺                                                                                                                                                                                                                  |
| 未识别 / 解析失败                                      | 无                                                                                                           | UI 显示占位；**绝不因此让提交失败**                                                                                                                                                                                                           |

**存储（随节点：`history_nodes` 追加 BLOB 列）**

- 硬约束：缩略图**不得写进 ChunkFile 内容**。`history_nodes.sha256` 是工作文件内容的摘要，scrub 与
  恢复都以它为准；把缩略图塞进 snapshot 会破坏摘要语义。因此缩略图是**派生旁路产物**，随节点行存在
  数据库中，不参与完整性校验与恢复。
- 已定：内容小，**不单开文件或表**。在 `history_nodes` 追加 `thumbnail`（BLOB）与 `thumbnail_version`
  （尺寸/编码版本）列，由**阶段 7 的 v4 → v5 迁移**一并建立（见 §0.4），旧仓库可读，旧节点该列为空
  → 显示占位。
- 随之简化：删除节点/分支、精简、检查点替换时缩略图**随行删除**，不进入 `pending_file_cleanup`，也
  不需要 `scan_unreferenced` 路径模式与灾备路径覆盖；整仓备份的 SQLite 副本天然包含缩略图。
- 读取按需：图/列表读取必须使用**显式列名**、不得带出 BLOB；新增只读命令（如
  `get_history_node_thumbnail`）在选中节点时单独拉取。缩略图损坏或解码失败只影响该节点预览，不影响
  图读取与其它节点。

**约束与验收**

- 抽取**有界、可取消、只读**工作文件头部区域；任何失败只跳过缩略图，不影响提交结果与摘要；缩略图带
  自身版本号，可安全重建。缩略图固定最大边长与编码（如 ≤512 px，WebP/PNG）。
- 内容未变化的快速检查路径不打开工作文件，沿用 head 已有缩略图；**存量节点不回填**（0.3 不做链上
  惰性抽取）。创建分支不新建节点（`app/workflows.rs` 的 `fork_artwork_branch` 只固化检查点），分支
  起点沿用原节点缩略图。
- 验收：`.clip`/`.psd`/位图提交后历史页可预览；损坏或未知格式回退为占位且提交成功；删除节点后缩略图
  按清理语义回收；灾备副本保留或可重建缩略图。

  门闩，并把实测写入 `docs/user/stress-test-report.md`。

**alpha1 完成条件**：GUI/headless 共享 use-case；所有仓库写入口经过 coordinator；反向依赖清零
（cleanup 不再导入 `pin_board`，灾备核心不再直接导入 library/authenticity）；设置 CAS 和跨进程冲突
有测试；事件丢失可由 revision 恢复；取消响应有明确上限（每 tile）；深链恢复和清理查询不出现已知的
线性退化；快速检查不再只依赖 size+mtime；v1 数据可读且新格式可回退；灾备完整性断言不减弱。
（压缩侧采用集已实测 CPU 无回退、内容损坏块级隔离、往返逐字节一致，见 §3.D。）

**alpha2 完成条件**：画板条目为多态（位图/DDS 仅一种 kind），清理/校验/灾备/导出按 kind 分派且不
假设实体文件；仓储空间仪表盘数值正确且不阻塞 UI；`.clip`/`.psd`/位图提交后历史页可预览；`v1`–`v4`
仓库可读，`v5` 由一次迁移产生；新增 kind 只需实现 provider，不改核心几何/缓存/旁路。

## 6. 非目标与待决策

- 不重写领域业务规则，不把所有函数强行放进通用插件系统，不为事件总线引入外部消息中间件。
- 0.3 不为画板一次性实现所有 kind 的交互（笔迹工具等）；本阶段只落地**多态条目模型 + 文字**这一种非
  位图 kind，以验证「新增 kind 只需实现 provider、不改核心几何/缓存/旁路」这一可扩展性目标。
- **压缩侧方向已定**（§3.D「研究结论」）：`O2 容器感知分块采用`、`O6 不采用`、`hash 不变`
  （O4 否决）、分块参数保持默认 `2/16/64 KiB`、快照 tile 级去重采用。阶段 4 在真实写入端复核并实现，
  仍只在实验开关下写 v2，不自动迁移已有文件。
- **仓储空间状态只读**（§3.G）：只做只读聚合与设置信息架构拆分，不引入独立顶层窗口、不持久化统计
  缓存、不新增 schema；DDS 分类按「是否有实体文件」判定，不按 kind 枚举。
- **缩略图存储位置已定**（§3.F）：随节点存于 `history_nodes.thumbnail`（BLOB）+ `thumbnail_version`，
