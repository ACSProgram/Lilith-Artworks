## 1. 批次划分与依赖顺序

划分原则：**底座先于功能**（契约、算法、数据模型先落地，功能只在其上叠加）；**同一 schema 迁移
只做一次**（schema 是全局基线，重复迁移会让每一批都要重跑一遍兼容验证）。

| 批次 | 阶段 | 范围 | schema | 交付判据 |
| --- | --- | --- | --- | --- |
| alpha1（已完成） | 1–5 | 命令运行时、设置与 owner lock、事件通道与 controller 模板、分块/恢复/完整性算法、调度/清理/灾备算法 | 不变，保持 v4；清理用连接内临时表 | 契约与行为见 `docs/architecture/overview.md`、`docs/modules/` 与 `CHANGELOG.md` |
| alpha2 | 6 + alpha1 测试与修复 | 仓储/备份设置分离与仓储空间状态 UI；补齐 alpha1 的回归测试与修复 | 不变，保持 v4 | 只读仪表盘数值正确且不阻塞 UI；设置拆分不回归；alpha1 完成条件全部通过 |
| alpha3 | 7–9 | 画板条目多态、节点缩略图、空闲链路校验 | 一次 v4 → v5 | 画板条目为多态；历史页免 restore 预览；链路校验按空闲时机做全链恢复校对 |

依赖顺序与边界：

- **阶段 6 排在画板改造之前**。为使它在阶段 7 之后仍然正确，阶段 6 的 DDS 分类必须按「**该条目
  是否存在实体文件**」（`file_path` 非空）判定，而不是按 kind 枚举；文字等无实体文件的 kind 没有
  位图载荷行，自然不计入 DDS 分类，因此阶段 7 落地后阶段 6 无需改动语义（只需重新定位 SQL）。
- **阶段 7 拥有 0.3 唯一一次 v4 → v5 迁移**，一次补齐 pin-board 的多态列（§2.2）、`history_nodes`
  的缩略图列（§2.3，供阶段 8 消费）与 `branch_notices` 告警表（§2.4，供阶段 9 消费）。阶段 8 只
  **消费**缩略图列，不另开迁移。
- **阶段 9 依赖阶段 5、6 与 7**：调度门控与防饿死 aging 来自阶段 5（已随 alpha1 完成），
  `branch_notices` 表与旧告警读写泛化来自阶段 7，设置页的「备份」页与「N 条链路待校验」入口来自
  阶段 6；与阶段 8 无依赖，可排在 7 之后的任意位置（列入队尾仅为表述顺序）。
- **阶段 6 的依赖是阶段 2、3、5**（均已随 alpha1 完成）：阶段 5 提供清理扫描模式与引用清单接口
  `contracts::ReferenceInventory`，阶段 6 的磁盘扫描与 DDS 分类直接复用它；阶段 7 若重建画板表，
  阶段 6 的聚合 SQL 需按新的 `file_path` 位置重新定位一次。

## 2. 剩余工作

### 2.1 仓储/备份设置分离与仓储空间状态 UI（阶段 6）`[alpha2]`

准确做法：

- **动机**：设置弹窗现有「仓库与备份」页把「仓库与数据安全」（仓库位置、完整性扫描、创建备份）、
  「自动备份」（调度与检查方式）和「文件清理」混在一页，而「仓储」（本地数据资产本身）与「备份」
  （灾备与调度）是两类不同心智模型；同时仓库占用、压缩比、分类占比等信息目前只在历史页按节点零散
  可见（`history_nodes.chunk_file_size`），没有仓库级视图，用户无法回答「仓库有多大、哪些作品/哪类
  文件占了多少、压缩效果如何」。本项把设置页按「仓储 / 备份」拆分，并为仓储补一个**只读空间状态
  仪表盘**。
- **设置信息架构拆分**（只重组导航与视图，不改写入路径与语义）：仓储页保留仓库位置、仓库完整性
  扫描、文件清理（队列 / 未引用扫描）并新增仓储空间状态；备份页承载自动备份调度与默认检查方式、
  创建备份（整仓灾备）与最近一次结果。写入仍全部经 alpha1 已落地的 `SettingsService::update`；
  命令名、DTO、用户文案不变（适配器只做装配）；托盘刷新、仓库切换与 `AppState` lease 语义不变。
- **空间状态 UI 形态（推荐：仓储域内单开一栏，不塞进设置页的一节）**：这是信息密度高、含图表与明细
  钻取的界面，放进设置弹窗的单列页会挤占配置项，且它本质是「仓库仪表盘」而非配置项。推荐在仓储域内
  提供**「设置 / 空间」两个视图**（页内 tab，或左侧导航新增「仓储空间」项），与仓库位置 / 完整性
  同属仓储；**不推荐**独立顶层窗口——0.3 不引入新的窗口生命周期与跨窗口状态。
- **只读聚合命令**（新增，如 `get_repository_storage_overview`）：从 SQLite 聚合，走共享读租约、不取
  运行锁、不写 `last_attempt_ms`，与 `list_pending_file_cleanup` 同类。口径：
  - **总量口径（避免重复计数）**：snapshot 文件字节 = `Σ history_nodes.chunk_file_size WHERE
    snapshot_path IS NOT NULL`；delta 文件字节 = `Σ history_edges.delta_size`（每条边对应一个 delta
    文件）。非 snapshot 节点的 `chunk_file_size` 被写成子边 delta 大小（`STORAGE_METADATA_SET`），
    含义是**该节点的重建读取量**，**不得再加进存储总量**。
  - **完整公式**：`总量 = snapshot 文件 + 全部 delta + 成品输出（final_artifacts，按规范化路径去重）
    + 认证输出（certification_records.output_bytes，按路径去重）+ 画板 DDS（文件系统扫描）
    + 其它（SQLite 主库与 WAL、repository/temp、未识别文件）`。缩略图是 `history_nodes` 的 BLOB，
    已含在 SQLite 主库内，不单列；分类占比之和以该公式为分母，「其它」兜底。
  - 按 artwork 占比：snapshot 与 delta 按 `history_nodes.artwork_id` 汇总；成品、认证与画板按所属
    artwork 归属；无法归属的记录进「其它」并单独列出。`library_nodes` 的分组树用于把作品归到分组。
  - 压缩比**分层报告，不混算整仓平均**：snapshot 用 `Σ logical_size / Σ snapshot 文件字节`；delta
    用 `Σ 父节点 logical_size / Σ history_edges.delta_size`（delta 表示子→父的变化，还原目标是父
    节点；v1 delta 头声明只作交叉核对，alpha1 阶段 4 落地的 `FormatVersion` 提供精确声明后才作为
    独立口径展示）。
  - 明细钻取：artwork → 分支 → 节点，逐行显示 `logical_size`、`chunk_file_size`（在 snapshot 行
    标注为快照文件大小，在 delta 行标注为重建读取量）、`chunk_count`、压缩比与是否 checkpoint /
    snapshot；画板 DDS 与认证输出按类别展开。
- **磁盘真实占用 vs DB 记录口径**：画板 DDS 与认证输出的大小不在 DB 大小列中，需一次受控的文件系统
  扫描（复用 alpha1 阶段 5 落地的 `scan_unreferenced` 遍历模式）才能得到磁盘实际值。SQLite 主库与
  WAL 的大小也只能从文件系统取得（缩略图 BLOB 已含在主库内，不二次相加）。仪表盘同时呈现「DB 记录
  大小」与「磁盘实际大小」两套口径；扫描未触发或不可用时降级为 DB 口径并明确标注。
- **与既有能力的关系**：只读命令经 alpha1 已落地的 `CommandContext` / `OperationCoordinator`（只读
  分类）；扫描耗时需进度时复用 alpha1 已落地的事件通道。
- **分类口径必须与 kind 解耦**：DDS 分类按「**该条目是否存在实体文件**」判定（即 `file_path` 非空），
  **不按 kind 枚举**。阶段 6 查询 `pin_board_images.file_path`；阶段 7 重建后同一判定改为 join
  `pin_board_bitmaps`（见 §1），只是 SQL 重新定位，口径不变。这样 §2.2 引入文字等无实体文件的
  kind 后，本项无需改语义（它们没有位图载荷行，自然不计入 DDS 分类），也就保住了「阶段 6 排在
  阶段 7 之前」的安排。

**关键取舍**

- **聚合权威口径**：以 SQLite 记录为权威（快、稳定），磁盘扫描作为可选补充（准、需遍历）；两者差异
  本身就是有用信号（DB 记录 vs 实际磁盘），不做静默合并。
- **是否持久化缓存**：不持久化、按需重算（避免为缓存新增 schema 与失效逻辑）；大仓库若需更快，先做
  查询次数 / 耗时基准再决定是否加内存缓存，**不新增表**。
- **是否进入统一事件 / 轮询体系**：单次读取即可返回时同步返回；含磁盘扫描时作为可取消长任务，复用
  统一进度通道与取消 token。

**约束与验收**

- **只读、不改仓库、不新增窗口**；不新增 schema 迁移（与 §2.2 / §2.3 的 v4 → v5 迁移无关）。
- 拆分后设置保存、仓库切换、托盘刷新与既有测试语义不变；仓储页原有的完整性扫描、文件清理、创建
  备份入口不丢失（创建备份归入备份页）。
- 数值正确性：空仓库 / 单作品 / 多作品下总量与占比正确；分类占比之和等于总量（含「其它」兜底）；
  压缩比与 `history_nodes` 记录一致；删除 / 精简后统计随之更新。
- 大仓库聚合有基准（查询次数与耗时），不阻塞 UI；扫描路径可取消。
- `v1`–`v4` 仓库可读；未配置仓库时仪表盘显示空态而非报错。

### 2.2 画板条目模型泛化（多态 item）与原生文字（阶段 7）`[alpha3]`

准确做法：

- **动机**：现状把画板条目**硬编码为「一张 DDS 位图」**——`pin_board_images.file_path` 是实体文件、
  `read_texture` 读 DDS、`PinBoardImage` DTO 只有像素宽高、清理/校验/导出/灾备全部围绕 DDS 文件。
  这使画板只能承载位图：文字被迫先栅格化成 PNG → BC7 DDS（`PinBoardModule.tsx` 的 `renderTextImage`），
  于是**放大即放大位图 → 发糊**，位置也由栅格化时的 `padding`/`measureText` 决定而随缩放漂移。
  目标是把条目模型泛化为**多态 item**：每个条目带 `kind` 与按 kind 解释的载荷，**位图退化为其中一种
  kind**；文字为首个非位图 kind，后续可扩展笔迹（stroke）等，使画板真正成为「画板」。
- **为什么列入 0.3（而非顺手加功能）**：这是一次横切**存储模型 + 渲染分发 + 全部旁路**的改造，牵动
  schema 迁移、命令面/DTO、渲染器分发与清理/校验/导出/灾备，属于架构底座。
- **分层设计**：
  - **存储层**：**公共条目表 + 按 kind 载荷子表**（已定，见「关键取舍」）。`pin_board_items` 只保留
    与 kind 无关的公共列（`id`、`board_id`、`kind`、`created_ms`）；位置/图层/排序/变换仍按现状存于
    `pin_board_history` 的 step 行，不复制到条目表。位图载荷表 `pin_board_bitmaps`（`item_id` 主键 +
    `file_path`/`width`/`height`）；文字载荷表 `pin_board_texts`（`item_id` 主键 + `text`/`font_family`/
    `font_size`/`color`/`align`/`measured_width`/`measured_height`）。新增 kind 只加子表。
  - **渲染层**：渲染器按 `kind` 分发到对应 provider——位图 = 读 DDS；文字 = 前端按需栅格化。
    四边形 `points/uv`、命中判定、图层、step 历史**保持不变**（它们只依赖变换与包围盒，与 kind 无关）。
  - **旁路层**：清理、DDS 校验、导出、灾备**按 kind 分派**；无实体文件的 kind 不进入路径清单。
    分派通过 alpha1 阶段 5 交付的引用清单 provider 接口（`contracts::ReferenceInventory`）完成，
    **不把 `pin_board` 导入 cleanup**。
- **渲染路径（推荐：前端按需栅格化，复用既有纹理通道）**：文字 provider 用 2D canvas 按**请求长边
  `maxDimension`**（`texturePolicy` 已按视口缩放算出）重绘 → `ImageBitmap` → `copyExternalImageToTexture`
  上传为 `rgba8unorm` 纹理。既有两级缓存与「按 `maxDimension` 请求」机制**天然复用**：放大触发更高
  `maxDimension` → 重新栅格化 → 清晰，无需为文字新建缓存；纹理负载仍走既有 RGBA 分支（`isRgbaPayload`）。
- **为什么不由 Rust 栅格化**：需要内置 CJK 字体、文本整形与度量一致性，成本远高于前端；而前端已有
  canvas 度量与系统字体，**WebView2 的字体即最终显示字体**，度量与显示天然一致。Rust 端只负责存储与
  （导出时的）编码。
- **定位准确性**：文字项不再依赖栅格化 `padding` 决定视觉位置，改用「度量 → 四边形」映射；缩放只改
  视口变换，文字随四边形精确缩放，消除旧方案「缩放后偏移」。

**关键取舍**

- **表结构选型（已定）**：采用**公共表 + 按 kind 子表**（`pin_board_items` + `pin_board_bitmaps` /
  `pin_board_texts`），不采用 `pin_board_images` 宽表增列。理由：新增 kind 只加子表，公共表不积累
  NULL 列；代价是读取多一次 join，位图列表按 kind 过滤后 join 载荷表即可。`pin_board_history` 的外键
  从 `image_id → pin_board_images` 改为 `item_id → pin_board_items(id) ON DELETE CASCADE`，历史仍只
  记录变换/位置，不承担载荷。
- **命令面/DTO**：`PinBoardImage` 变为带 `kind` 的联合类型（可顺势更名为 `PinBoardItem`；前后端在同
  一提交内切换，不保留长期并存的两套 DTO）；导入/粘贴仍产生位图 kind；新增按 kind 的创建命令（如
  `create_pin_board_text`），文字项不再走图片导入链路。
- **step 历史是否承载载荷（0.3 决定：不承载）**：0.3 只支持创建、删除、移动、图层与排序；**不支持
  创建后改字/改色/改字号**，因此 `pin_board_history.transform_json` 保持纯变换语义。这样文字载荷只有
  一个当前版本，无需为撤销/重做引入载荷快照。后续若要支持编辑，按「载荷版本表 + step 引用版本」扩展，
  不改本阶段已定的公共表/子表边界；该扩展不在 0.3 承诺。

**主要改动面（打破「每个条目都有 DDS」不变量）**

非位图条目没有实体文件，会触碰若干假设「每行 `pin_board_images` 都有 DDS 路径」的既有路径，需逐处
按 kind 分派：

| 位置 | 现状假设 | 多态条目下的处理 |
| --- | --- | --- |
| `cleanup::scan_unreferenced` / `referenced_path_kind`；`library/schema.rs` 的路径 UNION（含 `pin_board_images.file_path`） | 每行有 `file_path`，参与引用判定与孤儿扫描 | 非位图 kind 无 `file_path`，**不进入路径清单**，避免被判为「缺失文件」 |
| `cleanup::scrub_board_dds` | 逐条 `pin_board_images` 记录校验 DDS 存在/归属/解码 | 只校验位图 kind，跳过其余 |
| `read_texture`（`pin_board/repository.rs`） | 读取 DDS，超请求长边时解码缩放为 RGBA 预览 | 按 kind 分派：位图读 DDS，文字返回「无 DDS」信号交前端栅格化 |
| `read_image_png` / `export_images`（`pin_board/repository.rs`） | 解码 DDS → PNG / 写盘 | 按 kind 分派：位图读 DDS；文字由前端按导出分辨率栅格化为 RGBA，经专用命令交 Rust 编码 PNG |
| 灾备 / 恢复 | 递归复制 DDS 文件 + manifest 逐文件清单 | 非位图 kind 随 SQLite 走，**无需路径覆盖**，灾备天然覆盖 |

**文字导出链路（落实口径）**

- 新增一次性写盘命令（如 `write_pin_board_item_rgba`）：入参为导出目录中已授权的目标路径、像素宽高与
  RGBA 缓冲；Rust 用现有 `image` crate 编码 PNG 并原子发布，不读 DDS。授权与路径校验复用既有导出
  目录授权（2026-10-16 安全批次已落地），不新开通道。
- 前端按导出倍率（目标长边由导出设置决定）用与屏幕显示**同一套字体度量函数**在 `OffscreenCanvas`
  上绘制，保证屏幕与导出定位一致；单张 RGBA 载荷设上限（如 64 MiB，超限则该条目报错而非降采样），
  批量导出逐条处理，避免一次 IPC 传多张大图。
- `read_image_png`（预览）对文字 kind 直接返回「无位图」信号，由前端画布渲染；只有显式导出才走上述
  写盘命令。

**schema 与兼容**

- 这是 **pin-board 表自 v2 引入以来的首次 schema 变更**（当前 `SCHEMA_VERSION = 4`）。按 §1 的 schema
  边界做**向前兼容的 v4 → v5 表重建 + 回填**（不是 append-only）：旧仓库可读，旧 `pin_board_images`
  行迁移为 `kind = 0`（位图）的条目，`pin_board_history.image_id` 迁移为 `item_id`。
- **本阶段（阶段 7）拥有 0.3 唯一一次 v4 → v5 迁移**，在一个事务内完成全部持久 schema 变更：
  1. 建 `pin_board_items`、`pin_board_bitmaps`、`pin_board_texts`，按上文字段定义；三表均以
     `board_id`/`item_id` 级联删除。
  2. 把 `pin_board_images` 复制为 `pin_board_items(kind = 0)` 与 `pin_board_bitmaps`；
     重建 `pin_board_history` 指向 `pin_board_items`，保留全部 step 行。
  3. 删除旧表并重建索引（`pin_board_items(board_id, id)`、位图/文字子表按 `item_id` 主键、
     `pin_board_history(board_id, item_id, step)`）。
  4. `history_nodes` 追加 `thumbnail`（BLOB）与 `thumbnail_version`（整数）列，供阶段 8 消费。
  5. 建 `branch_notices` 并把 `branches.backup_disable_notice_pending = 1` 的行迁移为
     `kind = 'backupDisabled'` 通知，随后删除旧列（单一机制，见 §2.4）。
  6. 建路径索引（`stored_path`/`snapshot_path`/`delta_path`/`output_path`），供 cleanup 使用。
  7. `repository_meta.schema_version = '5'`。
- **重建方式**：SQLite 的表重建需在 `PRAGMA foreign_keys = OFF` 下进行（事务外切换），提交后先
  `PRAGMA foreign_key_check` 再恢复 `ON`；任一步失败整笔回滚，不留下半迁移仓库。新仓库的
  `create()` 直接建 v5 结构；**v1 → v2 迁移用的建表 SQL 必须冻结为 v2 旧形状**，不能复用更新后的
  建表常量，否则 v1 仓库会在 v2 步骤建出 v5 表、随后 v5 步骤无法重建。
- 迁移测试覆盖：v1/v2/v3/v4 仓库各升级到 v5 后数据与 step 历史完整、外键与级联删除正确、旧备份
  告警迁移后行为不变、失败注入时整笔回滚；新仓库从 v5 直接创建。

**约束与验收**

- 非位图条目**不落 DDS**、不进入 `pending_file_cleanup` 与孤儿扫描；无实体文件变化。
- 栅格化**有界、可取消**：单张文字纹理受既有 `PIN_BOARD_NATIVE_TEXTURE_LIMIT` 与上传预算约束；缩放
  触发的重绘需**去抖**，避免连续缩放抖动反复栅格化。
- **字体一致性**：固定字体族（沿用 `Microsoft YaHei UI` / `Segoe UI` 并兜底），创建时把度量结果
  （宽高）持久化；跨机字体缺失只影响显示度量，不改四边形尺寸。
- 验收：位图行为**不回退**（现有画板功能、清理、灾备、导出语义不变）；文字放大到 400% 边缘清晰；
  文字与位图在同一缩放下定位偏差 ≤ 1px；导出 PNG 含正确文字且与屏幕度量一致；RGBA 写盘命令拒绝
  未授权路径与超限载荷；`v1`–`v4` 仓库可读；`scan_unreferenced` / `scrub_board_dds` 不把非位图
  条目当作缺失文件；`npm run test:pin-board` 与 `cargo test pin_board --lib` 覆盖 kind 分派、迁移与
  外键级联；**新增 kind 只需实现 provider，不改核心几何/缓存**。
- **不在本项承诺**：具体新增 kind 的交互（笔迹工具等）不在 0.3 落地，0.3 只落地多态模型 + 文字这一种
  kind；**创建后编辑文字（改字/改色/改字号）不在 0.3 范围**——`pin_board_history` 保持纯变换语义，
  只有创建、删除、移动、图层与排序可撤销。后续扩展需引入载荷版本表，届时另立计划。

### 2.3 节点缩略图（提交时生成，免 restore 预览）（阶段 8）`[alpha3]`

准确做法：

- **动机**：查看某个历史节点（尤其 `.clip`/`.psd` 这类分层工作文件）的内容，目前只能 `restore`
  出完整文件再用外部应用打开，代价高且打断浏览。
- **做法**：在**创建节点时**顺带抽取一份缩略图随节点保存。提交/自动备份的 worker 本来就要打开并
  流式读取工作文件（`backup/worker.rs`、alpha1 阶段 4），此刻抽取缩略图的边际成本最低；历史页直接
  显示缩略图，无需 restore。
- **依赖**：本阶段消费阶段 7 建立的 `history_nodes.thumbnail` 列（**不另开迁移**）与 alpha1 阶段 4
  落地的容器解析模块（**不重复实现**），并由 alpha1 阶段 1 的提交 use-case 调用。这三条是 §4.2 依赖
  表里阶段 8 的真实前置。
- **关键取舍**：缩略图按**节点**存储、与链位置无关，因此查看时**不需要**对 delta 链做惰性区间读，
  避免把 alpha1 阶段 4 的 `ChunkStore` 区间读取复杂度引入 UI 路径。代价是存量节点没有缩略图（见下）。
- **归属**：抽取属「工作文件格式」能力，放在独立模块（如 `src-tauri/src/preview/`），由提交
  use-case 调用并把结果交给 history/backup 存储；backup 领域不硬依赖具体格式（呼应「领域互不导入」）。
  格式检测复用 alpha1 阶段 4 的容器解析模块，不重复实现。
- **界面**：缩略图只读、按需加载。**选中节点时在右侧详情区显示**（时间轴模式左侧已是既有的时间轴
  列），未选中或格式无预览时显示占位；节点卡片不内嵌大图。

**各格式来源（落实前按实测确认）**

| 格式 | 缩略图来源 | 备注 |
| --- | --- | --- |
| `.clip` | CSFC 容器内嵌 SQLite（`SQLi` 块）的 `CanvasPreview` 表，存画布 PNG | 复用容器解析模块定位 `SQLi` 块（研究仓 `tools/harness/src/clip.rs` 的 `parse_csfc`/`walk_tiles` 为参考）；该 PNG 使用非标准 filter 字节（ImageMagick 拒收、需 ffmpeg），`image` crate 解码需容错或回退 |
| `.psd` / `.psb` | 优先 Image Resources 段的缩略图资源（ID 1036 = PS 5.0+，28 B 头 + JFIF/JPEG；ID 1033 = PS 4.0）；取不到时退回 Image Data 段的合并合成图 | 合成图只需按段长跳过 Layer and Mask 段，**不必解码图层**；compression 0 raw / 1 RLE / 2 ZIP / 3 ZIP+prediction；PSB 多处长度字段为 8 B（PSD 为 4 B）。alpha1 阶段 4 的容器模块当前对 `.psd` 只 detect + 回退、结构待逆向确认 |
| 位图（png/jpg/webp/tiff/bmp/gif） | 直接解码并缩放 | 复用现有 `image` crate（`src-tauri/Cargo.toml` 已启用这些 feature） |
| 其它分层（`.kra`/`.ora` = ZIP 内 `mergedimage.png` 等） | 可选 | 后续再加，不在 0.3 承诺 |
| 未识别 / 解析失败 | 无 | UI 显示占位；**绝不因此让提交失败** |

**存储（随节点：`history_nodes` 追加 BLOB 列）**

- 硬约束：缩略图**不得写进 ChunkFile 内容**。`history_nodes.sha256` 是工作文件内容的摘要，scrub 与
  恢复都以它为准；把缩略图塞进 snapshot 会破坏摘要语义。因此缩略图是**派生旁路产物**，随节点行存在
  数据库中，不参与完整性校验与恢复。
- 已定：内容小，**不单开文件或表**。在 `history_nodes` 追加 `thumbnail`（BLOB）与 `thumbnail_version`
  （尺寸/编码版本）列，由**阶段 7 的 v4 → v5 迁移**一并建立（见 §1），旧仓库可读，旧节点该列为空
  → 显示占位。
- 随之简化：删除节点/分支、精简、检查点替换时缩略图**随行删除**，不进入 `pending_file_cleanup`，也
  不需要 `scan_unreferenced` 路径模式与灾备路径覆盖；整仓备份的 SQLite 副本天然包含缩略图。
- 读取按需：图/列表读取必须使用**显式列名**、不得带出 BLOB；新增只读命令（如
  `get_history_node_thumbnail`）在选中节点时单独拉取。缩略图损坏或解码失败只影响该节点预览，不影响
  图读取与其它节点。

**约束与验收**

- 抽取**有界、可取消、只读**工作文件头部区域；任何失败只跳过缩略图，不影响提交结果与摘要；缩略图带
  自身版本号，可安全重建。缩略图固定最大边长与编码（如 ≤512 px，WebP/PNG）。
- 内容未变化的快速检查路径不打开工作文件，沿用 head 已有缩略图；**存量节点不回填**（0.3 不做链上
  惰性抽取）。创建分支不新建节点（`app/workflows.rs` 的 `fork_artwork_branch` 只固化检查点），分支
  起点沿用原节点缩略图。
- **检查点与 snapshot 替换不重新抽取**：检查点不改变工作文件内容。若在同一节点上建立 snapshot，保留
  该节点缩略图；若检查点新建节点行，复制被检查点化节点的缩略图。只有真正读取了新工作文件内容的提交
  才生成/更新缩略图；复制失败只让新节点无缩略图，不影响检查点结果。
- 验收：`.clip`/`.psd`/位图提交后历史页可预览；损坏或未知格式回退为占位且提交成功；删除节点后缩略图
  按清理语义回收；灾备副本保留或可重建缩略图。

### 2.4 空闲链路校验重构（默认关闭、按空闲时机、全链恢复校对）（阶段 9）`[alpha3]`

**动机**：0.2 已落地「空闲链路校验」（`backup/scheduler.rs` 的第二优先级 `IdleVerify`，加
`branches` 的 `verified_history_id` / `verified_ms` / `verify_error` 列），但口径与维护者
预期不符：常驻运行没有开关；校验范围收敛到 head 的单个 snapshot——`materialization_chain` 在
目标节点持有 snapshot 时只返回该节点，而 head 恒持有 snapshot，因此中间任何一条 delta 损坏都
发现不了，「链路健康」名不副实；没有窗口空闲判定（用户正在使用时也可能跑）；没有频率控制；
失败只停留在历史页分支状态行，没有走作品库告警。维护者 2026-10-17 给出新口径，本节按其重构。

**维护者口径（2026-10-17）**：功能默认关闭；近期有改动的链路才进入审查清单，没有修改且经过
检查的链路不再查；只在「主窗口打开不算空闲」的时机运行，且不打扰频繁的自动备份；优先级最低，
频率只作量级参考（如每分支每天一次）、**不写死为时间规则**；校验 = 对整条链做一次完整恢复并
做哈希校对，通过即说明链上任何节点都没问题；失败要找出有问题的节点并报错，复用多次自动备份
失败的报错做成 shared 模板。

准确做法：

- **开关与设置**：新增全局设置 `idleLinkVerifyEnabled`，**默认 false**（`#[serde(default)]`
  即可，旧设置文件缺省即关闭，不需要 settings 版本迁移）。入口落在阶段 6 拆页后的「备份」页：
  开关 + 行为说明 + 「N 条链路待校验」只读计数（复用 `automaticBackupFileCount` 的快照统计
  模式，走共享读租约、不取运行锁）。该计数是派生的只读查询，**不写入设置快照、不持久化**。关闭时
  调度器完全跳过自动校验；**手动「重新校验此分支」不受开关影响**。托盘「暂停所有自动备份」继续
  一并暂停本功能（「别动仓库」的用户意图不变）。
- **首次开启的存量 backlog**：不做一次性补跑。开启后按「每次空闲窗口至多一条」自然消化，设置页
  显示待校验数；急用可手动重查单条，或运行全库完整性扫描兜底。这样保持「不打扰自动备份」的取舍，
  也避免开启瞬间形成长时间的全库读写。
- **审查清单（派生队列，不新建表）**：未进回收站、`head_history_id` 非空、
  `verified_history_id` 与 head 不一致（含 NULL）且 `verify_error` 为空的分支（现有查询口径
  保留）。三条规则：
  - **入队**：新提交改变 head（现有语义）；**精简、检查点建立/取消、snapshot 修复**会改写链
    文件但不变 head，随各自事务按 artwork 粗粒度清 `verified_history_id`，保证「已验证」只
    对当前链文件成立（粗粒度 vs 精确到受影响分支为阶段 9 待决）。
  - **通过后**：写 `verified_history_id` / `verified_ms` 并清空 `verify_error`；无改动不再
    入队——这是唯一硬规则，且与时间无关。
  - **失败后**：写 `verify_error` 退出队列，不自动重试，直到 head 再变化或用户手动重查
    （现有语义保留）。
- **空闲时机门控（按序，任一不满足即退出本轮，等待下次唤醒）**：
  1. 主窗口**不可见或已最小化**才算空闲：调度循环轮询 `is_visible()` **与** `is_minimized()`，任一
     命中即视为空闲（Windows 上最小化窗口的 `is_visible()` 可能仍为 true，两个都要查）；隐藏到托盘
     或最小化均算空闲（校验只读仓库文件、不碰工作文件，最小化时用户在用别的软件也不受干扰——明确
     取舍）。窗口可见且未最小化 = 用户正在使用，本轮不跑。
  2. 无前台命令等待、无待处理手动提交、无到期自动备份（沿用 alpha1 阶段 5 的调度优先级与让位机制）。
  3. head 静默 ≥ `IDLE_VERIFY_DELAY_MS`（10 分钟，现有常量）：避免校验正在被连续改写的链；
     这是防抖，不是频率。
  4. 取得运行锁后锁内复查：head 未变、仍空闲、仍无竞争（现有 `run_idle_verify` 结构保留）。
- **频率：每次空闲窗口至多一次，不设时钟**。「空闲窗口」= 主窗口从可见转为隐藏/最小化的一次
  连续期间，进程内判定，**无持久化、无计时器**。一次尝试无论完成、失败还是被抢占，都消耗该
  窗口的名额，下一次自动校验要等新窗口。候选按 head 创建时间最旧优先、每轮至多一条（现有）。
  典型日用（每天显隐数次）≈ 每天数条以内，且每条都对应真实改动；窗口连续悬挂数天也只校验
  一条——自觉的低频取舍，急用可手动重查或跑全库扫描。维护者的「每分支每天一次」仅作量级参考，
  不实现为任何计时器。
- **不打扰自动备份（维护者点名的取舍）**：
  - **选择期避让**：有到期备份就不启动（门控 2）。
  - **运行期抢占**：全链校验可能持续数分钟，这期间备份到期不能干等。校验循环在**每个 delta 步边界**
    调用 alpha1 阶段 5 提供的 `should_yield()`；一旦有到期自动备份、前台等待或待处理手动提交，立即
    停止、不写任何结果，让调度器先运行高优先级任务。不新增按 kind 的外部取消入口，也不依赖单线程
    调度器从外打断；用户手动取消仍走既有取消路径。
  - **防饿死复用 alpha1 阶段 5 的 aging**（该阶段已交付「调度优先级 + aging 防饥饿」）：本功能
    **不另设时间阈值**——早期提案里的「挂起超 7 天免抢占」经维护者确认不采纳（计时式阈值），饥饿
    问题统一交回调度器的 aging。
  - 手动提交与前台命令的让位沿用现有 `foreground_waiting` / `manual_pending`，不新增机制。
- **全链恢复校对（本节核心）**：对整条链做一次**完整恢复并哈希校对**——从 head 的 snapshot
  出发，沿父链逐条应用反向 delta 直到 root，每步结果与数据库摘要比对，最终根文件内容流入
  sink 逐块验哈希并核对整文件摘要。一次物化即证明：每条 delta 都被实际应用、每个节点摘要都
  被校对，链上任何节点都没问题。
  - **实现**：history 新增 `full_materialization_chain(head_id)`——纯父链查询，**绕过
    `materialization_chain` 的「就近 snapshot」短路**，保证中间存在检查点/分支起点 snapshot
    时也从 head 走完整条链；restore 侧把 `resolve_chain` 重构为接受显式链（或新增
    `resolve_full_chain`），复用 ChunkStore 分段、逐条 resolve、每步摘要比对与
    `copy_original` 逐块验哈希；取消与进度按步报告（与 alpha1 阶段 4 的 `CancelToken` 口径对齐）。
  - **沿途 snapshot 文件级校验的边界**：全链恢复只读取 head 起始 snapshot 的内容；链上其它 snapshot
    节点（中间检查点、分支起点、root）不在恢复路径上，逐个 `validate_snapshot`（文件摘要 + 全部分块
    验哈希）。**只校验本链节点上的 snapshot**，不遍历其它分支；跨分支与全库范围仍由
    `scrub_repository_integrity` 负责。这样「本链任何节点都没问题」的口径完整且代价有界。
  - **失败定位到节点**：每步摘要不符 → 「历史节点 X 的摘要与历史数据库不匹配」；delta
    缺失/损坏 → 「历史节点 X 的反向 delta 损坏或缺失」；中间 snapshot 损坏 → 同样带节点 id。
    全部写入现有 `verify_error` 列；历史页分支状态行照旧展示（独立于备份失败的第三态），
    错误文案现在带节点 id。
  - **代价**：约等于链上全部 delta 载荷之和 + 根文件一次流式读出，比 0.2 的 head 快照检查
    重；由「默认关闭 + 窗口空闲 + 每窗一条 + 最低优先级」兜住。全库完整性扫描
    （`scrub_repository_integrity`）保持按需全量定位，两者互补（既有口径不变）。
- **失败报错：kind 驱动的 shared 模板**。复用「连续失败禁用自动备份」的报错链路（作品树角标
  + 作品库顶部告警条 + 「查看分支设置」导航 + 「知道了」确认），泛化为按 kind 呈现：
  - **schema（阶段 7 建立并泛化）**：新建 `branch_notices(branch_id TEXT NOT NULL REFERENCES
    branches(id) ON DELETE CASCADE, kind TEXT NOT NULL CHECK (kind IN ('backupDisabled',
    'linkVerifyFailed')), message TEXT NOT NULL, created_ms INTEGER NOT NULL,
    PRIMARY KEY (branch_id, kind))`；复合主键让同一分支可同时有 `backupDisabled` 与
    `linkVerifyFailed`，且同 kind 只保留一条（重复失败更新 `message`/`created_ms`）。旧
    `branches.backup_disable_notice_pending = 1` 在 v5 迁移中转为 `backupDisabled` 行，**随后删除
    旧列**（单一机制，不保留只读兼容列）。阶段 7 同时把
    `next_backup_disable_notice_target` / `acknowledge_backup_disable_notices` 泛化为
    `next_branch_notice_target` / `acknowledge_branch_notices`（按 artwork/kind 过滤），作品树计数
    改为「有待处理告警的分支数」。
  - **阶段 9 只新增行为**：链路校验失败写入 `kind = 'linkVerifyFailed'`；校验通过时删除该分支的
    `linkVerifyFailed` 通知（`backupDisabled` 仍保持确认制）；前端换用 kind 驱动的共享告警组件。
- **手动重查升级**：`reverify_branch_history` 从「清错误 + 唤醒调度等待」改为**前台立即执行
  全链校验**（进度 + 可取消 + 写同一套结果列）。低频率的自动节奏下，手动入口必须即时，否则
  按钮点了要等到下一个空闲窗口才跑。

**关键取舍**

- **频率不写死时间**：用「每次空闲窗口至多一次」的机会式节流代替每日计时器；换来频率随真实
  使用自然浮动（约每天数条以内）、零持久化状态、重启安全。代价是长假悬挂只校验一条——接受，
  急用有手动入口。
- **抢占 vs 备份延迟**：全链校验重且时长不可控，不抢占会让频繁备份场景的备份延迟累积；抢占
  的代价是忙仓库上校验可能反复中途退出（不写结果、下窗续查），防饿死交回调度器的 aging。
  不做「挂起 N 天豁免」式计时阈值。
- **最小化算空闲**：校验只读仓库、不碰工作文件，最小化时跑不影响用户别的操作，换来更多校验
  机会；若维护者改为「只认隐藏到托盘」，门控 1 随之收紧。
- **通知存新表而非新列**：与备份禁用告警共用一张表才是真正的 shared；代价是一次 schema
  迁移（已并入阶段 7）与旧列迁移（迁移后删除旧列）。

**约束与验收**

- 默认关闭；关闭时除手动重查外零调度行为。
- 窗口可见且未最小化期间绝不自动运行；运行中在 delta 步边界检测到更高优先级任务时通过
  `should_yield()` 停止，不写结果、不推进 `verified_ms`、不清 `verify_error`。
- 一次空闲窗口内多条待校验分支只执行一条；窗口重新可见再转入空闲后执行下一条。
- 全链校验通过 = 根文件整文件摘要一致 + 每步节点摘要一致 + 逐块哈希正确 + 本链沿途 snapshot
  文件级通过；任一失败的错误信息带节点 id 并写入 `verify_error`，同时入队 `linkVerifyFailed` 通知。
- `branch_notices` 使用 `(branch_id, kind)` 复合主键；同一分支可同时存在两种通知，重复失败只更新
  既有行；删除分支级联删除通知；校验通过删除 `linkVerifyFailed` 但保留待确认的 `backupDisabled`。
- 回归覆盖：中间存在检查点时仍从 head 走完整链；精简/检查点后分支重新入队；`should_yield` 抢占不写
  结果；旧 `backup_disable_notice_pending` 迁移为 `backupDisabled` 后行为不变且旧列已删除；`v1`–`v4`
  仓库经 v5 迁移后可读。
- 手动重查在开关关闭时仍可用且立即执行；设置页待校验计数与派生队列口径一致。
- 日志按 `docs/guides/logging.md`：开始/结束/耗时走 `run_logged` 常规档，失败为 `warn`，
  不带隐私内容。

## 5. 验证与完成条件

- 日常阶段只运行与改动匹配的 `cargo fmt --check`、`cargo check --lib`、`cargo test --lib`、
  `npx tsc --noEmit`、`npm test`（素材板范围可用 `npm run test:pin-board`）和 `git diff --check`；
  不在普通收尾阶段运行压力测试（见 `docs/guides/validation.md`）。
- 0.3 发布前由维护者显式安排压力测试：取消/崩溃、4 GiB 与 8 GiB 往返、损坏恢复、规模、DDS、认证和
  跨进程门闩，并把实测写入 `docs/user/stress-test-report.md`。

**alpha2 完成条件**：仓储空间仪表盘数值正确（总量口径不重复计入非 snapshot 节点的
`chunk_file_size`，分类占比之和等于总量）且不阻塞 UI、扫描可取消；设置页拆分后设置保存、仓库切换、
托盘刷新与既有测试语义不变；alpha1 完成条件（见 §3）全部通过。

**alpha3 完成条件**：画板条目为多态（位图/DDS 仅一种 kind），清理/校验/灾备/导出按 kind 分派且不
假设实体文件；`.clip`/`.psd`/位图提交后历史页可预览；`v1`–`v4` 仓库可读，`v5` 由阶段 7 的一次事务
迁移产生，同一迁移包含 `branch_notices`、缩略图列与路径索引；新增 kind 只需实现 provider，不改
核心几何/缓存/旁路；空闲链路校验默认关闭、仅在主窗口隐藏或最小化时自动运行、以「恢复根文件 + 逐块
验哈希」证明全链健康，失败定位到节点并经 kind 驱动的共享告警呈现，手动重查即时可用。

## 6. 非目标与待决策

- 不重写领域业务规则，不把所有函数强行放进通用插件系统，不为事件总线引入外部消息中间件。
- 0.3 不为画板一次性实现所有 kind 的交互（笔迹工具等）；阶段 7 只落地**多态条目模型 + 文字**这一种
  非位图 kind，以验证「新增 kind 只需实现 provider、不改核心几何/缓存/旁路」这一可扩展性目标。
- **仓储空间状态只读**（§2.1）：只做只读聚合与设置信息架构拆分，不引入独立顶层窗口、不持久化统计
  缓存、不新增 schema；DDS 分类按「是否有实体文件」判定，不按 kind 枚举。
- **缩略图存储位置已定**（§2.3）：随节点存于 `history_nodes.thumbnail`（BLOB）+ `thumbnail_version`，
  由阶段 7 的 v4 → v5 迁移建立；不单开文件或表，不参与完整性校验与恢复。
- **画板表结构与历史语义已定**（§2.2）：采用 `pin_board_items` + 按 kind 载荷子表，v5 表重建并回填；
  `pin_board_history` 只存变换，0.3 不支持创建后编辑文字。
- **空闲校验的告警与存量策略已定**（§2.4）：`branch_notices` 用复合主键并级联删除，旧
  `backup_disable_notice_pending` 迁移后删除；首次开启不一次性补跑，按空闲窗口逐条消化。
- 关闭握手与诊断体系保持既有语义（专用握手、诊断模式只影响探针与取证），本轮不重新设计。
- **仍待实现阶段决策的项**（标注其阻塞的阶段）：
  - 阶段 6：设置页拆分后仓储 / 备份的导航层级（左导航项 vs 页内视图）。
  - 阶段 7：文字栅格化的缩放去抖窗口与最大纹理边长；文字导出 RGBA 载荷上限的最终取值。
