## 1. 背景

崩溃与清理路径当前存在四类缺口（均为代码事实，来源见 §2）：

1. **画板结算在事务提交前删除 DDS**。若提交随后失败，记录回滚而文件已消失，形成
   「数据库仍有图片记录但 DDS 丢失」的不可逆不一致。
2. **历史文件清理失败被静默忽略**。磁盘空间持续泄漏，用户无从得知、无法重试。
3. **崩溃孤儿不会被回收**。「先发布文件、后提交数据库」窗口内的 snapshot/delta
   不进清理队列；灾备被强杀时暂存目录残留。压力测试批次 2 已实测确认（见
   `current-handoff.md` 批次 2 第 4 点）。
4. **画板 DDS 无完整性检查**。损坏、缺失、孤儿 DDS 只能在实际读取或恢复时暴露。

四个缺口指向同一个结构性原因：**清理动作没有统一的「记录 → 执行 → 重试 → 可观测」
账本**。`cleanup.rs` 的 `pending_file_cleanup` 队列已经是这个账本的雏形，本计划不做
新机制，而是把所有清理路径收敛到它上面，并补上它缺少的「未引用文件扫描」能力。

## 2. 现状盘点（代码事实）

**既有队列机制（`src-tauri/src/cleanup.rs`，全部沿用，不改语义）：**

- 事务内入队：`enqueue_repository_file(_with_hash)` / `enqueue_repository_directory` /
  `enqueue_external_file`，`(path_kind, path)` 唯一，带可选期望 SHA-256 与原因。
- 提交后重放：`cleanup::run(root, ids)` 逐条执行「引用检查 → 摘要比对 → 删除」，
  成功删行、失败写 `last_attempt_ms` / `last_error` 并留在队列，天然可重试。
- 防误删三重护栏已存在：`referenced_path` 查询五张表（最终成品、认证副本、历史节点、
  历史边、认证导出记录）；`safe_repository_path` 拒绝越出仓库边界；期望摘要不匹配
  即保留。
- 重试命令 `retry_pending_file_cleanup` 已注册（`app/cleanup_commands.rs`）。

**当前各自为政的清理路径：**

| 路径 | 现状 | 问题 |
| --- | --- | --- |
| 画板回收站删除/清空（`pin_board/repository.rs`） | 事务内删记录 + 入队目录，提交后 `cleanup::run` | **正确范式**，本计划把它推广到其余路径 |
| 画板结算 `finalize_board`（`repository.rs:898-911`） | 事务内直接 `fs::remove_file` 删 DDS，commit 在第 913 行 | 提交失败 → 记录回滚但 DDS 已消失 |
| 分支删除的历史文件（`app/workflows.rs:273-277`） | `history::delete_branch` 返回 `storage_paths`，调用方对未引用路径直接 `remove_file` 且 `let _ =` 忽略失败 | 失败静默泄漏 |
| 提交后旧 snapshot 释放（`backup/worker.rs` 等） | 多处提交成功后直接删除仓库文件 | 同上，且进程被杀时留在磁盘（批次 2 B1 实测） |
| 灾备暂存目录（`backup/repository_backup.rs:111`） | `StagingDirectory::drop` 只在进程存活时清理 | 强杀后 `.lilith-artworks-*.tmp` 永久残留 |
| 认证预览会话（`authenticity/pipeline.rs`） | 每会话 `temp/authenticity-preview-<UUID>/` | 不清理（P2「超期临时目录」，不在本计划） |

**队列缺的能力：**只有「重放」，没有「发现」——`cleanup::run` 不会扫描未引用文件，
因此崩溃孤儿（从未入队）永远无法被回收。

## 3. 目标与非目标

**目标：**

1. 所有「提交成功后才应发生的仓库文件删除」统一走队列：事务内入队、提交后重放、
   失败可重试、状态可观测。
2. 新增未引用文件扫描（历史孤儿 + 画板孤儿 DDS），作为队列的发现机制，产出
   「报告 + 用户确认后清理」。
3. 灾备暂存目录的识别与清扫。
4. 仓库完整性扫描扩展覆盖画板 DDS（损坏、缺失、孤儿）。
5. 设置页呈现清理队列状态与扫描入口。

**非目标：**

- **不做 schema 迁移**。`pending_file_cleanup` 现有列（含 `last_attempt_ms` /
  `last_error`）足够；仓库 schema 保持 v4，`verify-metadata.mjs` 断言不变。
- **不引入新依赖**。目录结构是固定的两层（`artworks/<id>/{snapshots,deltas,boards}`），
  std `fs` 遍历即可，不需要 walkdir。
- **不清理 `repository/temp/`**（认证预览会话属 P2「超期临时目录清理」，另行处理）。
- **不改分块格式**、不改变既有取消/进度契约、不触碰 `history::commit` 的事务边界。
- **扫描不做无头子命令**。同仓库多进程并发没有跨进程锁（todo「同仓库多进程并发缺乏
  防呆」），扫描入口在哨兵锁落地前只经 GUI 进程内暴露。
- **不做 GUI 自动化**；界面验收按 `validation.md` 由维护者人工确认。

## 4. 设计方案

### 4.1 画板结算改提交后清理（批次 A）

`finalize_board` 中「删除已标记删除图片的 DDS」改为：

1. 事务内对每个被删除的 `image_id` 执行
   `cleanup::enqueue_repository_file_with_hash(…, "pin_board_finalize")`
   （期望摘要取图片导入时落库的 SHA-256；若记录无摘要则用不带哈希的入队并接受
   「文件内容已变化则保留」的保守行为）。
2. 保留既有 `bump_revision` → `commit` 顺序不变。
3. 提交成功后由调用方执行 `cleanup::run`（与画板回收站删除同范式）。

**语义变化（需维护者确认）**：原来「DDS 删除失败 → 结算整体报错」，改为「删除失败
→ 结算成功、条目留在队列可重试」。这消除了「提交成功但结算报错」的悖论状态
（此时记录已更新而文件仍在，重试结算会因 revision 变化失败）。

### 4.2 历史文件清理入队（批次 B）

1. `app/workflows.rs` 分支删除：对 `storage_paths` 中未引用的路径改为
   `enqueue_repository_file`（带删除前查询到的 SHA-256 可选），随后 `cleanup::run`。
   `history::storage_path_referenced` 的既有判断保留为入队前的快路径，真正的引用
   复查仍由 `cleanup::run` 执行。

   **落实偏差（维护者 2026-10-04 确认）**：入队不在调用方、而在领域函数自身的
   SQLite 事务内完成——`history::{delete_branch, delete_subtree, unmark_checkpoint,
   commit, apply_compaction, set_snapshot}` 在事务内复查引用后入队并返回 cleanup id，
   调用方只负责 `cleanup::replay`。因此 `history::storage_path_referenced` 不再作为
   调用方快路径：引用复查改为复用 `cleanup::referenced_path_kind`（事务可见本事务
   尚未提交的写入），该函数已随本批次移除。入队不登记期望 SHA-256——snapshot/delta
   按 history id 命名且发布后不再改写，引用复查已是充分护栏，登记摘要需在入队前
   完整读一遍文件（大文件代价高）。
2. 排查全部「提交成功后直接删除仓库文件」的调用点（`backup/worker.rs` 旧 snapshot
   释放、`restore.rs` 精简后旧实体清理等），统一改为入队 + 重放。事务内的**回滚**
   删除保持直接删：回滚路径上文件本就未被数据库引用，直接删失败只留泄漏不留不一致，
   由批次 C 的扫描兜底。
3. 无头命令与 Tauri 命令层共用同一领域函数，改动自动覆盖两条入口。

### 4.3 未引用文件扫描（批次 C，本计划唯一的新能力）

新增 `cleanup::scan_unreferenced(root, cancelled, progress) -> Vec<ScanCandidate>`：

- **范围固定**：`artworks/*/snapshots/`、`artworks/*/deltas/`（画板 DDS 在批次 E
  并入）。只考虑匹配既有命名模式的文件（`<UUID>.lbd` snapshot、`<UUID>-to-<UUID>.lbd`
  delta、`<image_id>.dds`），其余一概不报告。
- **判定**：复用 `referenced_path` 的表查询逻辑做反向检查（文件路径不在任何引用列中
  即为候选）。
- **护栏（缺一不可）**：
  1. 文件修改时间早于宽限期（建议 30 分钟，≥ 空闲校验延迟 10 分钟），避免与进行中的
     提交、精简赛跑；
  2. 扫描经 `run_exclusive` 持仓库操作锁，与调度器、前台长命令互斥；
  3. 期望摘要校验沿用（候选入队时登记当前 SHA-256，重放时内容已变即保留）。
- **两段式**：扫描只产出报告（路径、体积、原因），**不删除**；用户在设置页确认后，
  候选批量入队并立即重放。首次落实也可只做「报告」，自动清理入口后置。
- 复用 `cleanup::run` 的既有重放，不新造删除逻辑。

### 4.4 灾备暂存目录清扫（批次 D）

`.lilith-artworks-*.tmp` 位于灾备目标目录（仓库之外），不入 `pending_file_cleanup`
（现有三种 `path_kind` 都不覆盖仓库外目录，且无数据库引用可查）：

- `create_repository_backup` 启动时（`validate_destination` 之后）扫描
  `destination_parent` 顶层匹配 `.lilith-artworks-*.tmp` 且修改时间早于宽限期的目录，
  逐个 `remove_dir_all`，把「回收数量/失败数」追加进返回报告；无法删除不阻断本次备份。
- 命名模式 `lilith-artworks-` 前缀 + `.tmp` 后缀 + 32 位 hex backup_id 足够特异，
  误删风险限于同名碰撞（_UUID simple 命名，可忽略）；仍只碰顶层、不递归匹配。
- 暂不提供针对历史目标的独立扫描入口（目标目录是用户任选位置，应用不持久化它）。

### 4.5 完整性扫描覆盖画板 DDS 与双向检查（批次 E）

挂入 `scrub_repository_integrity`（`app/workflows.rs:24`）现有两段之后新增第三段：

- **文件 → 记录（孤儿检测）**：遍历 `artworks/<aid>/boards/<bid>/*.dds`，不在
  `pin_board_images` 记录中的报为孤儿候选，并入批次 C 的报告与确认清理流程。
- **记录 → 文件（缺失检测）**：`pin_board_images` 每条记录的 `image_id.dds`
  必须存在且通过校验——路径归属（DDS 必须在其画板目录下）、DDS/BC7 头、声明的
  尺寸与长度、SHA-256（与导入时落库摘要比对）。
- 报告并入现有 `RepositoryScrubReport`（新增字段，前端同步展示）；**只报告不自动
  修复**，缺失 DDS 的修复属历史迁移议题，不在本计划。

**落实偏差（2026-10-04，已核实）**：本节的「SHA-256（与导入时落库摘要比对）」未实现
——`pin_board_images` 无摘要列，且 §3 明确不做 schema 迁移，维护者确认跳过摘要比对，
改为「路径归属 + DDS/DX10/BC7 头 + 声明尺寸与记录一致 + 数据长度 + BC7 全块解码」。
BC7 解码步骤为维护者所选（§7 第 4 条）；`bcdec_rs::bc7` 是全函数（任意 16 字节输入
不返回错误），因此该步骤走一遍完整解码路径、守住边界与长度，不判定像素内容。缺失/
损坏 DDS **报告不失败**（计数并入报告、命令仍成功返回），孤儿 DDS 另经 §4.3 的
`scan_unreferenced` 报告与确认清理。

## 6. 不变量与风险

**不变量：**

- 清理永远「先记录后删除」：事务内入队、提交后重放；两阶段各自幂等
  （重放对已删文件视为成功，沿用现状）。
- 任何删除前必须通过引用检查；带期望摘要的条目摘要不匹配即保留。
- 扫描只报告匹配已知命名模式且超过宽限期的文件，只报告不删除，删除需用户确认。
- 仓库 schema 保持 v4；新增依赖数为 0；不修改 CI；不触碰取消/进度契约。

**风险与缓解：**

1. **扫描误删正在使用的文件。** → 命名模式 + 宽限期 + 操作锁 + 引用复查 + 摘要校验
   五层护栏；候选确认制。
2. **结算语义变化引入回归。** → 批次 A 单测覆盖「提交失败 → 文件保留 → 重放删除」
   全链；GUI 结算成功/失败文案同步核对。
3. **队列膨胀。** 长期失败条目堆积（如外部文件被占用）。 → 报告区分「待清理」与
   「失败待重试」；本计划不引入自动过期，是否需要清空入口留给维护者决定。
4. **与压力测试批次 4/5 的重跑成本。** A、B 改动历史/画板写路径，C/D/E 组相关断言
   可能需重跑（`stress-test-plan-2026-10-04.md` §11.4 已接受该成本）；建议在批次 4
   之前完成 A、B。
5. **画板 DDS 压力测试的前置。** 计划 H 组（画板 DDS 损坏/缺失/孤儿）明确依赖本计划
   的批次 E 落实。
