## 发布结论

`0.1.0-rc.1` 的源码和 Windows NSIS 已公开，可继续作为明确标注风险的发布预览版保留，但当前项目 **不具备 `0.1.0` 正式发布条件**。本轮未发现需要立即下架仓库的凭据泄露、私钥或 P0 级公开安全事件；源码、架构说明和修正后的公开文档可以继续公开。

当前 HEAD `a55305b` 已位于公开标签 `v0.1.0-rc.1`（`3ec1590`）之后，包含 schema v9、`com.lilith.artworks` 标识和行为变化，但三个版本入口仍写 `0.1.0-rc.1`。这些字节不能继续使用已发布的版本身份；下一个候选版必须是 `0.1.0-rc.2` 或更高版本，并保留 `rc.1` 标签与资产不变。

公开 `rc.1` 安装包 SHA-256 为 `94FA2E441785436FA6C169DB38F96C4EEB6904C295B0A18094117E83499A1D94`，本地复核与 GitHub 资产一致，但 Authenticode 状态为 `NotSigned`。在下一个候选版发布前，应把 `rc.1` 标为已被替代并明确提示不要承载唯一副本或不可替代的数据；本轮未修改任何远端 release。

## 审查范围与证据边界

- 审查了约 14,000 行 TypeScript/TSX/Rust 生产代码、65 个生产代码文件，以及架构、模块、验证、贡献、安全、许可、变更日志、CI 和 Tauri 打包配置。
- 当前测试资产为 6 个前端测试文件、18 个前端用例和约 41 个 Rust 测试；关键的 ChunkFile、调度器、C2PA、TrustMark 和认证命令仍缺直接测试。
- npm 生产依赖审计为 0 个已知漏洞；完整审计发现锁定的 Vitest 3.2.4 命中 critical `GHSA-5xrq-8626-4rwp`，影响启用 UI/API 的开发服务器场景，需升级到 3.2.6 或更高版本。
- RustSec 审计发现 `rsa 0.9.10` 的 `RUSTSEC-2023-0071`，由 `c2pa 0.90.11` 的 native crypto 链路引入且上游没有稳定修复版。普通本地使用风险低于网络服务，但 PS256 签名路径必须禁用、替换或形成明确的风险接受与回归测试。
- GitHub 私密漏洞报告当前未启用；`SECURITY.md` 已增加不泄露技术细节的公共联系请求兜底，但正式版前仍必须提供并实测真正的私密渠道。
- 本轮是静态审查与轻量验证，不等于 Windows GUI、真实签名证书、第三方 C2PA 回读、大文件内存或安装升级验收。

## 已有基础

- 前端领域 API、应用层跨模块编排和 Rust storage/domain/workflow 边界总体清楚，普通打开仓库不会隐式创建数据库。
- SQLite 已启用 WAL、外键、FULL synchronous 和 busy timeout；历史提交使用 no-clobber 发布、摘要和失败清理，认证副本已有持久 cleanup intent。
- 私钥使用 `Zeroizing`，未写入数据库、设置或日志；前端未获得通用文件读写权限，CSP 与 dialog scope 基础较收敛。
- 历史树事务和前端纯模型已有基础测试，CI 能覆盖前端构建、前端测试、Rust 格式和库测试。

## P1：下一个公开候选版之前必须完成

- [ ] **P1-01 备份可恢复性与仓库灾备。** `backup/worker.rs` 在内容摘要未变化时不校验 HEAD snapshot，`backup/restore.rs` 创建检查点也只判断路径存在于数据库；缺失或损坏的 `.lbc` 会被报告为成功。使用前必须校验受控文件与数据库摘要，能够修复或明确阻止操作；增加可中断的全库 scrub。SQLite 元数据是当前单点故障，还需实现共享锁下的一致性仓库备份与恢复演练，或先建立经过实测的退出应用后整仓备份政策。
- [ ] **P1-02 仓库身份、路径与并发隔离。** ready 仓库 A 切换到 ready 仓库 B 时，前端只依赖布尔 `ready`，旧树和旧 Artwork 最长可保留到轮询，甚至向新仓库发送旧 ID。后端部分 mutation 也可在捕获旧 root 后跨越仓库切换。引入 repository generation/lease，切换时原子清空并使旧请求失效；所有持久化 ID 必须验证为 UUID 或单一安全路径组件，打开仓库时做语义校验，覆盖克隆仓库同 ID 与 `..` 路径测试。
- [ ] **P1-03 受控文件摘要与 C2PA 不变量。** 最终成品、认证仓库副本和历史恢复在使用前没有统一对照数据库中持久化的 SHA-256；仓库文件被替换后仍可能签名、预览或再次导出。发布后还只确认存在 active manifest，没有要求验证状态合格或逐项核对 record ID、TrustMark ID 和本次声明。发布、预览、再导出、恢复与 scrub 必须统一校验，并对 C2PA 结果 fail closed，向用户报告“受控文件缺失、损坏、被替换或声明不匹配”。
- [ ] **P1-04 删除语义与外部文件保护。** 永久删除 Artwork 当前会删除仓库外首次发布的用户 JPG，而 UI 只提示删除“全部内容”。默认应保留外部导出；若确需删除，必须逐路径列出并单独显式选择。增加发布、取消发布、Artwork 永久删除和哈希不匹配的端到端测试。
- [ ] **P1-05 大文件内存上限。** delta 恢复会同时持有完整压缩数据和无上限解压结果；认证管线和隐藏发布页会创建多份全分辨率像素、JPEG 与 base64 data URL。改为流式或有硬上限的解压，限定像素、边长、压缩后/解压后字节数，发布页仅在激活时加载并使用缩略图或分块处理。用 1-4 GB 工作文件及 8K/16K、50/100 MP 图片记录峰值内存和可理解的拒绝行为。
- [ ] **P1-06 自动备份状态机。** 分支设置只在 branch ID 变化时同步，本地旧值可在调度器第 5 次失败自动关闭后再次写回并清除通知；短于 3 秒的备份也可能完全错过 busy 轮询。区分用户 dirty 与服务端更新，增加单调 completion revision/event；取消、退出和发布竞态使用 typed error，不计为失败，拿到运行锁后再次检查分支仍可调度。
- [ ] **P1-07 发布状态与 TrustMark 身份。** 发布元数据和预览读取处于同一异常路径，预览损坏会让已发布分支显示为未发布并隐藏取消入口；自动生成的 TrustMark ID 还会跨分支和发布复用。先提交发布元数据，再独立加载/重试预览；取消发布始终可达；将 watermark ID 绑定到分支或一次待发布操作，并在切换、禁用和成功发布后清空。
- [ ] **P1-08 版本、迁移与旧标识。** 增加 v8→v9 自动迁移测试和迁移前备份；现有 v4→v5、v7→v8 会删除认证记录，必须明确最低支持版本、导出/提示和数据保留策略。在 `rc.1` 仓库副本上完成升级、外键与完整性检查，明确 `art.lilith.artworks` 设置/日志/C2PA label 到 `com.lilith.artworks` 的一次性迁移或不兼容策略，并实测安装升级与卸载。发布前把 package、Cargo、Tauri 和锁文件统一升到 `0.1.0-rc.2`，不得移动 `rc.1` 标签。
- [ ] **P1-09 依赖与构建基线。** 将 Vitest 升到 3.2.6 或更高版本；把已 EOL 的 Node 20 CI 升到受支持的 Node 24 LTS；为 `rsa`/PS256 给出禁用、替换或书面风险接受。CI 增加官方 npm audit、RustSec、许可与 SBOM 门槛，并按 Windows 实际目标分类仅限其他平台的 Rust 告警。
- [ ] **P1-10 许可、安全渠道与可信产物。** 当前配置已开始打包根 GPL、第三方摘要和 Adobe 原始模型许可，但完整的 Windows 目标许可闭包、项目版权持有人、About/Legal 入口仍缺失。正式候选版需生成包含版本、版权和正文的许可包，启用并实测私密漏洞报告，从不可变标签在干净 CI 构建，签名并时间戳主程序和安装包，发布 checksum、SBOM、许可包和 provenance，且由 CI 解包断言法律文件存在。
- [ ] **P1-11 发布测试矩阵。** 为缺失 HEAD 自愈、压缩炸弹/超大 delta、仓库路径穿越、受控文件替换、C2PA 声明匹配、调度取消、真实 C2PA/TrustMark fixture、schema v1-v9、`foreign_key_check`、清理崩溃点和安装包资源增加自动测试。任何数据可靠性修复在故障注入和恢复演练通过前不得标记完成。

## P2：`0.1.0` 正式版之前必须完成

- [ ] **P2-01 崩溃一致性。** 检查点和精简的历史文件发布纳入持久 cleanup intent/reconciliation；对文件与发布目录提供平台等价的 durable publish 屏障，启动时处理临时文件和合法 orphan，文件删除失败不得吞掉。永久删除已提交元数据但后续清理失败时，要返回结构化的部分成功状态。
- [ ] **P2-02 授权、取消与安全退出。** 恢复目标、Artwork/fork 工作文件和仓库目录统一执行 dialog scope；ChunkFile 分块检查取消，C2PA/时间戳有取消和超时，退出过程显示明确状态且不长时间阻塞窗口事件线程。
- [ ] **P2-03 仓库完整性与稳定读取。** 打开时增加 `foreign_key_check`、图归属、ID/path 语义检查；后台 scrub 校验所有管理文件。备份和最终成品复制不能只依赖 length+mtime，应验证文件身份及读取前后稳定性，或明确要求源文件关闭并检测违反条件。多个旧数据库候选必须稳定判定或要求用户选择。
- [ ] **P2-04 事务与设置前向兼容。** `create_branch` 的分支插入和起点 checkpoint 更新必须处于同一事务。高版本或无效 `settings.json` 进入只读/保留原文状态，托盘暂停和窗口状态捕获不得覆盖未知字段；增加降级启动后关闭窗口的回归测试。
- [ ] **P2-05 规模与查询。** 分支删除移除 O(n²) 路径，历史和认证记录分页；前端图计算预建索引并改为迭代实现，树和记录列表虚拟化。至少记录 10k、50k、100k 节点的加载、删除、内存和交互基线。
- [ ] **P2-06 前端错误恢复与事务反馈。** 批量精简部分成功后也刷新状态；历史初始加载失败显示错误和重试；应用增加顶层 ErrorBoundary；设置取消恢复实时主题/密度且异步加载不能覆盖用户草稿；证书路径不跨重启伪装为仍获授权。
- [ ] **P2-07 可访问性与输入。** 树支持方向键、Home/End 和 roving tabindex；区域选择提供键盘等价；对话框实现 focus trap、Escape 和焦点恢复；修正低于 WCAG AA 的次要文字对比度、过小字号、IME Enter 与视口外菜单。
- [ ] **P2-08 最终用户文档。** README 补充安装、升级前备份、schema 不可降级、卸载后数据保留、手动/自动更新渠道、支持范围和已知限制；模型来源记录精确下载 URL、上游 commit 与取得日期；确定并统一项目版权持有人和年份。

## 分阶段执行计划

1. **完整性与隔离。** 完成 P1-01 至 P1-04；退出条件是损坏、替换、路径穿越、跨仓库竞态和外部导出删除测试全部通过，且能从一致性备份恢复代表性仓库。
2. **状态机与资源边界。** 完成 P1-05 至 P1-07 和 P2-02；退出条件是大文件峰值受控、取消/退出有界、短任务不会丢事件、发布状态和 TrustMark ID 生命周期测试通过。
3. **迁移与发布工程。** 完成 P1-08 至 P1-11；退出条件是唯一 `rc.2` 版本、迁移矩阵、私密披露、许可包、标签构建、签名、SBOM 和安装包解包检查全部有证据。
4. **正式版质量。** 完成全部 P2；在干净 Windows 普通用户环境执行下列人工验收并至少保留一个候选观察周期，期间不得出现未解释的数据损坏、不可恢复备份或安全边界回归。
5. **正式发布。** 从已验收提交升为 `0.1.0`，创建不可复用的签名标签；由 release workflow 构建并发布，不使用开发机手工产物替换 CI 资产。

## Windows 人工验收清单

1. 安装、首次启动、`rc.1` 升级、仓库创建/打开/切换、单实例、托盘和显式退出。
2. Artwork 树、搜索、拖放、多选、回收站、外部导出保留和永久删除逐路径确认。
3. 分支提交、自动备份重试/取消/自动关闭、fork、恢复、精简、检查点、损坏 HEAD 修复和整仓恢复。
4. 发布预览、原图切换、C2PA 签名/取消/再次导出、TrustMark 区域识别与跨 Artwork 溯源；使用第三方工具回读 C2PA。
5. 在支持上限附近的大图和工作文件上记录耗时、峰值内存、取消延迟与退出时长；超限输入必须给出稳定且可理解的错误。
6. 校验 v8→v9 数据、外键、受控文件 SHA、旧标识策略、schema 不可降级提示和升级/卸载后的数据保留。
7. 用普通用户账户验证 exe/installer Authenticode 与时间戳，解包确认 GPL、第三方许可包、Adobe 模型许可、SBOM 和版本信息存在。

## 需要维护者确定的发布决策

- 项目公开版权持有人名称，以及安装包和 About/Legal 中使用的法定显示文本。
- Windows 代码签名证书、时间戳服务和密钥托管方案。
- 工作文件和图片的正式支持上限，以及超限时拒绝还是降级处理。
- 永久删除 Artwork 时外部首次导出是否永远保留，或仅在逐路径二次确认后删除。
- 是否把外部仓库视为不可信可交换输入；若否，必须在威胁模型和用户文档中明确限制。
- 首个正式版仅支持手动更新，还是在发布前投入签名 updater 与回滚设计。
