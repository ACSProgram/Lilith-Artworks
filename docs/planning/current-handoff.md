### 认证 fixture 与 PS256 说明

- **真实认证 fixture** 已固定为约 41 KB 的真实 C2PA JPEG/TrustMark 样本和公开测试专用 ES256 凭据，自动覆盖成功、文件被替换、无效签名、声明不匹配等 fail-closed 分支。它补充的是回归测试能力，不否定维护者已经完成的手工使用。
- **PS256 风险** 指 C2PA 依赖链中的 `rsa` 库安全公告。它不是 TrustMark 算法，也不表示当前默认的 ES256 发布必然失败；只有启用 PS256 RSA 签名路径时才直接相关。正式支持该路径前，项目需要升级/替换依赖、禁用该选项，或记录风险接受并用回归测试锁定行为。

## `0.1.0-rc.2` 放行步骤

以下顺序用于避免拿本地构建代替标签产物，也避免在标签创建后继续修改同一版本。

### A. 本地自动预检（维护者执行）

1. 确认工作区只包含本阶段文件，使用 Node 24 运行 `npm ci`。
2. 运行 `npm run verify:release-metadata`、`npm run legal`，并确认 `licenses/THIRD_PARTY_LICENSES.html` 没有未提交漂移。
3. 运行 `npm run build`、`npm test`。
4. 运行 `cargo fmt --check --manifest-path src-tauri/Cargo.toml` 和 `cargo test --manifest-path src-tauri/Cargo.toml --lib`。这是重依赖完整验证，由维护者安排；代理不在日常收尾中重复执行。
5. 运行 `npm run tauri -- build` 生成本地 NSIS，仅用于标签前人工验收，不作为最终发布资产。

### B. 本地安装包人工验收

1. **准备。** 使用普通 Windows 用户和可丢弃的新仓库；准备小型常规文件、1–4 GB 工作文件、8K/16K 或 50/100 MP 图片、可丢弃的 ES256 证书，以及第三方 C2PA 回读工具。记录版本、机器配置、安装包 SHA-256、开始/结束时间、峰值内存和失败日志。
2. **安装与生命周期。** 从 `rc.1` 安装状态升级到本地 `rc.2`；验证首次启动、单实例、创建/打开/切换新仓库、关闭到托盘、托盘恢复和显式退出。卸载后确认仓库和预期的用户数据保留。不要用旧 schema、旧设置或旧应用标识验证迁移，因为本候选版不声明支持这些迁移。
3. **素材库。** 创建文件夹和 Artwork，执行重命名、搜索、Ctrl/Shift 多选、拖放排序、区域选择、回收站恢复、永久删除和清空回收站；确认工作文件、选择和搜索结果不串到另一仓库。
4. **历史与调度。** 执行提交、fork、恢复、检查点、精简和分支删除；验证短周期自动备份、取消后不立即重启、连续失败通知、手动重新启用和损坏 HEAD 修复。退出时任务应在可接受时间内取消或收尾，窗口不得无状态地长时间卡住。
5. **灾备恢复。** 从设置创建整仓 bundle，分别验证完成和取消清理；退出后移走原仓库，从 bundle 的 `repository/` 打开副本并运行 scrub，确认历史、最终成品和认证记录独立可用。
6. **仓库隔离。** 用含相同 Artwork/branch UUID 的 A/B 克隆仓库快速切换，确认树、选择、工作区、历史、发布状态和延迟搜索结果不串仓。
7. **认证与预览。** 完整执行 TrustMark/C2PA 发布、首次导出、再次导出、识别、跨 Artwork 溯源和取消发布；第三方回读 C2PA，并用随包模型验证 TrustMark。取消发布应保留首次外部导出，只清理仓库内副本、记录和配置。放大后切换原图/导出图应保留倍率和视口；损坏预览时记录和取消入口仍可达。
8. **压力与错误。** 对大工作文件和高像素图片记录耗时、峰值内存、取消延迟和退出时长；超出实现硬上限的输入必须被稳定拒绝并显示可理解的错误，不得留下发布临时文件或半成品记录。
9. **法律与版本。** 在 About/Legal 和安装目录核对版本 `0.1.0-rc.2`、GPL、第三方许可闭包和 Adobe 模型许可。若本地包启用签名，验证安装包和主程序的 Authenticode 状态与可信时间戳；未签名候选版只用于验收并必须在发布时披露。

每一步记录“通过/失败/未执行”、样本规模和日志位置。失败项先修复并递增候选版本；不得修改或复用已经推送的 `v0.1.0-rc.2` 标签。
