## 2. 测量方式与新增能力

阶段 0 补齐了三处 0.2 未覆盖的测量能力（均不改变产品行为）：

- **取消延迟**：`tests/stress_support` 的闸门驱动新增计时——在发出 `cancel` 到进程退出之间
  取差，得到「操作观察到取消并收尾完成」的延迟。只在带闸门（`--cancel-on-stdin`）的取消场景
  有值；驱动循环每 5 ms 轮询一次子进程，因此该值是**上界**，比真实收尾时间多出 0–5 ms。
- **锁等待**：复用逐检查点闸门，把整仓灾备停在「正在复制仓库文件」（此时它持有跨进程写哨兵），
  在该窗口内测量只读命令的响应延迟与第二个写者 / 内容级只读命令的**拒绝**延迟。
- **调度扫描**：无头入口新增只读探针 `scheduler-scan`（`history::list_scheduled`，按 `b.id`
  全量列举），返回分支数与进程内扫描耗时；它不取运行锁、不写任何状态。

真实仓库场景通过 `Spawn::scope` 覆盖 `--workspace`（作用域根必须是仓库目录的已存在祖先），
其余参数不变。测量都走真实可执行文件，与其余压力组同一纪律。

复现（数值必须用 release 档；`--test-threads=1` 保证真实仓库场景互不争用）：

```text
cargo build --release --features headless
$env:LILITH_STRESS_BIN='target/release/lilith-artworks.exe'
$env:LILITH_BASELINE_REPO='D:\temp\Artworks'
cargo test --features headless --test stress_baseline -- --test-threads=1 --nocapture
```

原始数值同时追加到 `<target>/stress/report.jsonl`（`group = "0.2-baseline"`、`perf: true`）。

## 3. 实测数据

### 3.1 深链恢复（合成夹具，release）

确定性夹具：256 个节点、每个工作文件 96 KiB，逐节点一次提交（每次一个独立进程）。

| 指标 | 值 | 说明 |
| --- | --- | --- |
| `commitPerNodeMs` | **53.9 ms** | 单次提交摊薄（含进程启动与打开仓库） |
| `restoreOldestMs` | **223.9 ms** | 恢复最早节点，穿越 255 步反向增量 |
| `chainStepMs` | **0.9 ms** | 恢复每步摊薄（`restoreOldestMs / 255`） |
| `restoreHeadMs` | **42.1 ms** | 恢复 head（直接读 snapshot） |

对照 `stress_bench` P1（48 节点、同级文件）的 1.6 ms/步，链深加大后每步摊薄反而更低，
说明 0.2 的链解析在 96 KiB 级 delta 上**未随链长线性退化**；阶段 4 的段索引应以**大文件、
多段**场景为主战场，深链只是回归护栏。

### 3.2 取消延迟（合成夹具 + 真实仓库，release）

延迟 = 从发出 `cancel` 到进程退出的实测值。提交载荷 4 MiB；恢复为 256 节点链。

| 场景 | 逐检查点（ms） | 最大 |
| --- | --- | --- |
| 提交（4 MiB 载荷，5 检查点） | 12.3 / 14.9 / 15.4 / 15.6 / 11.5 | **15.6 ms** |
| 恢复（256 节点链，6 检查点） | 12.9 / 12.9 / 12.8 / 13.8 / 14.0 / 13.3 | **14.0 ms** |
| 整仓灾备复制阶段（真实仓库） | 13.2 | 13.2 ms |

0.2 的取消粒度是**检查点级**（节点 / 阶段边界），延迟稳定在 **12–16 ms**，与载荷大小、链位置
无明显相关（由进程收尾与资源回收主导，而非数据量）。该值含 ≤5 ms 的轮询粒度，按上界解读：
真实「观察到取消 → 收尾完成」只会更短。对照计划 §3.D 的研究结论（原文见
`archive/0.3-architecture-algorithm-plan-alpha1-2026-10-05.md`；每 tile = 320 KiB
原始数据，写 ≤12 ms / 恢复 ≤5.4 ms），0.2 的实测与之同量级，但 0.2 的取消点比「每 tile」粗；
阶段 4 引入 `CancelToken` 后应把取消地板对齐到每 tile，并保持该量级。

### 3.3 锁等待（真实仓库，release）

写者（整仓灾备）持有跨进程写哨兵期间，逐条探针的耗时与结果：

| 探针 | 耗时 | 结果 |
| --- | --- | --- |
| `list-tree`（只读） | 31.2 ms | 成功，未阻塞 |
| `list-history`（只读） | 28.6 ms | 成功，未阻塞 |
| `scheduler-scan`（只读） | 26.4 ms | 成功，未阻塞 |
| `verify`（只读） | 27.0 ms | 成功，未阻塞 |
| 第二个写者 `cleanup` | 29.8 ms | **被拒**：仓库正在被另一个进程写入；不支持同一仓库的多进程写入 |
| 内容级只读 `scrub` | 30.2 ms | **被拒**：仓库正在被写入，请稍后重试 |

0.2 的写哨兵是**立即拒绝**（`busy_timeout = 0`）而非排队：第二个写者在 ≈30 ms 内拿到明确
错误，只读命令完全不受影响（26–31 ms 即「进程启动 + 打开仓库」的固定开销）。阶段 1 的
`OperationCoordinator` 与阶段 2 的统一 owner lock 必须保持这两条语义：**只读不被写锁挡住**、
**写者让位可观测**，不回退成让第二个写者排队等待。

### 3.4 调度扫描（真实仓库，release）

`history::list_scheduled`（按 `b.id` 全量列举候选）：

| 指标 | 值 |
| --- | --- |
| 外部耗时（含进程启动 + 打开仓库） | 27.1 ms |
| 进程内扫描耗时（`scanMs`） | **5 ms** |
| 候选分支数 | 2 |

本仓只有 2 个已调度分支，数值主要由「打开仓库」构成，扫描本身 ≈5 ms。阶段 5 把它改为
deadline 优先的候选生成后，应在**多分支仓库**上重测才能看出索引收益。

### 3.5 清理查询（真实仓库，release）

| 指标 | 值 | 结果 |
| --- | --- | --- |
| `scan-unreferenced` | 66.2 ms | 未引用文件候选 0 |
| `cleanup`（队列重放） | 32.2 ms | 待清理队列 0 |

健康仓库下两者都是「遍历 + 比对」的线性成本，0 候选/0 待清理；阶段 5 改为连接内临时引用表
的批量 anti-join 后，用同一仓库对比查询次数与耗时。

### 3.6 灾备 I/O（真实仓库，release）

整仓灾备（扫描 + 复制 + 校验 + 发布）：

| 指标 | 值 |
| --- | --- |
| `backupMs` | **234,894 ms（≈3.92 min）** |
| 源仓库字节 | 10,556,232,017 B |
| 副本字节 | 10,556,232,529 B（+512 B manifest） |
| 吞吐 | **≈42.86 MiB/s** |

阶段 5「边复制边计算 digest、manifest 复用摘要」应提升吞吐；对照口径保持「校验语义不弱于
0.2」，即吞吐提升不得以放弃逐文件摘要为代价。

### 3.7 任务耗时（真实仓库，release）

| 任务 | 耗时 | 规模 |
| --- | --- | --- |
| `verify`（重开 + 完整性 + 语义校验） | 46.3 ms | 主库 856 KB |
| `scrub`（全库历史链逐块校验） | **182,475 ms（≈3.04 min）** | 59 节点 / ≈9.83 GiB |
| `list-tree`（整树装配） | 357.5 ms | 7 个树节点 |
| `list-history`（每作品） | 28.5 ms | 3 个 Artwork |
| `verify`（灾备之后复核） | 39.7 ms | 源仓库未变 |

`scrub` 是全库校验里最重的一环（≈3 min），远超其余任务；阶段 4/5 的算法改动应以 `scrub`
与灾备为「不能被拖慢」的两个上界。`list-tree` 357 ms 对 7 个节点偏高，但同一构建档、同一仓库
在 §3.3 的锁等待窗口里只用了 31.2 ms——差异更像**本次采集的第一条树装配**（冷缓存、首次读）
而不是装配算法。因此不要把 357 ms 当成树装配的成本基线；阶段 1/3 若要判断它是否夹带了多余
IO，需在同条件下复测（先跑其它任务再测，或重复取最小值）。

## 5. 约束与说明

- **不改产品行为**：阶段 0 只新增 headless 只读探针 `scheduler-scan`、测试支持（取消延迟计时、
  `Spawn::scope`）与 `stress_baseline` 组；无头入口 feature 门控、不进发布产物，GUI 路径不变。
- **真实仓库副本只做读与「不写源仓库」的整仓灾备**：运行后源仓库数据字节数不变（测试会断言），
  唯一副作用是写命令取得哨兵时创建的 `.lilith-write-lock.sqlite3`。本次采集后已用采集前的
  pristine 副本还原 `D:\temp\Artworks`（449 文件、10,556,232,017 B，与采集前一致）。
- **真实仓库副本是外部临时资料，不是本项目的长期测试标准**：`D:\temp\Artworks` 只服务阶段 0 的
  一次性采集，0.3 计划落实后撤除。本报告的数值不写入任何基线文件、不设阈值、不进 CI；阶段 1–5
  的对照看同机同档的复测或合成夹具（本组 B1/B2 与 `stress_bench`），不要把它当成后续批次的
  默认测试对象。2026-10-25 的复测使用它的独立副本 `D:\temp\Artworks-2026-10-25`，未改动原副本。
- **绝对耗时机敏**：同一仓库的两次采集里 `verify` 为 46–67 ms、`scrub` 为 182–190 s，其余
  指标波动更小；比对看**同档相对变化**，不把绝对值当门槛。
- `stress_baseline` **不进 Windows CI**，也不在日常收尾运行；它需要 `LILITH_BASELINE_REPO`，
  未设置时真实仓库场景**明确跳过**（不是失败）。2026-10-25 的对比复测是临时恢复的一次性
  探针，运行后已删除，仓库中仍没有这个测试目标。

复测的 4 个未引用候选是副本里**早已存在**的冗余增量与中断残留临时文件（修改时间在
2026-09-10 至 2026-10-08），不是本次运行产生的；测试只报告计数、没有删除它们。

### 7.3 结论

- **取消与锁语义未回退**：取消地板保持 12–16 ms；写者持有跨进程哨兵时，只读命令仍在
  26–37 ms（主要是进程启动与打开仓库）内返回，第二个写者与内容级 `scrub` 都被明确拒绝。
- **深链恢复没有随重构退化**：256 节点链的每步摊薄从 0.9 ms 降到 0.8 ms，最早节点恢复从
  223.9 ms 降到 196.5 ms，head 直接从快照读的 42.1 → 39.9 ms。
- **规模不敏感的查询基本持平**：调度扫描、未引用文件扫描与清理队列都在同一量级（±6%）。
- **`scrub` 与灾备明显变快**：5.55× 与 4.40×。这来自 0.3 的段索引、管道化读写与 v2/v6
  存储路径，但也含同一副本、磁盘缓存已热与迁移后元数据的影响；不能把它当成跨机器标准。
- **`verify` 的 +15.6% 是毫秒级固定成本**：0.2 与当前的 `verify` 都在几十毫秒量级，主要受
  进程启动与打开仓库支配；`list-tree` 的 357.5 ms 则是 0.2 采集时已注明的**首次冷读**，
  当前 32.4 ms 与锁等待窗口里的 31–37 ms 一致，不是装配算法回归。
- 本次对比是一次性复测，不设阈值、不进 CI；长期回归仍看 `stress_bench` 与
  `2026-10-25` 全量压力测试报告。
