## 0. 结论摘要

1. **有一组测试已经完成历史使命**：阶段 0 的一次性 0.2 基线组，官方文档也写明不是长期门槛。
2. **有一份性能基线表已经过期**：调试档仍是 0.2.0 时代的数据，新增场景没有基准。
3. **严格性能门有两个真实缺陷**：笔迹 5000 笔档的每笔耗时基线为 0（必判失败）；恢复吞吐量按“越小越好”比较（变快反而报回归）。
4. **若干测试的尺子太松或名不副实**：内存上限远大于被测数据、并发读没有验证“不阻塞”、大文件中断漏测一个取消点、并发拒绝统计因旧文案而永远为 0。
5. **有明确的高价值空白**：损坏快照后内容又变化的提交、大文件并行阶段被强杀、手动提交后的自动全量计数清零、后台保存提示、长笔迹跨视口裁剪。

**最值得先做的四件事**：退役一次性旧基线组；修两个严格性能门；补“损坏快照 + 内容变化再提交”；补“大文件并行阶段强杀”。

## 1. 建议退役或删除

### 1.1 `stress_baseline`：阶段 0 的一次性采集，已与长期回归脱节

**证据**

- 文件头写明它是“阶段 0：0.2 基线采集”，真实仓库副本是“外部临时资料”，
  “只把它当阶段 0 的一次性测量对象——不做长期夹具、不设阈值、不生成基线文件”
  （`src-tauri/tests/stress_baseline.rs:1`、`:14–17`）。
- `docs/guides/validation.md:87–90` 也明确：该组“不生成基线文件、不设阈值、不进 CI”，
  “不要在后续批次里把它当默认测试标准”。
- 合成部分（深链恢复、取消延迟）与 `stress_bench` 的 P1、`stress_cancel` 的 A1/A2
  大量重叠。
- 真实仓库部分在没有 `LILITH_BASELINE_REPO` 时直接跳过
  （`src-tauri/tests/stress_baseline.rs:331`），平时既不跑也不失败。
- 唯一独有的“取消延迟”只打印数值，没有阈值、没有基线文件，回归时不会失败。

**额外缺陷：构建档标错**

`build_profile()` 用测试脚手架自身的 `cfg!(debug_assertions)` 判断
（`stress_baseline.rs:70–76`），但文件头的标准命令是 debug 脚手架驱动 release 二进制
（`:19–26`）。因此按标准方式采集时，release 数字会被标成 `debug`，
与 `stress_bench` 后来引入的 `LILITH_STRESS_PROFILE` 口径不一致。

**影响**

保留它只会增加编译与维护成本，并给出一组无法作为门槛、还可能标错构建档的数字。
历史数值已经归档在 `docs/planning/archive/0.3-baseline-2026-10-18.md`。

**建议**

- 如果 0.3 发布前仍需要真实仓库的一次性对照：把真实仓库采集保留为手工脚本或一次性动作，
  从 `cargo test` 目标中移除。
- 如果不再需要 0.2 对照：直接删除整组。
- 无论哪种选择，不要再把它当长期回归门槛。

## 2. 指标已失效或会误判（必须修）

### 2.1 笔迹每笔耗时基线为 0，严格模式必判失败

**证据**

- `perf-baseline.json:95–96`：
  `writePerStrokeMs5000` 与 `writePerStrokeMs5000#cpu` 都是 `0.0`。
- 严格门断言 `ms <= base * factor`（`stress_bench.rs:346–359`）。
- 基线为 0 时，任何非零测量都不满足；而每笔值本身只有约 0.045 ms
  （225.4 ms / 5000 笔，`docs/user/stress-test-report.md:535`），基线按 0.1 ms
  取整写入就成了 0.0（`stress_bench.rs:1597–1599`、`:406–408`）；同一粗粒度下
  500 / 2000 档记为 0.1，只是侥幸压在阈值内而没有暴露。

**影响**

严格模式一旦启用（发布档基线含 P9），`writePerStrokeMs5000` 的墙钟比对会稳定失败
（它的 `#cpu` 条目因基线低于 50 ms 本就不参与比对）。它不是“性能退化”，而是指标
分辨率不足。目前严格模式不在 CI 中，所以这个缺陷没有暴露。

**建议**

- 每笔耗时改为“只记录”：注意 `wall_measure` 只省掉 CPU 记录、墙钟仍会进严格比对
  （`stress_bench.rs:300–310`），需要一个真正的“只记录/不比对”标志（或按标签排除），
  严格门只看整批写入/读取总量。
- 如果一定要保留每笔门槛，把基线与测量一起换算成微秒（或提高每笔点数），
  让数值稳定高于 0.1 ms 的写入分辨率。

---

### 2.2 恢复吞吐量被当成延迟比较，方向反了

**证据**

- `stress_bench.rs:648–651` 把 `restoreOldestMiBPerSecond`、
  `restoreHeadMiBPerSecond` 作为普通测量发出。
- 严格门的墙钟比对对每条测量无条件套用 `ms <= base * factor`
  （`stress_bench.rs:300–310`、`:354–359`），没有按指标方向分类。

**影响**

吞吐量本应越大越好。现在恢复速度提升 2.5 倍以上反而会被判成“性能回归”。
这会让真正的大幅优化无法通过严格门。

**建议**

- 为吞吐量指标增加“越大越好”的比较方向（例如 `>= base / factor`），或给这类指标
  加“只记录”标志——`wall_measure` 不是“只记录”，它只是省掉 CPU 条目，墙钟仍会被
  严格门比对。
- 墙钟、CPU 时间与吞吐量三类指标应使用不同的比较规则。

### 2.3 C7 少取消最后一个提交检查点

**证据**

- C7 注释写“逐个取消检查点各取消一次”
  （`src-tauri/tests/stress_large.rs:968–973`）。
- 实际循环是 `for target in 1..=5_usize`
  （`stress_large.rs:990`）。
- 提交路径的交互检查点总数是 6，最后一个是事务内标记点
  （`src-tauri/tests/stress_support/mod.rs:55–59`）。

**影响**

大文件档从未在“事务已写入、尚未提交”这个检查点取消。
而该点正是需要验证“已发布文件回滚”的边界之一；A1 的小文件用例覆盖了它
（`stress_cancel.rs:91` 按 `1..=COMMIT_CHECKPOINTS` 取消），
但大文件 + 并行管道的组合没有覆盖。

**建议**

把循环改为 `1..=COMMIT_CHECKPOINTS`，并让 C7 直接引用该常量，
避免以后新增边界时再次漏测。

### 2.4 并发测试仍在等待旧错误文案，拒绝统计实际失效

**证据**

- 仓库写锁冲突的稳定文案是
  “仓库正在被另一个进程写入；不支持同一仓库的多进程写入”
  （`src-tauri/src/repository_lock.rs:50`）。
- 旧的内容级只读拒绝文案是“仓库正在被写入，请稍后重试”
  （`repository_lock.rs:55`；它仍被内容级只读探测使用，如存储页扫描与画板 DDS 校验，
  不是死文案）。
- J5 仍用旧文案判断全库校验是否被拒绝：`:474` 匹配完整旧文案
  “仓库正在被写入，请稍后重试”，`:536` 只匹配前缀“仓库正在被写入”
  （`src-tauri/tests/stress_concurrency.rs:473–478`、`:536`）。
- 但 `scrub` 自 2026-10-19 起按前台写命令执行（`src-tauri/src/app/usecases/backup.rs:262–279`），
  另一个进程持锁时拿到的是写锁冲突文案，而不是旧的内容级只读文案；同组的 J6
  已按新文案断言并注明这次切换（`stress_concurrency.rs:553–560`、`:596–602`），
  J5 的注释（`:409–413`）还是旧口径。

**影响**

`scrubRefused` 永远为 false，真实拒绝被计入 `other_failures`。
报告会持续显示“其他失败”，让人误以为并发路径有未解释的错误。

**建议**

- 把 `:474` / `:536` 的匹配换成写锁冲突文案，与 J6（`:596–602`）对齐；替换时注意
  `repository_lock.rs:53` 还有一条只差一个“被”字的写等待超时文案，别拿错。
- 报告中继续分列“精简被拒绝 / 全库校验被拒绝 / 其他失败”三类（`:543–550` 已有计数
  与“本轮未触发”说明）；修好匹配后，全库校验的真实拒绝才会落进正确的桶。

## 3. 指标偏松或名不副实（建议改）

### 3.1 D1 深链内存上限远大于被测总量

**证据**

- 300 次提交 × 128 KiB 工作文件，总量约 37.5 MiB（`stress_scale.rs:145–146`）。
- 断言峰值内存 `< 256 MiB`（`src-tauri/tests/stress_scale.rs:239–242`）；
  峰值字段缺失时按 0 计（`:172`），断言只会更松。

**影响**

即使实现把整条链的每一份内容都留在内存里，37.5 MiB 仍然小于 256 MiB，
测试依然通过。它不能证明“内存不随链深增长”。

**建议**

- 把上限改成与被测总量挂钩的明确比例，或改成固定的小预算（例如 64 MiB）。
- 如果真实目的只是拦灾难性内存失控，应把注释改成“灾难性上界”，不要写成流式证明。

### 3.2 H3 素材板规模的内存上限基本恒真

**证据**

- 300 张 32×32 的 BC7 图，载荷约 0.3 MiB。
- 断言峰值 `< 512 MiB`（`src-tauri/tests/stress_pin_board.rs:463–470`），
  且整条断言包在 `if let Some(peak)` 里（`:464`），字段缺失时直接跳过。
- 文件头把“数百张”称为个人真实上限
  （`stress_pin_board.rs:35–38`），但产品上限是 20,000 条。

**影响**

无论检查逻辑是否随图片数放大，这条断言都会通过。它没有验证“内存有界”。

**建议**

- 要么把规模推到接近真实上限（例如数千到 20,000 条），
  要么把内存上限降到有意义的固定值，或删除这项主张。
- 规模提上去后，顺便覆盖导入上限 256 个文件的截断/拒绝路径。

### 3.3 J2“并发读不互阻塞”只验证了“都成功”

**证据**

- 标题声称并发读互不阻塞（`src-tauri/tests/stress_concurrency.rs:187–190`）。
- 实际只断言四个进程都成功、状态不变（`:213–224`），没有耗时或重叠证据。

**影响**

四个读命令完全串行执行也会通过。测试名承诺的语义没有被验证。

**建议**

- 增加一个宽松的墙钟上界，或按 J1 的做法对调用耗时断言（`stress_concurrency.rs:163–167`）。
- 如果担心机器抖动导致 flaky，可以只记录不设硬门槛，但不要再把“互不阻塞”写成已验证结论。

### 3.4 K2 带空格的标题用例没有独立断言

**证据**

- 先创建未加空格的 160 字符 emoji 标题，再创建带首尾空格的同一标题
  （`src-tauri/tests/stress_input.rs:164–173`）。
- 最后只断言树里存在未加空格的标题（`:175–183`）。

**影响**

如果 `trim` 完全失效，`:173` 的创建会按 166 个字符超限被拒绝，`expect_ok` 当场失败——
这一层没有被漏掉；真正会漏掉的是“按 trim 后的长度校验、却把原始值存库”这类实现：
带空格的版本作为第三个节点存在，而 `:175–183` 只要求两个无空格标题存在，照样通过。

**建议**

- 断言标题集合恰好是 emoji 与 CJK 两项，或断言不存在带首尾空格的标题；
  后者对“存原始值”这类实现更直接。

### 3.5 G2 只确认耗时字段被记录，不是性能门槛

**证据**

- 只断言 render / encode / signing 的耗时都 `> 0`
  （`src-tauri/tests/stress_authenticity.rs:600–607`）。

**影响**

这验证的是“产品自报了阶段耗时”，不是“发布有多快”。
可以保留为观测数据，但不应被当作性能证据。

**建议**

- 保留内存上限与回读正确性断言；把耗时断言改名为“阶段耗时已上报”，
  或在文档中明确它不构成性能门槛。

### 3.6 高频提交的 180 秒护栏基本不会触发

**证据**

- 20 次提交给 180 秒（`src-tauri/tests/stress_concurrency.rs:90–109`），
  平均每次 9 秒。

**影响**

正常实现远低于此，即使明显退化也未必触发。作为“效率护栏”意义很弱。

**建议**

- 删除护栏，或改成与同机基线挂钩的相对上限。
- 如果保留绝对值，应缩小到能反映“一次提交明显异常”的量级。

### 3.7 大文件内存与快照上界比现实现宽太多

**证据**

- C3 的内存允许值是 `逻辑大小 / 8 + 24 MiB`
  （`src-tauri/tests/stress_large.rs:652`）。
  4 GiB 档因此允许约 536 MiB，而并行管道自身预算只有 16 MiB
  （`src-tauri/src/backup/chunk_file/snapshot.rs:41–46`）。
- 快照开销允许“逻辑大小的 2% + 1 MiB”（`stress_large.rs:70–71`），而 v2 每块只多
  44 字节记录头（`src-tauri/src/backup/chunk_file/mod.rs:70–71`），对 16 KiB 平均块
  （同文件 `:345–352` 的默认 CDC 配置）约合 0.27%。

**影响**

它们仍能拦“把整份文件读进内存”这类灾难性错误，但已经不能证明“流式处理”。
如果文档引用这组数字作为流式证据，会高估测试强度。

**建议**

- 收紧到与当前管道预算相称的量级，或保留为灾难性上界并在注释与报告中明确说明。
- 不要再用这组上界证明“峰值内存与逻辑大小无关”。

### 3.8 前端两条测试名与当前行为不符

**证据**

- “keeps preview textures resident under the shared eviction budget”
  （`src/modules/pin-board/renderer.test.ts:165–183`）：
  预览纹理与高清纹理已经是两套独立预算
  （`src/modules/pin-board/texturePolicy.ts:22–34`），标题里的“shared”已过时；
  而且构造里高清表只有被保护的一张、没有可淘汰对象，两个断言近乎恒真——
  它实际只验证了“淘汰高清时不碰缩略图”这一条弱性质。下一条用例
  （`:185–201`）测的是缩略图自己的预算，方向相反，并没有覆盖它。
- “builds the stroke buffer once and only rebuilds when zoom changes”
  （`renderer.test.ts:478–533`）：逐段裁剪加入后，平移出超扫边距也会重建，
  测试正文本身已经这么期望（`:528–532`），标题与断言相矛盾；绑定同一行为的
  下一条用例（`:535–581`）覆盖更完整。

**影响**

标题会误导后来的人，以为缓存仍是共享预算、缓冲只在缩放时重建。

**建议**

- 把 165 改成：让高清预算真正超限并放一张可淘汰的高清纹理，断言只淘汰高清、
  缩略图保持；标题去掉“shared”。
- 把缓冲测试改名为“缩放或视口移出超扫边距时重建”，并与 `:535–581` 合并去重。

### 3.9 测试名承诺了没有验证的界面行为（低优先级）

- `src/modules/pin-board/PinBoardModule.test.ts:31–38` 的
  “toggles the floating annotation toolbar on an unmodified T”
  实际只验证快捷键常量与按键匹配，没有验证工具栏的显示/隐藏。
- 建议补一个组件级按键用例（该文件目前从不渲染组件，需要先搭渲染夹具）；
  如果短期不做，至少把标题改成“快捷键绑定正确”。

## 4. 建议新增的测试（按价值排序）

### 4.1 旧快照已损坏、内容又发生变化后再提交（高）

**现状**

R1 只覆盖“内容未变化”的路径：先改坏 head snapshot（`stress_damage.rs:56`），
再以未变化的内容提交，提交直接返回“内容未变化”、不读旧快照
（`src-tauri/tests/stress_damage.rs:97–126`）。

**为什么重要**

内容变化时，提交仍会打开 head snapshot 生成反向增量
（`src-tauri/src/backup/worker.rs:412–435`）。移除提交路径的整份复检后，
这条路径没有端到端测试。需要确认它是：干净失败、不推进历史、不留下半成品、
不把损坏扩散到新节点。

**建议**

在 `stress_damage` 增加一条：损坏 head snapshot → 修改工作文件 → 提交。
断言错误可读、节点数不变、没有新增 snapshot/delta、重新打开仓库仍可用，
且恢复旧节点仍被拒绝。

### 4.2 大文件并行阶段被强杀（高）

**现状**

- 取消/强杀测试的基准提交几乎都用 96 KiB 工作文件，后续写入多在 64–80 KiB。
- 并行管道在文件不小于 4 MiB 时启用（低于阈值走串行，单核也保持串行；
  `src-tauri/src/backup/chunk_file/snapshot.rs:41`）。
- C7 只在大文件的交互检查点取消，并在第一个检查点强杀
  （`src-tauri/tests/stress_large.rs:990–1042`）。

**为什么重要**

reader → 多个哈希 worker → 顺序 writer 是最近新增的路径。
进程在管道中间被强杀时，临时文件、半成品快照、锁状态是否有残留，
目前没有跨进程端到端验证。

**建议**

- 补一条大于 4 MiB 的提交，在管道处理阶段强杀。
- 断言：没有半成品快照/增量、临时文件可被清理、仓库可重开、历史不推进。
- 注意和已知边界区分：`stress_crash` 的 B1 已如实记录“发布后、提交前”强杀会留下
  完整的已发布孤儿且当前不会被自动回收（`src-tauri/tests/stress_crash.rs:28–39`）。
  在管道/发布前阶段强杀不应出现这种已发布孤儿；若覆盖发布后的检查点，断言要按
  该已知行为设计。
- 另补一条 4 MiB ± 1 的边界用例，确认启用/不启用并行管道的切换都正确。

### 4.3 手动提交后自动全量计数是否清零（高，成本低）

**现状**

- 逻辑在 `src-tauri/src/app/usecases/backup.rs:43–49`：提交用例只要成功返回就清零
  连续快速命中计数（GUI 手动提交与无头提交共用该入口，`manual_priority` 只影响
  优先与让位）。
- 目前只测了清零帮助函数本身（`src-tauri/src/backup/scheduler.rs:1322`），
  没有测这个入口真的调用了它。

**为什么重要**

如果接线失效，用户每次手动保存后，后台仍会按旧计数提前强制全量检查，
表现为“刚保存过又跑一次完整检查”。

**建议**

在应用层用例测试里断言：手动提交成功后库中的连续命中计数归零；
失败或取消时不清零。

### 4.4 素材板后台保存提示（中高）

**现状**

- 订阅后台结算状态的 hook（`src/modules/pin-board/usePendingSettle.ts:14–37`）
  没有任何测试。
- 只有结算队列本身的纯逻辑测试。

**为什么重要**

这是用户在切换画板后唯一能看到的反馈：延迟 800 ms 才出现、
失败立即显示并保留（重试按钮在消费层 `PinBoardModule.tsx`，不在 hook 内）。
接错会导致“改动没写进仓库但界面不说”。

**建议**

补 hook 级测试：无任务时不显示；短任务在延迟内完成不闪提示；
超过延迟显示数量；失败立即显示且带重试；重试成功后提示消失。

### 4.5 横跨视口的长笔迹逐段裁剪（中高）

**现状**

只测了整条笔迹完全在裁剪框外时被丢弃
（`src/modules/pin-board/strokeRender.test.ts:326–342`）。

**为什么重要**

最近的优化改成了逐图元裁剪（`src/modules/pin-board/strokeRender.ts:269`）。
如果裁剪边界算错，横跨视口的长笔迹可能被整段削掉，表现为“平移后笔迹断掉”。

**建议**

补一条长笔迹：一部分图元在框内、一部分在框外，断言框内图元保留、框外图元丢弃，
且可见段连续。

### 4.6 素材板真实上限与条目类型过滤（中）

**建议覆盖**

- 一次导入超过 256 个文件时的截断/拒绝路径（剪贴板粘贴在
  `src-tauri/src/pin_board/mod.rs:521–523` 截断，导入命令在
  `repository.rs:1486–1488` 拒绝）。
- 接近 20,000 条上限时的写入与拒绝（强制点在 `repository.rs:978` 与 `:1223`）。
- 画板中同时存在位图、文字、笔迹时，DDS 完整性与孤儿扫描只统计位图，
  文字与笔迹不参与文件检查（`pin_board/scrub.rs:16`）。

前两项上限目前没有任何测试覆盖（现有压力夹具刻意按 100 张一批导入、避开了
256 与 20,000）；第三项在压力测试里没有混合条目用例。

### 4.7 原生整理命令的参数边界（中）

`src-tauri/src/pin_board/mod.rs:557–588` 对“少于两张图、间距越界、退化条目被
跳过后不足两张”有校验，但现有测试只覆盖整理算法本身（`arrange.rs` 的单测），
没有从命令入口验证这些拒绝路径。该命令是纯计算、不经 `OperationCoordinator`
（`:551–555`），单元测试直接调用即可，不需要无头进程。

### 4.8 强杀后临时文件清理闭环（中低）

仓库根 `temp/` 下的 `.tmp*` 暂存文件清扫（`src-tauri/src/cleanup.rs:578` 的
`sweep_repository_temp`）有单元测试（`:1376–1452`），但缺少“并行管道处理中被强杀
→ 残留临时文件 → 下次启动清理”的跨进程闭环（现有强杀用例要么断言无残留，
要么只记录孤儿事实）。可与 4.2 合并。

### 4.9 可选硬化：门控守护的扫描范围（低）

`src-tauri/tests/gate_guard.rs:26–41` 的目标集合只收集 `stress_*.rs`
（门控检查 `:44–68` 与临时目录检查 `:80–112` 共用这一份列表）。
如果将来新增一个不带 `stress_` 前缀、却会启动无头二进制的集成测试，
它不会被门控守护检查到。建议扫描 `tests/` 顶层除守护自身外的全部 `.rs`，
或至少把所有会启动子进程的测试纳入检查。

## 5. 不建议新增的测试

### 5.1 自适应强制全量的端到端流程

阈值随队列与文件大小分档、计数归零、检查方式记录、重启后读取，已经有较完整的
单元测试（`src-tauri/src/backup/scheduler.rs`）。再开一套无头入口成本高，
收益主要是重复验证。

### 5.2 前端硬性耗时门槛

`strokePerfProbe` 目前只验证输出结构与非负耗时，这是合理的 smoke test。
给它加绝对耗时门槛会把机器噪声变成 flaky 断言；CPU 侧成本仍按维护者手工探针复测，
帧率继续由真实适配器人工确认。

### 5.3 GPU 帧率与界面自动化

项目明确禁止 GUI 自动化，界面视觉、手感与帧率继续走人工验收。

## 6. 建议处理顺序

1. **删除或退役 `stress_baseline`**，同时修正它的构建档标注问题（若暂不删除）。
2. **修严格性能门**：
   - 每笔耗时改为只记录（需要真正的不比对机制，见 §2.1）或提高测量分辨率；
   - 吞吐量改为“越大越好”或只记录；
   - 刷新或删除调试档基线表。
3. **修会误导报告的信号**：
   - J5 的错误文案与拒绝分类；
   - C7 补第 6 个检查点；
   - D1/H3/J2/G2/K2 的弱断言。
4. **补高价值空白**：
   - 损坏快照 + 内容变化再提交；
   - 大文件并行阶段强杀与 4 MiB 边界；
   - 手动提交清零自动全量计数；
   - 后台保存提示 hook；
   - 长笔迹跨视口裁剪。
5. **按需要补中低优先级**：素材板上限、整理命令边界、临时文件清理闭环、门控扫描范围。
