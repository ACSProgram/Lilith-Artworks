# 架构审查整改计划复核（2026-11-03）

审查对象：`architecture-review-remediation-plan-2026-11-03.md`。

本复核对照了计划、当前交接/待办、相关模块文档，以及计划涉及的前端和 Rust 实现。它评估
计划的范围、方案与验收是否合理，不表示计划已获批准，也没有修改被审查计划或实施代码。

## 结论

计划有不少可验证的清理项，但把低风险事实修正、行为变更、重复收敛、测试搬迁和数个高风险
模块重构捆成约 15k 等效新增代码的七批整改，范围明显大于当前证据所能支持的必要程度。建议
先落实已核实的文档/注释错误和明确重复；将行为变化独立验收；把大文件拆分与 SQL 所有权调整
降为逐项决策的候选，不以预设文件数、行数或批次数作为完成目标。

## 需要调整的方案

### 1. “等效新增代码”会奖励不必要的改动

计划第 1.4 节把纯移动按 10% 折算，并为每批设定约 2–3k 等效新增代码，偏差超过 30% 还要
解释。代码行数与行为风险、维护收益没有稳定关系；这套指标会给拆模块、搬测试和补文档施加
人为产量目标，与第 1.3 节“不为拆分而拆分”相冲突。

建议删除批次代码量目标和偏差说明，改用结果验收：修复了哪项缺陷、减少了哪些真实重复、建立了
什么测试接缝、改动是否保持契约。拆分类任务以依赖方向清晰、独立测试成立、调用方不需要传递
宽泛可变上下文为准，不以 facade 行数为准。

### 2. 批次规模和顺序缺少风险隔离

第 3 节安排七批、约 15k 等效代码，且批次 7 汇总前面所有工作；批次 3 将多组 Rust 测试外移
及生产模块拆分放在一个全量批次，批次 4 又混合保存契约、几何、hooks、测试组织和 CSS。即使
每批通过测试，回归也难以定位到具体行为变化，维护者手工验收则被集中推迟到高风险批次之后。

建议按“可独立合并和验证的缺陷”组织工作，而非先承诺七批。先完成批次 1 中确认无行为变化的
文档、注释和确切死代码；抽象收敛、UI 行为修正、各文件拆分分别形成独立决策和小批次。每批
在自身范围内验收后再决定是否继续，不预设总体代码量或完成时间。

### 3. 右键菜单统一带来计划未承认的行为变化

第 1.2 节声明“不改变产品行为”，第 4.6 节却明确要为 History/Library 增加 Escape、滚动和
缩放时关闭菜单的行为。共享 `ContextMenu` 确有这些关闭监听，而当前两个模块各自处理 Escape
和点击外部。此项可以是合理的 UX 修复，但不是无行为变化的重构；第 4.8 节也没有 GUI 验收，
无法验证菜单定位、滚动容器和缩放下的关闭表现。

建议把该项标为有意行为修正，单独定义验收（键盘、页面/树滚动、窗口缩放、菜单定位及焦点），
并由维护者手工确认。若本轮严格要求行为不变，就暂缓接入共享菜单。

### 4. 前端保存载荷“完全一致”不符合当前契约

第 7.1 节把 `pendingSettle.ts` 与 renderer 的 `editableItems` 描述为“最高危的重复”，要求共享
唯一映射并测试两者输出一致。但当前 `pendingSettle` 为文字条目总是带完整文字载荷；renderer 的
`editableImages()` 只在文字签名变化时带载荷。Rust `save_board` 将有载荷视为文字更新请求，且
据此推进历史步骤。因此两条路径代表不同的保存语义，不是可以直接统一成同一输出的重复实现。

建议先为两个输入契约分别命名并写测试：切换快照必须保留完整文字状态，常规保存只发送变更文字
载荷。若要共享，最多共享字段转换/克隆等纯逻辑，保留调用方决定是否包含载荷；不要断言两个
完整请求相等。

### 5. 跨领域删除方案没有可行的事务传递设计

第 9.1 节默认由应用 usecase 顺序调用两个领域公开能力并保持一个事务，但现有 `library` 永久
删除与 `history` 重置各自在自己的 repository 中打开连接并创建事务；现有 usecase 的公开仓储
调用也接收 root，而非同一个 `Transaction`。Library 永久删除需在事务内清理 `final_artifacts`
和 `history_nodes`；History 重置需在同一事务内更新 `artworks` 与 `library_nodes`。若要跨调用
共享事务，就必须重构仓储入口、暴露 transaction 层级接口并处理领域依赖；这不是当前方案里
“顺序调用”即可做到的，也可能把 SQL 与 schema 耦合转移到 app 层。

建议默认保持现有单事务实现，并在 schema/模块文档登记必要的跨域表约束与所有者理由，再用回滚
测试锁住原子性。只有在能明确事务 API、所有权边界和调用方向后，才另立重构方案；不要把消除
跨域 SQL 本身设为验收目标。

### 6. 共享前端 DTO 的放置和 API 复用边界需要重写

第 4.4 节提出将 `PinBoardTextureCacheLevel` 作为 pin-board 类型供 `app/types.ts` 导入，但
`app` 反向依赖 `modules/pin-board` 会让应用配置类型依赖页面领域模块。另一个重复实际不只两处：
该 union 同时出现在 `app/types.ts`、`pin-board/types.ts` 和 `pin-board/texturePolicy.ts`。计划
也没有说明如何处理后者。

`BackupRuntimeStatus` / `BackupTaskKind` 可放在中立 DTO 模块供双方引用；但两个 API 封装属于
不同的调用入口，History API 仍应由 History controller 消费，不能为了少一个 `invoke` 包装而
让 History 调用 `app/api`。`get_backup_runtime_status` 的前端命令名本身只有一份注册，重复的
只是两处类型化调用包装。

建议区分“共享 DTO”与“领域命令 API”：跨模块配置 DTO 放入中立契约位置；各模块继续经自己的
`api.ts` 调用同名 Tauri 命令；合并前先查所有实际定义与消费者，不按单纯文本相似度决定所有权。

### 7. `storage.rs` 可能被扩张为杂项工具箱

第 5.1 节打算往基础 `storage.rs` 放文件摘要、哈希、SQLite sidecar 清理、不覆盖发布、连接闭包
和路径唯一化。这里面有些跨领域重复可能值得收敛，但用途并不都属于存储基础设施：sidecar
清理有不同文件集合和错误上下文；发布有临时文件同步、错误类型与目录前置条件；哈希还有可取消、
抽样及错误语义差异。尤其“2 份实现”一项与“至少 3 处调用”准入条件冲突，计划本身也要求差异
明显时保留，却仍在目标列表中安排抽取。

建议对每个候选先列出调用点、输入/输出语义、取消需求和错误映射，再单独判断。优先只提取行为
完全一致且能减少真实维护分叉的纯算法；不要为了拥有统一入口把不同策略塞入 `storage.rs`。
`with_connection` 也应先确认调用样板的真实形状和收益，不要仅以 24+ 次 `map_err` 数量决定
增加闭包层。

### 8. 拆分目标过度预定，且 facade 行数不是质量指标

第 6 节预定拆出 `create.rs`、`cleanup.rs`、`storage_overview.rs`、`dds.rs`、`rendition.rs`
多个文件；第 8 节进一步列出 renderer 的九个子模块，并将 facade 设为 600–800 行。行数大
不自动代表边界不清：拆分若要求传递大型可变状态或暴露更多 `pub(super)` 接口，会增加理解成本。
素材板文档已记录 GPU 与导出实现已有独立文件；renderer 仍承担状态机与画板生命周期协调，计划
也承认其中存在强耦合。预先规定九个模块和 800 行上限，可能迫使实现形成薄封装和状态搬运。

建议先画出当前依赖/状态所有权，只拆能独立测试或独立变化、且不需传递宽泛 renderer 状态的
边界。每个候选拆分前列出消费者和要解决的具体问题；无独立收益的留在原处。测试外移可跟随
实际生产代码拆分，不必作为七个大测试模块的独立整理工程；避免为测试文件位置扩大生产可见性。

### 9. 测试组织和切片不应成为独立改造目标

第 6.1 节把七个大型内联 Rust 测试模块整体搬到同级 `tests.rs`，第 7.3 节又要切分
`App.repositorySwitch.test.tsx`。Rust 子模块测试可访问父模块私有项；移到兄弟模块可能需要
调整可见性。计划只要求测试数量不变，无法证明断言质量或访问边界没有变宽。单个 2,222 行测试
文件也不一定需要依照新生产模块一一切分。

建议仅在生产代码拆分后，按测试归属和可维护性移动相关测试；记录断言/测试行为差异，而不只
核对数量。测试组织如果没有独立痛点，就不单独安排全仓搬迁。

### 10. “只被测试使用”不能直接推出死代码

第 4.3/10.2 节把 `TOOL_PEN`、`delete_subtree` 作为候选处理。计划对 `TOOL_PEN` 同时提议
删除常量或 `#[cfg(test)]`，而工具编号可能是稳定的序列化/协议语义；只在 Rust 调用点被测试引用
不足以证明常量本身无生产意义。`delete_subtree` 虽然只为测试保留自检入口，但有助于覆盖与
prechecked 生产入口不同的防御性路径。

建议分别检查数据格式、跨语言映射、失效保护和未来维护用途。确认仅是重复测试夹具后再删除；
否则保留并说明用途，不用“只有测试引用”作为死代码规则。

### 11. 批次 7 又重复了已在前批次处理的事项

第 10.2/10.3 节再次审查 `Modal`、两个 DTO 副本、`TOOL_PEN`、`delete_subtree`，而批次 1 已
要求处理；第 10.3 节又处理 `src-tauri/gen/schemas/` 与空 `examples/`，前者在批次 1 已列为
待确认、后者在批次 1 已列入删除。批次 7 的“复核”没有清楚说明它是独立验收、条件步骤还是
文档重复，容易引起二次改动或不一致记录。

建议每项只指定一个负责批次；最终审计只核对变更记录、未决项和文档完整性，不再重复执行删除或
重做决策。对 `gen/schemas` 明确列出生成命令、被版本控制文件及 Tauri 配置依据后再决定是否忽略，
避免根据“可能自动生成”删除现有受跟踪产物。

## 建议补充

- 每批增加“证据与退出条件”：引用实现位置、当前行为/缺陷、目标行为、需维护者手工确认的
  部分；证据不足的候选标为待调查，不写成审查已确认的问题。
- 将行为修复、纯重构和文档修正分开标注；凡可能影响 UI、保存载荷、SQL 事务或错误语义的项目，
  写出相应的回归测试与人工验收，不用全量测试通过替代行为验收。
- 增加批次间独立性说明，尤其批次 3 与 6 共享 Rust repository 文件、批次 4 与 5 共享 pin-board
  保存/renderer 边界；若需要调整顺序，说明真实依赖，而不是仅按“大改后置”。
- 为跨领域 SQL 的保留例外定义最小维护约束：涉及哪些表、为何必须同事务、由哪个操作维护、哪项
  测试防止部分提交。这样可解决实际维护风险而不强迫跨领域事务框架。
- 对 `ContextMenu` 行为修正、CSS 导入顺序和 GUI 生命周期验收指定具体验收场景，并与明确不运行
  GUI 自动化的边界一致。
- 复核 `CHANGELOG.md` 条目按最终实际行为归类；若是内部重构且用户行为无变化，避免用笼统的
  “新增/修复”掩盖行为变化或制造过量条目。

## 证据边界

本复核没有运行构建、测试或 GUI，也没有重新执行计划所称的全量审查。它针对的是计划与当前
工作区源码/文档可直接对照的方案问题；依赖版本公告、所有候选文件的引用情况及其它审查报告的
完整证据仍应在实施前按对应入口验证。
