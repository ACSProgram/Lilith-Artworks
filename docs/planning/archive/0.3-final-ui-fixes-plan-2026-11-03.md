## 1. 背景

0.3 的功能工作已经收口，2026-11-03 用一次性无头探针和两轮真实仓库副本 UI 验收把能程序判定
的部分跑完（见 `archive/handoff-log-2026-11-03.md` 的 §7–§9）。剩余的人工验收项并不是功能
没写，而是需要制造故障、真实素材、开发模式或精确时序；这些条件在当前实机上无法安全或稳定
复现，所以不能靠再跑一轮同样的 UI 验收解决。

本批次只处理 `todo.md` 的「待实现 / 待补强」里已经确认、修复边界清楚的产品问题；不把需要
协议改动、性能测量或上游依赖升级的条目硬塞进来。

## 2. 剩余人工验收项为什么还完成不了

| 真实 `.procreate` 缩略图 | 本机没有真实样本，只有合成 ZIP 单测 | 一个真实 `.procreate` 文件 |
| 自动备份启动与让位 | 调度要等 10 秒静默，且当前打开分支没有在观察窗口内启动 | 更长静默窗口或更慢的备份目标；是等待型验证，不是一次点击 |
| 同进程写者排队 | 备份太快，保存没有和备份真正重叠 | 慢速备份目标（网络盘/U 盘）或在备份进行中持续保存 |
| 未保存画板切换的提示瞬间 | 提示条存在时间很短，快照式自动化容易错过 | 录屏或更慢的保存路径；只能证明“没出错”，抓不到瞬间 |
| 只读仓库下的画板写回失败与重试 | 整仓 ACL 会让应用更早报“无法读取仓库”；只锁数据库会让 SQLite 无法打开 WAL；只锁画板目录不影响数据库里的布局 | 数据库仍可打开、但保存时写入失败的条件，例如真实磁盘写满；在实机上不安全 |

共同原因可以归成四类：

1. **需要故障注入**：取消命令失败、只读仓库写回失败。正常 UI 不会产生这些分支。
2. **需要开发模式改源码**：错误边界、热更新。
3. **需要外部素材或跨进程操作**：真实 `.procreate`、资源管理器拖放。
4. **需要精确时序或长时间等待**：两个 busy 重叠、自动备份让位、同进程排队、瞬态提示。

因此这些项应继续留在 `todo.md`，由维护者在合适环境手工完成；本批次不伪造证据。

## 4. 实施项

### 4.1 A：检查点取消返回中性文案

**现象**：取消普通检查点后，界面弹出红色「操作提示」：
「历史节点 `fc288bb4-…` 的备份文件（恢复链 delta）无法读取：操作已取消」。日志
`outcome=cancelled`，但文案看起来像备份损坏。

**成因**：

- 取消检查点时如果该节点没有现成增量，`set_checkpoint` 会调用
  `build_reverse_delta`（`src-tauri/src/app/usecases/backup.rs:190`）。
- 链解析失败时，`open_chain_file` 把包括取消在内的所有错误都拼成
  「的备份文件（恢复链 delta）无法读取：…」（`src-tauri/src/backup/restore.rs:882`
  与 `:888`）。
- `set_checkpoint` 用 `CommandError::from` 原样保留字符串
  （`src-tauri/src/app/usecases/backup.rs:171`、`:199`）。`classify_legacy` 虽然会把
  含「已取消」的消息归为 `Cancelled`（`src-tauri/src/app/command_runtime/error.rs:145`），
  但提示条只显示 message，所以用户仍看到“无法读取”。

**方案**：

1. 在 `CommandContext` 增加一个统一的小工具，例如
   `cancelled_or(&self, message: &str, error: impl Into<String>)`：
   用户已请求取消时返回 `CommandError::cancelled(message)`，否则走
   `CommandError::from_legacy`。判定以 `context.is_cancelled()` 为准，和现有
   `reverify_branch` 的做法一致（`src-tauri/src/app/usecases/history.rs:273`）。
2. 在以下调用点使用它：
   - `set_checkpoint` 的启用路径：`"检查点生成已取消"`；
   - `set_checkpoint` 的取消路径（`build_reverse_delta`）：`"检查点操作已取消"`；
   - `delete_subtree` 固化父节点检查点：`"删除操作已取消"`；
   - `create_branch_at_checkpoint`：`"创建分支已取消"`；
   - `enter_publication` 固化发布检查点：`"进入发布已取消"`。
   这五处都可能因为同一原因弹出“备份文件无法读取”，只改检查点一处会留下同类问题。
   收尾复核时另发现恢复（`restore`）与缩略图刷新（`refresh_thumbnail`）走同一条链解析路径，
   一并纳入同一映射。
3. 不改操作日志的 `outcome`，仍由运行时记录 `cancelled`。

**测试**：

- 在 `src-tauri/src/app/usecases/backup.rs` 的 `tests` 模块加一个已预取消的
  `CancelToken` 用例，调用 `set_checkpoint(false)`，断言：
  `kind == Cancelled`、`code == "cancelled"`、message 为中性文案，且不含
  “无法读取”。
- 另加一个非取消错误用例，确认真正的链损坏仍原样返回“无法读取”并被归为 `Io`。
- 既有 `manual_commit_keeps_quick_hit_count_on_cancellation` 已示范
  `execute_with` 的预取消写法（`src-tauri/src/app/usecases/backup.rs:477`）。

**手工确认**：在副本仓库取消一个普通检查点，红色提示条只出现“检查点操作已取消”，
历史节点仍保持“非检查点 + 保留 delta”。

### 4.2 B：进度条与作品标题分行

**现象**：完整性检查运行时，进度条占据历史页标题行，作品标题被截断成「伊...」「OC设...」，
`ARTWORK 历史` 换行。

**成因**：进度条渲染在 `.history-header-actions` 内
（`src/modules/history/HistoryModule.tsx:316`），和标题共用一行；`.operation-progress`
最小宽度是 `min(330px, 34vw)`（`src/styles/history.css:45`），窄窗口下把标题挤掉。
只有 `max-width: 1180px` 时才通过 `order: 3` 换行（`src/styles/history.css:409`），
而验收发生在更宽的窗口。

**方案**：

1. 把 `OperationProgress` 从 `.history-header-actions` 移出，仍放在 `<header>` 内，
   作为标题与操作区之后的独立行。
2. `.history-header` 改成两列网格：
   - 第一行：`.history-title` + `.history-header-actions`；
   - 第二行：`.operation-progress` 横跨两列，`width: 100%`、`min-width: 0`；
   - 列间距 20px，进度条自身与第一行之间用 `margin-top` 留白，避免无进度时多出空行。
3. `.operation-progress` 的内部列改为 `minmax(0, 1fr) 28px`，宽屏时占满整行，
   不再固定 300px；删除 1180px 断点里已经失效的 `order: 3` 规则。
4. `max-width: 900px` 时标题、操作区、进度条各自一行，避免操作区再挤压标题。

**测试**：

- 在 `HistoryModule.test.tsx` 加断言：运行时进度条是 header 的直接子元素，
  不在 `.history-header-actions` 内；标题与进度条同时存在。
- 布局本身由维护者在 1280 / 1100 / 900 三种窗口宽度下看一次：标题不再截断、
  进度条完整、取消按钮可点。

### 4.3 C：设置页长任务 busy 状态统一

**现象**：完整性检查期间，「创建备份」「开始扫描」直接禁用，「扫描磁盘占用」仍可点击，
点击后才弹「已有备份操作正在运行…」。

**成因**：`RepositoryStoragePanel` 的扫描按钮只根据 `scanning`（当前操作是
`storage-scan`）和 `loading` 禁用（`src/app/RepositoryStoragePanel.tsx:162`、`:166`），
没有接收 `settingsBusy`；而空间页其它入口用 `settingsBusy` 禁用
（`src/app/settings/SpaceSettingsPage.tsx:72`、`:88`、`:123`）。

**方案**：

1. 给 `RepositoryStoragePanel` 增加 `busy` 与 `busyLabel` 两个 props，由
   `SpaceSettingsPage` 传入 `maintenance.settingsBusy` 和
   `visibleSettingsRuntime?.progressLabel ?? null`。
2. 「刷新」与「扫描磁盘占用」统一使用 `disabled={busy || loading || scanning}`；
   按钮 `title` 在 busy 时给出「当前有长任务正在运行」。
3. 在 `.storage-toolbar-copy` 下增加一行状态文字：`当前任务：{busyLabel ?? "已有备份操作正在运行"}`，
   让用户知道按钮为什么不可用；没有 busy 时不渲染。
4. 保持 `settingsBusy` 的既有来源不变（设置保存、清理与四个长任务都会置位），
   不再让任何一个入口走“点击后才拒绝”的旧路径。

**测试**：

- 在 `App.repositorySwitch.test.tsx` 补一条：完整性检查运行中，
  「扫描磁盘占用」`disabled`，且状态行显示当前任务；扫描结束后恢复可点。
- `useRepositoryMaintenance.test.tsx` 已有 busy 拒绝与完整性失败用例
  （`:61`、`:89`），保留作为命令层的兜底；若时间允许，再补备份/垃圾扫描/磁盘扫描
  三个失败提示的断言，覆盖 todo 中“四个长任务失败提示”的逻辑侧。

### 4.4 D：历史页按控件分级禁用（可裁剪）

**现象**：`HistoryModule` 的分支设置、提交框、精简控件统一使用
`disabled={busy || runtime.busy}`（`src/modules/history/HistoryModule.tsx:330`、`:343`、
`:357`、`:358`、`:363`、`:369`、`:397`、`:407`）。`runtime.busy` 包含后台自动备份与空闲
校验，后台任务运行时整页输入都不可用。

**方案**：

1. 把“写操作锁”和“草稿编辑锁”分开：
   - `writeLocked = busy || runtime.busy`：提交、精简、检查点、删除、重置、缩略图重提、
     分支设置保存仍用它；
   - `draftLocked = busy`：只在本页自己的操作进行时阻止输入。
2. `BranchSettings` 增加 `saveLocked` prop：
   - 输入框和路径选择用 `draftLocked`；
   - 650ms 防抖保存的 effect 在 `saveLocked` 为真时只把状态标成「未保存」，不提交；
     `saveLocked` 变回 false 后依赖变化会重新计时并保存。
3. 提交备注输入框去掉 `runtime.busy`，只保留 `busy` 与分支可用性判断；「提交」按钮
   仍保留 `runtime.busy`，避免后台任务期间发起新的历史写入。
4. 精简模式的选择与删除继续按 `writeLocked` 禁用：后台刷新可能改动图结构，让用户在
   这期间选节点会产生过期选择；这一条作为有意保留，并在注释 / 文档里说明。
5. 节点信息、视图切换、搜索等只读控件本来就不受 `runtime.busy` 影响；检查一遍
   确认没有遗漏。

**测试**：

- `HistoryModule.test.tsx`：`runtime.busy + taskKind="automaticBackup"` 时，分支名称与
  提交备注可编辑，「提交」「精简当前分支」「删除节点」仍禁用；切到
  `taskKind="userOperation"` 时输入框也禁用。
- `HistoryControls.test.tsx`：分支设置有未保存改动且 `saveLocked` 时，不调用
  `onSave`；解锁后防抖结束调用一次。
- 手工确认：自动备份进行中输入分支名称和提交备注，界面显示「未保存」，备份结束后自动
  写回，不弹错误。
