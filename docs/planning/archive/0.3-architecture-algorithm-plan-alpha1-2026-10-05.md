- **分支级快速检查开关**（`branches.backup_quick_enabled`）：§3.D 的 cheap fingerprint 升级

### 0.4 批次划分与依赖顺序

划分原则有两条：**底座先于功能**（契约、算法、数据模型先落地，功能只在其上叠加）；**同一 schema
迁移只做一次**（schema 是全局基线，重复迁移会让每一批都要重跑一遍兼容验证）。

| 批次                | 范围                            | schema                | 交付判据                                                  |
| ----------------- | ----------------------------- | --------------------- | ----------------------------------------------------- |
| 0.3-alpha1 架构与算法底座 | §3.A–E（阶段 1–5）                | 不变，保持 v4；无新增持久 schema（清理用连接内临时表）；可读 v1–v4     | 所有仓库写入口经过 coordinator；取消 / 深链 / 清理 / 灾备算法有基准            |
| 0.3-alpha2 功能批次   | §3.G + §3.H + §3.F + §3.I（阶段 6、7、8、9） | 一次 v4 → v5            | 仓储空间只读仪表盘；画板条目为多态；历史页免 restore 预览；链路校验按空闲时机全链恢复校对                |

**alpha2 内部顺序为 6 → 7 → 8；阶段 9 依赖阶段 5、6 与 7**：

- **阶段 6 保留原安排，排在画板改造之前**。为使它在阶段 7 之后仍然正确，阶段 6 的 DDS 分类必须按
  「**该条目是否存在实体文件**」判定，而不是按 kind 枚举；文字等无实体文件的 kind 没有位图载荷行，
  自然不计入 DDS 分类，因此阶段 7 落地后阶段 6 无需改动语义（只需重新定位 SQL）。
- **阶段 7 拥有 0.3 唯一一次 v4 → v5 迁移**，一次补齐 pin-board 的多态列（§3.H）、`history_nodes`
  的缩略图列（§3.F，供阶段 8 消费）与 `branch_notices` 告警表（§3.I，供阶段 9 消费）。阶段 8
  只**消费**缩略图列，不另开迁移。
- **阶段 8 排在阶段 7 之后**：缩略图存储列由阶段 7 建好，阶段 8 只做抽取、回退与回收。
- **阶段 9（§3.I）依赖阶段 5、6 与 7**：调度门控与防饿死 aging 来自阶段 5，`branch_notices`
  表与旧告警读写泛化来自阶段 7，设置页的「备份」页与「N 条链路待校验」入口来自阶段 6；与
  阶段 8 无依赖，可排在 7 之后的任意位置（列入队尾仅为表述顺序）。
- **阶段 6 的依赖是阶段 2、3、5**：阶段 5 提供清理扫描模式与引用清单接口，阶段 6 的磁盘扫描与
  DDS 分类直接复用它，不再标为「可选」。阶段 7 若重建画板表，阶段 6 的聚合 SQL 需按新的
  `file_path` 位置重新定位一次。

**为什么不是「A–F 进 alpha1、画板进 alpha2」**：§3.F 与 §3.H 原设计共用一次 v4 → v5 迁移。若把
§3.F 留在 alpha1、§3.H 推到 alpha2，只剩两条路：其一，两次迁移（v4 → v5、v5 → v6），schema 基线被
反复改；其二，alpha1 提前把 pin-board 的多态列也建出来，而「宽表 vs 公共表 + kind 子表」在 §6 仍是
未决项，等于提前冻结未定型的结构。同时，§3.H 是架构底座而 §3.F / §3.G 是新增功能，把底座推到功能
之后，会让 alpha1 的清理 / 校验 / 导出 / 灾备先按「每行都有 DDS」的旧不变量实现，alpha2 再按 §3.H
「主要改动面」逐处返工。

**基线敏感度**：alpha2 各节的行号与验收口径以 **alpha1 落地后的代码**为基线。alpha1 会重排
`app/settings.rs`、`app/workflows.rs`、`lib.rs` 与 `cleanup.rs` 的入口，因此 alpha2 实施前必须按
符号名重新定位一次，并同步更新 §0.3 的定位表。

本轮不改变产品范围，只把会在实施时产生歧义或返工的口径写死：

  `(branch_id, kind)` 复合主键并级联删除。见 §3.I、§4.2。
- **画板表结构**：采用「公共条目表 + 按 kind 载荷子表」；`pin_board_history` 外键改为指向公共
  条目表。v5 是向前兼容的表重建 + 回填，不承诺 append-only；阶段 6 的空间聚合查询在阶段 7
  后需重新定位 `file_path`。见 §3.G、§3.H。
- **统计口径**：仓储占用按「snapshot 文件 + 全部 `history_edges` delta + 成品/认证/画板 DDS +
  其它」计算；`history_nodes.chunk_file_size` 只作为节点重建读取量，不并入存储总量。见 §3.G。
- **错误契约**：typed `CommandError` 在 Tauri 适配层归一为现有字符串错误，结构化字段进入
  事件/日志；前端 `invokeCommand` 负责把 typed error 转成 `Error(message)` 并挂载可选字段。

- **空闲校验**：门控同时检查 `is_visible()` 与 `is_minimized()`；运行期由校验循环在 delta 步
  边界通过 `should_yield` 让位给出到期备份，而不是依赖单线程调度器外部取消。见 §3.I。
- **依赖与归属**：`CancelToken` 由阶段 1 定义；阶段 9 增加阶段 6 依赖（设置页入口）；跨模块
  引用/完整性 provider 放在中立契约模块，不把 `pin_board` 导入 cleanup。见 §3.A、§3.E、§4。
- **发布基础设施**：`tools/release/verify-metadata.mjs` 的版本→schema 映射（0.2.x→v4、
  0.3.x→v5）与 Windows CI 的 `dev` 推送已在开发线启动时落地；阶段 7 用该映射校验 v5。

## 2. 0.3 目标架构

目标不是再增加一层「万能总线」，而是让每个跨边界动作只有一个可测试的执行路径：

```text
Tauri adapter       headless adapter       (future maintenance adapter)
       \                   |                         /
        ---- CommandContext + typed use-case ----
                    |
          OperationCoordinator
   operation id / lock order / cancel / progress / events
                    |
       RepositorySession + domain services
   Library | History/Backup | Authenticity | Pin-board
                    |
       SQLite + chunk files + cleanup ledger
```

约束如下：

1. adapter 只解析 DTO、检查文件选择器授权、装配 context 和映射错误，不包含业务分支。
2. use-case 不依赖 Tauri 类型；所有长操作接收 `OperationContext`（取消、阶段进度、日志、operation
   id、授权能力）。
3. 固定锁序为：跨进程仓库门闩 → coordinator 运行分类 → repository lease → repository operation
   guard → SQLite transaction。只读操作不得取得写锁；锁等待和让位必须可观测。
4. 事件总线不取代事务结果。命令返回最终 DTO，事件只表达 started/progress/finished、仓库变更和
   清理队列变化；UI 丢事件后用 revision 做一次快照补偿。
5. schema 与 ChunkFile 均采用**向前兼容**：旧仓库必须能经迁移打开，0.3 不在原地破坏 0.2 数据。
   ChunkFile 先保留 v1 reader，再以 feature flag/新版本写入。**0.3 只做一次 schema 迁移**：
   alpha1 不产生持久 schema 变更（连接内临时表不算），alpha2 的阶段 7 一次完成 v4 → v5。
   v5 允许表重建与数据回填（画板多态、旧告警列迁移），因此**不承诺 append-only**；迁移必须
   在一个事务内完成并覆盖 v1–v4 仓库（见 §0.4、§3.H）。
6. **关闭握手保持专用**，不作为事件总线里的普通事件：它必须保留「请求 → 前端结算 → 确认 → 15 秒
   兜底强退」的确认语义与不可逆 `shutting_down` 状态（rc.2 已实现）。事件总线只承载进度、失效与
   仓库变更通知。
7. **复用既有诊断体系**：事件通道的传输、运行切片（run id）、target 与标签沿用 rc.2 的日志/诊断
   基础设施（`docs/guides/logging.md`），不新建第二套观测通道；诊断模式只影响探针与取证，不改变
   事件语义。
8. **画板条目为多态**：领域层以「`kind` + 按 kind 解释的载荷」表达条目，位图/DDS 只是其中一种；渲染
   按 kind 分发到对应 provider，跨模块旁路（清理、校验、灾备、导出）按 kind 分派，**不假设条目都有
   实体文件**。
9. **事件契约唯一**：`AppEvent` 的枚举、字段与版本在 alpha1 阶段 1 定义；阶段 3 的前端订阅
   provider 只消费该契约，不另立一套。「冻结」指 v1 的封套与语义稳定，字段以可选方式扩展、
   新事件以增量版本追加，不要求 alpha2 的需求在阶段 1 就全部预知。

## 3. 改进工作流

每节标注所属批次：`[alpha1]` / `[alpha2]`。

### A. 契约与执行底座（必须最先）`[alpha1]`

准确做法：

- 在 `src-tauri/src/app/` 新增 `command_runtime`/`usecases`，定义 `CommandContext`、
  `RepositorySession`、`OperationId`、`OperationClass`（read、foreground、background）和 typed
  `CommandError { code, kind, message, retryable, operation_id }`；`CancelToken` 也在本阶段定义，
  阶段 4 的所有 I/O 步骤直接消费同一类型，不另行定义。
- **错误跨 IPC 的契约**：Tauri 命令仍返回现有的字符串错误（保持 0.2 的 `invoke` 失败形态与用户
  文案），typed `CommandError` 由适配层归一为字符串；`code`/`kind`/`retryable`/`operation_id`
  写入事件与日志，供 UI 决定重试与呈现。前端 `invokeCommand`（`src/shared/tauri.ts`）把已知的
  结构化错误重建为 `Error(message)` 并挂载可选字段，`App.tsx` 现有的 `String(error)` 路径不回归。
- `OperationCoordinator` 提供 `run_read`、`run_write`、`run_foreground`、`run_background`；统一
  `spawn_blocking`、运行锁、取消 token、阶段进度、耗时日志和事件发布。
- **本阶段定义 `AppEvent` v1 信封与首批事件**（枚举、字段、版本，见 §3.C 的事件清单）：信封字段
  （repository key、operation id、domain、phase、current/total、cancellable、completion revision）
  冻结，后续只允许追加可选字段；新增事件类型以独立版本号引入。阶段 3 只在此契约上补前端订阅与
  轮询降级，不重新定义事件；避免同一通道做两遍。
- 先迁移 create-artwork、settings、history fork/publish、backup commands 四组高风险入口，再迁移
  cleanup、pin-board 和 authenticity；每次迁移保持 command 名、DTO、用户文案不变。
- 把 `headless.rs` 改成 context 装配器，GUI workflow 也调用同一 use-case；加入「同一输入在两入口
  返回相同结果/错误码/锁分类」的契约测试。
- 按领域提供 `register_commands()` 分组函数或单独 registry 文件，集中注册仍保留，但不再让
  `lib.rs` 维护所有实现细节。

验收：create-artwork 等入口不再出现未经过 coordinator 的写流程；锁序测试覆盖正常、取消、切仓库
和退出；`cargo test --lib`、`cargo check --lib`、`npx tsc --noEmit`、`npm test`、`git diff --check`
通过。

### B. 仓库状态、设置与生命周期 `[alpha1]`

准确做法（在 rc.2 已有的握手与诊断设施上补齐，不另起炉灶）：

- `SettingsService::update(patch, expected_revision)` 成为设置页和托盘唯一写入口，原子写 JSON、
  更新内存快照、唤醒调度器和刷新托盘菜单在同一流程完成；陈旧 revision 返回 `settings_conflict`，
  不静默覆盖。现状是托盘 `set_automatic_backups_paused`（`app/settings.rs`）直接
  `write_json_atomic`，绕过了统一保存路径。**revision 是设置文件自己的单调计数，与 schema、
  ChunkFile 格式和版本号无关**：每次成功写入 +1，启动时读入，不参与发布元数据。
- 在仓库根目录增加 OS 文件锁和 owner metadata（PID、启动时间、应用版本、心跳）。GUI、headless 和
  维护命令打开仓库前都 acquire；冲突返回 `repository_busy`，异常退出只在 owner 已失效且满足 stale
  条件时回收。**落实口径（2026-10-18）**：按写操作 acquire/release，只读命令不取；锁本身仍是
  现有 SQLite 哨兵（内核锁即存活证明），owner 元数据写在同目录的 JSON 侧车文件里，取得锁即
  覆盖旧记录，不按 PID/心跳强行回收；锁文件从作品数据库发现、灾备复制与未引用扫描中排除。
- **复用现有哨兵，不另建第二把锁**：`repository_lock.rs` 的 SQLite 哨兵已覆盖 headless 的写命令并
  保证强杀不残留（锁由内核在句柄关闭时释放）；本阶段把它提升为仓库级 owner lock（同一锁文件 +
  owner metadata），GUI、headless 与维护命令共用。headless 现有的「写入命令持哨兵」路径改为持统一
  owner lock；只读命令仍不取该锁。
- 关闭路径**沿用 rc.2 的握手**（`app_shutdown_requested` / `confirm_app_shutdown` / 15 秒兜底），
  只把「结算失败、participant 超时、等待命令未返回」接入结构化诊断（复用 `[watchdog]` 与
  `[forensic]` 通道），不再新建 LifecycleCoordinator 去替换它。若后续需要冻结新命令，作为握手内部
  的排队规则实现，而不是新的并发层。
- 新增 `AppRuntimeProvider`、`useSettingsController`、`useRepositoryMaintenance`、
  `RuntimeProgressProvider`、`SettingsDialog` 和 `NoticeCenter`，App 只负责路由与注入。

验收：托盘与设置并发保存有 CAS 测试；双进程打开同仓库的冲突、stale owner 和释放可测；仓库切换/
退出期间最后一次素材板结算不丢失；现有 repository-switch 测试保持通过。

### C. 事件总线与模块模板 `[alpha1]`

准确做法：

- **`AppEvent` v1 信封已在阶段 1 定义并冻结**，本阶段只做消费侧：前端建立一个订阅 provider，
  controller 通过 repository key 和 operation id 丢弃旧事件，命令响应仍负责最终状态。事件清单
  （定义在阶段 1）为
  `OperationStarted`、`OperationProgress`、`OperationFinished`、`RepositoryChanged`、
  `CleanupQueueChanged`；事件带 repository key、operation id、domain、phase、current/total、
  cancellable 和 completion revision。**关闭请求不进事件总线**（见 §2 约束 6）。
- 复用诊断体系的传输与切片：事件经统一 provider 分发，落到日志时沿用 `run id`/`target`/标签，避免
  与 `log_frontend_diagnostics` 并行两套通道。
- 轮询保留为丢事件/启动恢复的 3 秒兜底，稳定后去掉 350 ms 高频轮询（当前在 `App.tsx` 的备份态
  轮询与 `useHistoryController.ts` 的递归轮询）。
- 统一模块目录契约：`types.ts`（边界 DTO）、`api.ts`（typed command adapter）、
  `use*Controller.ts`（竞态/请求代次/错误/忙状态）、`Module.tsx`（视图）。抽出 `useRequestEpoch`、
  `useAsyncOperation` 和 `useRuntimeSubscription` 三个小工具，避免复制各 controller 的 request ref
  和 finally 模式。
- Pin-board 先把生命周期、保存/导入/导出状态迁入 controller；WebGPU renderer 仍是纯渲染器，Channel
  只承载大 payload，状态变化走统一事件。渲染器的设备复用与占位符已由 rc.2 落地，不在本轮改动。

验收：四个领域 controller 使用同一套竞态与错误策略；事件丢失后 revision 补偿；不改变现有 DTO 与
页面功能。

### D. 分块、恢复与完整性算法 `[alpha1]`

准确做法：

- 在 `chunk_file.rs` 把格式头、chunker、hash、compression 抽成策略接口和明确的 `FormatVersion`。
  保留 v1 reader；新增版本先只在实验开关下写入，并记录配置，禁止按机器默认推断格式。
- **v2 激活口径（落实时按此执行）**：开关是**应用设置** `chunkFileFormatV2`，沿用 §3.B 的
  `SettingsService` 保存；**2026-10-18 维护者决定默认开启**，设置页保留开关以便回退到 v1。开关只
  决定**新写入**的 ChunkFile 版本，不重写既有文件、不做仓库级批量迁移。每个 ChunkFile 的头部自带
  版本与策略位，reader 按文件头分派，因此同一仓库可长期混存 v1/v2；纯 v1 仓库在开关关闭时行为与
  0.2 完全一致。0.3 发布前仍按阶段 4 的 benchmark 复核（判据：往返逐字节一致、CPU 不回退、恢复
  时延不劣化）；无论默认值如何，切换都只影响此后新生成的 snapshot/delta，旧节点在自然替换（重新
  snapshot、检查点、精简）时才会写成 v2。开关状态写入提交/检查点/精简的诊断日志，便于解释仓库
  内的版本分布。
- `ChunkStore` 维护按虚拟偏移排序的 segment 起点和 reader 游标：顺序读命中当前段，跳跃读用二分
  查找；跨段读取一次完成。用深链和大文件 benchmark 比较 p50/p95，超过阈值才启用更复杂的索引结构。
- 把 `CancelToken` 传入 `ChunkFile::create`、reverse delta、payload copy、`resolve_chain`、
  `copy_original`、scrub 和 checkpoint。**检查粒度对齐研究结论**：转码步的取消地板是**每 tile**
  （320 KiB 原始数据，写 ≤12 ms / 恢复 ≤5.4 ms），更细的「每 64–256 KiB」在转码步不可达；廉价的
  框架块（zstd/none）可按块或每若干块检查。统一返回 typed Cancelled；所有临时输出由 guard 清理，
  进度按已处理字节而非只按节点数报告。
- `materialization_chain` 改成一次递归 CTE 返回链节点、父子边和路径，避免深链逐节点 SQL；scrub 按
  链批量解析，必要时使用有界磁盘缓存，避免对同一 delta 反复解压。
- 快速检查基线增加算法版本和 cheap fingerprint（至少 size、mtime、首尾采样；可用时加入 OS
  file-id/change counter）。基线不匹配或时间精度不足必须回退全量；手动提交继续强制全量。
- 在损坏恢复上保持当前语义：先验证 chunk/整文件摘要，再原子发布；把错误分类为缺失、格式、chunk
  摘要、整文件摘要和输出冲突，便于 UI/重试决策。
- **抽出单一容器解析模块**（如 `src-tauri/src/format/`）：负责 `.clip`/`.psd` 的 `detect` 与容器块
  定位，本阶段用它做 tile 对齐分块，阶段 8 用它定位缩略图块。**不在两处各写一份**——研究仓的
  `tools/harness/src/o5.rs` 与 `clip.rs` 只是参考实现，主仓合成为一个模块。

**研究结论（实测回流，2026-10-11）**

`research/compression-optimization/` 已按本节要求完成 P0–P5 的调查与实测（真实仓库
`F:\LilithData\Artworks`，3 作品 / 36 版本 / 6.32 GB），给出可直接落地的 v2 规格：

- **采用集（v2 = v1 + 四项）**：`格式 v2`（版本号 + 策略位 + 每块 `codec/recipe/logical_len`）→
  `O2 容器感知分块`（`.clip` 按 tile 对齐，解析失败一律回退 CDC）→ `快照 tile 级去重` →
  `O5 鲁棒性加固`（两轴错误分类 / 块级隔离 / 每 tile 取消 / 写入开关）。采用顺序
  **格式 v2 → O2 → 去重 → O5**。
- **收益是分层的，不能只看整仓**：整仓 **6.32 → ≈6.17 GB（−2.44%）**，但该数字被两个**物理不可压
  对象**主导（3D 快照占快照 67%、录屏 delta 占 delta 字节 78%）；**图层为主作品**的收益才是量级性的
  ——delta 净降 **18.6%**（含记录）、带 tile 容器单对最高 −47%、快照 tile 流可 −34%~−44%。**主收益
  应表述为「鲁棒性/可回退/版本分派」**，空间收益按文件类型分列，不用整仓平均。
- **O2 是收益主力且免费**：纯图层编辑 delta 净降 **18.6%**（含记录）、分块 CPU **−8%**；无 tile
  容器仅 −5.4%；回退 36/36，CDC 重建与仓库 33/33 一致。
- **O5 已量化到可验收**：80 个注入故障证明内容损坏**块级隔离且可单块修复**（受影响面恒为 1）；帧级
  损坏（`stored_len`/截断）**只保前缀恢复**（16%–96%）、不可隔离；错误分类扩成 `class × dimension`
  两轴；未知能力归 `Incompatible`（能力缺口，非数据损坏）；取消地板 = 每 tile（320 KiB），
  写 ≤12 ms / 恢复 ≤5.4 ms。
- **格式与块记录**：头部带 `version/chunker/hash/codec/adapter`；块记录 36 → 44 B（+8 B/块，本仓
  +1.5 MB，占整仓 0.02%）；`tools/harness/src/o5.rs` 提供 v2 容器读写器与两轴分类的**最小可运行
  样例**，可作为 `chunk_file.rs` 策略接口与读取器分派的参考。
- **明确否决**：`O6 解码域转码`（提交 **+104×** / 恢复 **+42×**，违反研究方案 **§8** 的「CPU ≤2×」
  验收线，且本仓可压上限仅 9.7%）；`O1/O1-lite`、`O3`、`O4`、`O7`（SQLite 页级）；`F3`（改分块
  参数，图层净降仅 −0.99%，未过 5% 门槛）→ **保留默认 `2/16/64 KiB`，不引入配置分支**。
  「图层文件 −1/3」属于已否决的 O6 路，**不作为 0.3 目标**。
- **必做的写入端加固**（尚未落地）：超 `max` 的结构单元**必须 CDC 切分**，否则 3D 大块截断恢复极差；
  `.psd` 适配器当前只 **detect + 回退**（结构待逆向确认）。

> 详细规格见研究仓 `docs/plan.md §3 / §8`，逐项代价见其 `docs/architecture-decisions.md`，整体对比见
> 其 `docs/v1-vs-v2-comparison.md`。研究仓全程**只读**真实数据。

验收：取消延迟按字节规模有上限（每 tile 口径）；深链恢复不再随 segment 数线性退化；v1 仓库可读，
v1/v2 混存仓库可读且开关关闭时新写入仍为 v1；损坏 snapshot/delta 不生成半成品且可重试；新增
benchmark 只作为 0.3 决策证据，不替代日常轻量检查。

### E. 调度、清理与灾备算法 `[alpha1]`

准确做法：

- 用 deadline heap 或 SQL `ORDER BY due_at, last_attempt, branch_id` 生成候选，维护唤醒信号；优先级
  固定为前台等待 > 手动提交 > 到期自动备份 > 空闲校验（口径重构见 §3.I），并用 aging 防止低优先级长期饥饿。取得锁后
  继续做资格复查。
- 每个任务拥有独立 `OperationId` 与 cancellation token；取消/让位只作用于目标后台任务，不再依赖单一
  `cancel_requested` + 多个补丁集合。失败退避按分支记录，不能阻塞其它分支。
- 调度执行仍以 repository writer lease 保证 SQLite 写互斥；只有证据表明跨 Artwork 并行有收益时，
  才引入按 repository/artwork 分片的 worker，先不并行写事务。
- cleanup 使用批量临时引用表，使用 anti-join 一次判定未引用集合，按 256–1000 条分批、每批可取消且
  幂等提交。**alpha1 不新增持久索引**：引用表是连接内 `TEMP` 表（随连接结束消失），分批事务复用同一
  临时表；`stored_path`/`snapshot_path`/`delta_path`/`output_path` 的持久索引随阶段 7 的 v5 迁移
  建立，届时 cleanup 切换为索引查询，临时表路径保留为兜底。
- **本阶段交付「引用清单 / provider 接口」**：cleanup 只接收通用清理目标或公开清单接口，不再直接
  导入 `pin_board::repository` 的路径常量（当前 `cleanup.rs` 顶部就导入 `is_dds_name`、
  `parse_board_dds_path`、`BOARD_DIRECTORY`）。该接口是 **§3.H 的前置条件**——阶段 7 要按 kind 分派
  清理/校验，只能通过它实现，否则又要把 `pin_board` 导进 cleanup。
  - **归属**：接口定义放在中立的契约模块（如 `src-tauri/src/contracts/`，或等价的
    `repository_contract.rs`），不放在任何一个领域内；领域实现 trait，应用层注册实现列表。
  - **最小形状**：`ReferenceInventory` 提供 `collect_targets(&Connection) -> Vec<ManagedFile>`
    （规范化路径 + 所有者类别 + 是否可删）与 `validate_target(&Connection, &ManagedFile) ->
    ValidationOutcome`。cleanup 用前者做 anti-join 与孤儿判定，scrub 用后者按所有者校验。
  - **演进规则**：阶段 5 只实现历史 snapshot/delta、成品、认证输出与画板 DDS 四类；阶段 7 增加
    kind 维度的导出/引用方法时以**新方法**扩展 trait，不改已冻结的方法签名，避免 alpha1 提前
    假设「每个条目都有实体文件」。
- **灾备完整性 provider 同样注入**：`repository_backup.rs` 不再直接导入 `library`/`authenticity`，
  改为接收契约模块中的读取 provider（manifest 校验、成品/认证文件清单）；领域原语仍由应用层装配，
  灾备核心只负责复制与 manifest。
- 灾备复制阶段边复制边计算 digest；manifest 校验复用已取得摘要，最终发布前保留一次抽样或全量可配置
  复核。外部文件变化继续以复制前后 metadata 复核拒绝。

验收：多分支到期任务不因一支失败固定停 60 秒；前台等待可观测且不会被后台抢锁；清理查询次数和大规模
孤儿耗时有基准；灾备 I/O 次数下降且校验语义不弱于 0.2；cleanup 不再导入 `pin_board` 的路径布局常量。

## 6. 非目标与待决策

- 不重写领域业务规则，不把所有函数强行放进通用插件系统，不为事件总线引入外部消息中间件。
- 0.3 不为画板一次性实现所有 kind 的交互（笔迹工具等）；本阶段只落地**多态条目模型 + 文字**这一种非
  位图 kind，以验证「新增 kind 只需实现 provider、不改核心几何/缓存/旁路」这一可扩展性目标。
- **压缩侧方向已定**（§3.D「研究结论」）：`O2 容器感知分块采用`、`O6 不采用`、`hash 不变`
  （O4 否决）、分块参数保持默认 `2/16/64 KiB`、快照 tile 级去重采用。阶段 4 已在真实写入端实现，
  开关默认开启、只影响新写入，不自动迁移已有文件；发布版默认值仍按 §3.D 的判据复核。
- **仓储空间状态只读**（§3.G）：只做只读聚合与设置信息架构拆分，不引入独立顶层窗口、不持久化统计
  缓存、不新增 schema；DDS 分类按「是否有实体文件」判定，不按 kind 枚举。
- **缩略图存储位置已定**（§3.F）：随节点存于 `history_nodes.thumbnail`（BLOB）+ `thumbnail_version`，
  由阶段 7 的 v4 → v5 迁移建立；不单开文件或表，不参与完整性校验与恢复。
