# 0.4 作品数据库拆分计划：架构审阅与改进建议

- 审阅对象：`0.4-artwork-database-upgrade-scheduling-and-identification-plan-draft-2026-10-22.md`
- 审阅日期：2026-10-22
- 范围：总体架构、数据与事务边界、升级恢复、并发调度和实施顺序；不逐项评估代码行数。

## 总体判断

每个作品使用独立数据库，方向合理。作品历史、素材板和发布记录留在同一作品库，能保留作品内的事务边界；仓库根库继续拥有作品目录和跨作品查询入口，也符合现在的分层。保留旧版迁移链、先在暂存区构建、把作品 ID 显式传入作品级命令，这些决定都值得保留。

草案最需要补强的不是拆库本身，而是拆库后多出了一组跨数据库的事实副本和多文件升级流程。作品库提交与根索引更新不是一个 SQLite 事务；作品库文件移动与根库替换也不是一个文件系统事务。当前草案把这两类边界主要交给“失败后标记 dirty”与状态文件处理，恢复规则还不够闭合。与此同时，升级界面、全库功能改造、两类持久索引、新调度器和运行态列表都放进 0.4，整体方案容易在解决并发之前先引入过多协调层。

建议保留“每作品一库”的方向，但先把数据权威、升级激活和锁的职责写成可验证的不变量；再按正确性底座、按作品并行、识别体验分阶段实施。不要为三个现有领域预先搭建通用插件式生命周期框架。

## 建议保留的架构决定

- **作品库是作品内事务边界。** 历史、素材板和发布数据都属于该作品；发布记录继续与分支、历史节点保持同库外键。跨作品写入因此可以并行，同一作品仍串行。
- **根库只拥有仓库级事实。** 作品树与作品身份留在根库；作品内领域数据留在作品库。跨作品索引是派生读模型，不能成为第二份权威数据。
- **升级不复制载荷。** 只在暂存区重建数据库，避免把大体积历史文件纳入升级事务。旧版迁移步骤保持冻结，新布局从目标 schema 建立并搬运数据。
- **命令显式携带作品 ID。** 这比从节点、画板或分支 ID 扫描所有数据库定位更容易理解，也减少隐式路由。
- **领域模型不合并。** 继续让应用层编排跨领域流程，复用现有 `ArtworkDbHandle`（计划新增）和 `ReferenceInventory` 契约即可；不抽象统一历史、画板和发布数据格式。

## 开工前应修正的架构问题

### 1. 把存储迁移与并发调度分成两个可验收阶段

目前 0.4 同时改变仓库布局、启动路由、所有作品级命令、垃圾扫描、空间统计、整仓备份、空闲校验、长任务执行模型和识别搜索。虽然计划分成八批，但首批可用版本仍要等这些路径全部改完，数据迁移与并发调度也难以分别归因。

建议先完成一个**仍保持全仓单写者**的 v7 阶段：作品库拆分、显式升级、所有读写和文件引用路径多库化、树与清理功能、整仓备份/恢复，以及失败隔离都要正确工作。锁暂时继续串行，不引入新的公平调度。该阶段验收后，再把锁作用域缩到作品并引入有界长任务并发。这样可以先证明“数据放对且能恢复”，再证明“不同作品可以并行”，故障面更容易定位。

升级开始界面属于显式迁移所必需的入口，可以和执行器一起实施；识别页位置、前端任务列表和高级公平策略则不应阻塞拆库阶段。识别控制器当前已不接收作品或分支，实际改动主要是搜索数据源和导航编排，宜按独立功能处理。

### 2. 明确投影索引的一致性协议

`branch_index` 和 `certification_index` 都是根库中的派生数据。作品库事务完成后再更新根库，存在进程崩溃或根库写入失败的窗口。此时若只在根库里写 `dirty` 标志，同一故障可能连标志也写不进去；仅提供手动重建也会让正常搜索长期漏记录。

如果树刷新和识别搜索必须避免逐库查询，建议保留根库投影，但为它们共用一个可重放的同步机制：作品库在原事务中记录待投影变更；应用层以幂等方式更新根库投影，确认后再清除待处理项。根库更新成功、确认失败时重复执行也必须安全。启动或后台修复可用同一机制收敛，手动重建作为修复入口，而不是日常一致性的唯一保证。

投影字段应限制在真实跨作品热路径需要的最小集合。`branch_index` 不要顺手复制完整分支状态；识别索引只存搜索和定位必需字段，命中后仍以作品库记录为准。SQLite 对根库写事务本身已有串行化，因此不要再加一把独立的全局索引锁；用短事务和幂等更新即可。

### 3. 把升级定义成可恢复的多文件协议，而非单文件原子事务

“先放好所有作品库，最后替换根库”是合理顺序，但根库替换只能作为**逻辑激活点**，不能让前面的多个文件移动变成原子操作。应明确每个暂存文件归属哪个升级批次、何时可被视为活动数据，以及每个崩溃点如何幂等重试或清理。

- 升级前取得独占维护租约，停止接纳新操作并排空已有读写。当前 owner lock 的职责是拒绝跨进程写入，普通读取不取它；升级规则还要覆盖仍打开的数据库句柄和 headless 入口。若跨进程读者不受同一维护租约约束，就必须由单实例/仓库打开规则保证升级期间不可能存在，不能只假设“没有写者”就足够。
- v1–v5 的工作副本应通过 SQLite 一致性备份机制生成，不能只复制主数据库文件而遗漏 WAL 中已提交的数据。迁移和校验均针对这份稳定快照进行；不要为了提交而提前改写活动旧库的 checkpoint 状态。
- 暂存全部作品库并完成校验后，再将作品库放到最终路径，最后替换根库。根库应带升级批次标识，作为是否已激活的事实来源；状态文件用于记录进度和清理，不应单独授权一次可能过期的提交。
- 应用重启后继续提交前，重新取得维护租约并确认活动旧库仍与生成暂存库的源快照一致。若用户在上次退出后通过旧版写过仓库，必须废弃或重建暂存结果，不能把旧快照直接覆盖到新版本。

目前“成功后自动删除旧根库”会让一次不可逆 schema 迁移失去最后的恢复源。建议 0.4 alpha 至少保留旧根库快照，直到新版本完成首次打开和仓库自检；确认稳定后再由维护者选择清理。载荷没有复制，保留的主要是数据库元数据，恢复价值远高于它带来的实现复杂度。若坚持全部成功后自动删除，也应把它明确列为接受不可逆损失的产品决策，而不是迁移协议的默认步骤。

对单作品迁移失败也应采取同一原则：失败作品的目录和载荷不能立刻按普通未引用文件处理。继续使用新仓库时，应保留可恢复的旧数据来源，或在提交前明确要求用户放弃该作品的历史元数据；不能只留下一个失败标记，再让垃圾扫描把相关文件视为孤儿。

### 4. 以现有命令协调器扩展作用域，不再建第二套任务系统

仓库已经有 `OperationCoordinator`、`CommandContext`、优先级写闸门、取消令牌和运行事件。作品拆分后优先给现有协调器增加作品作用域及重任务配额，让同一入口继续负责 GUI、headless 和维护命令；不要再旁建一套与它各自维护 busy、取消、排队和退出状态的“控制总线”。

把**正确性锁**和**资源限额**分开即可：每个作品一个写闸门；只有整仓备份、升级这类确实需要全局一致快照的操作取得仓库级独占屏障；高内存长任务用一个有界配额控制并发。普通完整性扫描、垃圾候选扫描可以按作品逐个加锁并在删除前复查，不必仅因“跨作品”就暂停整个仓库的所有写入。

全局长任务上限是合理的，但三档任务分类、每种命令映射、前台优先、轮转、公平 aging、每作品排队去重、运行态列表和定向取消不必一次全部实现。先复用已有优先级，限制重任务并发，并验证作品 B 的交互写不会等待作品 A 的长任务。若随后测出后台饥饿，再加轮转或 aging。长任务让位点还必须明确释放作品闸门并结束当前事务；只检查“应当让位”却继续持锁，前台同作品操作仍无法插队。

### 5. 避免为三个固定领域引入通用生命周期插件

计划中的作品库句柄和作品作用域引用清单有明确的复用价值。创建、删除、备份、恢复、校验的“领域生命周期钩子”则尚未证明会减少复杂度：这些流程的数据依赖与失败语义并不相同，把它们做成通用回调反而会隐藏顺序与错误处理。

建议沿用当前应用层显式编排方式：在 `app/usecases` 或备份编排中明确调用各领域的公开仓储能力；共享层只提供连接、路径、身份校验、迁移与文件清单能力。增加领域时需要显式补齐其备份或删除路径，是清晰的编译期责任，不必为未来扩展建立运行时注册体系。

### 6. 让启动界面遵循现有单窗口生命周期

显式升级/新建仓库入口是必要的，但开始界面应复用现有主窗口、标题栏和窗口控制。当前应用采用单窗口、无原生装饰及托盘生命周期；计划中的“开始界面自带标题栏/窗口控制”会让同一个窗口切换视图时出现两套外壳语义。把它实现为主窗口内的启动路由即可，并明确“退出/不升级”会真正结束进程，不被“关闭窗口即隐藏到托盘”的常规行为截走。

## 建议的落地顺序

1. **先定权威与恢复协议。** 写清根库、作品库、索引和文件清理队列分别谁是权威；确定投影重放方式、升级源快照、激活标记、重启恢复与旧库保留策略。
2. **完成 v7 正确性底座。** 加入作品库句柄与身份校验；迁移并改造所有依赖数据库的跨作品路径，包括树、删除、清理、空间、备份/恢复和校验。此阶段保持现有全仓写入串行，保证所有操作仍可用。
3. **验收并发边界。** 在现有协调器中接入作品闸门与有限长任务配额；先证明不同作品的短写能并行、同一作品仍串行、整仓一致性任务可安全独占，再逐步加公平策略。
4. **单独接入识别投影。** 复用现有识别控制器，只迁移全库搜索和结果导航所需的数据访问。先验证索引重放和缺库/损坏隔离，再调整前端任务展示。

每阶段的验收应针对其核心失败面，而不是只按文件或代码行数划批。数据库迁移测试除逐版本夹具外，应覆盖带 WAL 的源库、升级进程重启后旧库曾被改写、根库切换前后强杀、投影更新成功但确认失败、以及失败作品的恢复与清理边界。

## 结论

推荐保留“作品独立数据库 + 根库拥有目录和跨作品读模型”的主方向。开工前优先补齐两件事：第一，跨库派生索引必须有可靠重放机制；第二，升级必须在旧库快照、维护租约和重启恢复之间闭环。然后复用现有命令协调器分阶段引入作品级并行，暂缓通用生命周期钩子和完整公平调度框架。这样保留拆库带来的并行与故障隔离收益，同时控制新增一致性机制的数量。
