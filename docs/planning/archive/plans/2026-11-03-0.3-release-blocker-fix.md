# 0.3 发布阻塞修复批次计划（2026-11-03）

状态：**已实施并提交**（2026-11-03；结论见 `../handoff/2026-11-03.md` §7）。本批次只处理两件阻塞
`0.3.0` 正式版的事——认证成品/认证副本的垃圾扫描缺口
（产品缺陷，2026-11-03 探针实测）与 zstd 依赖审计红（CI 门禁）。两件都不改数据库 schema、不改
界面交互，合并为同一批次提交、同一轮验证，打完即具备切 `0.3.0` 的技术前提。

本文件是执行依据；完成后结论写入当天的交接日志并从 `../../todo.md` 删除对应条目。

## 1. 一句话结论

产品侧只有一个真缺陷：`ArtifactReferenceInventory` 没有实现 `scan_candidates`，导致取消发布时
「因内容被替换而保留」的成品副本与认证副本永远进不了设置页「空间」页的垃圾扫描候选，用户看得见
磁盘被占用却找不到清理入口；补一个约 40 行的目录遍历即可闭合，风险面很窄。另一件是纯依赖升级，
把 zstd 从 0.13 升到 0.14 让四条 RUSTSEC 公告清零、CI 转绿。两件互不相干，但都必须在打
`v0.3.0` 之前完成，因此并成一批。

## 2. 问题与证据

### 2.1 缺陷 A：认证成品与认证副本不进垃圾扫描（P2，实测确认）

- **现象**：取消发布时，若仓库内成品副本或认证副本的内容已被替换，命令按设计不登记清理、把文件
  原样留在仓库里（日志 `[cleanup] retained`）。`docs/modules/authenticity.md` 承诺这类文件「由
  设置页『空间』页的垃圾文件扫描负责发现」，实际扫描根本不会列出它们。
- **证据**：2026-11-03 探针 S3.5 连续两次失败，不是断言写错——把副本 mtime 调到 40 分钟前（越过
  30 分钟宽限期）后仍不出现在 `scan_unreferenced` 结果里，而 `cleanup-unreferenced` 显式传该路径
  可以删掉。结论见 `../handoff/2026-11-03.md` §3。
- **代码位置**：`src/authenticity/contracts.rs:12` 的 `impl ReferenceInventory for
  ArtifactReferenceInventory` 只实现了 `collect_targets`；`scan_candidates` 走
  `src/contracts/reference.rs:71` 的默认空实现。对比 `src/history/contracts.rs:63` 与
  `src/pin_board/contracts.rs:73` 都有实现。
- **影响**：孤儿副本永久占用磁盘，且用户没有入口清理（只能手工按路径找）。另外 `publish` 的
  `stage_copy_with_sha256` 在 `artifacts/<branch>/` 下写 `.tmp*` 暂存文件，进程被强杀时留下的
  残留同样看不见。

### 2.2 阻塞 B：zstd 四条公告让 CI 红（P1，门禁确认）

- `dev` 最近两次推送（10-30 历史重置、10-31 图标）的 Windows CI 都失败在同一处：`validate` 全绿，
  `dependency-audit` 的 `cargo audit` 报 4 条新公告，全部在 zstd 栈上：`RUSTSEC-2026-0391`
  （zstd 0.13.3）、`0398`/`0403`（zstd-safe 7.2.4）、`0410`（zstd-sys 2.0.16）。
- 修复版已发布：zstd ≥0.14.3、zstd-safe ≥8.2.0、zstd-sys ≥2.1.2。zstd 是 `src-tauri/Cargo.toml:55`
  的**直接依赖**（delta 压缩/解压），只能由本仓库升级。
- 实际暴露面比标题小（0391 是复用上下文串流、0398 是 `Seekable`、0410 是 wasm 分配器），真正沾边
  的是 0403（解码失败时暴露未初始化内存），而 delta 解码正是读仓库文件的路径。门禁是硬的，发行
  政策要求审计通过才能打标签。

## 4. 轨道 A：补齐认证成品与认证副本的扫描候选

### 4.1 候选规则

`scan_candidates(&self, artwork_directory, files)` 只碰两处，全部用 `is_file()` 判定、不跟随
符号链接、不递归到未知层级：

| 目录 | 命中 | reason |
| --- | --- | --- |
| `artworks/<artwork>/artifacts/<branch>/` 直属普通文件 | 任意文件名 | `最终成品副本未被引用` |
| `artworks/<artwork>/artifacts/<branch>/certifications/` 直属普通文件 | 任意文件名 | `认证副本未被引用` |

- 目录不存在按空处理（与 `history/contracts.rs` 的 `collect_scan_directory` 一致）；非 UTF-8 文件名
  跳过。
- 路径布局只从 `authenticity/publication_repository.rs` 的 `final_artifact_directory` 与
  `certification_copy_path` 推导，不在扫描侧另写一套拼接规则。

### 4.2 为什么用「引用反查」而不是文件名白名单

扫描主流程本来就用 `collect_targets` 得到的相对路径做 anti-join（`src/cleanup.rs:730`），候选只要
如实列出目录里的文件，正在使用的成品与副本会被自动排除。文件名白名单（`<uuid>.<ext>`）看起来更
保守，但会漏掉两件真实存在的东西：崩溃残留的 `.tmp*` 暂存文件，以及用户手工改名过的副本——这两类
正是最需要被扫到的。宽限期与删除前的 SHA-256 复查已经兜住了误删风险。

### 4.3 边界与风险

- **宽限期照旧**：候选仍要过 `SCAN_GRACE_MS`（30 分钟，`src/cleanup.rs:31`）。刚被替换的副本不会
  立刻出现，最迟 30 分钟后可见；这一点要写进文档，避免用户以为扫描失灵。
- **并发安全**：发布中的副本刚写入就落在宽限期内；确认清理时 `cleanup_unreferenced_cancellable`
  会重新复查引用并逐条登记当前 SHA-256，内容在确认前变化即保留，条目留队可重试。
- **候选变多**：修复后「空间」页会开始列出这类文件，这是修复目标而非回归；文案由 reason 承担，
  前端 `cleanupReasonLabel` 直接透传，不需要改。
- **不动 `forget_deleted`**：候选按定义就是没有任何记录引用的文件，删掉后不会留下悬空引用。

| 文件 | 改动 |
| --- | --- |

| `src/cleanup.rs`（仅测试） | 新增一个端到端扫描测试，仿 `scan_reports_orphan_board_dds_and_keeps_referenced_ones`（约 1512 行） |

### 4.5 测试

1. **清单级**：`artifacts/<branch>/` 下放「被引用成品」「孤儿成品」「孤儿认证副本」三类文件，断言
   只报后两者、reason 分别是两句文案、被引用文件不在结果里。
2. **端到端**：`scan_unreferenced` 列出孤儿 → `cleanup_unreferenced` 删除 → 孤儿消失、被引用文件
   仍在、`verify` 通过（仿画板 DDS 的既有测试）。
3. **空目录**：作品没有 `artifacts/` 时不报错、不产生候选。
4. **宽限期**：刚写入（未 aging）的副本不出现在候选里。
5. **回归**：`cancel_publication` 既有 2 个测试保持通过；`stress_cleanup` 的孤儿回收闭环不受影响。

### 4.6 验收口径

- 探针 S3.5 那条断言在单测里应转为通过；`[cleanup] retained` 日志仍留人工（无头入口不装日志器，
  见 `../handoff/2026-10-25.md` §10.4）。
- 人工只剩一步：替换副本 → 取消发布 → 等过宽限期 → 空间页扫描能看到它 → 确认清理后文件消失。

## 附录：剩余人工项为什么不能自动验证

`todo.md` 现在还有 26 条界面项与 10 组发布级桌面验收。它们不是「懒得做」，而是**通道不允许**：
项目的验证纪律（`docs/guides/validation.md`）禁止 GUI 自动化与输入模拟，而能产生这些事实的只有
GUI 进程——无头入口没有 WebView、没有窗口、没有调度器、不装日志器。按原因分六类：

| 类别 | 典型项 | 为什么自动化不了 |
| --- | --- | --- |
| 像素与观感 | 兜底卡片是否被挤出可视区、放置模式的 I 字光标与按钮点亮、底部提示条不该出现、画板交接提示条、检查点取消后统计怎么显示、缩略图在「节点信息」栏出现或整块消失 | 断言对象是布局结果与视觉反馈，不是数据；要么需要渲染截图比对（等价于 GUI 自动化），要么结论本身就是「看起来对不对」 |
| 仅 Tauri 宿主成立 | 顶条拖动、三个窗口按钮、打开日志目录、托盘勾选项、安装/卸载、签名与法律文件 | 这些 API 只在真实窗口宿主里存在；无头进程根本没有窗口 |
| 真实 OS 手势与外部程序 | 从资源管理器拖放 PNG/JPEG/WebP/TIFF、第三方工具回读 C2PA、用随包模型验 TrustMark | 需要操作系统级的拖放手势或第三方程序；模拟拖放属于输入操纵 |
| 真实设备能力 | 素材板在 WebGPU + BC7 适配器上的渲染 | 需要特定图形硬件；无头进程不初始化渲染管线 |
| 真实用户数据与环境 | 从 beta.1 安装升级与卸载、旧仓库副本做 v5 → v6 迁移（含旧设置）、仓库改只读或磁盘写满、真实 `.procreate` 样本 | 需要「上一版产出的仓库」与「上一版安装包」这类只存在于维护者机器上的真实资产；只读/写满要靠改环境 |
| 只有 GUI 进程才有的事实 | `[cleanup] retained`、`[boundary] caught`、`pin-board settle flush finished`、自动备份静默 10 秒 | 日志器与调度器只在 GUI 运行时装配；无头入口不装日志器（`../handoff/2026-10-25.md` §10.4 已记同一限制），要触发它们就得跑 GUI 并操作它 |

边界说明（「能做但没做」与「真不能做」的区别）：

- **预览缓存 512 MiB**：缓存模块本身有单测，但真正的累积由渲染管线按用户操作触发，无头入口没有
  预览命令；要自动化得先给无头加一套预览管线，成本远高于收益。
- **v5 → v6 迁移**：schema 层已有单测（`migrates_v5_boards_and_adds_backup_check_columns`、
  `failed_v6_migration_rolls_back_to_v5`），缺的是「真实旧仓库副本」这一层——这层需要 beta.1 产出
  的仓库，属于维护者本机资产。
- **自动备份 10 秒静默**：日志能取证（10.2 就是这么做的），但前提是 GUI 进程真的在跑并被真实写
  命令驱动；让代理去驱动它就越过了禁止输入模拟的红线。

因此本批次只把「能被程序判定」的部分做完，剩余 26 条 + 10 组留给维护者按清单逐项打勾。
