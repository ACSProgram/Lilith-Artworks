## 二、维护者决策记录

2026-10-18 维护者决定：

- **分支模型**：`main` 固定为 0.2 发布线（`v0.2.0`，指向 `0be6224`），不再接收 0.3 改动；
  `dev` 从 `0be6224` 创建，作为 0.3 开发线。历史与发布记录见
  `archive/handoff-log-2026-10-18.md`。
- **0.3 计划定稿**：采用 `0.3-architecture-algorithm-plan-2026-10-05.md` §0.5 的落实前修订
  （alpha1 不改持久 schema、阶段 7 一次 v4 → v5、画板公共表 + kind 子表、统计口径去重、
  typed 错误与空闲校验门控等），从阶段 0 开始实施。
- **阶段 2 owner lock 口径**：按写操作加锁（GUI、headless、维护命令在每次仓库写操作前
  acquire、操作结束释放；只读命令不取）；不采用 GUI 常驻持有。Windows stale owner 以
  SQLite 内核锁为唯一存活证明，取得锁即覆盖旧元数据，不按 PID/心跳强行回收。
- **阶段 2 前端范围**：按计划 §3.B 全量拆分 `AppRuntimeProvider`、`useSettingsController`、
  `useRepositoryMaintenance`、`RuntimeProgressProvider`、`SettingsDialog` 与 `NoticeCenter`；
  事件订阅与 controller 模板仍留给阶段 3。
- **阶段 3 事件 TTL**：事件丢失后的快照轮询固定为 3 秒（见计划 §6）；不引入按操作类型可配的
  计时器。作品树继续使用 30 秒兜底，因为后台自动备份写库不经过 coordinator 事件。
- **阶段 4 快速检查指纹**：复用 `branches.last_source_modified_ms` 存储版本化指纹，不新增 schema；
  采样首尾各 64 KiB，缺少亚秒 mtime 精度时退回全量。
- **阶段 4 ChunkFile v2 默认值**：默认开启，只影响新写入的节点；设置页保留 `chunkFileFormatV2`
  开关以便回退到 v1，旧 v1 节点始终可读。发布前仍用阶段 4 的 benchmark 复核往返一致性、CPU 与
  恢复时延。

2026-10-17 及更早仍然生效的决策：

- **空闲链路校验重构**：已落地口径存在的问题维持 0.3 计划 §3.I 的重构安排（默认关闭、按空闲
  时机触发、全链恢复校对、`branch_notices` 共享告警），归 0.3-alpha2 阶段 9，0.2 不再调整其
  口径。
- **签名**：Authenticode 签名仍无法进行。按 `docs/guides/release-policy.md`，未配置证书输入时
  允许未签名发布，但发布说明必须显著披露未签名状态及 SmartScreen 影响；签名相关的人工门槛项
  在签名可用前无法执行。
