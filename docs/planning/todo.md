## 一、待实现 / 待补强

| 优先级 | 事项 | 现状 | 影响 |
| --- | --- | --- | --- |
| P2 | 长任务与灾备调度并行的降级策略 | 纹理读取持共享读租约；灾备/扫描持仓库操作锁期间画板浏览可继续、画板写入会等待 | 实测卡顿不可接受时再评估，例如提供缩略图缓存或更明确的写入等待状态 |
| P2 | 超期临时目录清理 | `repository/temp` 会遗留认证预览会话目录（观察值约 40 MB） | 长期使用会累积占用；可考虑打开仓库时按创建时间清理超期临时目录并保留当前活动会话 |
| P2 | 历史长操作的结果刷新与批量化 | 精简仍由前端逐节点调用 `compact`；取消已改为前端批级标记（逐节点循环启动下一个节点前检查，命中即停止并刷新历史），某步失败仍靠命令报错与轮询刷新 | 大量节点操作会产生多次锁竞争；可提供一次性批量命令，返回完成数量、取消点与剩余节点 |
| P2 | 同一仓库内切换 Artwork 时结算失败的一致性 | 切换作品不再重挂载工作区，切换前由 `loadBoard` 先以旧画板完成 `finalize`（保存 + `finalize_pin_board`），失败即中止装载并保留旧画板 | 结算失败时 UI 已切到新作品而渲染器仍持有旧画板，两者短暂不一致；可评估失败时回滚 UI 或重试 |
| P2 | 跨画板保留纹理（切回更快） | 按「切换即全释放」策略，疯狂切换会产生 2–4 s 的异步纹理装载批次（含 DDS 解码与磁盘 IO 等待，非主线程阻塞） | 若要更顺滑的切回，可跨画板保留纹理复用，但常驻内存更高、预算管理更复杂 |
| P2 | 同仓库多进程并发缺乏防呆 | **无头侧已加跨进程哨兵锁**（`src-tauri/src/repository_lock.rs`，SQLite `BEGIN IMMEDIATE`，只对会写仓库的无头命令生效，由 `stress_concurrency` / I 组覆盖）；GUI 侧仍只有单实例插件 | 无头与无头已互斥，且强杀不残留锁（锁由内核在句柄关闭时释放）；**GUI 与无头同时写同一仓库仍不受保护**。下一步可让 GUI 也读取同一把锁，或把哨兵锁下移到仓库打开处。模块文档的「不支持同仓库多进程写入」说明仍待补 |
| P2 | 全库校验与精简并发时给出难以理解的错误 | `stress_concurrency` J5 实测：`compact` 与 `scrub` 真正并发时（4 轮里 1 轮命中），`scrub` 以「找不到历史节点」失败。`scrub` 是只读命令、不在哨兵锁覆盖范围内，因此两者之间没有互斥，只靠 SQLite 快照隔离与文件系统语义 | 不损坏数据（同轮结束后 `verify` + `scrub` 通过、每个节点仍逐位恢复，失败也是干净退出），但用户在精简进行中跑「全库校验」会拿到一个与原因无关的错误。修法二选一：① 让 `scrub_history` 在节点被并发移除时重读节点集合并按新状态继续；② 让全库级只读命令在哨兵锁被持有时给出明确提示（「仓库正在被写入，请稍后重试」）。两种都属于行为改动，需先定口径 |

## 二、待验证 / 待人工验收

按 `docs/guides/release-policy.md` 的「人工门槛」，以下项目对 `0.2.x` 仍未执行。可程序判定的
部分已由 `src-tauri/tests/` 的压力测试接管（见 `docs/guides/validation.md` 与
`docs/user/stress-test-report.md`），其中**八组便宜的分组已进 Windows CI**；保留人工复核手感；
界面视觉、交互手感与桌面集成仍由维护者手工验收。

已自动化覆盖、保留人工复核手感：

- 各处理阶段的取消边界（提交、恢复、精简、检查点、整仓灾备、认证签名），含**大文件**提交中途
  取消与强杀（C7）；
- 损坏文件的恢复路径（snapshot/delta 缺失或摘要不匹配），含**主库文件本身**损坏（误写/清空）
  时的干净失败（R3/R4），以及**随机化单点损坏逐文件、多种子扫描**（R5）与画板 DDS 的
  结构性损坏 / 随机改写（R6）；
- 画板 DDS 损坏、缺失、孤儿文件；
- 极端大文件与高像素压力的错误恢复；
- **解析器的畸形输入模糊**（容器 / DDS 头 / C2PA 清单 / 设置文件，见 `src/fuzz_support.rs`），
  断言不受信任的字节不能换来 panic、越界或无界分配；
- **输入域极值**（K 组）：非 ASCII 与 emoji 标题逐字符往返、标题长度按字符而非字节计数、
  空白与零宽字符的处理、非 ASCII / 含空格 / 深层路径的端到端可用、相对路径与工作区之外
  路径的明确拒绝；
- 无头入口的仓库写并发（哨兵锁明确拒绝第二个写进程；被强杀不残留锁），**多操作交错**
  （长写持锁时只读命令仍作答且看到一致状态：提交、整仓灾备、精简三类；并发读互不阻塞；
  真并发的「精简 + 全库校验」不损坏仓库——其中暴露的错误可读性问题见第一节 P2），
  以及进程内读租约（`app/settings.rs` 单测）；
- 核心算法性能基线（节点链、认证、画板 DDS、库树与搜索、整仓灾备、清理扫描；`stress_bench`，
  默认只记录、可经严格模式比对）。

仍需人工：

- 异常 RFC 3161 时间戳服务的失败与超时行为；
- 任务调度总控与空闲链路校验批次的界面项：空闲校验进行中触发取消、校验失败警告的展示与
  「重新校验此分支」清除路径、快速检查与空闲校验的组合、大链校验期间前台操作的响应性、
  校验失败后继续手动提交是否正常。

已人工验收（2026-10-16）：窗口几何持久化与设置加载稳健性、日志与诊断体系、素材板结算失败时
中止切换并提示、统一清理体系批次 A–F 的界面项。记录见 `archive/handoff-log-2026-10-16.md`。

不做自动化：

- 断电持久性——`Child::kill()` 不触及操作系统与磁盘缓存、也不保证目录项落盘，该保证由操作
  系统、磁盘与 SQLite `synchronous = FULL` 声明承担。
