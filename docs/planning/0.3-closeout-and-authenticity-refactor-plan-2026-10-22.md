## 1. 基线、原则与完成口径

### 1.1 当前基线

- 分支：`dev`
- 版本：`0.3.0-alpha.6`（未打标签）
- repository schema：v6
- 当前自动检查基线：`cargo check --lib` 通过，`npx tsc --noEmit` 通过
- 审查依据：2026-10-22 的只读架构审查与本次逐项核查

### 1.2 工作原则

1. 先修可见行为与过期描述，再做结构重构；每批只处理该批范围。
2. 重构以「移动代码 + 保留公开入口」为主，不顺手改业务规则。
3. 每批结束时必须满足该批的验证命令；涉及对应领域单测时跑定向过滤。
4. 不运行 `cargo build --release`、`npm run tauri build`、压力测试与 GUI 自动化。
5. 每批验证完成后按 `AGENTS.md` 分段提交；不执行 `git push`。
6. `CHANGELOG.md` 只写 `## Unreleased`；不创建带日期小节，不改五处版本字段。
7. 代码入口或契约变化时同步更新模块文档；历史增量按归档规则处理。
8. 不覆盖维护者正在进行的无关修改；每批开始前核对工作区。

### 1.3 完成定义

- 六批任务全部完成，或按 §10 的延期顺序显式延期；
- 工作区无编译错误、无新增 `dead_code` 告警；

## 3. 第二批：后端算法与仓储结构

**目标**：在不改变外部行为的前提下，抽共享算法内核、消除重复查询、把 `history/repository.rs`
按职责拆开，并降低调度器与 coordinator 的锁编排重复。

### 3.1 抽取恢复/校验的共享链步进内核

**现状**

`src-tauri/src/backup/restore.rs` 有两套几乎相同的链处理：

- `walk_chain`（约 :685–750）、`open_snapshot_content`（约 :791–836）、
  `resolve_parent_content`（约 :842–901）：全库校验按链共享前缀遍历；
- `resolve_chain`（约 :993–1108）：单目标从最近 snapshot 向下解析。

两者都负责「打开 snapshot → 校验整文件摘要 → 打开 delta → resolve → 校验目标摘要 → 读载荷」。
跨链共享前缀确实存在：`walk_verification_inventory` 用共享 `outcomes` 表，`starts` 按新到旧
排序，`walk_chain` 遇到已定论节点即停；`Blocked` 不算已定论，会被重走。

**改动**

- 在 `restore.rs` 内抽单步内核，例如：

  ```text
  struct ChainStep { layout: ChunkFile, payload_error: Option<ChainFailure> }
  fn open_snapshot_step(...)
  fn resolve_parent_step(...)
  ```

- `resolve_chain` 与 `walk_chain` 复用这两个函数；归因（`culprit`、`Missing` / `Damaged`）
  只保留一份。
- 不改变 `ResolvedChain` 的语义、进度标签与取消检查点位置。
- 不把「按链共享前缀」优化退化为逐节点 resolve。

**验收**

- `cargo test --lib backup::restore`（或对应过滤）全部通过；
- 恢复、精简、检查点、手动重查、全库扫描的现有单测不改变断言；
- 用现有 `stress_damage` / `stress_bench` 的口径做代码走查，不实际运行昂贵组。

### 3.2 校验结果批量写入

**现状**

`walk_verification_inventory` 的回调逐节点调用 `mark_node_verified` /
`mark_node_verify_error`；每次最终到 `history/repository.rs` 的 `record_node_verification`，
内部 `storage::open(root)?` 新建连接并配置 PRAGMA，再执行单条自动提交 UPDATE。
全库扫描上千节点会产生上千次连接与隐式事务。

**改动**

- 新增批量写入器，例如 `history::VerificationWriter`：
  - 持有一个 `Connection`；
  - `record(node_id, outcome)` 先累积；
  - 每 128 条或批次结束时提交一次事务；
  - 扫描取消时丢弃未提交批次，已提交批次保留（与现有「已处理批次仍提交」口径一致）。
- `scrub_history`、`verify_branch_history`、`run_verify_batch_locked` 改用同一写入器。
- 单节点 `verify_history_node` 的调用方若只写一个结果，仍可直接写，不强套批次。

**验收**

- 全库扫描结果、失败归因、`verified_ms` / `verify_error` 内容与改造前一致；
- 取消时不会把未完成节点写成通过或失败；
- 现有 `history` / `backup::restore` 单测通过。

### 3.3 收敛调度分支查询与状态写入口

**改动**

1. `list_scheduled` / `load_scheduled` / `count_scheduled_files` 的 SQL 与行映射收敛为共享
   常量/函数，只保留「带 id 过滤」与「计数」两个入口。
2. 删除 `validate_subtree_deletion` 与 `delete_subtree` 的重复前置检查：抽
   `ensure_subtree_deletable(connection, history_id, branch_id)`，validate 与 delete 共用；
   `usecases::backup::delete_subtree` 不再额外调用一次 validate（删除函数内部已复查）。
3. `fork_branch` 与 `create_branch_created` 共用一个内部函数，返回 `history_id`，
   外层决定是否再读整棵树。
4. `mark_error`、`mark_automatic_backup_error`、`mark_automatic_backup_skipped` 收敛为
   一个带枚举的 `record_branch_failure`（或 `BranchStatusUpdate`），明确三种语义：
   - 手动提交失败：只写 `last_error`；
   - 自动失败：写错误、递增失败数、写 `retry_at`、第 5 次关闭；
   - 路径不参与自动备份：写原因、清零失败数、清 `retry_at`、不关闭。

**验收**

- 调度、手动提交、网络路径跳过三类单测仍通过；
- 没有新增重复的 `last_error` 写入 SQL；
- `delete_subtree` 的 use-case 路径只做一次完整前置遍历。

### 3.4 `create_branch` 改为单事务

**现状**：`history/repository.rs` 的 `create_branch` 在同一连接上先插入 `branches`，再单独
`UPDATE history_nodes SET is_checkpoint = 1`，全程没有显式事务，两条语句各自隐式提交。

**改动**

- 把「插入 branches」与「标记起点 checkpoint」放进同一事务。
- 保留现有错误文案与唯一索引映射。
- 补一条失败注入单测：第二步失败时分支不存在（或使用事务回滚测试）。

### 3.5 拆分 `history/repository.rs`

     不执行 `image_resource::open`。
2. **避免整图复制**
   - `trustmark::decode_region` 改为接收拥有的 `DynamicImage`（或等价的 `Option` 形态）：
     有选区时裁剪后释放原图，无选区时直接移动，不再 `image.clone()`。
3. **模型摘要流式读取**
   - `state::file_sha256` 改为固定缓冲读取并更新哈希，避免一次 `fs::read` 约 62 MB。
   - 这是峰值内存优化，不是正确性修复；若实现成本明显高于预期，可在本批末尾单独报告。
4. **保持行为**
   - 识别结果字段、候选合并顺序、失败关闭条件保持不变；新增测试覆盖模型不可用路径。

## 9. 风险与回滚

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| `history/repository.rs` 拆分导致外部路径失效 | 编译失败或隐藏调用点漏改 | 保留 `history/mod.rs` re-export，外部路径不变；每移动一组函数立即 `cargo check --lib` |
| 校验批量写入改变取消语义 | 取消后节点状态与旧行为不一致 | 以「已提交批次保留、未提交批次丢弃」为唯一口径，补取消单测 |
| 恢复链共享内核改变归因 | 「文件丢失/损坏/无法检查」分类漂移 | 保留现有 `ChainFailure` 构造与归因单测，先纯移动再合并 |
| 前端组件拆分改变受控状态 | 选中节点/分支、精简选择回退 | 拆分前先抽 hook，保持 props 契约；`npm test -- src/modules/history` 作为门 |
| 删除 `default_panel` 破坏旧设置 | 旧 JSON 读取失败 | 依赖容器级 `serde(default)`；补旧设置文件解析测试 |
| 文档归位后索引失效 | 阅读入口找不到内容 | 同步更新 `ai-reading-guide.md`、`overview.md`、`archive/README.md` |
| `prepare_rendition` 统一后改变发布声明 | C2PA 清单内容变化 | 保留发布侧标题/创作者/权利/内容裁剪；用现有发布断言与新增等价测试锁定 |
| 认证大范围移动导致导入遗漏 | 编译失败 | 每完成一个子模块立即 `cargo check --lib`，批次结束 `cargo check --all-targets` |
| 识别取消/乱序语义变化 | 旧结果回填或取消失效 | 先补测试再替换请求代次；取消状态不交给 `useRequestEpoch` |
| 页面拆分导致 props 遗漏 | 编译错误或交互缺失 | 用 TypeScript 与现有组件测试兜底；识别视图保持两个回调 |

回滚策略：每批验证完成后即提交，回滚以「撤销该批提交」为单位，不使用
`git reset --hard`、`git checkout --` 等会丢弃维护者改动的命令。
